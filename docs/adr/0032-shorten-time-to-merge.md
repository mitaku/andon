## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-20）: マージと開発のサイクルをもう少し早めたい。CI の高速化の案は3つ。影響しないテストをスキップして短くする。テストを抜本的に見直す。事前の Lint などを整備して、そちらに寄せる。

言い直し: 縮めたいのは、担当が変更を書き終えてから main に入るまでの時間。いまは、手元の検査、CI の約4分、レビューの5〜8分が一列に並び、小さな変更でも 10〜16 分、直しが入ると倍かかる。CI の高速化の3案は、この列のうち CI と手元の検査を短くする手段に当たる。

いまの形（2026-11-20 の main と、2026-11-19 15:00 〜 2026-11-20 03:00 UTC の実測）:

- **tests の job**: 直近 44 回で 199〜365 秒、中央は約 231 秒。686 秒の回が1回（image の build の apt の2段が 210 秒と 290 秒かかった。Azure の mirror に替えたあと）。job の前準備（checkout・setup-go・go build・buildx）は 30〜40 秒。
- **job の長さを決める検査**: `tests/image.sh` が 165〜333 秒（速い回の内訳は、image の build が約 90 秒、起動しての検査が約 80 秒）。次が `tests/schema.sh` の 102〜220 秒と `tests/andon-dispatcher.sh` の 82〜191 秒。続いて `tests/apply-main.sh` が 24〜54 秒、`tests/andon-issue.sh` が 13〜43 秒、`tests/andon-gate.sh` が 8〜18 秒。残りの 23 本はどれも 7 秒以下。runner は 4 コアで、29 本を並べて走らせる。同じ検査の秒数が run によって倍ちがう（遅い runner に当たると全部が延びる）。
- **`tests/image.sh` を飛ばせた PR は 44 回に 0 回**。ほとんどの PR が `cmd/` か `internal/` に触り、判定（`tests/lib/image-scope.sh`）が走らせる側に倒す。飛ばせても job は `tests/schema.sh` の長さ（前準備を足して 2分15秒〜4分）までしか縮まない。
- **go の job** は 60〜78 秒（中央 67 秒）、**model の job** は 9〜30 秒（中央 13 秒）。律速でない。
- **PR の作成からマージまで**: 直近 17 本（夜をまたいだ 2 本を除く）の中央は約 16 分。CI を1回で通った PR では、CI の終了からマージまでの中央が約 8 分。
- **CI とレビューは直列**: 担当は checks が通るのを待ってからレビューを頼む（worker skill §3 の 4 と §4 の 1）。5 件で見ると、レビュアーの課題は CI の終了の 30 秒〜4分半あとにでき、4分半〜8分半で終わる。ゲートはその直後に決め、数秒でマージする。
- **PR の CI が落ちるのは稀**: 2026-11-11 からの 400 回のうち、PR の 237 回で失敗は 4 回（`tests/image.sh` が 2 回、`tests/words.sh` が 1 回、`tests/andon-dispatcher.sh` と `tests/schema.sh` が 1 回）。main の push の 163 回で失敗は 3 回。
- **手元と CI の重なり**: `cmd/`・`internal/`・`package/` などに触ると、`tests/run --changed` は `tests/image.sh` 以外の全部を選ぶ（`tests/lib/scope.sh`）。セルに Docker が無いので `tests/image.sh` は手元で走らない。2026-11-20 03:05 UTC のセルでは、担当2人が全部の検査を同時に回していて、16 コアに対して load average が 25 だった。
- **周回**: CI を2回以上回した branch は、直近 45 本のうち 29 本。直しが入ると CI とレビューをもう1周する。
- **量**: マージは 2026-11-19 の1日で 51 本、11-12 は 26 本。
- **main の決まり**: ruleset `main` が PR と、required checks の `tests`・`go` を求める。base の最新への追従は求めない。ゲートは PR の head の checks が揃うのを待つ。

## 前提（同意済み。番号）

1. **検査そのものを削ることも検討に入れる**（オーナー 2026-11-20）。いまの検査には過剰なものがありうる。順番の並べ替えと重複の解消に限らない。どれを削るかは「決めたこと」で1つずつ決める。

2. **CI の結果を待たずにレビューを始めてよい**（オーナー 2026-11-20）。CI が落ちた PR をレビューしてしまう無駄は、PR の CI の失敗が 237 回に 4 回の割合なら許す。ゲートは今までどおり、CI とレビューの両方がそろってから決める。

3. **手元の検査は速く返るものに寄せてよい**（オーナー 2026-11-20）。手元で回すのは、速く返る検査と、変えた所を直接見る検査だけにする。重くて関係の薄い検査は CI に任せ、CI で初めて落ちる回が少し増えることは受け入れる。線の引き方は「決めたこと」で決める。

4. **お金と外のサービスは足さない**（オーナー 2026-11-20）。無料の runner のまま、外のキャッシュや有料のサービスも足さない。CI の土台のイメージを GHCR に置く案の見送りも変えない。

5. **マージの関門の決まりも、必要なら変えてよい**（オーナー 2026-11-20）。required checks の顔ぶれ（いまは `tests` と `go`）・check の名前・ゲートが checks を待つ形を固定しない。重い検査を別の check に分けることも検討に入れる。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **目的は、担当が書き終えてから main に入るまでの時間を縮めること。CI の job の秒数はその手段**（2026-11-20）。CI の秒数に加えて、手元の検査との重なりと、CI とレビューが直列に並ぶ順も検討に入れる。理由: CI の job だけを縮めても、`tests/image.sh` を丸ごと無くして 2分15秒〜4分 までで、列の残り（レビューの 5〜8 分・手元の検査）が動かない。捨てた案: 「CI と手元の検査だけ」「CI の job の秒数だけ」。

2. **順番と重複だけを直す。検査の網は外さない**（2026-11-20）。することは3つ。PR を出したらすぐレビューを頼み、CI とレビューを並べる。`tests/schema.sh` がほかの検査を回し直す重複をやめる。手元は速い検査と変えた所の検査だけにする。CI の検査の顔ぶれと required checks はそのまま。理由: 効果の大半が順番の入れ替えで出る。並べると CI の約4分はレビューの 5〜8 分の裏に隠れ、CI の job をさらに縮めて効くのは、レビューなしの PR（直近 46 件の課題のうち 9 件）と CI が落ちて直す周回だけになる。捨てた案: 「CI の job も 2 分以下にする」（Go だけの PR で image の起動の検査を飛ばして最初の段の build だけにし、`tests/andon-dispatcher.sh` を割る。Go の変更が image の中の起動を壊しても main に入ってから分かる。この案を入れたあとの実測を見てから決め直す）。「重い検査を関門から外す」（約1分の速い層だけを required にする。main が赤くなる日が出て、1日 51 本のマージでは原因の PR を追う手間が大きい）。

   判断の材料にした事実:
   - `tests/schema.sh` は、command の出力を schema に通すために `andon-issue.sh`・`andon-gate.sh`・`andon-dispatcher.sh`・`andon-dispatcher-signal.sh`・`andon-measure.sh`・`andon-retro.sh`・`andon-retro-apply.sh`・`andon-signal.sh`・`andon-chief-of-staff.sh` の 9 本を自分の中でもう一度走らせる。`tests/schema.sh` の秒数は、ほぼ `tests/andon-dispatcher.sh` の2度目の実行の長さ。
   - `tests/andon-dispatcher.sh` を手元（セル）で1本だけ走らせると 148 秒（2026-11-20。load average 8〜21 の中）。
   - `andon issue review-request` は GitHub の checks を読まない。CI を待ってから頼む順は worker skill の文だけが決めている。ゲートは checks が走っている間 `wait` を返して待つ形を既に持つ。
   - `tests/image.sh` が PR で拾った本物の不具合は 237 回で 2 件。1 件は image そのものの変更（時刻の設定）。もう 1 件は Go に埋め込むファイルを Dockerfile が COPY していなかったもの。

3. **担当は PR を出したらすぐレビューを頼み、CI は裏で待つ**（2026-11-20）。直すのは worker skill の文だけで、コードは変えない。CI が落ちたら、レビューの結果を待たずに直して push し、レビューを頼み直す。古い commit を見たレビューは今の決まりのとおり回に数えない。理由: `andon issue review-request` は checks を読まず、ゲートは checks を待つ形を既に持つので、頼む時点を前へ動かすだけで並ぶ。捨てた案: 「dispatcher が PR を見つけて自動でレビュアーを起動する」（dispatcher のコードと課題の一生のモデルを変えることになり大きい）。「go の job が通ってから頼む」（無駄なレビューは減るが、縮むのが約3分になる）。

4. **手元で回すのは、軽い検査と、変えた所に対応する重い検査**（オーナー 2026-11-20）。いつも回すのは gofmt・`go vet`・`go test ./...` と軽い `tests/*.sh`。重い検査（`andon-dispatcher.sh`・`schema.sh`・`apply-main.sh`・`andon-issue.sh`・`andon-gate.sh`）は、その検査が見る部分を変えたときだけ手元で回す。対応の表は `tests/lib/scope.sh` に持たせる。CI は全部を走らせる。オーナーはこのとき、テストの作り方そのものの見直しも求めた（下の 5 から先で決める）。捨てた案: 「軽い検査だけ」（決まりは単純だが、dispatcher を変えた PR が CI で初めて落ちる回が増える）。「今の線のまま」（手元で `andon-dispatcher.sh` の 148 秒を毎回待つ）。

5. **release の job の上限は 30 分のまま**（2026-11-20）。理由: リリースは稀で、打ち切られても同じタグの job を回し直せる。上限を上げると、遅くなったことに気づきにくくなる。捨てた案: 「45 分に上げる」「release の job でも apt を Azure の mirror から取る」（配る image の取得元を変えないという今の決まりを覆す）。

6. **場面の確かめを Go のテストへ移す。一番重い dispatcher の検査から段階的に**（2026-11-20）。1 節を 1 つの Go のテストにし、節ごとに状態を作り直す。シェルには、command を外から打って一周させる道だけを残す。移した節ごとに、わざと壊して落ちることを確かめる。新しい場面はこれから Go に書く。理由: Go の側は同じ偽物のやり方（偽の `hc`・`gh` を PATH に置く）で dispatcher の 117 個のテストを回していて、CI では Go のテスト全部が 22 秒で終わる。節が独立すれば 1 件ずつ走らせられ、変えていないパッケージのテストは Go の cache で飛ぶ。捨てた案: 「今の形のまま手入れする」（重なる 15 節を消して 2 本に割る。短縮は 2〜3 割の見込みで、筋書きが 1 本の形は残る）。「先に調べる課題を切る」。「見回りの 1 巡そのものを速くする」（どこまで縮むか分からない）。

   判断の材料にした事実（2026-11-20）:
   - `tests/andon-dispatcher.sh` は 62 の節が、2 つの台帳・1 つの一時ディレクトリ・1 つの偽の PR・本物の git の origin を順に使い回す。後ろの節は前の節が残した課題や控えに頼る。1 節だけ走らせることも、割って並べることもできない。
   - 行ごとの時刻を付けて走らせると 181 秒（付けないと 148 秒）。内訳は `andon` の呼び出しが 342 回で 114 秒、`jq` が 850 回で 33 秒、sleep が 146 回で 20 秒、git が 355 回で 6 秒。`andon dispatcher` は途中までの集計で 160 回、1 回あたり約 0.6 秒。
   - 62 節のうち、同じ振る舞いを Go のテストが既に確かめているのが 15 節、一部が重なるのが 34 節、シェルの側にしか無いのが 13 節。読むだけの調べによる見立てで、境目に判断を含む。移すときに節ごとに確かめ直す。
   - シェルにしか無い 13 節は、複数の command をまたいで一周させるもの、`andon issue settle` を 2 度打って gh を呼んだ回数を数えるもの、本物の git の worktree と branch を消すところまで見るもの、偽の gh の rate limit を見るものなど。
   - Go のテストは関数の差し替えを使わず、偽のシェルスクリプトを一時の bin に置いて PATH の先頭にし、内部の関数を直接呼ぶ。git は本物を起動する。台帳は一時ディレクトリに手で書いたファイル。Test 関数は `internal/dispatcher` に 117、`internal/issue` に 41、`internal/gate` に 16。

7. **テストより手前の手段で防げるものは、そちらへ寄せる**（オーナー 2026-11-20）。手段は、lint の規則・動的な検証・静的な型の設計・レイヤの設計・性能の計測・形式仕様・モデル検査。進め方は、先に調べる課題を 1 本切り、場面の節と重い検査を「どの手段で防げるか」で仕分けた表を作る。表を見てから、足す道具と直す設計をオーナーと決める。決めたこと 6 の Go へ移す対象は、手前の手段で防げない節だけになる。理由: どの節がどの手段で防げるかは 1 節ずつ読まないと分からず、道具を先に入れても何が防げるかが分からない。捨てた案: 「担当が節ごとに判断して寄せる」（足す道具や設計の直しが担当ごとにばらつく）。「仕分けを待たずに静的解析の道具・レイヤの依存の規則・検査の秒数の上限を先に入れる」。

   いま repo にある手前の手段（2026-11-20）: 課題の一生のモデルと規則（`model/`。CI の model の job が約 13 秒で回す）。状態の移り方を定義（`process/states/issue.yaml`）と照らして command が断る実行時の照合。JSON を `schema/` に通す照合。gofmt と `go vet`。ほかの静的解析の道具は入っていない。検査 1 本ごとの秒数は CI の表に出るが、上限を置いて見張る形は無い。

8. **決めたこと 3 を改める。レビュアーは 1 人ずつ。動いている間の頼み直しは command が断る**（2026-11-20）。担当は PR を出したらすぐレビューを頼む。CI が落ちたら直して push してよいが、頼み直すのは前のレビューの結果が届いてから。`andon issue review-request` は、その課題のレビュアーが動いている間は、別の commit の頼み直しも断る。CI が落ちた回はレビューを 1 回ぶん使い、上限を超えた回は今の決まりどおり Chief of Staff が起動するかを決める。決めたこと 3 の「コードは変えない」と「古い commit を見たレビューは回に数えない」は誤りだった。理由: 読むだけの反論役がコードから示し、Chief Engineer が `internal/issue/issue.go` と `internal/ledger/review.go` を読んで確かめた（下）。文だけの決まりを担当が破ると行き止まりに入るので、機械で止める。課題の一生のモデル（`model/IssueLife.tla`）はレビュアーが同時に 2 人いない形で書かれていて、コードがモデルに合う向きの直しになる。捨てた案: 「同じ決まりを skill の文だけで置く」（破ると行き止まりに入り、15 分後の「止まっている」の通知まで気づかない）。「すぐ頼み直せるように、古いレビュアーを止める・回の数え方・照合・ゲートの数え方を直す」（課題の一生のコードとモデルに広く触れる）。「go の job が通ってから頼む」（tests の job が落ちる回に同じ穴が残る）。

   反論で分かったこと（2026-11-20。走らせてはいない。コードの読み）:
   - 穴が出るのは、CI が落ちて、前のレビュアーが動いている間に新しい commit で頼み直す道だけ。CI が落ちない回は今のコードのまま並ぶ。
   - **行き止まり**: `review-request` が断るのは同じ commit のレビュアーが動いているときだけなので、別の commit ならレビュアーが 2 人同時に走る。照合はレビュアーの子課題を `updated` の順に並べて最後の 1 人だけを読む。古い commit のレビュアーが後に終わると、`andon issue ready` は「レビューが stale」で断り、頼み直しは「その commit のレビューはもうある」で断る。
   - **回は減る**: 回は、台帳にあるレビュアーの子課題の最大の番号に 1 を足したもの。前のレビュアーの子課題があるだけで次は 2 回目になる。worker skill §4 の 2 の「stale は回に数えない」はコードと合っていない。
   - **ゲートの数え方が食い違う**: 前の回の結果が出る前に頼み直すと、依頼書に再レビューの行が付かず全体のレビューになるが、ゲートは 2 回目として数え、前の回が指摘しなかったファイルの critical でない指摘を数えない。
   - **CI の失敗を担当に知らせる道が無い**: dispatcher が `doing` の課題で checks を読むことは無い。担当が turn を終えていると、気づくのはレビューの結果が届いて `ready` したあとのゲートの fix。
   - **Stop フック**: レビューが済んだあと checks を待って `ready` を遅らせると、Stop フックが止める。レビューが済んだら checks を待たずに `ready` へ進む（ゲートが checks を待つ）。
   - **CI を待つ文は残す**: Chief Engineer の文書の PR と `Review: off` の課題は worker skill §3 の 4 の checks の待ちに頼る。並べる文は §4 の 1 に置く。
   - **守られている**: 古い commit のレビューが新しい commit の承認として使われてマージに進む道は無い。`ready`・ゲート・マージの直前の読み直しがどれも head と照合する。同じ commit の二重起動も無い。モデルの規則 R1〜R6 に破れるものは無い。

9. **流れの順や状態の移り方を変える変更は、実装の前にモデルに書いて確かめる。最初に当てるのは、レビューを CI と並べる変更**（オーナー 2026-11-20）。課題の一生のモデル（`model/IssueLife.tla`）に、CI の状態と、レビュアーがどの commit を見ているかを足す。規則に「どの状態からも、取り消しを使わずにマージまで行ける」を足す。検査が通ってから、決めたこと 8 の command の守りを実装する。守りを外したモデルが新しい規則を破ることも、壊した見本（`model/broken/`）で確かめる。理由: 決めたこと 8 の行き止まりは、順を入れ替える案をモデルに先に書いていれば、オーナーが形を選ぶ前に検査で見つけられる種類の穴だった。今回は読むだけの反論がコードから見つけたが、反論が同じ穴をいつも拾うとは限らない。今の決まり（課題の一生の動きを変える PR は同じ PR でモデルも直す。ADR-0025）は、実装に合わせてモデルを直す順で、この順では穴が実装のあとにしか見つからない。捨てた案: 「statechart と形式検証を、開発からマージまでの流れの全体へ広げることを今決める」（どの流れをモデルにするか、何を規則にするかは、仕分けの表を見ないと決まらない。開いている問い 4 に残す）。「今までどおり、実装と同じ PR でモデルを直すだけにする」。

   判断の材料にした事実（2026-11-20。モデルの読み）:
   - モデルは、レビュアーが動いているかを真偽の値 1 つ（`reviewing`）で持つ。レビュアーが 2 人いる状態も、レビュアーがどの commit を見ているかも表せない。レビューを頼む動きのコメントは「その commit のレビュアーが動いている間は断る」で、別の commit なら 2 人目が走れることはモデルに写っていない。
   - モデルは CI の状態（走っている・落ちた・通った）を持たない。
   - 規則は 6 本（R1〜R6）で、どれも「この状態のときはこうなっている」の形。検査器は、次の動きが 1 つも無い状態が無いことも見ている（`model/check` の「どの状態からも先がある」）。決めたこと 8 の行き止まりは、取り消しなどほかの動きが残るので、この検査には当たらない。要るのは「マージまで行ける」の形の規則。
   - 検査器が書く状態の図（`-dump dot`）は、`model/conform.mjs` が既に読んで `process/states/issue.yaml` と照らしている。本物のモデルの状態の数は 112、CI の model の job は約 13 秒。

## やらないこと（範囲の外。理由）

- CI の土台のイメージを GHCR に置くこと。オーナーが今は見送ると決めた（2026-11-20）。
- 有料の大きい runner・外のキャッシュのサービス。前提 4。
- CI の検査の顔ぶれを減らすこと・`tests/image.sh` を飛ばす条件を広げること・required checks の顔ぶれを変えること。決めたこと 2 で、順番と重複だけを直すと決めた。前提 1 と 5 は検討に入れてよいという許しで、今回は使わない。2026-11-27 の実測を見て決め直す。
- dispatcher がレビュアーを自動で起動する形にすること。決めたこと 3。
- CI が落ちたらレビューの結果を待たずに頼み直せるようにすること（古いレビュアーを止める・回の数え方と照合とゲートの数え方を直す）。決めたこと 8。CI が落ちる回が増えて、レビューの 1 回ぶんが惜しくなったら考え直す。
- 見回りの 1 巡（`andon dispatcher --once` が約 0.6 秒）そのものを速くすること。どこまで縮むか分からない。仕分けの表（決めたこと 7）でレイヤの設計に当たる節が出れば、そこで扱う。
- dispatcher 以外のシェルの検査（`andon-issue.sh`・`andon-gate.sh`・`apply-main.sh` など）を Go へ移すこと。dispatcher の結果を見てから決める。
- image の build の apt が遅い日のぶれ（44 回に 1 回、686 秒）を無くすこと。GHCR を使わずに消す手が無い。CI がレビューの裏に隠れるので、待ちへの影響は小さくなる。

## 受け入れ条件

継ぎ目は 4 つ。GitHub の実行の記録（PR と checks の時刻）、`tests/lib/scope.sh` の出力、CI の tests の job が出す検査 1 本ごとの秒の表、`go test` の出力。どれも既にある継ぎ目で、新しい検査の道具は作らない。

1. **CI とレビューが並ぶ。** worker skill を直したあとに出た、レビューありの PR で、レビュアーの課題ができた時刻が、その PR の head の tests の check の終了より前になる。証拠: `gh pr view <n> --json statusCheckRollup --jq '.statusCheckRollup[] | select(.name=="tests") | .completedAt'` の出力と、`kanban show <レビューの課題の id>` の `created` を、5 本ぶん並べたもの。本物のラインでしか確かめられないので、観察の課題が数える（オーナーが見る）。skill の機械向けの手順が壊れていないことは `tests/package.sh` の出力（全部 ok）で見る。
   **レビュアーが動いている間の頼み直しは断られる。** レビュアーの子課題が `doing` のとき、head を進めて `andon issue review-request <id>` を打つと、0 でない終了コードと理由の 1 行が返り、`report.json` の `review_request` は変わらない。前のレビューの結果が届いたあとは通り、依頼書に再レビューの行が付く。証拠: `go test -run '<足したテストの名前>' ./internal/issue` の出力と、その守りを外したときの FAIL の出力。`model/check` の出力（破れた規則が無い）。
   **モデルが先に行き止まりを見つける。** `model/check` の出力の規則の並びに、「取り消しを使わずにマージまで行ける」の規則がある。守りを外した見本（`model/broken/` に足す）は、その規則の破れで落ちる。証拠: `model/check` の出力（規則の並び・見本の行・状態の数）。モデルと規則の commit が、command の守りの commit より前にある。証拠: PR の `git log --oneline` の並び。
2. **`tests/schema.sh` がほかの `tests/*.sh` を回し直さない。** 証拠: CI の tests の job の表で、`tests/schema.sh` の秒が 30 秒以下（今は 102〜220 秒）。command は `gh run view <id> --log | grep -F '| tests/schema.sh |'`。command の出力を schema に通す確かめは減らさない。証拠: `bash tests/schema.sh` の出力のうち「command の出力:」で始まる ok の行の数が、直す前と同じ。緩めた schema での自己検査の ok の行も同じ数だけ残る。
3. **手元の検査が、軽い検査と対応する重い検査になる。** 証拠: `printf 'internal/retro/apply.go\n' | bash tests/lib/scope.sh` の出力に `tests/andon-dispatcher.sh`・`tests/schema.sh`・`tests/apply-main.sh` が無く、`tests/andon-retro.sh` がある。`printf 'internal/dispatcher/loop.go\n' | bash tests/lib/scope.sh` の出力に `tests/andon-dispatcher.sh` がある。知らないパスを渡したときの出力は、重い検査を含む（安全な側に倒す）。対応の表は `tests/ci.sh` が確かめ、`docs/image.md` の「手元は関係する検査だけ」の表と `AGENTS.md` の文も同じ PR で直す。CI の tests の job が走らせる検査の顔ぶれは変わらない。証拠: 直した後の main の push の run の表に 29 本が並ぶ。
4. **仕分けの表ができる。** `tests/andon-dispatcher.sh` の 62 節と重い検査（`schema.sh`・`apply-main.sh`・`andon-issue.sh`・`andon-gate.sh`・`image.sh`）について、節ごとに、今確かめていること・防げる手段（lint の規則・動的な検証・型の設計・レイヤの設計・性能の計測・形式仕様・モデル検査・Go のテスト・シェルに残す）・そう見た根拠のファイルと行、を並べた表が調べる課題の報告にある。オーナーが見る（`manual`）。
5. **Go へ移した節は、壊せば落ちる。** 移した節ごとに、Go のテストの名前と、確かめている振る舞いをわざと壊したときの `go test -run '<名前>' ./internal/dispatcher` の FAIL の出力が PR の本文にある。移した節は `tests/andon-dispatcher.sh` から消えている。移した Go のテストは節ごとに状態を作り直し、1 件だけでも通る。証拠: `go test -run '<名前>' -count=1 ./internal/dispatcher` の出力。
6. **dispatcher の場面の確かめが手元で 60 秒以下になる。** 証拠: セルで `time go test -count=1 ./internal/dispatcher` と `time bash tests/andon-dispatcher.sh` を続けて打った出力の合計（今は `tests/andon-dispatcher.sh` だけで 148 秒）。

## 依頼書に切る案（縦に薄く・依存だけ。切るのは Chief of Staff）

1. **レビューを CI と並べる。** 3 つを同じ課題で、モデル・守り・skill の文の順に。

   - `andon issue review-request` に、その課題のレビュアーが動いている間は別の commit の頼み直しも断る守りを足す（`internal/issue/issue.go`）。課題の一生の動きに触れるので、モデルの検査が通ってから実装する。
   - worker skill の文を直す（`package/skills/worker/SKILL.md`）。§4 の 1 を「PR を出したらすぐ頼む。checks は裏で待つ」にする。CI が落ちたら直して push してよいが、頼み直すのは前のレビューの結果が届いてから。レビューが済んだら checks を待たずに `ready` へ進む。§4 の 2 の「stale は回に数えない」をコードに合わせて直す。§3 の 4 の checks の待ちは、`Review: off` の課題と Chief Engineer の文書の PR のために残す。
   `package/skills/` に触れるのでオーナーがマージする。依存は無い。受け入れ条件 1。
2. **`tests/schema.sh` の回し直しをやめる。** ほかの検査が 1 度目の実行で写した command の出力を、`tests/schema.sh` が読む形にする。依存は無い。受け入れ条件 2。
