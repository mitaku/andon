# ADR-0026: PR と repo に残る文は、セルの外の読み手に通じるように書く（仕様・設計。2026-11-19）

- 状態: **決定（2026-11-19）**。人が対話の中で「決めた」と言った（[decisions/2026-11-19-adr-0026-pr-rules-for-outside-readers.md](../decisions/2026-11-19-adr-0026-pr-rules-for-outside-readers.md)）。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書き、この行を `覆された → ADR-NNNN` にする。小さな改めは「決めたこと」に下から足す。
- 主題: Andon が作る PR の題と本文、commit の題、repo に入るファイルに、セルの中でしか意味を持たないもの（台帳の課題番号・セルの資源）をどこまで出すか。PR の本文の形。

## 問題（人の言葉で。言い直しの段落）

人（2026-11-19）: 「いくつかPRを作る際のルールが必要そう。A-000Xなどは手元で作成されているIssueIDのため、PullRequest上のタイトルに出てきていても他の人が困る。Andon/Cellの用語やファイルリソースはドキュメントやリポジトリに出ないことが好ましい。PullRequest上にMemoとして内部IssueIDとして設ける程度はよいが、そのセル上のリソースを参照するような記述はやめるべきである。また、形式検証、状態マシンは非常に有用と感じたのと 1. 変更理由 2. やったこと 3. 変更範囲 4. トレードオフ（検討したが採用しなかった案と理由） 5. 変更の影響範囲 6. 検証結果と確かめ方 このあたりの情報があればよりレビュー負荷が下がりそう（pstackがやっているようなPRの形）」

言い直し（人が 2026-11-19 に「あってます」と答えた）: Andon が作る PR は、セルの外の人が読む。ところが今の PR は、セルの中でしか意味を持たない物を前提に書かれている。題に入った課題番号は台帳を持たない人には辿れず、台帳を作り直せば同じ番号が別の課題を指す。本文や文書がセルの台帳や wiki を出典として指しても、読み手は開けない。そこで、PR と repo に残る文は、repo と PR だけを見ている人に通じるように書く決まりにする。課題番号は PR の本文に控えとして 1 行置く程度にとどめ、セルの中の物を指す書き方はやめる。あわせて、PR の本文を 6 項目の形に揃え、レビューする人が差分を開く前に、なぜ変えたか・どこまで変えたか・何を捨てたか・どこに響くか・どう確かめたかを読めるようにする。状態が動く変更では、6 項目めの「検証結果と確かめ方」に、状態の図やモデル検査の結果を載せる。

## 前提（同意済み。番号）

1. **2026-11-19 対象**: 困っているのは、セルの外にいて repo と PR だけを見る読み手。決まりの対象は外に出る文のすべて（PR の題・本文・コメント、commit の題、repo に入るファイル）。セルの中に残る台帳・依頼書・報告は、今までどおり課題番号で書く。
2. **2026-11-19 何もしないと**: 辿れない課題番号が PR の題と git の履歴に増え続ける。レビューする人は、なぜ変えたかと何を捨てたかを差分から読み直し続ける。今決めて、これから作る PR から効かせる。
   - **改め（2026-11-19。同じ対話の中）**: 同意を取った文は「public にしたあとは履歴を書き換えられないので、直すなら早いほど安い」と、これから public にする前提で書いていた。人（2026-11-19）「すでにPublicです」。repo はもう public で（`gh repo view --json visibility` が `PUBLIC`）、PR の題も履歴も、今すでに外の人が読める。出た履歴は事実上書き換えられないので、作る PR が 1 本増えるごとに、直せない物が 1 つ増える。急ぐ理由は強くなる。
3. **2026-11-19 既にあるもので済む部分**: 新しい道具は足さない。6 項目のうち、やったこと・テスト結果・見送った指摘は今の PR にあり、検証の証拠は担当の報告（`report.json` の `acceptance[]`）にある。足りないのは、変更理由・変更範囲・捨てた案・影響範囲を書く決まりだけ。直すのは担当・Chief Engineer・Chief of Staff の skill の文が中心で、機械の検査を足すなら、PR の本文をすでに読んでいるゲートに足す。
4. **2026-11-19 配り方**: 決まりは Andon のパッケージの skill に置く。セルを更新すれば、そのセルが扱うすべての案件の repo の PR に同じ決まりが効く。案件の repo の側には、PR の雛形などのファイルを Andon からは足さない。

## 現地の事実（2026-11-19 に読んだもの）

- PR 262 本のうち 233 本の題に課題番号がある。台帳が作り直されたので、番号は一意でない（同じ番号が、時期の違う 2 本の PR の題に出ている。15 個）。古い台帳の番号（別の接頭辞）は 68 本の題にあり、その台帳はもう無い。
- マージは squash。この repo の設定は、題が `COMMIT_OR_PR_TITLE`、本文が `COMMIT_MESSAGES`（`gh api repos/{owner}/{repo}`）。branch の commit が 1 本なら、その commit の題と本文がそのまま履歴に入る（PR の題ではない）。複数なら PR の題が題に、commit の題の並びが本文に入る。直近のマージ 40 本のうち 27 本は commit が 1 本。直近 257 commit のうち 184 の題に課題番号がある。
- PR の本文は、この設定では履歴に入らない（本文の末尾に控えの行を置いた PR のマージ commit に、その行は無い）。本文に PR の本文を使う設定（`PR_BODY`）の repo では入る。
- remote には branch が 168 本残っていて、167 本の名前に課題番号がある（`git ls-remote --heads origin`。マージで branch を消す設定は切ってあり、片付けが消すのは手元の branch だけ）。squash の commit に branch の名前は入らない。
- テスト以外の Go のコードのコメントにも、実在の課題番号がある（架空の例の番号と混ざっている）。
- repo のファイル（テストを除く）: `docs/adr/` に 436 か所、`docs/decisions/` と `docs/decisions.md` に 163 か所。skill・`contract.md`・`ledger.md` に出る番号は、ほとんどが書き方の例。
- 今の決まり: worker skill §3 の PR の決まりは「本文に、やったこと・テスト結果・見送ったレビューの指摘」の 1 行で、題の決まりは無い。chief-engineer skill の文書の形は、題に Chief Engineer の課題の id を、出典にセルの wiki と台帳を書かせる。
- 機械: ゲート・dispatcher・measure は PR の場所を `report.json` の `pr` から読む。PR の題・本文・commit の題から課題番号を読む所は無い。measure は、題が `Revert ` で始まる PR を revert と数え、本文の `owner/repo#n` か PR の URL で、どの PR の revert・続きかを引く。ゲートが本文とコメントから読むのは添付の画像で、`<details>` の中にあっても当たる。dispatcher は、頭が `andon gate: ` のコメントをゲートのものと見分ける。レビュアーに渡るのは worktree と差分だけで、PR の題と本文は渡らない。レビュアーの指摘は `file` と `line` が必須（`schema/findings.schema.json`）。branch の名前は `<slug>/<id>-<題の短い形>` で、PR の画面に出る。
- 検査: `tests/public.sh`・`tests/words.sh` は repo のファイルだけを見る。PR の題・本文・commit の題を見る検査は無い。
- pstack（poteto-mode の「Opening a PR」）: 題は `type(scope): subject`。本文は 40 行以内で、`Why`・`What changed`・`Scope`・`Tradeoffs`（レビュアーが聞きそうな捨てた案だけ）・`Blast Radius`・`Verification` の順。中身の無い節は落とす。

## 決めたこと（番号・日付・理由・捨てた案）

1. **2026-11-19 規則は 1 本:「その repo と PR だけで解けるものだけ書く」。帰結が repo で違う。**（人が選んだ）
   - Andon 自身の repo: Andon の用語（セル・台帳・Chief of Staff など）は製品の語で、repo の用語集で解けるので書いてよい。書かないのは、このセルの具体物（実在の課題番号・セルのパス・wiki や台帳のページ・端末の名前）。
   - 案件の repo: Andon の用語も解けないので書かない。ふだんの言葉にする。
   捨てた案: 案件の repo だけに効かせる（Andon の repo の題と履歴に辿れない番号が増え続ける）／どの repo でも Andon の語を避ける（製品の語で製品の変更を説明できなくなる）。
2. **2026-11-19 課題番号は、PR の本文の末尾の控え 1 行にだけ置く。**（人が選んだ）
   PR の題・commit の題・commit の本文には入れない。担当が branch に積む commit も同じ（squash のマージは、commit が 1 本ならその題と本文を、複数なら commit の題の並びを履歴に入れる）。形は `Memo: 内部の課題番号 <id>`（repo が英語なら `Memo: internal issue <id>`）。
   理由: セルの中の人は PR から課題に戻れ、外の人は読み飛ばせる。PR と課題の対応は台帳（`report.json` の `pr`）が持つので、題から外しても機械は壊れない。
   捨てた案: どこにも置かない（PR から課題に戻るには台帳を PR の URL で探すことになる）／PR のコメントに置く（コメントと担当の手順が 1 つずつ増える）。
   仮（2026-11-19・Chief Engineer）: squash の本文に PR の本文を使う設定の repo では、控えの行が履歴に入る。これは許す（控えの 1 行はよい、の範囲と読んだ）。
3. **2026-11-19 セルの中の物を根拠にするときは、中身を写し、セルは指さない。**（人が選んだ）
   要る事実は数や結果ごと文書と PR に書き切り、要る資料は repo に入れる。出典に書くのは、repo の中の文書・外の URL・人の発言の日付だけ。ほかの作業は課題番号でなく、PR の番号か、何の変更かを言う言葉で指す。ADR の題にも課題番号を書かない。コードのコメントも同じ。書き方の例とテストに出る架空の番号はそのままでよい。
   ほかの PR を指すときは、PR の URL か `owner/repo#n` の形で書く（measure が revert と続きの PR を引く形。`#n` だけでは引けない）。外の Issue を閉じる行（`Fixes <url>`）は、本文の末尾、控えの行の前に置く。
   捨てた案: 指してよいが「外からは読めない」と断る（読み手が開けない根拠が repo に残り続ける）／PR だけ厳しくし、ADR と決定の記録は今までどおり（前提 1 の対象を狭める）。
4. **2026-11-19 PR の本文は 6 つの見出しをこの順で。3 節が必須、残りは書くことがあるときだけ。**（人が選んだ）

   | 見出し | 必須か | 書くこと |
   |---|---|---|
   | 変更理由 | 必須 | なぜ変えるか。困っていたこと |
   | やったこと | 必須 | 何をどう変えたか |
   | 変更範囲 | あれば | 触った所と、あえて触らなかった所 |
   | トレードオフ | あれば | 検討したが採用しなかった案と理由。見送ったレビューの指摘もここ |
   | 影響範囲 | あれば | この変更が届く先（呼び出し元・利用者・運用・戻せるか） |
   | 検証結果と確かめ方 | 必須 | 打ったコマンドと結果。読み手が自分で確かめる手順。画面の添付もここ |

   末尾に決めたこと 2 の控えの行。
   理由: 1 行の直しに 6 節を埋めさせると読む量がかえって増える。小さい PR は自然に短くなる。
   捨てた案: 6 節すべて必須で、無い節は「無し: 理由」（落とし忘れは起きないが、どの PR にも 6 節が並ぶ）／変更の大きさで分ける（大きさの線を決めて守らせる手間が増える）。
5. **2026-11-19 状態の移り方を変える変更は、「検証結果と確かめ方」に変更前と変更後の状態の図（Mermaid）を載せる。必須。**（人が選んだ）
   repo にモデルがあるときは、モデル検査の結果（調べた状態の数と、破れた規則が無いこと）も載せる。モデルが無い repo に、PR のためにモデルを新しく作ることは求めない。
   理由: 人（2026-11-19）「形式検証、状態マシンは非常に有用と感じた」。GitHub は PR の本文の Mermaid をそのまま描くので、道具は要らない。
   捨てた案: 担当の判断に任せる（載るかどうかが PR ごとにばらつく）／モデル検査まで必須にし、モデルが無ければ作る（1 本の PR のコストが大きく上がり、案件の repo に道具が増える）。
6. **2026-11-19 仮（Chief Engineer）: PR の題は今の書き方のまま、課題番号だけ外す。** repo に題の慣習（Conventional Commits など）や PR の雛形があれば、repo の決まりが先。見出しの言葉は repo の言語に合わせる（英語の repo は `Why`・`What changed`・`Scope`・`Tradeoffs`・`Blast Radius`・`Verification`）。revert の PR の題は GitHub の既定（`Revert "…"`）のまま（measure が題の頭で数える）。人が違うと言ったら直す。
7. **2026-11-19 守らせるのは担当の手引きの文だけ。機械の検査は足さず、レビュアーにも見させない。**（人が選んだ。2 度聞いた）
   守りは、担当の手引きと、マージする人の目。形が少しずつずれることは受け入れる。
   経緯: 1 度目の問いで人は「手引きだけ直す」を選んだ（Chief Engineer の推奨はゲートの検査を足す案だった）。そのとき Chief Engineer は「落とした節が空かはレビュアーが見る」と説明したが、反論で、今の作りでは効かないと分かった（レビュアーに PR の題と本文は渡らない・指摘は `file` と `line` が必須で題や本文の違反を書けない・`Review: off` の課題にはレビュアーがいない）。2 度目の問いで、人は「担当の手引きだけにする」を選んだ。
   捨てた案: ゲートが PR の題・本文・commit の題を確かめる（課題番号・セルのパス・必須の 3 節。`Review: off` の課題にも効く）／レビュアーに PR の題と本文を渡し、ファイルと行の無い指摘を書けるように約束を変える（3 つの中で変更が最も大きく、`Review: off` の課題には効かない）／差分の追加行まで機械が見る（Andon の repo はテストと書き方の例に架空の番号が多く、誤って止める）。
8. **2026-11-19 要点は開いたまま書き、長い物だけ `<details>`／`<summary>` に畳む。**（人が選んだ。人 2026-11-19「PRではHTMLのdetail/summaryが活用できるので、ユーザーの認知負荷を下げるためにも活用するとよい」）
   各節の要点は数行で開いたまま書く。畳むのは長くなる物だけ: コマンドの出力・ログ・モデル検査の出力・変更前の状態の図・見送った指摘の一覧・ファイルごとの細かい変更。`<summary>` には、開かなくても結果が分かる 1 行を書く（例「`go test ./...` の出力（通った。412 件）」）。変更後の状態の図は畳まない。
   捨てた案: 任意の 3 節をまるごと畳む（レビューで大事な捨てた案と影響範囲が、開かないと読めなくなる）／担当の判断に任せる（畳み方が PR ごとにばらつく）。
9. **2026-11-19 機械が PR と外の Issue に書く文も、外の人が読める文に直す。**（人が選んだ）
   ゲートが PR に残すコメントは、内輪の語（`needs_human`・`tier C`・`delegation merge=B`）を使わない文に書き直す。道具の名前（`andon gate`）は署名として残す。外の Issue への書き戻し（今は「Andon: 課題 <id> が終わった」）からは課題番号を外す。
   直したあとの例（文面は実装で決める）: 「andon gate: 人がマージする変更です（commit …）／理由: 手引きのファイルを変えている（package/…）。10 行／CI: 実行中（go, tests）／レビュー: まだ無い」。書き戻しは「この Issue に対応する変更がマージされた。PR: <URL>」。
   反論で分かった、実装で守ること:
   - commit に付く合否の印（`andon/gate` の説明文。今は「andon gate: needs_human（tier C）」）も同じく直す。
   - コメントの頭の `andon gate: ` は動かさない（dispatcher がこの頭でゲートのコメントを見分け、人の手直しから除く）。
   - コメントは今、ゲートの記録の理由（`reasons[]`）をそのまま写していて、理由の文に内輪の語（台帳・`issue.yaml`・`report.json`・条件表など）が出る。記録の文は変えず、コメント用の文を別に持つ。`contract.md` の「同じ内容を写す」を改める。
   - 書き戻しは 3 つの場合（マージした・マージせずに閉じた・PR が無い）の文を持つ。この文を定めた ADR-0011 の決めたこと 15 は、同じ ADR の「決めたこと」に下から改めを足す（決めたこと 10 の「直さない」は、過去の課題番号を書き換えないことで、決定の改めは今までどおり足す）。
   捨てた案: コメントをやめて commit の合否の印だけ残す（なぜ人のマージ待ちなのかを PR の上で読めなくなる）／今回は直さない（内輪の語のコメントが PR に残り続ける）。
10. **2026-11-19 過去は直さない。まだマージしていない PR も直さない。**（人が選んだ。2 度聞いた）
    マージ済みの PR の題と履歴、既存の ADR と決定の記録、コードのコメントは、当時の記録としてそのまま残す。新しい決まりは、手引きの直しがマージされたあとに始める課題の PR と文書から効かせる。
    経緯: 1 度目の問いで人は「過去は直さず、まだマージしていない PR だけ、マージの前に題から課題番号を外す」を選んだ。反論で、PR の題を直しても、commit が 1 本なら commit の題が、複数なら commit の題の並びが履歴に入ると分かった。そのとき開いていた PR は 1 本（commit 3 本）。2 度目の問いで、人は「何もしない」を選んだ（Chief Engineer の推奨は、PR の題だけ直す案だった）。
    捨てた案: 開いている PR の題だけ直す（履歴の題からは消えるが、本文に commit の題が残る）／commit も書き直して押し直す（レビューと確かめがやり直しになる）／ADR と決定の記録の約 600 か所も直す（当時の記録を書き換えることになる）／履歴の書き換えを含めて、あとでまとめて直す（問いに出したときは「public にする直前に」と書いたが、repo はすでに public で、この案は成り立たない。public の履歴の書き換えは、取り込んだ人の手元を壊す）。
11. **2026-11-19 価値の仮説は置かない。**（人が選んだ。Chief Engineer の推奨は、守られた PR の割合を 2 週間後に数える案だった）
12. **2026-11-19 branch の名前は変えず、決まりの対象外にする。その代わり、マージしたら remote の branch を自動で消す。**（人が選んだ）
    repo の設定「マージしたら branch を自動で消す」（`delete_branch_on_merge`）を入れる。入れるのは人の手で、1 回で済む。今残っている 167 本は触らない。
    理由: branch の名前の形（`<slug>/<id>-…`）は機械が読んでいる（起動し直しとゲートの照合）。squash の履歴に branch の名前は入らない。片付けが見るのは手元の branch・既定の branch・PR の状態で、remote の作業 branch には依らない（`internal/issue/finish.go`）。
    捨てた案: 既存の 167 本も消す（外に出ている物を消す作業で、消す前に人の承認が要る）／対象外と書くだけ（課題番号つきの branch が増え続ける）／名前から番号を外す（名前の形を読む機械を直すことになり、変更が最も大きい）。

## やらないこと

- **機械の検査を足すこと**（ゲート・`tests/` が PR の題・本文・commit の題・差分の追加行を見ること）と、**レビュアーに PR の題と本文を見させること**。決めたこと 7。
- **過去を直すこと**（マージ済みの PR の題・git の履歴・既存の ADR と決定の記録・コードのコメント）と、**まだマージしていない PR を直すこと**。決めたこと 10。
- **branch の名前を変えること**と、**今 remote に残っている branch を消すこと**。決めたこと 12。
- **案件の repo にファイルを足すこと**（PR の雛形など）。前提 4。
- **モデルの無い repo に、PR のためにモデルを作らせること**。決めたこと 5。
- **セルの中の文を変えること**（台帳・依頼書・報告）。今までどおり課題番号で書く。前提 1。
- **効いたかの観察**。決めたこと 11。
