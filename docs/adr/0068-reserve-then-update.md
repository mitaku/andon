# ADR-0068: マージの予約を合図に、dispatcher が main を取り込ませてからマージする（仕様・設計。2026-11-27）

- 状態: **決定（2026-11-27）**。オーナーが 2026-11-27 に「決めた」と答えた。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書く。
- 主題: main が動くたびに担当が PR を取り直すのをやめる。main より遅れた PR は、マージの時に 1 回だけ、機械が main を取り込ませて検査し直す。[ADR-0067](0067-stacked-start.md) の「やらないこと」の 1 と 2 が、次のテーマに回した問いである。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。この文書が変える約束は「決めたこと」に形を書き、実装の課題が写す（それまでは提案）。
- この文書の語: 「取り直し」は、担当が PR の branch を main の先へ rebase し、検査と報告をやり直すことを指す。「取り込み」は、PR の branch に既定の branch の先を merge commit 1 つで入れることを指す。「予約」は、GitHub の auto-merge の予約を指す。「base の最新を求める設定」は、既定の branch の ruleset の「Require branches to be up to date before merging」を指す。「列」は、同じ repo で、取り込みとマージを 1 本ずつ進める PR の並びを指す。

## 問題（オーナーの言葉で。言い直しの段落）

オーナーのマージを待つ PR は、main にほかの PR が入るたびに、担当の取り直しになる。取り直しのたびに担当が数分動き、検査が回り直り、オーナーの判断待ちの一覧の行も出し直しになる。オーナーが望むのは、PR がいくつたまっても担当の取り直しにならず、取り直しが要るならマージの時の 1 回で済むことである。main の検査を赤にしない守りは保つ。衝突の無い取り直しを機械が済ませてよいかも、同じ問いとして決める。たまった PR には新しい上限も新しい知らせも足さないことは、オーナーが前に決めている（[ADR-0065](0065-owner-waits-never-stop-launch.md) 決めたこと 2）。

## 読んで分かった事実（2026-11-27。main `550c6d2` と、Andon を開発しているセルの kanban で実測）

数えた期間は、2026-11-22 00:00 から 2026-11-27 00:00（UTC）の 5 日である。取り直しは、課題ごとの gate の記録を時刻順に並べ、隣り合う 2 件で PR の head が違う組として拾った。前後の head と main の分かれ目を git で比べ、衝突したか、PR の自分の差分が同じかを見た。

1. **取り直しのほとんどは、衝突を解くためではない。** 担当が rebase したのは 59 回だった。衝突を解いたのは 8 回で、担当が動いた時間は合計 89 分である。残りの 51 回は衝突が無く、合計 356 分だった。そのうち 44 回は、PR の自分の差分が rebase の前後で同じである。
2. **衝突の無い取り直しは、2 つの時に起きる。** gate が通したあと、マージを待っている間のものが 27 回で、205 分だった。gate が通す前に「base が古い」と差し戻されたあとのものが 23 回で、112 分だった。残りの 1 回は、gate がほかの理由で差し戻したあとのもので、39 分だった。マージを待つ間の取り直しは 16 件の課題で起き、多い課題では 1 件で 8 回と 6 回である。
3. **回し直しが失敗を見つけるのは、まれである。** 衝突の無い 51 回のうち、取り直したあとの最初の判定が差し戻しだったのは 3 回である。そのうち、新しい main で GitHub の checks が落ちたと記録から読めるのは 1 回だった。
4. **古い base の守り。** gate は、PR の分かれ目より後に main で検査の置き場が変わっていると、「base が古い」と担当へ差し戻す。PR 自身が検査の置き場を変えていて main が 1 commit でも進んだときも、同じに差し戻す（`internal/gate/decide.go` の `Decide` と、`internal/gate/gate.go` の `CheckPlaces`）。検査の置き場は、`tests/`、`.github/workflows/`、検証の地図、Go の `*_test.go` である。この守りは 2026-11-24 に PR #596 で入った。古い base の CI のまま入った PR で、main の `tests` が 2 回赤になったことが理由である。
5. **守りは、gate が通したあとには届かない。** gate は、approve かオーナー待ちを決めたあと、PR の head が動くまで回り直さない（`internal/issue/merge.go` の `headMoved`）。main が動いても回り直さない。そこで、マージを待つ PR は、Chief of Staff が `andon issue impact` の事実を読み、手引き（`package/skills/chief-of-staff/playbooks/finish.md`）の表に従って担当に rebase を頼んでいる。衝突したとき、検査の置き場が動いたとき、同じファイルが重なったときの 3 つで頼む。
6. **その頼みは、オーナーのマージに間に合っていない。** 守りが入ったあと（2026-11-24 15:00 から）にマージされた担当の PR は 60 本だった。dispatcher がマージした 33 本は、全部が main の先に追いついていた。オーナーがマージした 27 本は、13 本が古い base のまま入り、そのうち 12 本は検査の置き場が動いていた。オーナーのマージは、26 回の間隔のうち 11 回が 2 分以内である。続けて押す間に、rebase の頼みは届かない。
7. **ほとんどの main の動きが、検査の置き場に触る。** 5 日でマージされた担当の PR 169 本のうち、マージの時に base が古かったのは 73 本で、そのうち 68 本は検査の置き場が動いていた。守りは、実質「いつも base の最新に追いつく」を求めている。
8. **検査は速い。** 直近の成功 60 回で、PR の `tests` は中央値 4.7 分、最長 7.4 分だった。`go` は中央値 1.4 分である。担当の取り直しは 1 回あたり約 8 分かかっている（[ADR-0067](0067-stacked-start.md) 事実 3）。
9. **担当の取り直しで動くもの。** 担当は課題を `doing` に戻し、rebase して検査を通し、force push する。差分が同じならレビューは引き継がれる（`internal/ledger/review.go` の `SamePatch`。足した行と消した行が同じなら同じ差分とみなす）。それでも、報告を書き直して `andon issue ready` を打ち直す。head が変わるので、gate は前の head の問いを閉じ、新しい head で問いを出し直す。
10. **dispatcher のマージ。** dispatcher は、approve で自動のマージを任された PR を、`gh pr merge --squash --match-head-commit` でマージする。直前に、任されているかと、head と checks を読み直す。base が動いて GitHub が断ったときは、断りの文が決まった 2 つのどちらかなら、3 回まで打ち直す（`internal/issue/merge.go` の `approve` と `RetryMerge`）。
11. **dispatcher は、課題の PR を 1 分に 1 回読んでいる。** `andon issue settle` が、`doing` と `review` の課題の PR を `gh pr view` で読み、マージされたかを見て、印を揃える（`internal/issue/settle.go`）。dispatcher の巡は、1 つのセルの中では順に 1 つずつ動く。
12. **印と auto-merge についての前の決定。** [ADR-0056](0056-gate-required-before-merge.md) 決めたこと 2 で、オーナーは gate の印 `andon/gate` を main の必須の check にすると決めた。同じ ADR の決めたこと 15 で、repo の GitHub の auto-merge を切ると決めた。判定の前に予約すると、gate が緑を書いた時に、オーナー待ちの理由を読まないままマージされるからである。決めたこと 16 の切り替えは、まだ行われていない。今の main の ruleset が必須にしている check は `tests` と `go` で、base の最新は求めていない。repo の auto-merge は有効である。PR だけで走る job `isolation` は、必須でない。
13. **GitHub の merge queue は使えない。** マージの時に最新の main と合わせて検査してから入れる merge queue は、organization が持つ repo だけの機能である。GitHub の文書は「Pull request merge queues are available in any public repository owned by an organization, or in private repositories owned by organizations using GitHub Enterprise Cloud」と書いている。この repo は個人のアカウントが持っている。
14. **検査の re-run は、取り直しの代わりにならない。** `pull_request` の CI は、PR の head と base を合わせた merge commit を検査する。re-run は、最初に回した時と同じ commit で回る。GitHub がこの merge commit を作り直すのは、PR の branch に push されたとき、PR と base の分かれ目が変わったとき、今の merge commit が 12 時間より古いときだけである（2026-02-19 の changelog）。`workflow_dispatch` で回した job の check は、ruleset の必須の判定に使われない。
15. **使える部品。** base の最新を求める設定は、main より遅れた PR のマージを GitHub の側で断る。必須の check が 1 つも無いと効かない。auto-merge は、マージの条件が満たされていない PR に予約でき、条件が全部満たされると GitHub がマージする。個人の public repo でも使える。PR の branch に base を取り込ませる API（`PUT /repos/{owner}/{repo}/pulls/{pull_number}/update-branch`）は、base の先を merge で取り込み、`expected_head_sha` が今の head と違えば断る。rebase で取り込む口は GraphQL にだけある。auto-merge は、base が進んでも PR の branch を更新しない。
16. **GitHub の文書に書かれていないこと。** 設計が頼る動きのうち、次のものは文書に無い。遅れているだけで checks は通っている PR に、予約できるか。書き込み権限のあるアカウントの取り込みのあとも、予約が残るか。base が進んだときと checks が落ちたときに、予約が残るか。取り込みの merge commit の親の並びと作者。予約でマージされた PR の `merged_by`。PR を閉じたときに予約が消えるか。文書が書いているのは、書き込み権限の無い人が push したときと、PR の base を替えたときに予約が外れることだけである。
17. **`GITHUB_TOKEN` の更新では、CI が承認待ちになる。** ワークフローが `GITHUB_TOKEN` で PR を更新すると、その `pull_request` の run は承認待ちで作られる（2026-06-11 の changelog）。個人のアクセストークンか GitHub App の token の更新なら、ふつうに走る。セルの dispatcher は、セルの `gh` の token で API を打つ。
18. **モデル。** `model/IssueLife.tla` は、PR が main より遅れているかを持たない。持つのは、PR の向き先が既定の branch か前の課題の branch かである。gate が決めたあとに head が動く動き（`HeadMovesAfterGate`）と、担当が差分を変えずに rebase する動き（`WorkerRebasesSamePatch`）は持つ。規則は 21 本、状態は 168,644 である。
19. **head が動くと、今のコードで変わるもの。** レビューの照合は、担当の worktree の git で差分を比べる。gate が `git fetch` を打つのは、レビューが今の head のものだと分かったあとだけである（`internal/gate/gate.go` の `runChecks`）。GitHub の側で作られた commit は、だれかが取ってくるまで手元に無い。gate は、checks が 1 つも無いまま過ぎた時間を、課題が最後に `review` に入った時刻から数える（`internal/gate/decide.go` の `ChecksOverdue`。上限は条件表の 30 分）。gate は判定のたびに、PR に判定のコメントを 1 つ書く（`postGitHub`）。approve のまま 10 分たった課題は、dispatcher が Chief of Staff に通知する（`internal/dispatcher/route.go` の `stuck`）。片付けは、手元の branch の先がマージされた PR の head と違うと、branch を残す（`internal/issue/finish.go`）。
20. **オーナーの判断待ちの一覧の読み方。** `andon waiting list` は、今の head を報告の commit で読み、gate の問いが指す head がそれと違えば、古い問いとして飛ばす（`internal/waiting/waiting.go` の `mergeItem`）。読むのは kanban と課題の資料置き場と `project.json` だけで、GitHub は読まず、git も呼ばない（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 9）。オーナー待ちに数えない課題は、動いている課題に数えられ、起動できる空きを 1 つ使う（[contract.md](../contract.md) §25）。
21. **差分からは、衝突を解いたかどうかが分からない。** `SamePatch` は、衝突を解いた rebase でも、足した行と消した行が同じなら同じ差分とみなす。この緩さは、レビューの引き継ぎのために引き受けたものである（決定の記録 `docs/decisions/2026-11-21-review-carry-ignores-context-lines.md`）。
22. **積む仕組みは、一部が main に入っている。** [ADR-0067](0067-stacked-start.md) の決めたこと 8・10・16 が、この文書を書いている間に実装された（PR #671 と PR #673）。gate は、積んだ課題の PR に判定 `behind`（前の PR 待ち）を返し、積んだ PR では古い base を見ない。枠は、前の PR 待ちの課題を `slots.behind` に数える。差し戻しの率と振り返りは、`behind` の記録と、載せ替えを頼む差し戻しの記録を数えない。積む起動と、載せ替えの口 `andon issue restack` は、まだ無い。
23. **repo のモデルの検査器は、大きいモデルの状態の図を扱えない。** `model/check` の検査器 tla-ts は、状態の図を 1 本の文字列で書き出す。`model/reach.mjs` は、その図を 1 本の文字列で読む。「行ける」の形の規則は、この図を読んで調べる。main のモデルの 168,644 状態は扱える。261,102 状態の写しでは、書き出しが「Invalid string length」で止まった。567,048 状態の写しでは、メモリ不足で止まった。567,048 状態の写しを TLC で書き出した状態の図は 800MB で、1 行ずつ読めば、同じ規則を 1 分で調べられた。検査器に tla-ts を選んだのはオーナーである（[ADR-0025](0025-formal-model-in-repo.md) 決めたこと 2）。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案。あとから覆したら上書きせず下に足す）

### 範囲とマージの形

1. **2026-11-27 衝突の無い取り直しの 2 種類を、担当を呼ばない形にする。衝突を解く取り直しは担当のままにする（オーナーが決めた）。**
   対象は、gate が通したあとマージを待つ間の取り直しと、gate が通す前に「base が古い」で差し戻されたあとの取り直しである（事実 2 の 27 回と 23 回）。衝突を解く取り直し（8 回）は、今のまま担当が解き、解いたあとの差分をオーナーが見る。
   理由: 衝突の無い取り直しは、担当の判断を使っていない。衝突を解くと差分が変わるので、オーナーが見たものと入るものが変わる。
   捨てた案: マージを待つ間の取り直しだけを対象にする案は、gate の差し戻しの 23 回が残る。衝突を解く取り直しもマージの時にまとめる案は、オーナーがマージを決めたあとに差分が変わる。コードを変えずに Chief of Staff の手引きだけを直す案は、古い base のまま main に入ることを受け入れることになり、main の検査が赤になった 2 回（事実 4）に戻る。

2. **2026-11-27 main より遅れた PR は、オーナーがマージを予約し、dispatcher が main を取り込ませ、検査が通れば GitHub がマージする（オーナーが決めた）。**
   main の ruleset に、base の最新を求める設定を入れる。遅れた PR は、GitHub がマージを断る。オーナーは、遅れた PR では「Enable auto-merge」を押す。main に追いついている PR は、今と同じボタンですぐ入る。予約を見た dispatcher が、GitHub の API で main を PR の branch に取り込ませる。検査が新しい head で回り、gate が判定し直して緑の印を書くと、GitHub がマージする。マージするのは今と同じくオーナーで、dispatcher はオーナーの PR をマージしない。
   理由: 守りがオーナーのマージに届かないのは、オーナーが押してから main に入るまでの間に、だれも割り込めないからである（事実 6）。押すことを合図に変えれば、合図のあとの 1 回で取り込める。GitHub が断る形にすれば、続けて押しても古い base のまま入らない。
   捨てた案: 今のボタンのまま、main が動くたびに dispatcher がマージ待ちの PR 全部に main を取り込ませる案は、続けてマージするときに 1 本ごとに検査の 5 分から 7 分を待つことになり、PR の head と検査が main の動くたびに動く。予約を合図にして担当が 1 回だけ rebase する案は、担当の動く回数がマージ 1 本につき 1 回残る（1 回約 8 分。事実 8）。

3. **2026-11-27 [ADR-0056](0056-gate-required-before-merge.md) 決めたこと 15 を覆し、GitHub の auto-merge を有効のままにする（オーナーが決めた）。**
   決めたこと 15 が防ごうとした「判定の前の予約でマージされること」は、auto-merge を切る代わりに、決めたこと 10 と 11 の守りで防ぐ。同じ ADR の決めたこと 2（印を必須にする）と 14（抜け道を作らない）は生きている。
   理由: 予約が、決めたこと 2 の合図になる。合図を GitHub の外に作ると、だれがマージするかが変わる。
   細部: 守りには、短い窓が 3 つ残る。1 つ目は、gate が予約の有無を読んでから緑の印を書くまでの間（1 秒ほど）である。この間にオーナーが予約すると、その予約は外されず、緑になった時にマージされる。2 つ目は、Chief Engineer の文書の PR である。文書の PR は gate を通らないので、課題が `review` に入る直前に入れた予約は、dispatcher の次の読み（1 分以内）より先に `review` に入ると外されない。文書の PR が `review` に入るのは、オーナーが文書を「決めた」と言ったあとである。3 つ目は、オーナーが gate の問いに「担当に直させる」と答えてから、dispatcher が印を直すまでの間（1 分以内）である。この窓は、今のマージのボタンにもある。今は、印が必須でなく auto-merge も有効なので、判定の前の予約はいつでも通る。

### 仕組みが働く repo

4. **2026-11-27 仕組みが働くのは、既定の branch の ruleset が base の最新と印 `andon/gate` の両方を求める repo だけにする。gate と dispatcher は、それを GitHub から毎回読む（Chief Engineer が決めた）。**
   条件表にキーは足さない。ruleset が読めないときは、働かない repo として扱う。条件表のマージの方式が `rebase` の repo でも、仕組みは働かない。
   理由: 遅れた PR のマージを断れるのは GitHub だけである。取り込んだ head を、gate が判定し直す前に GitHub がマージしないようにできるのは、必須の印だけである。印が必須でない repo では、取り込んだ head で `tests` と `go` が通った時に GitHub がマージし、必須でない check と条件表の検査は、だれも見ない（事実 12）。設定のキーで切り替えると、キーと ruleset が食い違ったときに、守りの無い repo ができる。事実から読めば食い違わない。
   捨てた案: 条件表にキーを足す案は、上の食い違いが起きる。base の最新を求めるだけの repo でも働かせる案は、上の理由で、判定し直しの前にマージされる。読んだ値をしばらく使い回す案は、オーナーが設定を戻した直後に、gate の守りも GitHub の守りも無い時間ができる。
   細部: 読む口は `gh api repos/<owner>/<repo>/rules/branches/<既定の branch>` で、`required_status_checks` の規則の `strict_required_status_checks_policy` と、必須の check の名前に `andon/gate` が在るかを見る。古い形の branch protection は読まない。gate は判定のたびに読み、dispatcher は巡ごとに repo につき 1 回読む。base の最新だけを求めて印を必須にしていない repo は、今のまま動く。gate は古い base を差し戻し、担当が取り直す。`rebase` を外すのは、取り込みの merge commit を含む branch を GitHub が rebase でマージできるかが分からないからである。

5. **2026-11-27 仕組みが働く repo では、gate は古い base を差し戻しの理由にせず、Chief of Staff は衝突の無い rebase を頼まない（Chief Engineer が決めた）。**
   働かない repo では、gate の守りも手引きの表も今のままにする。
   理由: 働く repo では、main に入る head は必ず main の先を含み、その head で gate が、必須の checks も必須でない check も条件表の検査も見てから緑を書く。gate の今の守りより強い。働かない repo で守りを外すと、main を赤にしない網が無くなる。
   細部: `Decide` の「古い base」の 2 つの枝を、仕組みが働く repo では飛ばす。gate の記録には、判定の時に main が何 commit 先にあったかを `base_ahead` で残す。オーナーが設定を戻したときのために、dispatcher は、`base_ahead` が 1 以上のまま通した `review` の課題を、働かない repo で見つけたら、gate を回し直す。`andon issue impact` は、仕組みが働く repo かを 1 つの事実として出す。手引きの影響の表は、その事実があるとき、`checks_moved` の行と `overlap` だけの行で「何もしない」と読む。`conflict` の行と、前提が変わった行は今のままである。

### 取り込み

6. **2026-11-27 取り込みは GitHub の API に merge でさせる。dispatcher は担当の branch に git で書かず、rebase も force push もしない（Chief Engineer が決めた）。**
   [ADR-0067](0067-stacked-start.md) の「やらないこと」の 2 が挙げた懸念は、機械が担当の branch に push することと、報告の commit を機械が書き直すことだった。merge で取り込めば、担当の commit は 1 つも書き換わらず、報告の commit も書き直さない（決めたこと 8）。
   理由: merge commit が 1 つ載るだけなので、担当の手元の branch は早送りで追いつける。PR は squash でマージされるので、main の履歴に merge commit は残らない。セルから push しないので、担当の worktree と取り合わない。
   捨てた案: dispatcher がセルの中で rebase して force push する案は、担当の commit を書き換え、担当の手元と食い違い、報告とレビューが指す commit が消える。GraphQL の rebase の取り込みも同じである。GitHub Actions のワークフローに取り込ませる案は、`GITHUB_TOKEN` の更新では CI が承認待ちになり（事実 17）、避けるには repo に token を置くことになる。
   細部: 口は `PUT /repos/<owner>/<repo>/pulls/<n>/update-branch` で、`expected_head_sha` に今の head を渡す。打つのは、今の head を gate が通しているときだけである。head が動いていて断られたら、何もせず次の巡で読み直す。API が受け付けてから head が動くまでの間に次の巡が来ると、同じ head にもう 1 回打つことになるが、2 回目は何も変えないか、head が違うと断られる。

7. **2026-11-27 取り込みとマージは、repo ごとに 1 本ずつ、列に入った順に進める（Chief Engineer が決めた）。**
   列に入るのは、`review` で止めていない課題の PR のうち、gate が今の head か取り込みの元の head を通していて、オーナーの予約が生きているものと、dispatcher が自分でマージするものである。Chief Engineer の文書の PR は gate を通らないので、`review` で止めていず、予約があれば入る。順は、予約の時刻と、approve の判定の時刻で決める。dispatcher は、列の中に取り込みの検査を待つ PR が無いとき、遅れている PR のうち順が一番前の 1 本に取り込みを打つ。その PR がマージされるか、列から外れたら、次の PR へ進む。
   理由: 予約のある PR を一度に全部取り込むと、1 本入るたびに残りが全部また遅れ、検査が PR の数の 2 乗で回る。1 本ずつなら、PR の数だけで済む。
   細部: 列は控えを持たない。dispatcher が巡のたびに、1 分に 1 回の PR の読みと gate の記録から組み直す。1 つのセルの中では巡が順に動くので（事実 11）、取り込みは 1 本ずつ打てる。遅れは、既定の branch の先頭の commit が PR の head の祖先かで読む。GitHub の `mergeStateStatus` は、理由が重なったときの出方が文書に無いので、頼らない。衝突している PR は取り込めないので、飛ばして次へ進む。衝突は、今と同じく Chief of Staff が担当に rebase を頼む。取り込んだ PR の検査が条件表の待つ上限（30 分）を過ぎても終わらなければ、その PR を待たずに次へ進む。続けて予約した PR は、1 本につき検査 1 回分（事実 8）ずつ順に入る。
   細部（main の検査が落ちている間）: 既定の branch の先頭の commit で必須の checks が落ちている間は、取り込みを打たない。取り込めば、関係の無い PR が順に落ちて担当へ返るからである。この間、予約した PR の行には「main の検査が落ちていて待っている」と出す（決めたこと 13）。approve のまま待つ課題の今ある通知（事実 19）は、列で順を待っているだけの課題には出さず、main の検査が落ちて止まっているときは、その理由を添えて出す。main を直す PR が遅れているときは、オーナーが画面の「Update branch」を押すか、担当が rebase する。だれが取り込んでも、決めたこと 8 の形なら同じに扱う。
   捨てた案: 2 本目より後ろを先に取り込んでおく案は、上の理由で検査が増える。何本かを合わせて 1 回で検査する案は、merge queue が無いとできない（事実 13）。

8. **2026-11-27 取り込みの形の head は、報告とレビューと gate の問いを引き継ぎ、gate が新しい head で判定し直す（Chief Engineer が決めた）。**
   取り込みの形とは、次の 4 つを全部満たす head である。親が 2 つの merge commit である。親の一方が、報告の commit か、そこから同じ形でつながる head である。もう一方が、既定の branch の commit である。その merge commit の中身が、2 つの親を git が自動で合わせた結果と同じである。4 つ目で、衝突を手で解いた merge と、合わせる時に中身を書き足した merge を外す。だれが取り込んでも、形が合えば同じに扱う。オーナーが画面の「Update branch」を押したときも同じである。
   引き継ぐ時、gate は報告の commit と head の食い違いを差し戻しの理由にしない。レビューは今の照合で引き継ぐ。gate の問いは閉じず、出し直さない。問いが指す head は、報告の commit のまま変えない。Chief of Staff への知らせも、PR への判定のコメントも足さない。gate は新しい head で、checks が終わるのを待って判定し直し、印を書く。
   理由: 取り込みは PR の差分を変えない。変えないものについて、担当に報告を書き直させ、オーナーに同じ問いを出し直すのは、取り直しと同じ手間を残す。判定し直すのは、検査が新しい main と合わせて通ったかを、gate が必須でない check と条件表の検査も含めて見るためである。差分が同じかだけで見分けると、衝突を解いた merge も形に合ってしまう（事実 21）。それでは、解いたあとの差分をオーナーが見る決まり（決めたこと 1）が崩れる。
   捨てた案: 前の判定の記録を新しい head に写すだけの案は、新しい head の checks を gate が見ない。報告の commit を dispatcher が書き直す案は、機械が担当の報告を書くことになる。問いが指す head を新しい head に書き換える案は、オーナーの判断待ちの一覧がその問いを古い問いとして飛ばし、行が消える（事実 20）。
   細部:
   - gate は、PR の head が報告の commit と違うとき、形を見る前に、その head と既定の branch を担当の worktree の git へ `git fetch` で取ってくる（事実 19）。取ってくるだけで、worktree のファイルと branch は動かさない。親は `git rev-list --parents` で読み、自動で合わせた結果は `git merge-tree --write-tree` で作って、中身（tree）を比べる。
   - 形に合っても、レビューの照合（`SamePatch`）が同じ差分と見なさなければ、レビューは古いものとして今までどおり差し戻す。main が PR の変えた行のすぐ近くを変えたときに起きうる。まれな場合として受け入れ、回数を観察で数える。
   - 形に合わない head の動き（ふつうの commit、衝突を解いた merge）は今までどおりで、問いを閉じ、差し戻す。
   - gate の記録に、引き継いだ元の報告の commit を `carried_from` で残す。gate の問いを閉じる 2 つの口（`andon issue merge` と `andon issue ready`）は、今の head の記録の `carried_from` が問いの指す head と同じなら、今の問いとして残す。
   - 判定し直した結果が前と違うとき（委譲が変わって、approve がオーナー待ちになったときなど）は、問いを引き継がず、今の head が動いたときと同じに、前の問いを閉じて新しい判定のとおりに進める。
   - checks を待つ時計（事実 19）は、取り込みの形の head では、dispatcher がその head を初めて見た時刻から数え直す。数え直さないと、取り込んだ直後の、checks がまだ 1 つも無い数秒に gate が回ったとき、「checks が無いまま 30 分過ぎた」と読んで、検査を見ないまま通してしまう。
   - 受け入れ条件の証拠の記録は、今と同じく、古い commit のものとして記録に出すだけにする。
   - 差し戻しの率と振り返りの数えは、`carried_from` を持つ記録を数えない。取り込みの判定し直しは、同じ差分についての 2 度目の判定で、数えると通した記録が水増しになる。`behind` の記録を数えないのと同じ扱いである（事実 22）。
   - 片付けは、手元の branch の先が、マージされた PR の head の祖先なら、足された commit は無いものとして branch を消す（事実 19）。

9. **2026-11-27 dispatcher が自分でマージする PR も、遅れていれば取り込み、判定し直してからマージする（Chief Engineer が決めた）。**
   approve で自動のマージを任された PR は、オーナーの予約を待たずに列に入る。dispatcher は、遅れていれば取り込ませ、新しい head を gate が approve と判定してから、今と同じ `gh pr merge` を打つ。
   理由: 仕組みが働く repo では、遅れた PR の `gh pr merge` は GitHub が断る。決めたこと 5 で gate の差し戻しを外すので、その分をここで受ける。
   捨てた案: dispatcher も GitHub の auto-merge を予約する案は、マージの直前に任されているかを読み直す今の守り（事実 10）が効かなくなる。
   細部: 判定し直しと `gh pr merge` の間に main がまた動くと、GitHub は遅れを理由に断る。今の打ち直しは、断りの文が決まった 2 つのときだけである（事実 10）。断られたら、dispatcher は文を読まずに PR を読み直し、遅れていれば列に戻して取り込みからやり直す。オーナーへの問いにはしない。

### 予約の守り

10. **2026-11-27 gate は、初めて通す head に緑の印を書く前に、PR の予約を外す（Chief Engineer が決めた）。**
    gate は、approve かオーナー待ちを決めて緑の印を書く前に、PR の予約を読む。予約があれば、外してから印を書く。外さないのは、その head か、取り込みの元の報告の commit を、gate が前に通していて、そのあと課題が止められても `doing` に戻されてもいないときだけである。
    理由: 印が必須の repo では、GitHub は緑の印が付くまで予約のマージをしない。緑を書く前に外せば、オーナー待ちの理由を読む前の予約では入らない。前に通した head の取り込みなら、オーナーは通した差分と問いを見たうえで予約している。
    捨てた案: 予約の時刻と gate が通した時刻を比べる案は、GitHub の時計とセルの時計を比べることになる。セルの時計が遅れていると、通す前の予約を通したあとの予約と読み違える。
    細部: 外す口は `gh pr merge <n> --disable-auto` である。予約は `gh pr view --json autoMergeRequest` で読む。前に通したかは gate の記録で、止めと `doing` への戻りは kanban の記録で読む。残る窓は、決めたこと 3 の細部に書いた。

11. **2026-11-27 dispatcher は、生きていてはいけない予約を PR の読みのたびに外し、課題をやめる片付けも予約を外す（Chief Engineer が決めた）。**
    予約が生きていてよいのは、課題が `review` で、止めていず、gate が今の head か取り込みの元の head を通している間だけである。dispatcher は、1 分に 1 回の PR の読み（事実 11）で、そうでない PR に予約を見つけたら外す。担当が直している課題、gate が差し戻した課題、止めている課題、判定のあとに取り込みでない形で head が動いた課題が当たる。マージせずにやめる片付け（`andon issue finish`）も、PR の予約を外す。Chief Engineer の文書の PR は gate を通らないので、`review` でない間の予約と、課題が `review` に入った時刻より前に入った予約を外す。
    理由: 担当が差分を変えたあとに前の予約でマージされると、オーナーが見ていない差分が入る。やめた課題の PR に予約が残ると、片付けたあとは dispatcher がその PR を読まないので、外す機会が無い。この 2 つ目は、モデルが見つけた（決めたこと 18）。
    細部: PR の読みに `autoMergeRequest` の欄を足す。呼び出しの回数は増えない。文書の PR の時刻の比べは、GitHub の時計とセルの時計の比べになる。ずれが効くのは、`review` に入る前後の数秒に入った予約だけである。

### オーナーと担当に見えるもの

12. **2026-11-27 取り込んだあとの検査が落ちたら、今の差し戻しの道で担当へ返す。新しい知らせは足さない（Chief Engineer が決めた）。**
    gate が新しい head で差し戻しを決め、理由が担当へ届く。予約は決めたこと 11 で外れる。担当が直すと head と差分が変わるので、gate は新しい問いをオーナーに出す。その問いの文に、「予約のあと、main を取り込んだ検査が落ちたので担当が直した」の 1 文を足す。
    理由: 新しい知らせを足さないことは、オーナーが決めている（[ADR-0065](0065-owner-waits-never-stop-launch.md) 決めたこと 2）。問いの文に書けば、オーナーは予約した PR が戻ってきた理由を、その行で読める。

13. **2026-11-27 オーナーの判断待ちの一覧は、予約した PR の行を残して「予約済み」と出し、判断待ちの数から外して別に数える（オーナーが決めた）。**
    dispatcher は、生きている予約を見つけたら、課題の資料置き場に予約の控えを置く。控えには、予約の時刻と、列で何を待っているか（順、取り込みの検査、main の検査が落ちていること）を書く。予約が無くなったら消す。`andon waiting list` は、控えのある課題の行に予約済みであることと待っているものを出し、`slots.waiting` に数えず、新しい `slots.reserved` に数える。`slots.behind`（事実 22）と同じ足し方で、出力のバージョンは変えない。動いている課題（`slots.working`）にも数えないので、起動できる空きは今と変わらない。
    理由: 予約した PR は、オーナーの手を待っていない。行を消すと、列が進まない時に、何が残っているかが見えない。動いている課題に数えると、空きが 1 つ減る（事実 20）。
    捨てた案: 行に「予約済み」と出すだけで数を変えない案と、何も変えない案は、押し終えた PR が「あなたを待っている」と数えられ続ける。行を消す案は、上の理由で採らない。
    細部: [ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 8 の数え方に、予約済みを分ける 1 項を足す。同じ ADR の決めたこと 9 の、読むものを kanban と資料置き場に限る決まりは守る。控えを書くのは dispatcher だけなので、dispatcher が止まっている間は、控えが古いまま残る。

14. **2026-11-27 担当の skill と Chief of Staff の手引きを、取り込みに合わせて直す（Chief Engineer が決めた）。**
    担当の skill に、「gate の差し戻しを受けて直す前に、`git pull --ff-only` で branch の先を受ける」を足す。取り込んだ head で差し戻すとき、gate の差し戻しの文にも同じ 1 文を足す。Chief of Staff の手引きは、影響の表を決めたこと 5 のとおりに直し、列が進まない時の手を 2 つ足す。dispatcher が止まっている間は、予約した PR が進まない。オーナーが画面の「Update branch」を押せば取り込まれ、Chief of Staff が `andon gate` を手で打てば判定し直せる。main の検査が落ちている間も、列は進まない。揺れる検査なら回し直し、本当に壊れているなら、直す PR を先に入れる（決めたこと 7）。
    理由: 取り込みのあと、担当の手元の branch は origin より 1 commit 遅れる。知らずに直して push すると断られる。

15. **2026-11-27 積んだ課題の載せ替えは、[ADR-0067](0067-stacked-start.md) 決めたこと 13 のとおり担当の口のままにする（Chief Engineer が決めた）。**
    機械が担当の branch に入れるのは、決めたこと 6 の取り込みだけである。
    理由: 載せ替えは、前の課題が squash で入ったあと、積んだ課題の commit だけを main の先へ移す rebase である。merge の取り込みでは、前の課題の古い commit が branch に残り、差分の起点の数え方（ADR-0067 決めたこと 9）が変わる。積む起動と載せ替えの口はまだ実装されていないので（事実 22）、載せ替えが何回起き、何回衝突するかの数が無い。載せ替えたあとの PR は、ふつうの PR として列に入る。
    細部: ADR-0067 決めたこと 5 と 6 は、前の課題の今の head を報告の commit で読む。前の課題の PR が取り込まれると、origin の branch の先は merge commit になり、報告の commit と違うので、積む起動が断られる。積む仕組みの実装は、前の課題の今の head を、gate の一番新しい記録の head で読む。積んでいる間の PR は、gate の判定が `behind` で、通した判定でないので、列に入らず、予約があれば dispatcher が外す（決めたこと 11）。gate の記録のキーは `base_ahead` とし、ADR-0067 が判定と枠の数えに使う `behind` の語と分ける。

### 実測と切り替え

16. **2026-11-27 実装の前に、設計が頼る GitHub の動きを、捨てる前提の repo で実測する（Chief Engineer が決めた）。**
    見るのは、事実 16 の動きと、次の 4 つである。必須の印がまだ付いていない head では、checks が通っても予約のマージが起きないこと。取り込みの merge commit の中身が、手元の `git merge-tree --write-tree` の結果と同じになること。遅れた PR に `gh pr merge` を打ったときの断られ方。取り込みの API が受け付けてから、head が動くまでの時間。
    細部: 設計が成り立つために要るのは、次の 4 点である。仕組みが働く repo で、遅れているだけの PR に予約できる。セルの `gh` の token で取り込んだあとも、予約が残る。base が進んでも、checks が落ちても、予約が残る。必須の印が付くまで、予約のマージが起きない。4 点のどれかが成り立たなければ、合図の取り方をオーナーに聞き直す。merge commit の中身が手元の結果と同じにならなければ、決めたこと 8 の 4 つ目の条件の見方を選び直す。PR を閉じたときに予約が消えなければ、決めたこと 11 の外す相手に、閉じた PR を足す。作者と `merged_by` は、記録の読み方を決めるために見る。

17. **2026-11-27 切り替えは、実装を当ててから、オーナーが ruleset を変える。auto-merge は切らない（Chief Engineer が決めた）。**
    オーナーは、main の ruleset で base の最新を求める設定を入れ、[ADR-0056](0056-gate-required-before-merge.md) 決めたこと 16 のとおり印 `andon/gate` を必須に足す。2 つは同じ時に入れる。同じ決めたこと 16 の手のうち、auto-merge を切る手は行わない。
    理由: 戻す手が、base の最新を求める設定を外すことの 1 つで済む。外せば、gate の古い base の守りと Chief of Staff の頼みが、そのまま戻る（決めたこと 4・5）。

### モデル

18. **2026-11-27 課題の一生のモデルに、予約と取り込みの動き 6 つと規則 3 本を足す（Chief Engineer が決めた）。**
    足す状態は 5 つである。仕組みが働く repo か。PR が main より遅れているか。オーナーの予約が無いか、gate が通した head を見て入れたものか、そうでないか。今の head が取り込んだだけで、gate がまだ判定し直していないか。予約でマージされたか。
    足す動きは 6 つである。ほかの PR が main に入って、PR が遅れる。オーナーが予約する。dispatcher が、生きていてはいけない予約を外す。dispatcher が、gate の通した head に main を取り込ませる。GitHub が予約どおりにマージする動きは、gate が決めたあとと、決める前の 2 つに分ける。今ある動きのうち、gate が通す 2 つの動きは、見て入れたのでない予約を外す。課題をやめる動きは、予約を外す。オーナーのマージと dispatcher のマージは、仕組みが働く repo では、遅れている間は起きない。gate の回し直しのきっかけに、取り込んだ head を足す。
    足す規則は 3 本である。番号は、今の 21 本の続きから振る。
    - ruleset が印を必須にしていれば、予約でマージされるのは、gate が通した head をオーナーが見て入れた予約だけである。
    - やめた課題の PR に、予約は残らない。
    - 担当が衝突の無い rebase をしなくても、取り消しを使わずに届くどの状態からも、マージまで行ける。仕組みが働く repo でも成り立つ。
    壊した見本は 3 つ足す。gate が通す時に前からの予約を外さない見本は、1 本目で落ちる。やめる時に予約を外さない見本は、2 本目で落ちる。dispatcher が取り込まない見本は、3 本目で落ちる。
    調べた結果: main のモデル（事実 18）の写しに上を書き足して調べた。積んだ課題の動きも全部入れた写しは 567,048 状態である。TLC で、「行ける」の形でない規則 20 本（今ある 18 本と足した 2 本）が全部通った。「行ける」の形の規則 4 本（今ある 3 本と足した 1 本）は、TLC が書き出した状態の図を 1 行ずつ読んで調べ、全部通った。取り込みの動きを外した写しは、足した「行ける」の規則で落ちた。repo の検査器（`model/check --draft`）では、前の課題を持たない課題だけに絞った 120,462 状態の写しを調べた。今ある規則のうち積んだ課題の「行ける」の 2 本を除く 19 本と、足した 3 本が全部通り、壊した見本 3 つは、どれも狙った規則で落ちた。
    調べる途中で、設計の破れが 2 件見つかった。1 件目は、課題をやめたあとも PR に予約が残る道で、決めたこと 11 に片付けの手を足した。2 件目は、オーナーが「担当に直させる」と答えたあと、印が緑のまま残る間に、予約でマージされる道である。今のマージのボタンにもある窓なので、塞がずに、残る窓として決めたこと 3 に書いた。
    細部（検査を 2 つの写しに分ける）: 予約の動きを全部のモデルに足すと 567,048 状態になり、今の repo の検査器では調べられない（事実 23）。そこで `model/check` は、モデルを 2 つの写しで調べる。1 つは、積んだ課題の動きを持ち、予約と遅れの動きを持たない写しで、今と同じ 168,644 状態である。もう 1 つは、予約と遅れの動きを持ち、前の課題を持たない課題だけの写しで、120,462 状態である。どちらも今の検査器で扱える。控えの状態の数も 2 つ持つ。積んだ課題に予約と遅れが重なる状態は、CI では調べない。重なりは、この文書の検討で上のとおり 1 度調べ、全部通った。積んでいる間の PR は列に入らず予約も外され、載せ替えたあとは、ふつうの PR と同じ道を通る（決めたこと 15）。
    捨てた案（検査器を TLC に替える・検査器を直す）: 検査器を替えるのは、オーナーの決定を覆すことになる（事実 23）。この設計に要らないので、ここでは決めない（やらないこと 10）。
    細部: 遅れと予約は、仕組みが働く repo で、既定の branch に載った PR が `review` にいる間だけ数える形に絞った。モデルが持たないものは 5 つある。衝突。列の中のほかの PR と、main の検査が落ちている間の待ち。Chief Engineer の文書の PR。gate が予約を読んでから緑を書くまでの間。base の最新だけを求めて印を必須にしていない repo。衝突は、オーナー待ちの問いに「担当に直させる」と答えた時の動きと同じ道を通る。

## 反論で直したこと

設計の下書きとモデルの下書きを、別のコンテキストの読むだけの役に渡し、壊させた。返った指摘をコードと記録に照らし、次を直した。

1. **取り込んだ commit を、だれも手元に取ってこない。** レビューの照合は担当の worktree の git で比べるが、GitHub が作った merge commit は手元に無い（事実 19）。下書きのままでは、引き継ぎが必ず外れて担当へ差し戻っていた。決めたこと 8 の細部に、gate が先に取ってくることを足した。
2. **問いの指す head を書き換えると、判断待ちの一覧から行が消える。** 一覧は、報告の commit と違う head を指す問いを飛ばす（事実 20）。決めたこと 8 を、問いの指す head を変えない形に直した。決めたこと 13 も、予約済みを動いている課題に数えない形に直した。
3. **印が必須でない repo では、判定し直す前に GitHub がマージする。** 下書きは、base の最新だけを求める repo でも仕組みを働かせていた。決めたこと 4 を、印も必須の repo だけに絞った。モデルも同じに絞り、要らなくなった規則 1 本と壊した見本 1 つを外した。
4. **取り込んだ直後に gate が回ると、検査を見ないまま通す。** checks を待つ時計が、`review` に入った時刻から数えるからである（事実 19）。決めたこと 8 の細部に、時計を数え直すことを足した。
5. **衝突を手で解いた merge も、形に合っていた。** 下書きの形は、親が 2 つであることと、差分が同じことだけだった（事実 21）。決めたこと 8 に、自動で合わせた結果と同じ、の条件を足した。
6. **main の検査が落ちている間、列が黙って止まる。** 決めたこと 7 に、行に理由を出すことと、今ある通知に理由を添えることを足し、決めたこと 14 に手を足した。
7. **文書の PR で、列に入れる決まりと予約を外す決まりが食い違っていた。** 決めたこと 7 と 11 に、gate を通らない PR の扱いを書き分けた。
8. **読んだ ruleset を 10 分使い回すと、設定を戻した直後に守りが 2 つとも無い。** 決めたこと 4 を毎回読む形に直し、決めたこと 5 に、設定を戻したあとの回し直しを足した。
9. **dispatcher のマージが遅れで断られた時の道が無かった。** 決めたこと 9 の細部に足した。
10. **予約の時刻と通した時刻を比べると、時計のずれで読み違える。** 決めたこと 10 を、時刻を比べずに gate の記録と kanban の記録で決める形に直した。
11. **名指していなかった所。** 片付けで branch が残ること、列で待つ approve が通知になること、判定のコメントが増えること、判定が前と違う時の問いを、決めたこと 7 と 8 の細部に足した。積む仕組みとの重なりは、決めたこと 15 の細部に足した。
12. **数の食い違い。** 事実 2 の内訳が事実 1 の合計と 1 回合わなかった。残りの 1 回を書き足した。

文書を確定する前に main が進み、積む仕組みの一部が入った（事実 22）。main を取り直して、次を直した。モデルの写しを新しいモデルの上に作り直し、規則の本数と状態の数を書き直した（決めたこと 18）。repo の検査器が、予約の動きを全部足したモデルを扱えないことが分かり、検査を 2 つの写しに分けることを、事実 23 と決めたこと 18 に書いた。判定し直しの記録を差し戻しの率から外すことを、決めたこと 8 の細部に足した。予約済みの数の足し方を、`slots.behind` と揃えた（決めたこと 13）。

## やらないこと（範囲の外。理由）

1. **衝突を機械が解く。** 衝突を解くと差分が変わる。解いたものは担当が検査し、オーナーが見る（決めたこと 1）。
2. **repo を organization へ移して merge queue を使う。** repo を持つアカウントと URL が変わり、外への約束に触れる。列が詰まって、何本かを合わせて検査する形が要るようになったら、そのときに考える。
3. **列の先読みと、まとめての検査。** 決めたこと 7 の理由で採らない。
4. **積んだ課題の載せ替えを機械に移す。** 決めたこと 15。積む仕組みが入り、載せ替えの回数が数えられてから決める。
5. **オーナーへの新しい知らせと、たまった PR の数の上限。** オーナーが足さないと決めている（[ADR-0065](0065-owner-waits-never-stop-launch.md) 決めたこと 2）。
6. **Andon の外の PR を取り込む。** dispatcher が読むのは課題の PR だけである。外の PR は、オーナーが画面の「Update branch」を押す。
7. **仕組みが働かない repo の守りを変える。** gate の古い base の差し戻しと、Chief of Staff の rebase の頼みは、そのまま残す（決めたこと 5）。
8. **検査の置き場の定義を狭める。** main の動きのほとんどが検査の置き場に触るので（事実 7）、狭めても取り直しはあまり減らない。
9. **予約のマージの方式を揃える。** 予約がどの方式でマージするかは、オーナーが画面で選ぶ。今のマージのボタンと同じで、dispatcher は直さない。
10. **モデルの検査器を替える・直す。** 積んだ課題に予約と遅れが重なる状態を CI で調べるには、大きい状態の図を扱える検査器が要る。検査器を選んだのはオーナーで（事実 23）、この設計は検査を 2 つの写しに分ければ足りる（決めたこと 18）。重なりを CI で調べたくなったら、別のテーマにする。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に）

継ぎ目は 4 つである。gate の決定の式と事実の集め方は、Go の検査（`go test ./internal/gate/... ./internal/ledger/... ./internal/waiting/...`）で見る。取り込みの形の見分けは、一時の git の repo に本物の merge commit を作って見る。dispatcher の巡と GitHub への呼び出しは、偽の `gh` を使う筋書きの検査（`tests/andon-dispatcher.sh`・`tests/andon-gate.sh`・`tests/andon-issue.sh`）で、呼び出しの並びと記録を見る。規則は `model/check` で見る。GitHub の本物の動きは、条件 22 でセルの本物を使って見る。証拠は、どの条件も、打った command と、その出力のうち名指した行である。

1. 仕組みが働く repo で、PR の分かれ目より後に main で検査の置き場が変わっていても、gate は「base が古い」を理由にせず、approve かオーナー待ちを決める。gate の記録に `base_ahead` が残る。Go の検査で、同じ事実から、働かない repo では差し戻しが返ることも見る。
2. ruleset が読めないとき、base の最新だけを求めて印が必須でないとき、条件表のマージの方式が `rebase` のとき、gate は働かない repo と同じに決める（差し戻しが返る）。
3. `base_ahead` が 1 以上のまま通した `review` の課題があり、repo が働かない repo に変わると、次の巡で gate が回し直される。
4. 予約のある遅れた PR に、dispatcher が取り込みの API を、今の head を `expected_head_sha` に渡して 1 回打つ。予約の無い遅れた PR にも、gate がまだ通していない head の PR にも打たない。筋書きの検査で、偽の `gh` の呼び出しの記録を見る。
5. 同じ repo に、予約のある遅れた PR が 2 本あるとき、同じ巡で取り込みを打つのは、先に予約した 1 本だけである。それがマージされたあとの巡で、2 本目に打つ。取り込んだ 1 本目の検査が待つ上限を過ぎても終わらないときも、2 本目に打つ。
6. 取り込みの形の head で、gate はその head と既定の branch を取ってきてから形を見て、報告の commit の食い違いを理由にせず、レビューを引き継ぎ、checks を待ち、前と同じ判定を決める。gate の問いは閉じられず、新しい問いも、Chief of Staff への知らせも、PR へのコメントも出ない。gate の記録に `carried_from` が残る。`andon waiting list --json` に、その課題の行が残る。
7. 衝突を手で解いた merge commit と、合わせる時に中身を書き足した merge commit は、足した行と消した行が同じでも、形に合わない。ふつうの commit も合わない。gate は前の問いを閉じ、差し戻す。次の PR の読みで、予約を外す呼び出しが打たれる。
8. 取り込んだ直後で checks がまだ 1 つも無いとき、課題が `review` に入ってから 30 分を過ぎていても、gate は通さずに待つ。
9. 取り込んだ head で checks が落ちると、gate は差し戻しを決め、理由が担当へ届く。差し戻しの文に `git pull --ff-only` の 1 文が入る。次の PR の読みで、予約を外す呼び出しが打たれる。担当が直したあとの gate の問いに、予約のあとに検査が落ちたことの 1 文が入る。
10. gate は、初めて通す head に緑の印を書く前に、予約を外す。筋書きの検査で、偽の `gh` の呼び出しの記録に、予約を外す呼び出しが印を書く呼び出しより前に在ることを見る。前に通した head の取り込みの判定し直しでは、予約を外す呼び出しが打たれない。通したあとに止めたか `doing` に戻した課題では、打たれる。
11. `doing` に戻った課題、止めている課題、gate が差し戻した課題の PR に予約があると、次の PR の読みで外される。マージせずにやめる `andon issue finish` は、予約を外す呼び出しを打つ。
12. Chief Engineer の文書の PR は、`review` で予約があれば取り込みが打たれる。`review` に入る前に入った予約は、次の PR の読みで外される。
13. dispatcher が自分でマージする approve の PR が遅れていると、取り込みの呼び出し、新しい head の判定、`gh pr merge` の順に打たれる。`gh pr merge` が断られ、読み直した PR が遅れていると、オーナーへの問いは置かれず、次の巡で取り込みが打たれる。
14. 既定の branch の先頭の commit で必須の checks が落ちている間、取り込みの呼び出しは打たれない。予約の控えに、main の検査を待っていることが書かれる。
15. 列の中の順が前の PR が衝突していると、dispatcher はそれを飛ばし、次の PR に取り込みを打つ。
16. approve のまま 10 分たった課題でも、列で順を待っている間は、Chief of Staff への通知が積まれない。
17. 取り込まれてマージされた課題の片付けは、手元の branch が PR の head より 1 commit 遅れていても、branch を消す。
18. `andon issue impact` の出力に、仕組みが働く repo かの事実が出る。schema の検査（`tests/schema.sh`）で形を見る。
19. 予約の控えのある課題は、`andon waiting list --json` の行に予約済みと出て、`slots.waiting` にも `slots.working` にも数えられず、`slots.reserved` に数えられる。
20. `model/check` が通る。足した規則 3 本が控えに載り、足した壊した見本 3 つが、決めたこと 18 に書いた規則で落ちる。`model/check` は、決めたこと 18 の 2 つの写しを両方調べ、状態の数をそれぞれの控えと比べる。
21. 捨てる前提の repo での実測（決めたこと 16）の結果が、調べる課題の報告に、見た動きごとに、打った command と GitHub の返事で残る。
22. 本物で通す。Andon を開発しているセルで、切り替えのあと、main より遅れたオーナー待ちの PR 2 本を続けて予約する。担当の端末が動かないまま、2 本とも順にマージされ、どちらの PR も、マージされた head が main の先を含んでいる。オーナーが予約を押し、検証の課題が、gate の記録の `carried_from` と、`kanban` の記録に担当の `doing` への戻りが無いことを見る。

## 価値の仮説

1. **誰の何が変わるか。** オーナーのマージを待つ PR で、担当の取り直しが起きなくなる。オーナーは、たまった PR を続けて押して離れられる。古い検査のまま main に入る PR が無くなる。
2. **見る信号。** `source` は、課題ごとの gate の記録と、repo の git の履歴である。gate の記録の隣り合う 2 件で head が違う組を拾い、担当の衝突の無い取り直しを数える（事実 1 と同じ数え方。`carried_from` を持つ記録は、取り直しに数えない）。マージされた担当の PR について、マージの時に head が main の先を含んでいたかを、マージの commit の親と head の分かれ目から数える（事実 6 と同じ数え方）。予約からマージまでの時間は、予約の控えの時刻と、マージの時刻から数える。
3. **見る日。** 2026-12-18。
4. **誰が要るか。** オーナー。main の ruleset を切り替え、遅れた PR を予約で押す。
5. **効いたとどう分かるか。** 切り替えの日から見る日までの間、担当の衝突の無い取り直しが、5 日あたり 10 回以下になる（今は 51 回）。オーナーがマージした PR のうち、古い base のまま入ったものが 0 本になる（今は 27 本のうち 13 本）。予約からマージまでの中央値が 10 分以下である。
6. **何があれば止めるか。** 取り込んだあとの検査が落ちて担当へ返る PR が、取り込んだ PR の 5 本に 1 本を超える。または、予約からマージまでの中央値が 30 分を超える。または、gate が通す前に入った予約でマージされた PR が 1 本でも出る。どのときも、オーナーが base の最新を求める設定を外して元の守りに戻し（決めたこと 17）、次の手をオーナーと決める。
