# ADR-0030: トリアージが誤って閉じた項目を拾う網（仕様・設計。2026-11-19）

- 状態: **決定（2026-11-19）**。人が対話の中で「決めた」と言った（[decisions/2026-11-19-adr-0030-triage-close-safety-net.md](../decisions/2026-11-19-adr-0030-triage-close-safety-net.md)）。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書き、この行を `覆された → ADR-NNNN` にする。小さな改めは「決めたこと」に下から足す。
- 主題: トリアージ（`andon triage collect`／`apply`。[design.md](../design.md) §0.1）の `close` の判定。閉じた項目が誤りだったときに、気づく道と戻す道。
- 語は [design.md](../design.md) §0.1。
- 入力: 人の発言（2026-11-19）、`package/skills/triage/SKILL.md`、`package/skills/chief-of-staff/playbooks/triage.md`、`process/workstreams/triage.yaml`、`internal/triage/`、[contract.md](../contract.md) の `triage_max_issues` とトリアージの読み方、[decisions.md](../decisions.md) §4、[ADR-0011](0011-signals-and-value-loop.md)・[ADR-0020](0020-auto-memory-as-intake.md)・[ADR-0028](0028-improvement-loop.md)。

## 問題（人の言葉で。言い直しの段落）

人（2026-11-19、Chief of Staff へ）:

- 「トリアージで直す 5 件に選ばれなかったものはどうなるか」
- 「必要なものが 5 件以外にあった場合は？」
- （閉じた項目は二度と候補に出ず、気づけるのは適用の前に理由を読む Chief of Staff と、要約を読む人だけ、と聞いて）「んー、それは少し危ないんじゃないかな」

言い直し（人が 2026-11-19 に「合っている」と答えた）: 上限で選ばれなかった「直す」は次回また候補に出るので、危ないのはそこではない。危ないのは「閉じる」のほうである。閉じる判定は sonnet の担当が1件ずつ書き、Chief of Staff が適用の前に理由を読むだけで通る。通った項目は二度と候補に出ない。2026-11-19 の朝は 50 件のうち 43 件が閉じられた。誤りに気づけるのは、人が要約の表を読んだときだけで、トリアージは同じ日から毎朝回るので、その表は毎朝 40 行ほど出る。つまり、必要な直しや学びが誤って閉じられると、誰にも気づかれないまま失われる。直したいのは、誤って閉じたものが、人が毎朝表を読むことに頼らずに拾われるか、あとから戻ってくる形にすること。

## 読んで分かった事実（2026-11-19。main `fc4cd42` と、Andon を開発しているセルで実測）

1. **閉じた項目は二度と候補に出ない。** `andon triage collect` は、前回までの記録（台帳の `library/triage/*.json`）で `keep` 以外に仕分けた key を出さない（`internal/triage/collect.go` の `collectFrom`）。key は `<slug>:<出どころ>:<kind>:<本文の sha1>` で、本文が同じなら同じ key になる。
2. **上限で落ちた「直す」は消えない。** `fix`／`bundle` が上限（`triage_max_issues`。既定 3）を超えた分は、`apply` が `keep`「次回（起動する上限）」に書き換える（`internal/triage/decisions.go` の `capIssues`）。`keep` は次回も候補に出る。
3. **戻す口は1つあり、手で key を写す。** `apply` は、今回集めた key のほかに、前回までの記録にある key の決定も受ける（`internal/triage/apply.go`。検査は `tests/andon-triage.sh` の「Recorded keys can be revisited」）。閉じた項目を戻すには、次のトリアージの `decisions.json` にその key を `fix` で書く。Chief of Staff の手引きは「閉じたものは人が要約で見て戻せる（次のトリアージの依頼書に『<key> を fix に』と書く）」と書く。閉じた項目を一覧で読み直す command は無い。
4. **閉じても元の行は残る。memory だけはファイルが消える。** 報告の `## Next`・`## Remember` の行は、出どころの課題の `report.md` に残る。auto memory の項目は、`keep` 以外に仕分けると `apply` がファイルと目録の行を消し、本文と理由は記録（`library/triage/<日付>-<id>.json`）にだけ残る（[ADR-0020](0020-auto-memory-as-intake.md)）。台帳は git の外にある。
5. **閉じる判定を確かめる段は1つ。** 判定を書くのはトリアージの担当（プロファイルは `sonnet`）。Chief of Staff は `review` を受けて報告の要約表と `decisions.json` を読み、`andon triage apply <id> --dry-run` を打ち、「閉じる理由が読めない」なら戻す（`playbooks/triage.md` の 3）。トリアージは repo の無い課題で、独立レビューもゲートも通らない。`apply` が機械で確かめるのは、key の実在・理由が空でないこと・課題を閉じるときの status だけで、理由の中身は確かめない。
6. **「事後の要約で見る」は仮の決定だった。** [decisions.md](../decisions.md) §4 に、2026-11-03 の仮の決定として「不要の確認は事後の要約で見る（閉じたものは戻せる）」「周期は週 1 回」「直す・まとめるの上限は 1 回 3」がある。上限 3 の数の理由を書いた文書は無い。
7. **周期は毎朝になった。** Andon を開発するセルでは、トリアージのルーチンが 2026-11-19 から毎朝1回になった（[ADR-0028](0028-improvement-loop.md) 決めたこと 16）。1回に仕分けるのは 50 件まで。同じ日の夕方、未処理は 131 件（`remember` 64・`next` 42・`memory` 12・見送り 6・担当の無い課題 5・読めない報告 2）。
8. **2026-11-19 の朝の1回の中身。** 古い順に 50 件を仕分け、閉じた 43・直す課題 3・人へ 2・次回へ 2。閉じた 43 件の理由の内訳は、「済み」20・「対象が無い」8・「その場限り」12・「起きない」1・「読んだ」2。出どころは `next` 19・`remember` 22・読めない報告 2。
9. **振り返りも `## Remember` を読む。** [ADR-0028](0028-improvement-loop.md) 決めたこと 11 で、報告の `## Remember` と日報は振り返りが根拠として読むと決まっている。トリアージが閉じても、振り返りは同じ行を別に読む。ただし振り返りが拾うのは別々の2件以上で起きたことだけで、`## Next` と auto memory は読まない。振り返りの command は 2026-11-19 の時点でまだ実装の途中。
10. **その朝に閉じた 43 件を、別のコンテキストで1件ずつ実物と照らした。** 理由が実物と合い、失われるものが無いのは 40 件。知識ややり残しが失われうるのは 2 件で、どちらも判断で閉じたもの。
    - 1件は「その場限り」で閉じた学び（図を作る道具の書き方の注意）。理由は「モデルは TLA+ に移った」だが、[ADR-0025](0025-formal-model-in-repo.md) は破れの道つきの図を作るときにその道具を手で回し続けると決めており、次に図を作る担当がまた踏みうる。次の担当が読む場所（`AGENTS.md`・skill・docs・memory）には入っていない。
    - 1件は「起きない」で閉じたやり残しの候補（skill の中の番号の振り方をそろえる）。判定表の「起きない」は見送りの項目の行で、この項目には当たらない。実際の理由は「やる価値が小さい」という担当の判断。同じ調べる課題から出た、確からしさが同じく低い別の候補は人へ回されており、扱いがそろっていない。
    - ほかに、閉じた結論は正しいが理由の根拠（直した課題の取り違え）が誤っているものが1件。
    - 根拠を挙げて閉じた 28 件（「済み」「対象が無い」）と、報告を自分で読んで閉じた 2 件に、失われるものは無かった。
11. **「直す」にも誤りが1件あった。原因は古い checkout。** その朝に切られた直す課題の1つは、別の課題が同じ日に直してマージ済みの 5 か所を「今も残る」として切った重複だった（main `fc4cd42` で `git grep` は 0 件）。triage skill は確かめ方の例に `git -C "$GHQ_ROOT/<repo>" grep` を挙げる。セルのその checkout は `origin/main` より 28 commit 古く、直す前の文が残っていた。担当がどの木を見たかの記録は無い。
12. **判定がどの実物を見たかは記録に残らない。** `decisions.json` の `reason` は1行の文で、見た commit・打った command は欄に無い。
13. **判断で閉じた行の多くは決まり文句。** 担当は報告の `## Remember` に「計画との差:」の行を必ず書く（worker skill の報告の書式）。`collect` は節の行を全部項目にするので、この行も1件ずつ仕分けられる。その朝に「その場限り」で閉じた 12 件のうち 9 件がこの行。同じ日の夕方、未処理の `remember` 74 件のうち 23 件がこの行だった。
14. **閉じた学びのもう1つの家は wiki だが、写しは追いついていない。** Chief of Staff の手引きは、片付いた課題の報告をセルの wiki の元資料に写して要約すると書く。実測したセルで写されていたのは、片付いた課題 40 件あまりのうち 2 件ぶん。
15. **`decisions.json` に schema は無い。** 形は triage skill の §4 と `apply` のコード（`internal/triage/decisions.go` の `parseDecisions`）が持つ。`schema/` には無い。

## 前提（同意済み。番号）

1. **扱うのは「閉じる」の誤りだけ。**（人が 2026-11-19 に同意）1回に起動する直す課題の上限 3 と、その中で選ぶ順は変えない。上限で落ちた「直す」は次回また候補に出るので失われない。上限は、次回に回る件数が溜まり続けると分かったときに別の題で見直す。
2. **何もしない選択は取らない。ただし網は、判断で閉じる項目に絞った小さいものにする。**（人が 2026-11-19 に同意）実測で失われうるものが出たのは判断で閉じた側だけ（事実 10）。同じ率なら1日に 2 件ほどが気づかれずに失われる。実物で確かめられる閉じ方（「済み」「対象が無い」）は、今のまま速く通す。
3. **確かめる実物を最新の main にすることを、この題の範囲に入れる。**（人が 2026-11-19 に同意）古い木を見ると、直っているものを「残っている」と誤るだけでなく、新しく入ったものを「無い」と誤って閉じることも起こりうる（事実 11）。
4. **網は人の手を前提にしない。**（人が 2026-11-19 に同意）人が毎朝表を読むことにも、判断で閉じる項目を毎朝人への問いとして出すことにも頼らない。人に届くのは、今までどおり人にしか決められないものだけ。その朝に判断で閉じた項目は 13 件あり、全部を人へ回すと毎朝 13 問ほどが人に届く。
5. **既にあるもので済ませ、山を作らない。**（人が 2026-11-19 に同意）新しい役も、常駐も、新しい保存先も足さない。使うのは、今あるトリアージの記録と command、判定表、Chief of Staff の確かめの段。迷ったら「次回へ」に倒して未処理を溜める形にもしない（[ADR-0028](0028-improvement-loop.md) 前提 6）。変更は Andon のパッケージの command と skill として入れ、どのセルにも届く。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **2026-11-19 網は2段で組む。判断で閉じられる範囲を狭め、残った判断の閉じを Chief of Staff が1件ずつ読む（案 B）。**
   - **狭める（土台）**: 閉じ方の種類を判定の記録（`decisions.json`）の欄にし、`andon triage apply` が項目の種類との組み合わせを確かめる。「起きない」は見送りの項目だけに許す。やり残しの行（`## Next`）は、済んだ根拠か対象が無い根拠があるときだけ閉じられる。担当が報告に必ず書く「計画との差」の行は、トリアージの項目として拾わない。確かめる先は最新の main にする。
   - **読む**: 残った判断の閉じを `andon triage apply --dry-run` が別の表で出す。Chief of Staff が1件ずつ、閉じてよいか覆すかを書く。`apply` は、判断の閉じ全部に Chief of Staff の判定が無ければ断る。根拠を挙げた閉じ（「済み」「対象が無い」）は今のまま通す。
   理由: 実測で失われうるものが出たのは判断で閉じた側だけ（事実 10）。土台だけで、その朝の誤りの片方（「起きない」の当て違い）は機械が断れる。決まり文句の行（決めたこと 5 の 2）を外すと、判断の閉じはその朝の数え方で 15 件から 4 件に減る。残った数件を、担当より強いモデルが別のコンテキストで読む形が、人の手を増やさずに置ける（前提 4）。読む段は今ある Chief of Staff の確かめの段で、新しい役は足さない（前提 5）。
   捨てた案: A 土台だけ（いちばん小さいが、学びを「その場限り」と誤って閉じる型が網なしで残る。その朝の 2 件のうち 1 件がこの型）／C 判断で閉じた項目を 14 日後に一度だけ候補に戻す（毎朝 50 件の枠を二度目の判断が使い、未処理が増える。同じ判定表を同じモデルが読むので同じ誤りを繰り返しやすい。前提 5 と擦れる）／トリアージの課題に別ブランドのレビュアーを付ける（新しい段。前提 5）／判断で閉じる項目を人が見てから閉じる（毎朝 10 件前後が人に届く。前提 4）。
   受け入れること: Chief of Staff の読みも誤りうる。Chief of Staff の読む量が毎朝数件増える。
2. **2026-11-19 確かめる先は command が決める。`collect` が最新の main を取り、`apply` が見た commit を照らす。** `andon triage collect` が、台帳の repo ごとに最新の main を取ってきて、その commit を出す。担当はその commit を読んで判定し、判定の記録に commit を書く。`apply` は、記録の commit が `collect` の出したものと違えば断る。triage skill の確かめ方の例は、セルの checkout の作業ツリーではなく、その commit を読む形に書き直す。
   理由: 古い木を見た判定は、文で頼んでも守られたかを誰も確かめられない（事実 11・12）。標準は機械が確かめる形から置く（[design.md](../design.md) §1.9 の判断と決断の置き場）。
   捨てた案: skill の文だけ直す（いちばん小さいが、守られたかを誰も確かめない）／文を直し、見た commit を記録に残すだけ（あとから辿れるが、古い木を見た判定も通る）。
3. **2026-11-19 「その場限り」の線は判定表に書かない。残った判断の閉じを読む Chief of Staff の見立てに任せる（推奨案は覆された）。** 判定表の「その場限り」の行は変えない。
   理由（人の選択）: 線は書かず Chief of Staff に任せる。
   捨てた案: 「その場限り」で閉じてよいのは、その課題の中で起きたことを述べる行だけ、と判定表に書く（Chief Engineer の推奨。担当の誤りを先に減らすが、判定表の文が増える）／済んでいる根拠が無い学びの行は判断で閉じず、全部どれかの行き先へ送る（失われないが、wiki に写す Chief of Staff の手が毎朝増え、wiki にその場限りの記録が溜まる）。
   受け入れること: 担当の誤りは減らないので、Chief of Staff が覆す回数がそのぶん多くなる。
4. **2026-11-19 その朝に閉じたもののうち、失われうると出た 2 件（事実 10）は戻す。** Chief of Staff が次のトリアージの判定にこの 2 件の key を書き足す（今ある戻す口。事実 3）。やり残しの候補（skill の中の番号の振り方をそろえる）は skill の直しなので、やるかどうかの問いが人に届く。道具の書き方の注意は、Chief of Staff が行き先を決める。この仕組みが入る前のトリアージはその朝の1回だけなので、さかのぼるのはここまで。
   捨てた案: 戻さない（どちらも重さが小さく、元の報告の行は残る）／やり残しの候補だけ戻す。

決めたこと 5 は、Chief Engineer が推奨案として書き、人が最後の確かめで認めたもの（2026-11-19）。

5. **2026-11-19 細部。**
   1. **閉じ方の種類と、閉じられる項目の組み合わせ。** `close` の判定は、閉じ方の種類の欄を必ず持つ。種類は2つの組に分かれる。
      - **根拠の閉じ**: 「済み」「対象が無い」と、行き先がある閉じ（「wiki へ」「Andon へ委譲」）。どの種類の項目にも使える。今のまま通る。
      - **判断の閉じ**: 「起きない」「その場限り」「当てはまらない」「読んだ: 拾うものなし」。使える項目は、「起きない」が見送りの項目だけ、「その場限り」が `## Remember` の行と auto memory だけ、「当てはまらない」が auto memory だけ、「読んだ」が読めない報告だけ。
      - やり残しの行（`## Next`）・担当の無い課題・人の判断待ち・`## 人に聞くこと`・`For AGENTS.md:`・外の信号・片付けの残りは、判断では閉じられない。根拠が無ければ、直す・人へ・次回へのどれかにする。
      - `apply` は、欄の無い `close` と、組み合わせに合わない `close` を断る。
      - この分け方で数えると、その朝の判断の閉じは 15 件（前提 4 の 13 件に「読んだ」の 2 件が加わる）。
   2. **拾わない行を2つ足す。** `collect` は、`## Remember` の節の「計画との差:」で始まる行を項目にしない。報告が無い人の課題（片付いた人の判断待ち）を「読めない報告」の項目にしない。どちらも、ほかの読み手（振り返り・`andon measure`）は今までどおり読む。
      理由: どちらも中身を読むまでもなく閉じる行で、判断の閉じの数を増やしている（事実 13。その朝の「読めない報告」2 件はどちらも人の課題だった）。
   3. **Chief of Staff の判定の形。** `apply --dry-run` は、判断の閉じを、項目の本文・担当の理由・出どころつきで別の表に出す。Chief of Staff は1件ずつ「閉じてよい」か「覆す」かを command で書く。判定はトリアージの課題のフォルダに置き、書き手は Chief of Staff だけ。判定は項目の key と担当の理由の文に結びつき、担当が理由を書き換えたら無効になる。`apply` は、判断の閉じに「閉じてよい」が1件でも欠けていれば断り、台帳に手を入れない。
   4. **覆したとき。** 今ある「担当に戻す」道を使う。Chief of Staff が担当に戻し、担当が行き先（直す・人へ・wiki へ・次回へ）を書き直す。覆したことは、適用のあとの記録に残る。
   5. **要約と記録。** 人が読む要約（`library/triage/<日付>-<id>.md`）の「閉じた」は、判断で閉じたものを先に、根拠で閉じたものを後に分けて出す。記録（同じ名前の `.json`）には、項目ごとの閉じ方の種類・担当が見た commit・Chief of Staff の判定が残る。
   6. **最新の main が取れないとき。** `collect` は止まる（古い木で判定させない）。auto memory と外の信号の項目は repo の commit を持たない。
   7. **古い記録。** この仕組みが入る前の記録（閉じ方の欄が無い）は、そのまま読む。書き直さない。前に閉じた key は今までどおり候補に出ない。
   8. **形式モデル。** 課題のステータスの移り方は変えないので、`model/` は変えない見込み。実装が確かめる。

## やらないこと（範囲の外。理由）
