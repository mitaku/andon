## 問題（人の言葉で。言い直しの段落）

人（2026-11-20、ADR-0032 の対話）: 「リントルール、動的検証、静的型設計、レイヤ設計、性能測定、形式仕様、モデル検査などで防止できるものはそっちに寄せるなどしましょう」「statechartと形式検証はトータルの開発からマージまでのライフサイクルの効率化に有用に思いました」。

言い直し（人が 2026-11-20 に「合っている」と答えた）: 検査を仕分ける調べもので、`tests/andon-dispatcher.sh` の 73 節と重い検査（`schema.sh`・`andon-gate.sh`・`andon-issue.sh`・`apply-main.sh`・`image.sh`）の 111 行のそれぞれが、テストより手前のどの手段で防げるかが表になり、候補が 21 件出た。決めたいのは、その候補のどれを入れ、どれを入れず、どの順で進めるか。ねらいは 2 つ。dispatcher の場面を Go のテストへ移す仕事（ADR-0032 の依頼書に切る案 5）が相手にする節を減らすことと、不良をテストより手前の段で止める形に寄せること。

仕分けの結果（2026-11-20 の調べもの。読むだけの見立てで、境目に判断を含む）:

- dispatcher の 73 節の主な手段は、Go のテストが 30、動的な検証が 15、モデル検査が 12、型の設計が 7、形式仕様が 4、性能の計測が 2、lint の規則が 2、シェルに残すが 1。
- 重い検査の 111 行は、Go のテストが 39、動的な検証が 25、シェルに残すが 21、形式仕様が 10、lint の規則が 9、レイヤの設計が 4、モデル検査が 3。
- dispatcher の 73 節のうち、同じ振る舞いを Go のテストが既に見ているのが 12 節。シェルだけが見ている所は、dispatcher の 9d・9d2・9e・16・20・21 と、`andon-gate.sh` の 9b・9c、`andon-issue.sh` の回の数え方。

## 前提（同意済み。番号）

1. **モデルは設計を確かめ、コードの退行はテストが見る。この分担を保つ**（人 2026-11-20）。モデルとコードは機械で照らしていない（ADR-0025 の前提 1）。モデルに場面を足しても、モデル検査に仕分けられた 12 節はシェルから消えず、Go のテストへ移すことになる。モデルに足す価値は、次にその流れを変えるときに、実装の前に設計の穴を見つけられること。
2. **並んで進んでいる変更が済ませる分は、この題から外す**（人 2026-11-20）。レビューを CI と並べる変更が、モデルに CI の状態とレビュアーが見る commit と、規則「取り消しを使わずにマージまで行ける」を足している。モデルに足す候補のうち残るのは、ゲートが判定したあとに head が動く場面。`tests/schema.sh` の回し直しをやめる変更（PR #328）が、Go の側に schema の検査器を足さずに回し直しを無くす。command が書く前に schema と照らす候補は、品質の問いとしてだけ扱う。同意のあと 2026-11-20 のうちに、2 つとも main に入った（PR #329 と PR #328）。今のモデルは規則が R1〜R7、状態が 900、守りを外した見本が 4 つ。
3. **お金と外のサービスは足さない。足す道具は無料で、版を固定でき、開発と CI だけで使うもの**（人 2026-11-20）。ADR-0032 の前提 4 と同じ。利用者に配る `andon` と image には入れない。
4. **入れる候補の物差しは 3 つ**（人 2026-11-20）。(1) シェルの節が消える。(2) その種類の不良がまるごと起きなくなるか、シェルしか見ていない穴が塞がる。(3) 次に流れを変えるときに、実装の前に設計の穴を見つけられる。どれにも当たらず、コードが整うだけの候補は入れない。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **検査の秒数の上限は、今は置かない**（人 2026-11-20）。dispatcher の場面を Go へ移し終えて数字が落ち着いてから決め直す。それまでは 2026-11-27 の観察が秒数を数える。理由: 同じ検査の秒数が runner によって倍ちがうので、今の数字で落とす上限を置くと、遅い runner に当たった回が落ちる。Go へ移すと数字そのものが変わり、今置いた線はすぐ引き直しになる。捨てた案: 「上限を超えた検査を CI の注記に出すだけにする」（落ちないが、読む人がいないと効かない）。「落とす上限を置く」。

2. **repo に固有の規則は Go のテストと字面の検査で書き、加えて汎用の静的解析 golangci-lint を CI に足す**（人 2026-11-20。Chief Engineer は「Go のテストと字面の検査だけ」を推したが、人は golangci-lint も足すほうを選んだ）。repo に固有の規則は、ソースを読む Go のテストと `tests/*.sh` の字面の検査で書く（`workflow_test.go`・`tests/package.sh` と同じ今の形）。理由: 表で lint に当たった 11 行はどれも repo に固有の規則で、`hc send` や `gh api` は exec に渡す文字列なので、既製の禁止規則では書けない。golangci-lint は表の節を減らさないが、表に出ていない種類の不良を拾う。捨てた案: 「自作の analyzer を `go vet -vettool` で回す」（型まで見られるが、`golang.org/x/tools` への依存と書く量が増える）。

3. **課題の一生のモデルに、ゲートが決めたあとの変化を今足す**（人 2026-11-20）。足す行動は 3 つ。判定のあとに PR の head が動く。PR が閉じて開き直される。merge の設定と委譲が変わる。規則を 1 本足す: 「dispatcher が自動でマージするのは、ゲートが approve と判定した head で、その時点で任されているものだけ」。「取り消しを使わずにマージまで行ける」の規則は、閉じた PR を開き直す道を含めて成り立つことを確かめる。守りを外した見本を足す。通知の配達と resume の回数は、その流れを変える題が出たときに、ADR-0032 の決めたこと 9 のとおりモデルへ先に書く。理由: 間違った自動マージは main に入り、ラインで一番高くつく破れになる。今のモデルはこの 3 つの変化を持たず、自動でマージしてよいものを言う規則も無い。シェルの節では 4a・4d・4d-2・9・9f・10 がこの場面を見ていて、Go のテストの重なりはどれも一部か無し。知っていて受け入れたこと: 状態の数が増えて検査が何秒になるかは測っていない。この流れを変える予定は今は無い。捨てた案: 「今は足さない」（仕事は増えないが、自動マージの規則が無いまま）。「通知の配達と resume も別のモデルとして足す」（タイマーと回数を一から写す仕事になる）。

4. **golangci-lint は 2 段で入れる**（人 2026-11-20）。1 段目は errcheck 以外（staticcheck・unused・ineffassign・govet）を入れ、今出る 16 件を直す。2 段目で errcheck を、テストと出力への書き込みを除く設定で入れ、残る約 73 件を直すか、理由を書いて除く。理由: 約 73 件には `json.Unmarshal` や `syscall.Flock` のエラーを見ていない所があり、本物の見落としが混ざりうる。出力への書き込みとテストの指摘は数が多く、直しても得るものが小さい。捨てた案: 「errcheck は入れない」（約 73 件が読まれないまま残る）。「PR が足した行だけを見る」（今ある指摘が残り、古い行に触れた PR で指摘が出る）。

   判断の材料にした事実（2026-11-20。golangci-lint v2.15.0 を既定の設定でセルの中で当てた）:
   - 指摘は 511 件。errcheck が 495、staticcheck が 9、unused が 6、ineffassign が 1。govet は 0。かかったのは 28 秒（16 コア）。
   - errcheck の 495 件は、テストの中が 185、それ以外が 310。310 のうち 237 は `fmt.Fprintf`・`fmt.Fprintln`・`fmt.Fprint` で出力へ書く呼び出し。残りの約 73 件は `f.Close` が 18、`os.Remove` が 8、`json.Unmarshal` が 6、`stdout.Write` が 5、`syscall.Flock` が 4 など。1 件ずつは読んでいない。
   - staticcheck の 9 件は、書き方の提案（QF1001 が 7、QF1002 が 1）とエラーの文の書き方（ST1005 が 1）。

5. **golangci-lint の設定ファイル `.golangci.yml` は、人がマージする変更（ゲートの条件表のレベル C）に足さない**（人 2026-11-20。Chief Engineer は足すほうを推したが、人は足さないほうを選んだ）。設定を変える PR は、独立レビューとゲートに任せる。捨てた案: 「レベル C に足す」（linter を外す変更を人が見るが、設定を触るたびに人のマージが要る）。

   golangci-lint の細目（2026-11-20。Chief Engineer が推奨案で決めた。人には問いにしていない。違えば下に足して直す）: 回す場所は CI の go の job と、手元でいつも回す検査（gofmt・`go vet`・`go test` と同じ段）。版は repo の `mise.toml` で固定し、手元の道具はそこから入れる。CI が別の所に版を書くなら、揃いを検査で見る。image には入れない（前提 3）。

6. **schema の照合を、既製の Go の検査器 1 つに一本化する。`andon` は約束の JSON を書く前に schema と照らす**（人 2026-11-20。Chief Engineer ははじめ「binary に小さい自作の検査器を入れる」を推した。人が「JSON Schema Validator のようなものを活用するのは。検査器を 2 つ用意するのは微妙では」と言い、既製に寄せる形に引き直して人が選んだ）。2 段で進める。1 段目: `andon` に既製の JSON Schema の検査器のライブラリと `schema/` を入れ、約束の JSON を書く前に照らし、合わなければ書かずに落とす。2 段目: `tests/schema.sh`・`tests/process.sh` の照合を `andon` の command 経由にし、`package/lib/andon/schema_check.py` の照合の役と、`cmd/kanban/schema_test.go` の中の自作の照合をやめる。`schema_check.py` に残るのは、schema そのものの決まりを見る役と、文書の例を取り出す役（検査器ではない）。理由: 場面を Go へ移すと、command が書いた JSON を schema に通す確かめが消える（下の事実）。書く前に照らせば、どのテストでも本番でも照らされ、出力を写す表が要らなくなる。検査器が自作と既製の 2 種類あると、同じ schema の読み方が食い違いうる。捨てた案: 「binary に自作の検査器を入れる」（自作が 3 つになる）。「既製を足し、Python の自作は残す」（検査器が 2 種類のまま）。「既製の検査器を Go のテストの中だけで使う」（本番では照らされず、通すのを忘れたテストの出力も照らされない）。

   知っていて受け入れたこと: ライブラリは配る `andon` の依存になる（今の依存は 3 つ）。検査器か schema が誤ると、command が書けずに止まる。schema の `pattern` は検査器ごとに正規表現の方言が違うので、Go の正規表現でも同じ意味になることを schema の決まりに足して確かめる。標準に無いキーワード `uniqueKeys` は既製の検査器が読み飛ばすので、一意は今までどおり command の側で確かめる。

   判断の材料にした事実（2026-11-20。読むだけの反論役がコードから示し、Chief Engineer が抜き取りで確かめた）:
   - `tests/schema.sh` の 5 は、シェルの検査が `ANDON_EMIT_DIR` に写した command の出力を、固定の表で schema に通す。表にあるファイルが無いと落ちる。`tests/andon-dispatcher.sh` は 35 か所で 38 のファイルを写している。
   - Go の側に、command が書いた JSON を schema に通す検査は無い。`internal/contract` の `Write` は照らさずに書く。通知の `Detail` は `map[string]any` で、型でも縛られない。
   - 検査器は今、自作が 2 つ。`package/lib/andon/schema_check.py`（Python の標準ライブラリだけ。315 行。照合・schema の決まり・文書の例の取り出し・まとめて回す口）と、`cmd/kanban/schema_test.go` の中の照合。
   - 既製の候補（あることと依存だけを確かめた。draft 2020-12 の対応は実装の最初に確かめる）: `github.com/santhosh-tekuri/jsonschema/v6`（v6.0.3。動かすときの依存は `golang.org/x/text`）、`github.com/google/jsonschema-go`（v0.4.3。依存は `go-cmp`）。どちらにするかは実装が決める。

7. **`log.jsonl` の行と `kanban ready --json` の形の schema を足す**（2026-11-20。Chief Engineer が推奨案で仮に決め、人が最後の確かめで「決めた」と言った）。`schema/ledger` に足し、kanban の本物の出力と、Go のテストが手で書く台帳の両方を通す。理由: Go のテストは本物の kanban を呼ばず、手で書いた `log.jsonl` を使う（`internal/dispatcher/outcome_test.go`・`internal/issue/issue_test.go`）。場面を Go へ移すと、kanban が書く形と dispatcher の読み手がずれても、どのテストも落ちなくなる。今の `schema/ledger` は config・issue・questions・routine の 4 本だけで、行の形を固定する検査は無い。

8. **repo に固有の lint の規則は、今は 2 つ入れる**（人 2026-11-20）。
   - **フックの 1 行目**: `package/hooks/` の 4 本の最初の実行行が `command -v andon >/dev/null 2>&1 || exit 0` であることを字面で見る。どこかにあることではなく、最初の実行行であることを見る。理由: dispatcher の検査の 12・13a・13c が見ている「andon が無ければ通す」の確かめが要らなくなる。`stop` のフックのこの場合は、今どの検査も見ていない。
   - **全部の workflow を見る**: `.github/workflows/` の全部を actionlint・ghalint・pinact に通す。理由: 今は `tests/image.sh` が `tests.yml` だけを container に mount して回していて、`go.yml` と `model.yml` はこの 3 つの道具に通っていない。
   入れなかった規則: 「dispatcher が `hc send` を打てる所を今の 3 か所に限る」（節は消えず、新しい送り先が黙って増えることを止めるだけ）。「schema の決まりに、どの object も知らないキーを許さないことと、改名前の語を置かないことを足す」（わざと緩くしている所を名指しで除く手間が要る）。「ゲートが REST の `repos/<slug>` と `user` を打たないことを字面で見る」（`tests/andon-gate.sh` の 2a は、base と作者の違いが needs_human になる振る舞いも見ていて、字面の検査では代わりにならない。ここを通る Go のテストは無い）。

9. **型の設計は 3 つ直す。直すのは、その節を Go へ移す課題の中**（人 2026-11-20）。先に型を直してから、その型の Go のテストを書く。
   - **失敗を数えて諦める控え**: 影響の集め・人の手直しの集め・結果の記録が、失敗の回数を `map[string]int` で 3 か所に別々に持つ（`internal/dispatcher/state.go`）。1 つの型にする。dispatcher の検査の 1c・1d-4 と 1e の打ち直しの部分が、1 つの型のテストで済む。
   - **予約キーの照合を通った値**: 照合の結果を真偽の値で持ち回っていて、照合を忘れても値が読める（`internal/dispatcher/loop.go`・`state.go`）。照合を通った値だけを読める型にする。dispatcher の 0d と `tests/andon-gate.sh` の 8。
   - **ゲートの落ち方**: gh の上限で落ちたかどうかを、終了コード 3 とエラーの文の「rate limit」という文字列で見分けている（`internal/issue/merge.go`）。落ち方を型か終了コードで分ける。dispatcher の 9e。
   直さない型: 端末のアドレスと `<machine>/<address>` の区別、`hc get` の答えの 3 通り。前提 4 の物差しに当たらない（整うだけ）。その節（21・22）は Go のテストへ移す。捨てた案: 「先に別の課題で直す」（シェルの節が残ったまま型を変えるので、同じ所を 2 度触る）。「型は直さない」（照合の忘れや文字列の見分けがテストでしか止まらない）。

10. **ゲートとマージ・人のマージの見張りの状態の定義をモデルと照らすかは、モデルを広げた結果を見てから決める**（人 2026-11-20）。先に決めたこと 3 のモデルの広げ方だけを入れ、状態の数と検査の秒数を見る。理由: 状態の定義は 10 本あり、モデルと照らし、command が定義に無い移り方を断るのは `process/states/issue.yaml` の 1 本だけ。`gate.yaml` の状態は、マージの記録の 4 つの欄（Decision・Merged・Wait・Approved）の組み合わせで表されていて、モデルの変数と 1 対 1 でない。照らすには道具と対応表を広げる仕事が要る。捨てた案: 「2 本をモデルと 2 方向で照らす」。「実行時にも照らし、`andon issue merge` と `settle` が定義に無い移り方を断る」（マージの道のコードに広く触れる）。

- **検査の秒数の上限を置くこと**。決めたこと 1。
- **自作の analyzer を `go vet` で回すこと**。決めたこと 2。
- **GitHub に聞く回数を、動かすときに数えて上限を置くこと**。上限に当たったときの振る舞いという新しい設計が増え、前提 4 の物差しのどれにも当たらない。回数の確かめ（1 分に 1 回・REST を 0 回・reset まで 0 回）は、偽の gh の呼び出しの記録を数える今の手口のまま、Go のテストへ移す。

- **型の設計のうち、決めたこと 9 で直さないとした 2 つ**。
- **`process/states/` の `once: true` を実行時に照らすこと**。決めたこと 10 と同じく、モデルを広げた結果を見てから。

## 受け入れ条件

継ぎ目は 5 つ。CI の go の job、`go test` の出力、`model/check` の出力、`tests/package.sh` と `tests/schema.sh`・`tests/process.sh` の出力、workflow の静的検査の出力。どれも既にある継ぎ目で、本物の道具と本物のファイルで走らせる。条件ごとに、通る出力と、守りを外したときに落ちる出力の両方を PR の本文に書く。

1. **golangci-lint の 1 段目**（決めたこと 2・4・5）。CI の go の job が golangci-lint を回し、errcheck 以外の既定の linter で指摘が 0 件。証拠: `golangci-lint run ./...` の出力と、go の job が成功した run。使われない関数を 1 つ足すと落ちる。証拠: そのときの出力。版は `mise.toml` に 1 か所で、CI が別の所に版を書くなら、ずらすと落ちる検査がある。証拠: ずらしたときの出力。image に入っていない。証拠: `grep -c golangci image/Dockerfile image/aqua/aqua.yaml` の出力が 0 で、同じ grep が `mise.toml` では 1 以上になる。
2. **golangci-lint の 2 段目**（決めたこと 4）。errcheck を、テストと出力への書き込みを除く設定で有効にして、指摘が 0 件。除いた呼び出しには、設定かコードに理由が 1 行ある。証拠: `golangci-lint run ./...` の出力と、`json.Unmarshal` の戻り値を捨てる 1 行を足したときに落ちる出力。直した約 73 件のうち、振る舞いが変わるもの（今まで黙って進んでいた失敗が表に出るもの）は PR の本文に並べる。人が見る（`manual`）。
3. **フックの 1 行目**（決めたこと 8）。`bash tests/package.sh` の出力に、`package/hooks/` の 4 本それぞれの ok の行がある。1 本のフックで、その行の前に別の実行行を足すと落ちる。証拠: 両方の出力。
4. **全部の workflow を見る**（決めたこと 8）。actionlint・ghalint・pinact が `.github/workflows/` の 3 本（`tests.yml`・`go.yml`・`model.yml`）を通す。証拠: 検査の出力に 3 本の名前が出ることと、`go.yml` の action の固定を外した写しで落ちる出力。workflow を足したら、その workflow も見られる（ファイルの名前を検査に書かない）。

6. **書く前に照らす**（決めたこと 6 の 1 段目）。約束の JSON を書く command が、schema に合わない値を書こうとすると、書かずに 0 でない終了コードで終わる。証拠: `go test -run '<足したテストの名前>' ./internal/contract` の出力と、照合を外したときの FAIL の出力。照合を通らずに約束の JSON を書く所が無い。証拠: ソースを読む Go のテストの出力と、照合を通らない書き込みを 1 つ足したときの FAIL の出力（約束の JSON を書く所は今、`contract.Write` の呼び手が 13、`contract.Marshal` の呼び手が 14、それ以外で JSON を書くファイルが 20 ある）。`schema/` の全部の `pattern` が、選んだ検査器で読める。証拠: そのテストの出力。今の出力が全部 schema に合っている。証拠: `go test ./...` と CI の tests の job が通った run。
7. **検査器を 1 つにする**（決めたこと 6 の 2 段目）。`tests/schema.sh` と `tests/process.sh` の ok の行の数が、直す前と同じ。証拠: 直す前と後の `bash tests/schema.sh | grep -c '^ok'` と `bash tests/process.sh | grep -c '^ok'` の出力。`package/lib/andon/schema_check.py` に照合の口が無く、`cmd/kanban/schema_test.go` に自作の照合が無い。証拠: `python3 package/lib/andon/schema_check.py validate <schema> <その schema に合う JSON>` が、0 でない終了コードと使い方の文で終わる。同じ command は、直す前の commit では 0 で終わる。`package/` に触れるので、セルで実測する。
