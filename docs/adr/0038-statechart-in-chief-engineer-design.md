## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-20、Chief of Staff への発言）: 「アイデア：反論を回す際にstatechart使ってもらう、もしくは反論を回す前にstatechartを使う　とよいかも？」

オーナー（2026-11-20、言い直しへの直し）: 「人が読むことでは重要ではなく、CEの検討の中でstatechartを活用してヌケモレをなくすこと、それをさらに開発に活かせること、その後形式検証ができることで全体の品質向上を目指せること　というような目的」

言い直し（オーナーが 2026-11-20 に「合っている」と答えた）: Chief Engineer が設計を検討する中で、状態の間を動く設計を statechart のモデルにして調べ、順番や状態のヌケモレを、決める前になくす。図をオーナーが読むことは主な目的ではない。Chief Engineer が作ったモデルと規則は捨てずに開発へ渡し、担当がそれを土台に実装する。そのモデルを repo の形式検証（`model/` と CI の検査）へつなげて、設計・開発・検証が同じモデルでつながり、全体の品質が上がる。

### 確かめた事実（2026-11-20）

1. **過去の設計文書の反論。** Chief Engineer の設計文書 8 本（ADR-0025〜0030・0032・0033）のうち、反論を走らせた跡があるのは 5 本。拾えた指摘は 50 件で、順番や状態の穴が 3 件、事実の誤りが 17 件、範囲・コスト・言葉などが 26 件、中身が分からないものが 4 件。順番や状態の穴の 3 件は、すべて ADR-0032 の 1 本から出て、オーナーが形を選んだあとに見つかった（ADR-0032 決めたこと 8）。
2. **反論が拾わなかった例。** ADR-0030 は反論を走らせていない。文書の PR を出したあとに、Chief of Staff がトリアージの 1 項目の動きを TLA+ のモデルにして調べ、規則 4 本のうち 3 本の破れを見つけた。決めたこと 6 がそのあとに足された（ADR-0030 の事実 17・決めたこと 6）。
3. **状態の間を動く設計の数。** 8 本のうち、設計の対象が状態の間を動く流れそのものだったのは 2 本（ADR-0030・ADR-0032）。2 本とも、順番の穴はオーナーの決定のあとに見つかった。
4. **道具はこのセルで動く。** pstack 0.15.43 の statechart は、このセルに入っている TLC（`tla2tools` 1.7.4）と Java（temurin 25）で動く。repo の課題の一生のモデル（`model/IssueLife.tla`・`IssueRules.tla`・`IssueRules.cfg`）の写しを repo の外で回すと、約 2 秒で規則 8 本を調べ終えた（900 状態）。repo の入口 `model/check`（検査器は tla-ts）は約 4 秒で全部通った。
5. **statechart を使った調べる課題の実績。** いまあるコードをモデルに写して調べた課題が 4 件ある。かかった時間は 12 分・18 分・29 分・12 分。見つけた規則の破れは 3 件・5 件・6 件・3 件で、どれも本物のコードで 1 歩ずつ再現した。4 件とも、これから作る設計ではなく、いまあるコードのモデルだった。
6. **いまの決まり。** ADR-0032 決めたこと 9 は「流れの順や状態の移り方を変える変更は、実装の前にモデルに書いて確かめる」。これが効くのは実装の課題の中で、Chief Engineer がオーナーと案を選ぶ段ではない。ADR-0025 は、課題の一生の動きを変える PR に、同じ PR で `model/` を直すことを求める。
7. **pstack はこのセルだけにある。** ADR-0021 の前提 3 のとおり、パッケージは変えていない。Chief Engineer の skill（`package/skills/chief-engineer/SKILL.md`）はパッケージに入り、全部のセルへ配られる。ADR-0021 の「やらないこと」は、Chief Engineer に pstack の指示を足さないと決めている。
8. **Chief Engineer の決まり。** Chief Engineer はコードを書かない。反論は読むだけのサブエージェントに頼む。話しても決まらない問いの試作は、捨てる前提の小さい課題として Chief of Staff に頼み、自分では書かない（skill の手順 4・6）。
9. **statechart の道具と検査器。** pstack 0.15.43 の statechart の道具は Java の TLC を直接呼ぶ。検査器を tla-ts に差し替える口は無い。tla-ts で回す変更は、本家で PR #1151（`github.com/cursor/plugins`。2026-11-01 から開いている）として出ていて、まだマージされていない。入ると既定が tla-ts になり、Java は環境変数で指定したときだけ使う。
10. **tla-ts だけでも調べられる。** repo がバージョンを固定している tla-ts（`model/package-lock.json`。0.0.10）を repo の外に入れ、壊した見本を回すと、1 秒かからずに破れた規則と、初めの状態から破れまでの動きの並びが出た。repo のモデル一式と課題の状態の定義の写しを repo の外に置いても、`model/check` はそのまま約 5 秒で通った。要るのは Node だけで、Node は image に入っている。
11. **statechart と tla-ts の出し方の違い。** tla-ts を直接回すと、最初に破れた規則 1 本で止まる。statechart は破れた規則を外して回し直し、破れた規則すべてについて最短の道を 1 回で出す。
12. **置き場。** pstack の plugin（7.4MB）は `~/.claude/plugins` にあり、セルを作り直しても残る。Java（303MB）と TLC（2.2MB）は plugin に含まれず、statechart を初めて回したときに道具が mise で入れる。置き場は作り直しで消え、次に回したときにもう一度入る。どれも image には入っていない。

### 範囲を広げたあとに確かめた事実（2026-11-20。配り方を読み、読むだけのサブエージェントの反論を走らせた。指摘は 14 件で、Chief Engineer が読み直して確かめたものを書く）

13. **参照で入れる口。** yomiyasu は `gh-skills.txt` の 1 行で入る（boot が `gh skill install` で Claude Code と Codex の両方に入れ、起動のたびに `gh skill update --all` で上げる。`<skill>@<バージョン>` と書けば固定でき、更新は固定した skill を飛ばす）。パッケージの既定の一覧はいま空で、「既定は空」と書いた文が `package/gh-skills.txt`・`internal/boot/extskills.go`・`docs/design.md`・`docs/operate.md` と ADR-0018 にある。pstack は Claude Code の plugin で、設定の 2 つのキー（marketplace の登録と plugin の有効化）で次のセッションの始めに入る。Claude Code の公式の文書によれば、この 2 つのキーは管理用の設定（boot が `package/settings.json` から置く）に書いても同じに効き、管理用の設定で有効にした plugin はセルの利用者の設定では外せない。`package/settings.json` のキーの集合を固定している検査は無く、許しの規則だけを縛るキー（`allowManagedPermissionRulesOnly`）ともぶつからない。
14. **pstack は自動では上がっていない。** Claude Code の公式の文書によれば、marketplace の自動更新の既定は、公式の marketplace だけが入で、ほかは切。このセルの設定に `autoUpdate` は無く、入っているバージョンは 2 日前の 0.15.43 のまま、本家は 0.15.46 に進んでいる（2 日で 3 バージョン）。管理用の設定の項目は利用者の設定の同じ名前の項目を丸ごと置き換えるので、上げるなら管理用の設定に `autoUpdate` を明示で書く。バージョンの固定は、marketplace の source に 40 桁の `sha` を書く形でできる（Claude Code 2.1.324 から。セルは 2.1.329）。
15. **起動との関係。** 役はどれも対話の `claude` で起動され、非対話（`-p`）の起動は無い。plugin が最初のターンに間に合わなくても、statechart を使うのは対話の途中なので困らない。ネットワークが無いとき・gh にログインしていないときも、boot と役の起動は落ちない（外の skill は入らず 1 行出るだけ。plugin は cache から読む）。gh にログインしていないセルには yomiyasu が入らない。pstack は公開の repo から git で取るので gh のログインは要らない。
16. **入れただけで載るもの。** pstack に hook・MCP・常に読まれる rule は無い。skill は 57 本で、`setup-pstack` 1 本を除いてモデルからは呼べない（`disable-model-invocation`。使うには `SKILL.md` を読んで従う。置き場のパスにはバージョンの番号が入り、バージョンごとに変わる）。`setup-pstack` はモデルから呼べて、走らせると `~/.claude/rules/` に毎セッション読まれる rule を書く。サブエージェントの型が 2 つ（コードを書く役と、コメントを消す役）全部の役の一覧に載る。本家の写しは Claude Code 向けだけで、Codex で動く役には入らない。Chief Engineer のプロファイルは Claude の 1 つだけ。
17. **statechart は「行ける」の形の規則を調べない。** repo のモデルの規則のうち、R7（マージまで行ける）は `model/reach.mjs` が読む行で、検査器の設定ではコメント。statechart が読むのは不変の規則と行き止まりの検査だけなので、R7 は調べない（事実 4 の「規則 8 本」は、型の規則・R1〜R6・行き止まりの検査）。ADR-0032 の順番の穴は、行き止まりの検査に当たらず「行ける」の規則で見つかった種類だった。
18. **写しに案を足すと `model/check` は落ちる。** `model/check` は、状態の数と規則の集合を控え（`expected.txt`）と比べ、対応表（`issue-map.txt`）と `process/states/issue.yaml` を 2 方向に照らし、壊した見本が破れで落ちることを確かめる。案を足した写しは、控え・対応表・見本を直さない限りどこかで落ちる。控え・対応表を弱める変更はオーナーが見る決まり（`AGENTS.md`）。事実 10 の「約 5 秒で通る」は、手を入れていない写しの数字。
19. **statechart の手順の最後はコードでの再現。** statechart の本文は、見つけた道を本物のコードでテストか実演として再現し、起きなければモデルが誤りと考えよ、と書く。Chief Engineer はコードを書かない。
20. **渡し方の決まり。** Chief Engineer の skill は「渡すのは文書だけ」、Chief of Staff の切り方の手引きは「渡されるのは文書だけ」と書く。モデルのファイルを添える形（決めたこと 4）は、この 2 か所に例外の文が要る。課題の資料置き場はセルの repo の置き場の下にあり、セルを作り直しても、課題が片付いても残る（決めたこと 4 の理由の「作り直すと消えうる」は誤りで、消えない）。担当がほかの課題の資料を読む前例もある。
21. **許しの確認。** 管理用の設定の許しの一覧に、`node`・`mise`・statechart の道具は無い。許しの規則は管理用の設定のものだけが効き、「次から聞かない」は残らない。Chief Engineer が statechart を回すたびに、オーナーに確認が出る。
22. **試しの判定はまだ記録が無い。** ADR-0021（pstack）は「全セルへ入れるかは判定のあとの題で決める」、ADR-0013（yomiyasu）は「30 件通したところで材料をまとめ、オーナーが、既定に入れる・セルだけで続ける・やめる、のどれかを決める」と書く。どちらも判定の記録は無い。yomiyasu を通した記録は 32 件ある（2026-11-19〜20）。材料のまとめ（主な直しの例・言い換えられた語・読み違えの例）は作られていない。
23. **ほかの決定との食い違い。** ADR-0035（同じ日に決定）は、やらないことに「pstack の `create-formal-verification-skill` も使わない（形式モデルは ADR-0025 が既に持つ）」「ほかのセルの案件の repo には広げない」と書く。前者は決めたこと 9 とぶつかる。ADR-0025 の「検査器はセルに配るパッケージと image には入れない」は tla-ts のことだが、全セルの Chief Engineer が statechart を回すと、どのセルにも初回に Java と TLC が入る（事実 12）。
24. **検査に当たる所。** `tests/package.sh` は、Chief Engineer の skill に資料置き場を `issues/<id>/library/<題…>` の形で書くと落ちる。`tests/image.sh` の偽の `gh` は `auth status` 以外を別の命令に差し替えるので、既定の一覧が空でなくなると boot の `gh skill` が化ける（ADR-0018 が「boot が `gh skill` を打つなら直す」と書いている）。

## 前提（同意済み。番号）

1. **statechart は反論を置き換えず、状態の間を動く設計のときだけ足す**（オーナーが同意 2026-11-20）。順番や状態のヌケモレが出るのは、状態の間を動く設計に限る。反論の指摘の大半は、事実の誤りや範囲の指摘で、モデルでは拾えない（事実 1〜3）。反論はいまのまま残す。
2. **検討が長くなることを受け入れる**（オーナーが同意 2026-11-20）。何もしなければ、順番の穴は実装の課題で初めて見つかり（ADR-0032 決めたこと 9）、設計を決め直すために Chief Engineer とオーナーの対話へ戻る。検討の段でモデルを書けば、オーナーが決める前に穴が見つかり、実装の課題はそのモデルを引き継げる。代わりに、状態の間を動く設計の題では検討が長くなる（目安は事実 5 の 12〜29 分）。
3. **いまあるモデルを土台にする**（オーナーが同意 2026-11-20）。課題の一生に触れる設計では、新しいモデルを一から書かず、repo の `model/` の写しに案を書き足して調べる。開発へは同じモデルへの差分として渡せる。新しくモデルを書くのは、モデルがまだ無い流れ（dispatcher の配達・トリアージ・gate など）の設計のときだけ。
4. **対象はこのセルと Andon の repo に限る**（オーナーが同意 2026-11-20）。pstack と TLC が入っているのは Andon を作るセルだけ（事実 7）。ほかのセルや、ほかの案件の repo の設計でも使えるようにする話は、この題の外に置き、効きめを見てから別の題にする。
   - **取り下げ（2026-11-20。同じ対話の中）**: オーナーが「pstack, yomitokuはCELL標準にしてもいいと今は思っている」と言い、全セルへ配る設計をこの題に含めると選んだ（決めたこと 10）。「yomitoku」は文の推敲の skill の yomiyasu のこと。
