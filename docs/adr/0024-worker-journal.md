# ADR-0024: 担当が課題ごとに日報（過程・感想・改善の思いつき）を書く（仕様・設計。2026-11-12。Chief Engineer の課題 A-0186）

## 問題（人の言葉で。言い直しの段落）

人（2026-11-12、Chief of Staff への発言）: 「アイデア: Kanban の Issue にそれぞれ作業者の日報とか書いてもらうと改善にいいかも」。

人（2026-11-12、Chief Engineer との対話）: 「過程や感じたこと、改善できそうなことなどの感想などを忌憚なく書いてもらえばよいかなと思っている。最終的に環境の見直しにつながったり、改善が見込める。また今の KANBAN のレトロスペクティブはもう少し活用の余地があるのでオーナー向けの Daily の報告書なんかが出来上がってもいいと思う」。

言い直し（人が「合っている」と言った。2026-11-12）。担当に、課題ごとの日報を書いてもらう。中身は結論ではなく、過程・感じたこと・改善できそうなことの感想で、忌憚なく書く。今の報告の `## Remember` は「次の課題への学びを、その行だけで通じるように」という結論向けの書式で、感想や不満や思いつきを書く場所が無い。日報を読む側は、今は名前と目的だけの「ふりかえり（Retrospective）」のワークストリームで、環境の見直し（skill・依頼書・`AGENTS.md`・テストを直すこと）につなげる。オーナー向けの Daily の報告書は、人が別の題に分けた（やらないこと）。

### 読んだ事実（2026-11-12。台帳と main `6aa10b8`）

- ふりかえりのワークストリーム（`process/workstreams/retrospective.yaml`）は `name`・`title`・`purpose`（「課題の終わりと週 1 回、記録からつまずきを拾い、環境を直す」）だけで、きっかけと手順は書かれていない（ADR-0017 決めたこと 3）。

- 今の Remember を読んでいるのは、検収のときの Chief of Staff（依頼書の経緯の実例: 担当が「計画との差」に書いた詰まりから課題を切った）。

## 前提（同意済み。番号）

1. **まず書かせる（2026-11-12。人が Chief Engineer の案を退けた）。** この題で決めるのは、日報を書かせる所だけ。読む側（誰がいつ読んで何を直すか）は、たまった日報を見てから考える。
   人が退けた案: 書く側と読む側を同じ題で決める（Chief Engineer の推奨。Remember が 286 行読まれずにたまっているので、読む側を決めないと同じになる）／日報は足さず、今ある Remember を読んで直す流れを先に回す。
2. **既にあるもので済ませる（2026-11-12 同意）。** 日報のために新しい役・常駐・新しい command は作らない。担当が今持っている口（課題の終わりに打つ `andon issue report` と、台帳の自分の課題のフォルダ）に乗せる。足すのは worker skill の書き方の数行が中心。
3. **忌憚なく書ける条件（2026-11-12 同意）。** 日報は検収・ゲート・見守りの判定に使わない。日報の中身（書いていない・短い・不満が書いてある）を理由に差し戻さない。機械（dispatcher・ゲート）は日報を読まず、人と AI が読む Markdown にする。このことを worker skill に書いて担当に伝える。
4. **日報は足すもので、今の報告は変えない（2026-11-12 同意）。** 報告は結論を検収のために書くもの、日報は過程と感想を改善のために書くもので、読み手と目的が違う。今の報告の書式（`## Report`・`## 計画`・`## Next`・`## Remember`・「計画との差」）と、トリアージが行ごとに拾う道は変えない。
5. **配り方と重さ（2026-11-12 同意）。** 日報の書き方はパッケージの worker skill に書き、版上げで全セルの担当（Claude Code も Codex も）に届く。ラインそのものの変更なので実装の PR はレベル C（人がマージ）。まずこのセルで試し、効かなければ skill の数行を戻す。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **2026-11-12 日報は、台帳の課題のフォルダの別ファイル `issues/<id>/library/journal.md` に、担当が追記する（案 B）。**
   理由: 詰まったその場で書きためられる（終わってからまとめると整いすぎる）。検収が読む報告と分かれ、前提 3 を保ちやすい。台帳に課題ごとに残り、worktree を片付けても消えない。
   捨てた案: A（報告に `## 日報` の節を足す）は、報告を打つたびに全体を書き直すので途中で書きためられず、検収の紙と混ざる。トリアージの `collect` は報告を行ごとに読むので、日報の中の「見送」「For AGENTS.md:」を含む行を別の項目として拾ってしまう。C（日報を足さず auto memory〈ADR-0020〉に任せる）は、課題と結びつかず、確かめた事実と学び向けで感想の場所ではない。Codex の担当は書けず、週1の蒸留で消える。
2. **2026-11-12 書く時機は「その場で追記＋終わりに感想」。** 詰まった・迷った・回り道した・うまくいった、のその場で 1〜数行を追記する。報告を書く前に、全体の感想と改善できそうなことを足す。「日」ごとには書かない（担当の作業は 1 件あたり平均 1.5 時間）。
   理由: その場で書いたものが一番生のまま残る。終わりの感想だけだと整ったまとめになり、長い課題では途中の迷いが抜ける。
   捨てた案: 「終わりに 1 回だけ」は、手間は最小だが、整ったまとめになり途中の迷いが抜ける。「工程の区切りごと」は、小さい課題に重く、書くことが無い工程でも埋めることになる。
   受け入れること: 途中の追記は忘れられやすい。忘れても差し戻さない（前提 3）。
3. **2026-11-12 中身は軽い型。** 途中の追記は自由な 1〜数行（どの工程で・何が起きて・どう感じたか）。終わりに「感じたこと」「改善できそうなこと」の 2 つだけ見出しを置く。worker skill には書くきっかけの例（依頼書の分かりにくさ・skill の邪魔だった所と助かった所・道具・待ち・やり直し）を数個並べるだけで、答える義務は無い。
   形の例（人が選んだもの）は次のとおり。

   ```
   # A-0200 の日報

   - 理解: 依頼書の「完了条件」が 2 通りに読めて 10 分迷った。結局 ADR の追記を読んで決めた。
   - 作業: tests/run の待ちが長い。その間に文書を直したが、結果を待たずに進めてよいのか不安だった。

   ## 感じたこと
   正直、worker skill §4 は長くて毎回読み直す。

   ## 改善できそうなこと
   - 依頼書に ADR の追記の有無を書く欄があると助かる
   ```

   理由: 人の言葉（過程・感じたこと・改善できそうなこと）がそのまま形になる。型が強いと埋め草が増え、忌憚のない感想が出にくい。
   捨てた案: 「完全に自由（型も見出しも無し）」は、課題ごとのばらつきが大きく、あとで読み比べにくい。「決まった問いに毎回答える」は、読み比べやすいが「特になし」が並ぶ。
4. **2026-11-12 書くのは担当だけ。** 課題の型（直す・調べる・観察・トリアージ）は問わない。レビュアー・Chief of Staff・Chief Engineer は書かない。
   理由: 題のとおり。レビュアーの「読むだけ」の決まりと、Chief of Staff・Chief Engineer の手順を変えずに済む。足りなければあとから広げる。
   捨てた案: 「担当とレビュアー」は、レビュアーが書いてよいものの決まりを広げる。「課題を持つ全部の役」は、直す skill が 3 つに増える。
5. **2026-11-12 読む側が決まるまでは、置いておき、見る日にまとめて読む。** 日報は台帳に置くだけで、読む手順は決めない（人と Chief of Staff が読むのは自由）。価値の仮説の「見る日」に、今ある観察の課題がたまった日報をまとめて読み、オーナーに要約を返す。そこから読む側の題を始める。
   理由: 前提 1。読む仕組みを足さずに、今ある観察の課題の道だけで「たまったものを見る」機会を作れる。
   捨てた案: 「Chief of Staff が検収のたびに読んで課題に切る」は、読む側を半分決めることになり、検収と混ざって前提 3 が弱まる。「finish のたびに wiki の `raw/` へ写す」は、Chief of Staff の仕事が増える。今も報告の写しは 136 件中 3 件しか行われていない。
   受け入れること: 台帳が残るのはセルがある間だけなので、セルを建て直すと日報は消える。
6. **2026-11-12 細部（問わずに推奨案として書き、最後に確かめたときに人が認めた）。**
   - 名前は人の言葉のまま「日報」（英語は journal）。「日」ごとには書かないが、課題ごとの記録の名として使う。用語集に足す。
   - `journal.md` は担当が自分で作って追記する（command は足さない。前提 2）。worker skill §2 の「書く場所」は今も台帳の自分の `issues/<id>/library/` を含むので、置き場の決まりは変えない。「`library/` の JSON は手で書かない」の決まりもそのまま（日報は Markdown）。
   - worker skill の工程表の「振り返り」の「出すもの」に日報を足し、日報の節を1つ置く（置き場・時機・軽い型・きっかけの例・前提 3 の約束）。
   - 差し戻しや再レビューで `doing` に戻ったら、同じファイルに続けて追記する。
   - 秘密・資格情報は書かない。
   - `andon issue ready`・ゲート・`Stop` フック（`andon issue stop-check`）・`andon triage collect` は、日報の有無も中身も見ない（前提 3）。
   - chief-of-staff skill に 1 行足す: 日報は検収の判定に使わない。日報の中身を理由に差し戻さない。

## やらないこと（範囲の外。理由）

- **オーナー向けの Daily の報告書**（2026-11-12 人）: 別の Chief Engineer の題に分ける。
- **読む側の手順**（前提 1）: ふりかえりのワークストリームの中身・トリアージの `collect` に日報の項目を足すこと・finish のたびに wiki へ写すこと・Chief of Staff が検収のたびに読む決まり。どれも、たまった日報を見てから別の題で決める。
- **機械が読む形**（前提 2・3）: schema・`report.json` のキー・日報のための command・書かせるためのフック・`ready` での検査。
- **今の報告の書式を変えること**（前提 4）: `## Remember`・「計画との差」・`## Next` はそのまま。
- **レビュアー・Chief of Staff・Chief Engineer の日報**（決めたこと 4）。
- **日報の採点**: 日報や担当を点数で評価しない（前提 3。judge を入れない線は [design.md](../design.md) §1.9 の 4）。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に。既存の継ぎ目を優先し、できるだけ高く、できるだけ少なく）

継ぎ目は 2 つ: `tests/package.sh`（skill の本文）と、セルでの実測。

- A1. **worker skill**: 日報の節があり、置き場（`issues/<id>/library/journal.md`）・時機（その場で追記＋報告の前に感想）・2 つの見出し（「感じたこと」「改善できそうなこと」）・判定に使われないこと・秘密を書かないこと、が書いてある。工程表の「振り返り」の「出すもの」に日報がある（`tests/package.sh`）。
- A2. **chief-of-staff skill と用語集**: chief-of-staff skill に「日報を検収の判定に使わない・日報の中身を理由に差し戻さない」がある。用語集に「日報」がある（`tests/package.sh`）。
- A3. **機械は読まない**: 実装の差分に `internal/`・`schema/`・`cmd/` の変更が無い。
- A4. **セルでの実測**（版上げのあと。Chief of Staff）: Claude Code の担当と Codex の担当を 1 つずつ起動し、`journal.md` が台帳の課題のフォルダに書かれること、書くときに許可の確認で止まらないことを見る。止まるなら人へ戻す（許可を足すかは人が決める）。

## 価値の仮説

人が同意（2026-11-12）。数（7 割・10 件・3 件・8 割・2 割）は Chief Engineer の見立てで、観察のときに実数と一緒に見直す。

1. 誰の何が変わるか: オーナーと、あとで決めるふりかえりの読み手。担当の過程・感想・改善の思いつきが、課題ごとに台帳に残る。
2. 見る信号: 台帳の数（実装が入ってから閉じた担当の課題のうち `journal.md` がある割合と行数）、`andon measure` の `doing` の時間（手間が増えていないか）、オーナーの目視（観察の課題の要約と日報そのもの）。
3. 見る日: 2026-11-26。
4. 誰が要るか: オーナー（要約を読み、「直したい」ものを選ぶ）と、観察の課題の担当。
5. 効いたとどう分かるか: 実装が入ってから閉じた担当の課題の 7 割以上に日報があり、そこから「報告（Remember・計画との差・Next）には無い改善の種」が 10 件以上挙がり、オーナーがそのうち 3 件以上を「直したい」と言う。
6. 何があれば止めるか: 日報の 8 割以上が報告の言い換えか「特になし」／担当の `doing` の平均が入れる前（1.5 時間）より 2 割以上伸び、原因が日報と見られる／日報に書くことで担当が作業を控えた・取り繕った例が出た。どれかに当たれば、skill の数行を戻すかを人が決める。

当たったら、たまった日報と要約を材料に、読む側の題と Daily の報告書の題を始める（開いている問い 1・2）。
