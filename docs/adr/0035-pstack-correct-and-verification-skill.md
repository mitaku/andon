## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-20）: 「PStackのcorrect, create-verification-skillsを活用したらもっとAndonの開発サイクルが改善しないかな？」

言い直し（オーナーが 2026-11-20 に「OK」と答えた）: Andon を作る開発サイクルで、2つのことを良くしたい。1つ目は、担当が同じ種類の誤りを繰り返し、オーナーとレビュアーが同じ直しを何度もしていること。これを、決まりの文を足して直すのではなく、設計・型・lint・テストで起きない形にしたい。2つ目は、担当の「確かめた」が検査の通過にとどまりがちなこと。本物の Andon を利用者と同じ道で動かして証拠を取る手順を、repo に1つ持ちたい。pstack の `correct` と `create-verification-skill` はこの2つに当たるので、借りられるなら借りたい。決めたいのは、skill をそのまま工程に入れるのか、足りない所だけを Andon の今の仕組みに移すのか、入れないのか。

## 読んで分かった事実（2026-11-20。main `e01ab26` と、Andon を開発しているセルで実測）

### pstack の2本（0.15.43。本文は写していない）

1. **`correct`** は、1つのセッションが見つけて直すまでを通す skill。手順は4つ。(1) 直近の commit・revert・レビューのコメント・エージェント向けの指示のファイル・回避策を説明するコメントを読み、誤りを種類にまとめる。2回起きたものを種類と数える。(2) 種類ごとに、効く一番上の段で直す。段は、設計で無くす、型で書けなくする、直し方を名指す lint か CI の検査、振る舞いのテスト、文書かエージェント向けの決まり、の順。文書は判断が要るものだけ。(3) 多い種類から、1種類1 commit で直す。新しい検査が、過去の本物の誤りで落ちることを確かめる。例外は当たる行に、理由・期限・オーナーの承認をつけて書く。(4) エージェント向けの指示のファイルに、決まりと、それを守らせるものを対にした表を持つ。オーナーが直したら、誤りを直して決まりを足す。決まりが既にあって守らせるものが無ければ再発で、同じ変更の中で一番上の段で直す。誤りが起きようのなくなった決まりは表から消す。
2. **`create-verification-skill`** は、repo 専用の検証の skill（`verify-<app>`）を作る skill。作る skill の節は、起動（Launch）・診断（Doctor）・動かす（Drive）・証拠（Evidence）・片付け（Cleanup）・補助のスクリプト（Helpers）。加えて、利用者から見た機能ごとに「何か・どう辿り着くか・どう動かすか・何が見えれば動いた証拠か」を1ファイルずつ書いた機能の地図を持つ。証拠の基準は、本物の利用者の道を通すこと、操作と結果の両方を取ること、副作用も見ること、mock は本番の境界が既に外を切り離している所だけ。作った skill は、渡す前に1機能を通しで動かして確かめる。置き場は repo の中（Claude Code では `.claude/skills/verify-<app>/`）。
3. 対になる **`maintain-verification-skill`** は、機能の地図を保つ定期の仕事。機能ごとに読むだけのサブエージェントがソースから仕組みを説明し、1つのセッションが全機能を本物で動かし、確かめた直しだけを PR 1本にする。製品のコードは直さない。
4. 3本とも、名前で呼ばれたときだけ動く（`disable-model-invocation: true`）。

### `correct` に当たる、いまの Andon

5. **振り返り（[ADR-0028](0028-improvement-loop.md)）が同じ骨格を持つ。** 2回以上起きたつまずきだけを拾い、直す先を5段（設計・型、テスト・lint、決まった手順の確かめ、skill・指針、文面）で上から選ぶ。「根拠が別々の2件以上」「skill か文面を選ぶなら上の段で止められない理由」は command が確かめる。見つける役（読むだけ）と直す役（別の課題の担当）を分け、直しは PR として今のライン（レビュー・gate）を通る。
6. **振り返りは、このセルでまだ1回も回っていない。** command と skill はマージ済みだが、セルで1回通してルーチンを置く手（ADR-0028 の P1-3）が残っている。2026-11-20 に `andon retro collect --days 7` を読むだけで打つと、前の振り返りは無し、片付いた課題が 78 件、オーナーが打った文が 72 件、オーナーの手直しがあった課題が 32 件、レビューを受けた課題が 45 件でうち 16 件が2回以上のレビューを要った。
7. **`correct` にあって、振り返りに無いもの。**
   - 新しい検査が、過去の本物の誤りで落ちることを確かめる決まり。振り返りが切る直す課題の依頼書と PR の本文（ADR-0028 決めたこと 10）には無い。近いものは [ADR-0032](0032-shorten-time-to-merge.md) 決めたこと 6 の「移した節ごとに、わざと壊して落ちることを確かめる」で、Go へ移す節に限る。
   - 決まりと、それを守らせるものを対にした表。`AGENTS.md` は箇条書き 22 行で、検査や command を名指す行が 12、守らせるものが書かれていない行が 10。
   - 例外の書き方（当たる行に、理由・期限・オーナーの承認）。
   - オーナーが直したその場で回すこと。振り返りは毎朝のルーチンで、オーナーが打った文を次の朝に読む。
   - repo の側の入力。`correct` は commit・revert・指示のファイル・回避策のコメントを読む。振り返りが読むのは kanban の記録（手直し・gate・レビューの指摘・報告）とオーナーが打った文で、`AGENTS.md` の守らせるものの無い行や、コードの中の回避策のコメントは読まない。
8. **`AGENTS.md` には、文書の段で直した実例が溜まっている。** 2026-11-20 の1日で7行足された（PR #324 で6行、PR #330 で1行）。うち1行は「`tests/schema.sh` に新しい schema を足すときは8か所を触る」で、`correct` の一番上の段が言う「手で揃える一覧を、正が1つの形に替える」に当たる。
9. **オーナーの方針は同じ向き。** 「テストの前に、手前の手段（lint・動的な検証・型・レイヤ・計測・形式仕様・モデル検査）で防ぐ」（オーナー 2026-11-20。ADR-0032 決めたこと 7）。検査の仕分けから足す道具を決める題が、別の Chief Engineer の対話で並んで進んでいる（golangci-lint を CI に足すことなどを決めている途中）。標準の置き方「機械が確かめる形 → 文 → オーナーのレビュー」は [ADR-0006](0006-survey-fix-decide.md) 決めたこと 14 にある。

### `create-verification-skill` に当たる、いまの Andon

13. **利用者が触る面は、画面ではなく CLI と常駐の係。** 主な面は `andon`（`internal/cli/cli.go`）と `kanban`。ほかに、見回りの dispatcher、セルを起動する `andon boot`、hook 4本（`package/hooks/`）、セルの image とホストの `bootstrap`、Herdr App の mod（`package/host/`）がある。

### 反論で分かったこと（2026-11-20。読むだけの反論役がコードから示した。走らせてはいない）

オーナーが案を選ぶ前に、証拠・検証の skill・対応表の3つの案を別のコンテキストに壊させた。

- **証拠を command が `report.json` に書く形は成り立たない。** `andon issue report` は報告を作り直し、引き継ぐのは `pr`・`estimate`・`plan` だけ。command が書いた行は、次の報告で消える。記録のファイルを正にするしかない。
- **kanban に残す記録は、担当が手でも書ける。** 課題の `library/` は担当が書いてよい場所で、設定で止めていない。記録を gate が確かめても、強さは今の `report.json` と同じ自己申告。偽造できない証拠は、head の CI の結果だけ。
- **head が動くたびに、記録は古くなる。** 記録の commit と head の一致を求めると、レビューや CI の直しの commit のたびに全部撮り直しになる。CI を2回以上回した branch は直近 45 本のうち 29 本（[ADR-0032](0032-shorten-time-to-merge.md)）。
- **「誤りを戻すと落ちる」の記録は、head と同じ commit では撮れない。** 誤りを戻した状態は、未 commit の変更を足した木か、別の commit になる。
- **CI の検査の確かめは、表の行があるだけでは足りない。** 飛ばした検査も表に `skip` の行が出る。go の job には表が無く、テストの名前はログに出ない。文書だけの PR では `go test ./...` を飛ばして成功で終わる。
- **gate は全セルに届く。** CI の表の形は Andon の repo だけのもの。種類の無い pass を戻す決まりを gate に入れると、表を持たない案件の repo の担当も止まる。開けるなら、条件表の repo ごとのキーで開ける。
- **検査の切り離しは、シェル1つの中だけで効く。** `tests/lib/isolate.sh` は環境変数で切り離す。エージェントの Bash は呼び出しごとに環境が戻るので、手順を複数の呼び出しに分けると、後の呼び出しがセルの本物の kanban を見る。1機能の手順は、切り離しを自分で読むスクリプト1本にする必要がある。
- **repo の中の skill の置き場は、検査の範囲の表に無い。** `.claude/skills/` と `.agents/` の変更は、知らないパスとして一番重い側に倒れ、文だけの直しでも image の build まで走る。語の検査（`tests/words.sh`）と skill の検査（`tests/package.sh`）は、この置き場を見ない。
- **`andon retro collect` に `AGENTS.md` を読ませる形は、約束の原則に反する。** [contract.md](../contract.md) の原則 1 は、機械が Markdown を読む例外を足さないと決めている。表を読むのは振り返りの担当にする。手直し1件を再発に数える形も、「根拠は別々の2件以上」を確かめる command が断る。
- **`AGENTS.md` だけの PR では、足した検査が走らない。** `AGENTS.md` は文書扱いで、選ばれるのはいつも走る 6 本だけ。表の検査は、いつも走る側に置く必要がある。
- 当たらないと確かめた所: `AGENTS.md` の形を読む既存のコードは無く、表にしても壊れない。repo の中の skill は image・`go:embed` に影響しない。置き場は [ADR-0004](0004-project-layout.md) の決めと合う。
- 証明できなかった所: worktree の `.claude/skills/` を担当の Claude Code が読むか。Codex が repo の `.agents/skills` の symlink をたどるか。

## 前提（同意済み。番号）

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **オーナーが直したその場では回さない。毎朝の振り返りに任せる**（オーナー 2026-11-20）。`correct` は「人が直すたびに回す」と決めているが、Andon は今のままにする。理由: 1回の手直しから決まりや検査を足さない線（別々の2件以上）を保てる。振り返りはこのセルでまだ1回も回っていないので、まず回してから、遅いと感じたら決め直す。手で撃つ口は既にある。捨てた案: 「オーナーが同じ直しを2度目だと言ったら、Chief of Staff が朝を待たずに振り返りを手で撃つ」。「直されたことが `AGENTS.md` に既にある決まりで、守らせる検査が無ければ再発と数え、振り返りを待たずに直す課題に切る」（`correct` の形に一番近い。手直し1件を再発に数えることになる）。

2. **証拠は、走らせた記録を kanban に残す。gate は、報告の行が記録を指すときだけ中身を見る**（オーナー 2026-11-20）。新しい command が、渡された command を走らせ、出力・終了コード・その時の commit・commit していない変更の有無・時刻を、kanban の課題のフォルダに記録する。正は記録のファイルで、報告の `acceptance[]` の行は記録を id で指す（任意の欄を足す。約束のバージョンは上げない）。`andon issue ready` と gate は、行が記録を指しているとき、記録があり、終了コードが期待どおりであることを確かめる。記録の commit が head より古くても戻さず、gate の記録に古いことを出す。記録を指さない行（CI の検査の名前を書く今の形・画面の添付の URL・`manual`）は今のまま通す。
   理由: 足りないのは CI で回せない確かめの跡（事実 23）。CI の検査を名指す証拠（67 個のうち 63 個）は、gate が既に head の CI を待っていて、申告が嘘だった例は見つかっていない。記録を指す行だけを見る形なら、表も記録も持たない案件の repo の担当は止まらない。記録は検証の skill で動かした跡の置き場にもなる。
   受け入れること: 記録は担当が手でも書けるので、強さは自己申告のまま。減るのは「走らせずに pass と書く」ことで、出力が残るので Chief of Staff・オーナー・振り返りが後から読める。
   捨てた案: B「CI を正にする」（Andon の repo に限り、gate が head の CI のログで名指した検査の ok を確かめる。偽造できないが、go の job に検査ごとの表が要り、CI で回せない確かめはオーナーが見ることになる）。C「A と B の両方」。D「置き場の決まりを skill に書くだけ」（守られたかを誰も見ない）。反論の前の形「証拠を3種類に分け、種類の無い pass を gate が戻す」（command が書いた行が次の報告で消える。全セルの担当が止まる。head が動くたびに撮り直しになる）。

3. **依頼書が名指す受け入れ条件の行が報告に無ければ、command が断る**（オーナー 2026-11-20）。Chief of Staff が課題を切るとき、その課題が満たす受け入れ条件の番号を、機械が読める形で課題に持たせる。担当が「できた」と返す command（`andon issue ready`）は、その番号の行が報告に無ければ断る。番号を持たない課題は今のまま。
   理由: 受け入れ条件の欄は、書かなければ何も起きない（事実 24）。依頼書が受け入れ条件を名指す PR つきの課題 20 件のうち、5 件は報告に欄が無いままマージまで進んでいた。決めたこと 2 の記録も、行が無ければ見られない。
   捨てた案: 「Chief of Staff の手引きに、欄が無ければ戻すと1行足す」（文の決まりで、守られたかが機械で分からない）。「この題では扱わず、振り返りが繰り返しとして拾うのを待つ」。

4. **「セルで実測」を、repo の中の検証の skill にする。動かすのは、セルへ当てたあとに起動する独立の検証の担当**（オーナー 2026-11-20）。
   - **置き場と中身**: `.claude/skills/verify-andon/` に、手順（当てる・診断する・機能ごとに動かす・証拠を残す・片付ける・補助のスクリプト）と、機能の地図（機能ごとに、どう辿り着くか・どう動かすか・何が見えれば動いた証拠か・どのパスを変えたら動かすか・どの検査が既に見ているか）を置く。作るのは課題1本で、依頼書は pstack の `create-verification-skill` を手順として名指す。中身は Andon の語で書き、pstack の本文は写さない（前提 3）。渡す前に、1機能を通しで動かして確かめる。
   - **誰が・いつ**: Chief of Staff が、マージ済みの変更をセルへ当てたとき（`image/apply-main.sh apply`）に、検証の課題を1件切る。Claude の担当が skill を読み、当てた差分に当たる機能だけを本物で動かし、出力を決めたこと 2 の記録に残す。実装した担当とも Chief of Staff とも別のコンテキストで動く。kanban の課題なので、跡とコストが課題ごとに残る。新しい役・dispatcher の段・gate の条件は足さない。
   - **検証の担当もエージェントを起動しない**（前提 3）。本物のエージェントを起動して見る機能（担当の最初の turn・hook）は、skill を作る課題が機能ごとに「検証の担当だけで見られる」「Chief of Staff が試しの課題を起動し、検証の担当が画面を読む」「オーナーが見る」に仕分けて地図に書く。
   - **検証の担当は製品のコードを直さない。** 動かなかった機能は報告に書き、直す課題に切るのは Chief of Staff。
   - **反論を受けた細部**: 切り離した場所で動かす手順は、切り離しを自分で読むスクリプト1本にする（エージェントの Bash は呼び出しごとに環境が戻る）。検査の範囲の表（`tests/lib/scope.sh`・`image-scope.sh`）に `.claude/` の行を足し、文だけの直しで image の build が走らないようにする。語の検査（`tests/words.sh`）の対象に足す。
   理由: 担当はエージェントを起動できないので、skill の文・hook・テンプレートが本物でどう効くかは、マージしてセルへ当てたあとでないと確かめられない。`package/` に触れる PR は直近 7 日の 90 本のうち 37 本で、セルで動かした跡はほぼ残っていない（事実 23・26）。command の振る舞いには検査が 29 本あり、マージのあとに main の CI が落ちた課題は 61 件のうち 3 件、revert は 0 件（事実 25・27）。マージの前に足すと、マージまでの時間を縮める決定（[ADR-0032](0032-shorten-time-to-merge.md)）と逆を向く。独立の担当にするのはオーナーの案（「独立エージェントを用意してもいいかも」）で、Chief of Staff のコンテキストを検証で太らせない。
   捨てた案: V1「担当がマージの前に、切り離した場所で1機能を動かす」（今の検査と重なり、skill の文と hook に届かない）。V3「マージの前と当てたあとの両方」。V4「担当がマージの前に本物の Claude Code を起動する口を作る」（担当はエージェントを起動しない決まりを改めることになり、大きい）。「Chief of Staff が自分で動かす」（Chief Engineer の最初の推奨。オーナーが独立の担当を選んだ）。「検証専用の Claude Code のサブエージェントを repo に置く」（担当のサブエージェントは読むだけ、の決まりを改めることになる。Codex に口が無い。オーナーは形を Chief Engineer に任せた）。「レビュアーと同じく dispatcher が PR ごとに検証役を起動し、gate が結果を待つ」（dispatcher・gate・課題の一生のモデルに手が入り、PR ごとにエージェント1つ分のコストと待ちが増える）。

5. **機能の地図は、検証の担当が直す。定期の保守の仕事は足さない**（オーナー 2026-11-20）。検証の担当は、動かして見つけた地図と手順の食い違いを、その課題の PR 1本で直す。直してよいのは skill の置き場（`.claude/skills/verify-andon/`）の中だけ。加えて、いつも走る検査が、目次とファイルの対応と、手順が名指す command の実在を確かめる。
   理由: セルへ当てるたびに検証の担当が地図を読んで動かすので、食い違いはその場で見つかる。pstack の `maintain-verification-skill` の要点（確かめた直しだけを PR 1本に・製品のコードは直さない）を、検証の課題にそのまま持たせられる。検査をいつも走る側に置くのは、文書だけの PR では足した検査が選ばれないため（反論）。
   捨てた案: 「機能を変える PR が、同じ PR で地図も直す」（形式モデルと同じ決まり。担当の仕事が PR ごとに増える）。「kanban のルーチンが定期に保守の課題を足し、全機能を動かす」（当てた差分に当たらない機能の食い違いも拾えるが、定期のコストがかかる）。

6. **`AGENTS.md` を「決まり｜守らせるもの」の対にし、検査もする**（オーナー 2026-11-20）。守らせるものは、検査・command・hook・repo の設定の名前。無い行は「無し」と理由を書く。いつも走る検査が、名指された検査の実在を確かめる。振り返りの担当が表を読み（skill `retro` に手順を足す）、「無し」の行に当たる繰り返しを、検査や設計へ移す候補にする。誤りが起きようのなくなった行は消す。
   理由: 守らせるものの無い決まりが、どれかが見えるようになる。`AGENTS.md` は 22 行のうち 10 行に守らせるものが書かれておらず、1日で 7 行増えた（事実 7・8）。文に置いた標準が守られないときは、文を増やす前に機械の段へ下ろせないかを見る、という今の方針（[ADR-0006](0006-survey-fix-decide.md) 決めたこと 14）を、表が毎回思い出させる。
   反論を受けた形: 表を読むのは振り返りの担当で、`andon retro collect` は変えない（機械が Markdown を読む例外を足さない。[contract.md](../contract.md) の原則 1）。繰り返しの数え方は「別々の2件以上」のまま（決めたこと 1）。表の検査は、`AGENTS.md` だけの PR でも走る側に置く。
   捨てた案: 「各行に守らせるものを書き足すだけで、検査は足さない」（書かれた検査が消えても気づけない）。「持たない」。

7. **今ある「無し」の行は、一度だけ棚卸しする**（オーナー 2026-11-20）。`AGENTS.md` を表にする課題が、「無し」の行ごとに、どの段（設計・型、テスト・lint、決まった手順の確かめ）へ移せるかを候補として返す。どれを直す課題に切るかは、Chief of Staff が今の決まり（調べる課題の候補の扱い。[ADR-0006](0006-survey-fix-decide.md)）で決める。棚卸しはこの1回だけで、あとは振り返りに任せる（前提 2）。
   理由: 振り返りは新しく2回起きたものだけを拾うので、今ある行は、また誤りが起きるまで動かない。今ある行は、どれも誤りが起きたあとに足された行。Chief Engineer の読みでは、無い 10 行のうち 4〜5 行は検査か設計へ移せる（例: 「`go:embed` を足したら `image/Dockerfile` も直す」「ADR を足したら決定の記録も足す」は検査にできる。「報告を書き直すとレビュー依頼が消えるので打ち直す」は command の側で無くせる。「`tests/schema.sh` に schema を足すときは8か所を触る」は正を1か所にできる）。見立てで、仕分けは課題が1行ずつ確かめる。
   捨てた案: 「表にして『無し』と理由を書くところまで。移すのは振り返りが繰り返しを拾ったときだけ」。

8. **繰り返しを止めるために検査を足す直しは、誤りを戻すと検査が落ちることを記録で示す**（オーナー 2026-11-20）。振り返りと棚卸し（決めたこと 7）が切る直す課題のうち、検査を足すものが対象。依頼書の受け入れ条件に「誤りを戻すと検査が落ちる」を1つ入れ、決めたこと 2 の command の「落ちることを期待する」形で撮った記録を証拠にする。この記録は、誤りを戻した木（commit していない変更がある木）で撮ってよい。行が無ければ command が断る（決めたこと 3）。
   理由: 落ちない検査は、足しても何も止めない。今ある近い文（受け入れ条件のテストは先に落ちるのを確かめる・Go へ移した節はわざと壊して確かめる）は文の決まりで、振り返りが切る直す課題には入っていない。
   捨てた案: 「検査を足す PR すべてに、担当の skill とレビュアーの観点で求める」（検査を足した PR かを機械で見分けられず文の決まりになる。全セルの担当に届く）。「今のまま。command に形は持たせるが、使うかは担当に任せる」。

9. **検証の課題は、当てた差分が地図に当たるときだけ切る。同時に動くのは1つ**（オーナー 2026-11-20。決めたこと 4 の「いつ」を細かくする）。Chief of Staff は、セルへ当てたとき、当てた差分が機能の地図の「どのパスを変えたら動かすか」に当たるときだけ検証の課題を切る。検証の課題が動いている間は切らず、次の回が、前の検証が見た commit からの差分をまとめて見る。検証の担当は、見た commit の範囲を報告に書く。
   理由: このセルでは、andon の PR がマージされるたびに Chief of Staff がセルへ当てる決まり。マージは直近 7 日で 90 本（1日約 13 本）、`package/` に触れるものは 37 本（1日約 5 本）で、当てるたびに切ると検証の担当が1日に何度も起動される。並行の上限は 4（事実 26・28）。
   捨てた案: 「kanban のルーチンが毎朝1件足し、前回からの差分をまとめて見る」（コストは1日1回で Chief of Staff の手も要らないが、壊れが分かるのが最長で翌朝）。「頻度を決めず、Chief of Staff かオーナーが要ると見たときだけ切る」（切り忘れると跡が残らない）。

10. **[ADR-0021](0021-pstack-in-cell.md) の「やらないこと」を改める**（2026-11-20。Chief Engineer が推奨案で仮に決め、オーナーが最後の確かめで「決めた」と言った）。 pstack の `create-verification-skill` は、検証の skill を作る課題が手順として1回読む（決めたこと 4）。`correct` と `maintain-verification-skill` は工程に入れず、要点だけを Andon の仕組みに移した（決めたこと 5・6・8）。画面の確かめ（[ADR-0018](0018-screen-check-tooling.md)）と気づきの蒸留は今のまま。担当は skill を Skill tool で呼ばず、依頼書が名指した SKILL.md を読んで従う（3本とも、名指されたときだけ読まれる設定になっている。事実 4）。
    理由: 前提 2・3 と決めたこと 4 から出る帰結。ADR-0021 は「Andon が既に持つものに替えない」としてこの2本を外したが、検証の skill を作る手順は Andon に無かった。

11. **記録と検証の skill の細部**（2026-11-20。Chief Engineer が推奨案で仮に決め、オーナーが最後の確かめで「決めた」と言った）。
    細部:
    - 記録の置き場は、kanban の課題の `library/` の下の新しいフォルダ（今ある `library/evidence/` は別の用途に使われているので、名前を分ける）。記録1件は、約束の JSON 1つと出力のファイル1つ。形の正は `schema/` に足す。出力は上限で切って残す。command と置き場の名前は実装が決める。
    - 通ることを期待する記録は、commit していない変更が無い木で撮ったものだけを `andon issue ready` と gate が通す。落ちることを期待する記録（決めたこと 8）だけ、commit していない変更があってよい。
    - 記録の command は、課題の一生の動きに command を1つ足すので、状態の定義（`process/states/issue.yaml`）とモデルの対応表（`model/`）も同じ PR で直す。
    - 検証の skill は、名指されたときだけ読まれる設定にする（Andon の repo で働くほかの担当のコンテキストに載せない）。検証の課題の依頼書が SKILL.md のパスを名指す。Codex 向けの置き場は [ADR-0004](0004-project-layout.md) のとおり symlink。
    - 検証の skill の補助のスクリプト1本が、commit の範囲を受け取り、差分が当たる機能の名前を出す。Chief of Staff はこれで検証の課題を切るかを決める（決めたこと 9）。
    - `.claude/skills/` は、gate の条件表で自動でマージできる側（`package/gate.json`）。検証の担当が出す地図の直しの PR は、オーナーを待たない。

## やらないこと（範囲の外。理由）

- **`correct` を工程に入れない。オーナーが直すたびに回さない。** 同じ誤りを見つけて直すループは振り返りの1本だけ（前提 2・決めたこと 1）。振り返りの数え方（別々の2件以上）・頻度・直す課題の上限も変えない。
- **`maintain-verification-skill` を定期の仕事にしない。** 地図は検証の担当がその場で直す（決めたこと 5）。
- **マージの前の検証を足さない。** 担当がマージの前に動かす手順（V1）、担当が本物のエージェントを起動する口（V4）、dispatcher が PR ごとに検証役を起動して gate が待つ形は、どれも足さない（決めたこと 4）。gate の判定の条件は、決めたこと 2・3 の2つのほかは変えない。
- **証拠を CI のログと機械で照らさない。** 記録の強さは自己申告のまま（決めたこと 2 の捨てた案 B）。
- **`andon retro collect` に `AGENTS.md` を読ませない。** 表を読むのは振り返りの担当（決めたこと 6）。
- **検査の例外の書き方（理由・期限・オーナーの承認）は、この題で決めない**（オーナー 2026-11-20）。行ごとの例外は今シェルの静的解析の注釈 2 か所だけ。[ADR-0034](0034-prevention-before-tests.md) が golangci-lint の 2 段目で「除いた呼び出しには理由を1行書く」と決めている。期限とオーナーの承認を足すかは、開いている問い 1。
- **ほかのセルの案件の repo には広げない**（前提 5）。検証の skill と `AGENTS.md` の表は Andon の repo だけ。記録の command と `andon issue ready` の守りはパッケージに入るので全セルに届くが、記録を指さない報告と、受け入れ条件の番号を持たない課題は今のまま通る。
- **pstack の本文を repo に写さない・訳さない**（前提 3）。pstack の `create-formal-verification-skill` も使わない（形式モデルは [ADR-0025](0025-formal-model-in-repo.md) が既に持つ）。
  - **改め（2026-11-20。[ADR-0038](0038-statechart-in-chief-engineer-design.md) の決めたこと 9・21）**: 調べる課題で 1 回だけ走らせて報告する試しは除く。repo に取り入れないことは変えない。
- **検証の担当は製品のコードを直さない。エージェントも起動しない**（決めたこと 4）。

## 受け入れ条件

継ぎ目は3つ。command の振る舞いは、今ある Go のテスト（`internal/`。一時の kanban）と場面の検査（`tests/andon-*.sh`）で見る。文書と skill の形は、文書だけの PR でも走る側の字面の検査で見る。本物のセルでしか見られないもの（検証の skill そのもの・skill の文の効き）は、記録の command で撮った記録を証拠にし、オーナーが見る（`manual`）と書く。

1. **走らせた記録が残る**（決めたこと 2・11）。成功する command を渡すと、課題のフォルダに記録（終了コード・commit・commit していない変更の有無・時刻・出力のパス）が書かれ、schema を通る。失敗する command では、終了コードが 0 でない記録になる。証拠: `go test ./internal/... -run '<足したテストの名前>'` の出力と、`bash tests/schema.sh` の出力に記録の schema の ok の行。
2. **落ちることを期待する記録**（決めたこと 8・11）。落ちることを期待する形で、落ちる command は期待どおりの記録になる。通る command を渡すと、記録の command が 0 でない終了コードで終わる。証拠: 同じ Go のテストの出力。
3. **`andon issue ready` と gate が記録を見る**（決めたこと 2・11）。報告の行が指す記録が無い・終了コードが期待と違う・通ることを期待する記録が commit していない変更のある木で撮られている、の3通りで `andon issue ready` が 0 でない終了コードで終わり、理由を出す。記録を指さない行だけの報告は、今までどおり通る。記録の commit が PR の head より古いとき、gate は戻さず、判定の記録に古いことを出す。証拠: Go のテストの出力と、`bash tests/andon-gate.sh` の出力に足した場面の ok の行。
4. **受け入れ条件の行が無い報告を断る**（決めたこと 3）。受け入れ条件の番号を持つ課題で、その番号の行が報告に無いまま `andon issue ready` を打つと断られ、足りない番号が出る。番号を持たない課題は通る。証拠: Go のテストの出力。
5. **検証の skill の形を検査が見る**（決めたこと 4・5）。`.claude/skills/verify-andon/` があり、検査が、目次とファイルの対応と、手順が名指す command の実在を見る。地図のファイルを1つ消すか、無い command を名指すと検査が落ちる。この検査は、文書だけを変えた PR でも走る。証拠: 検査の出力と、落ちることを期待する記録（受け入れ条件 2 の形）。
6. **差分から機能を引く**（決めたこと 9・11）。補助のスクリプトに commit の範囲を渡すと、差分が当たる機能の名前が出る。当たらない範囲では何も出ず、終了コード 0 で終わる。証拠: 検査の出力（当たる範囲と当たらない範囲の2通り）。
7. **検証の skill を通しで動かす**（決めたこと 4）。skill を作る課題が、1機能を手順どおりにセルの本物で動かし、片付けまで済ませる。動かす前と後で、セルの本物の kanban に検証の跡が残っていない。証拠: 記録の command で撮った記録。オーナーが見る（`manual`）。
8. **検証の担当が skill を読んで動かす**（決めたこと 4・9）。最初の検証の課題で、担当が依頼書の名指す SKILL.md を読み、当たる機能を動かし、見た commit の範囲を報告に書く。証拠: その課題の報告と記録。オーナーが見る（`manual`）。担当の Claude Code が worktree の `.claude/skills/` を自分で読むかは実測していないので、依頼書がパスを名指す道を既定にする。
9. **文だけの直しで重い検査が走らない**（決めたこと 4）。`.claude/skills/verify-andon/` の文だけを変えた差分で、image を build する検査が選ばれず、語の検査が選ばれる。証拠: `bash tests/ci.sh` の出力に、足した場合の ok の行。
10. **`AGENTS.md` の表を検査が見る**（決めたこと 6）。`AGENTS.md` の決まりが全部「決まり｜守らせるもの」の対で、守らせるものが検査・command・hook・設定の名前か「無し」と理由になっている。対になっていない行と、名指した検査のファイルが無い行で検査が落ちる。`AGENTS.md` だけを変えた PR でもこの検査が走る。証拠: 検査の出力、落ちることを期待する記録、`bash tests/ci.sh` の出力。
11. **棚卸しの候補が返る**（決めたこと 7）。候補の一覧に、「無し」の行ごとに1件、移す先の段か「移せない」と理由がある。証拠: 候補の一覧の件数が、表の「無し」の行の数と同じ。
12. **振り返りの手順**（決めたこと 6・8）。skill `retro` に、`AGENTS.md` の表を読む手順と、検査を足す直す課題の依頼書に「誤りを戻すと検査が落ちる」の受け入れ条件を入れる手順がある。証拠: `bash tests/package.sh` の出力。効きは、直したあとの最初の振り返りの報告でオーナーが見る（`manual`）。
13. **Chief of Staff の手引き**（決めたこと 3・9）。Chief of Staff の skill に、課題を切るとき受け入れ条件の番号を持たせる手順と、セルへ当てたあと検証の課題を切る条件（差分が地図に当たる・同時に1つ・前の検証が見た commit から）がある。証拠: `bash tests/package.sh` の出力。効きは、当てたあとに検証の課題が kanban に切られていることをオーナーが見る（`manual`）。
