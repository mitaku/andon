## 問題（人の言葉で。言い直しの段落）

人（2026-11-19、Chief of Staff へ貼った文書の要点）:

- 「Andon にはすでに自動マージとプロンプト改善の仕組みがある。これを強化し、プロンプト・スキルが実行結果から継続的に・安全に改善されるループにしたい。」
- 「基本方針: 改善を『PR』として扱う。改善エージェントがプロンプトを直接書き換えることはしない。」
- 流れは ①記録（版と結果）→ ②振り返り（定期）→ ③修正先の振り分け → ④評価（過去の課題のリプレイ）→ ⑤カナリア → ⑥昇格と自動ロールバック。
- ① で run ごとに残したいもの: 識別子と時刻・使ったプロンプトと skill の版・モデルと推論レベル・元の課題・結果（merged／rejected／reverted／ci_failed／abandoned）・自動マージの判定と理由・コスト（ターン数・トークン・所要時間）・人の修正（「一番価値が高い」）・マージ後の revert や障害との紐付け。秘密は記録に残さない。
- ② の採用条件: 「同じパターンが 2 回以上起きていること。1 回だけの事象から過剰なガードを足さない。」
- ③ の順（効き目が確かな順）: 設計や型で起きようのない形にする → lint やテストにして CI で検出する → hook など決まった手順のチェックにする → skill を直す → プロンプトの文面（最後の手段）。「削除」も改善の提案として出す。
- ④ の採点役は、改善案を作ったエージェントと別のコンテキストにする。
- 指標: 「『マージされた率』だけを追わない（無難で小さい PR ばかりになる）。revert とマージ後の障害を必ず指標に含める。」
- 今回の範囲: 現状の調査、Phase 0（記録）、Phase 1（振り返りと改善案の PR。自動マージはしない）。Phase 2（評価セットとリプレイ・別コンテキストの採点・カナリア・自動ロールバック）と Phase 3（危険の低い改善だけを今あるゲートで自動マージ）は設計のメモだけ。
- やらないこと: 改善エージェント自身のプロンプトを自動の改善の対象にすること。プロンプトや skill の変更の自動マージ（Phase 3 まで）。今ある自動マージの作り変え。今ある記録の削除や移行。
- 止まって人に確かめる点: 今ある仕組みが方針と衝突する・プロンプトと skill が版管理されておらず保存の構造を変える必要がある・記録に個人情報や顧客のデータが入りうる・今あるデータの移行や削除が要る。

言い直し（人が 2026-11-19 に「合っている」と答えた）: Andon は、課題を流すライン（依頼書 → 担当 → レビュー → ゲート → マージ）は回っている。一方、ラインそのもの（skill・プロファイル・hook・テスト・ゲート）を実行の結果から直す外側のループは、設計と受け口だけがあり、読んで直す所が無い。人の文書が言う「既にあるプロンプト改善の仕組み」は、この設計（振り返り）と受け口（`corrections.json`・報告の `## Remember`・日報・auto memory・`andon measure`）のこと。困りごとは2つ。

1. **後から辿れない。** ある課題が「どの版の skill・どのモデルと effort で動き、どう終わり、人がどこを直し、マージ後にどうなったか」を1か所で読めない。版はそもそも残っていない。
2. **読んで直す仕事が無い。** 記録から、2回以上起きたつまずきだけを拾い、効き目の確かな順に振り分けて PR にする仕事が無い。直しは人が気づいたときに頼むだけになっている。

人が言い直しに足したこと（2026-11-19）: 「後回しグセがついているように思う」。指す先はラインの全体（人が同じ日に選んだ）: 担当は見つけたことを報告の `## Next` と `## Remember` に回して終え、読む側の仕組みは「設計だけ」「読む側はあとで決める」と決めてきた。実測したセルでは、2日で未処理が 103 件溜まり、週1のトリアージは置かれていない（事実 18）。この題では、受け口をもう1つ足して終える形にしない。

今回決めるのは、この2つを埋める形。課題ごとの記録に版を紐づけて1件で読めるようにする（Phase 0）。振り返りを、手で打てて定期でも回せる仕事にし、改善案を人がマージする PR として出す（Phase 1）。リプレイの評価・カナリア・自動ロールバック・改善の自動マージは、今回は設計のメモだけにする。

人の文書と変える点（人が 2026-11-19 に言い直しと一緒に認めた）: 文書は実装まで1つのセッションでやる形で書かれているが、Andon では Chief Engineer は実装せず、設計を文書にして Chief of Staff が課題に切る。調査は別のファイル（`docs/improvement-loop/SURVEY.md`）にせず、この ADR の「読んで分かった事実」に入れる。

## 読んで分かった事実（2026-11-19。main `8309e18` と、Andon を開発しているセルで実測）

### 実行（run）の一生

1. Andon で「run」に当たる単位は**課題**。人の依頼を Chief of Staff が依頼書に切り（`kanban add`）、`andon issue start` が担当の端末を起動する。担当は自分の worktree で働いて PR を出し、`andon issue report`・`ready` で台帳に返す。dispatcher がレビュアー（実装と別ブランド）を起動し、ゲート（`andon gate`）を回し、条件が揃えばマージして `andon issue finish` で片付ける。レビュアーは親の課題の子（`<id>-r<k>`）として別の課題になる。差し戻しのあとの直しは同じ課題の中で続く。
2. 役は Chief of Staff・Chief Engineer・担当・レビュアー。ランタイムは Claude Code と Codex の2つ。起動行はプロファイル（`package/templates/*.md` の8枚）の `command:` にあり、モデルと effort はそこで固定される（例: 既定の担当は `claude --model opus --effort high`、レビュアーの既定は `codex` に `-m <モデル> -c model_reasoning_effort="max"`）。課題ごとに選べるのは `issue.yaml` の `profile` の名前だけ。
3. 「yard」は Andon の前身（仮設の工場）の名前で、repo に残るのは用語の対応表・schema の説明文・経緯の文書だけ。今の Andon と境界を持つ別の仕組みは無い。

### 自動マージの判定

4. 判定は `internal/gate/decide.go`。まず差分からレベル A／B／C を決める（`package/gate.json` の条件表: 触ったパス・追加行のパターン・行数 500／1000。報告の `acceptance[]` の `manual` と `risk.one_way` で上がる）。次に順に見る: 台帳と PR の食い違い → 委譲の範囲 → 検査の失敗 → GitHub の checks → 独立レビュー（レベル B／C か `review: on` で必須。Must fix の残り・見送り）→ 受け入れ条件 → 画面の添付 → checks の待ち。結果は `approve`／`fix`／`wait`／`needs_human` の4つ。
5. **スコアは無い。** 理由に当たるのは記録の `tier_reasons` と `reasons`（1行ずつの文）。記録は課題の `library/gate/<head の SHA>.json`（`at`・`pr`・`head`・`tier`・`tier_reasons`・`changed_lines`・`checks[]`・`github_checks`・`review`・`acceptance`・`delegation`・`decision`・`reasons`・`merged`）。
6. マージに進むのは `approve` かつ課題の `merge: auto` かつ委譲（`project.json` の `delegation.merge`）の範囲内のときだけ。Andon 自身の repo の委譲は型 `andon` でレベル B まで。条件表のレベルは次のとおり。
   - **レベル C（いつも人がマージする）**: `package/skills/**`・`package/templates/**`・`package/hooks/**`・`package/gate.json`・`package/settings.json`・`package/codex.rules`・`package/environment.md`・`package/writing.md`・`**/AGENTS.md`・`.github/workflows/**`・`image/**` など（[design.md](../design.md) §1.10 の `line-change`: 「Andon のパッケージは常に人」）。
   - **レベル B**: `internal/**`・`cmd/**`・`schema/**`・`package/lib/**`・`**/*.sh`、それに A の許可リストに無いパス（`REVIEW.md` など）。
   - **レベル A**: `docs/**`・`tests/**`・`README*`・`CHANGELOG.md`。
   A と B の PR は、課題が `merge: auto` なら自動でマージされる。

### プロンプトと skill の置き場と版

7. エージェントの振る舞いを決める文は、次の所にある。
   - Andon の repo の `package/`: 役の skill 7本（`skills/<名>/SKILL.md`。Chief of Staff の手引き `playbooks/` 10本を含む）・プロファイル 8枚（`templates/`）・全役が毎セッション読む `environment.md` と `writing.md`・hook 4本・`settings.json`（managed settings）・`codex.rules`・`gate.json`。
   - 案件の repo: `AGENTS.md`（担当の指針）と `REVIEW.md`（レビュアーの観点）。
   - セルの repo: `AGENTS.local.md`・`AGENTS.worker.md`・`gate.local.json`・`templates.local/`・外の skill の一覧（`local/gh-skills.txt`）。
   - 外から入るもの: `gh skill install` で入れる skill（版は固定せず、boot のたびに最新へ上がる）と、Claude Code の plugin（自動更新）。Claude Code と Codex の本体の版。
   - auto memory の目録（`/workspace/memory/MEMORY.md`）: Claude Code の全部のセッションに入る。git では追っておらず、トリアージが仕分けたファイルを消す（[ADR-0020](0020-auto-memory-as-intake.md)）。
8. `package/` は image の build で `/opt/andon` に写される（`image/Dockerfile`）。Claude Code は `--plugin-dir /opt/andon` と `--append-system-prompt-file /opt/andon/skills/<役>/SKILL.md` で読み、Codex は boot が張る symlink で読む。役の skill は起動のときに system prompt に入り、動いているセッションの間は変わらない。hook・`andon`・Chief of Staff の手引きは呼ばれるたびに実体を読むので、課題の途中でパッケージが当て直されると、起動のときと違う版になる（[ADR-0027](0027-apply-package-without-rebuild.md) の事実 7）。
9. **版は git で管理されているが、動いているセルが「どの commit の `package/` か」を run に結びつける印が無い。** `andon` に版を出す口は無く、`/opt/andon` に版のファイルも無い。image の元の commit は `kanban --version` で読めるだけ。実測したセルの `/opt/andon` は main より 46 commit 古く、`package/` の約30ファイルが食い違っていた。[ADR-0027](0027-apply-package-without-rebuild.md) は、1つの commit から `/opt/andon` を上書きして「どの commit から当てたか」の記録を1枚残すと決めているが、道具はまだ実装の途中。
10. 課題の記録に残るのは `issue.yaml` の `profile`（名前）と `session`（Claude Code のセッション id）だけ。プロファイルの中身（モデル・effort）は版で変わるが、その課題が動いたときの値は残らない。`session` は1つだけで、新しいセッションでの起動し直しと、レビュアーのブランドの切り替えで上書きされる。Chief of Staff と Codex は、起動のときにセッション id が決まらない。

    | 欄 | 今 | どこから取れるか |
    |---|---|---|
    | 識別子・開始と終了の時刻 | **ある（間接）** | 課題の id。時刻は `log.jsonl` の `status` の移りから数える。専用の欄は無い |

13. セッションログ（Claude Code は `~/.claude/projects/`、Codex は `~/.codex/sessions/`）はセルの named volume にあり、コンテナを作り直しても残る。`package/settings.json` に `cleanupPeriodDays` の指定は無く、Claude Code の既定（30日）で消える。台帳と memory と wiki はセルの repo（`/workspace`）にあり、台帳と memory は git で追っていない。
14. 実測したセルの2日分（課題 30 件・PR 15 本）: 自動マージ率 0%（15 本ともパッケージか指針に触れてレベル C か、`merge: person`）。ゲートの差し戻し率 100%（`fix` 2・`needs_human` 11）。`corrections.json` は 20 件、うち手直しありが 10 件。日報は 0 件。
15. `corrections.json` には意味の無い手直しが混ざる。例: ゲートの問いの推奨案「人が PR を読んでマージする」に対し、答え「人がマージした（PR の URL）」が `override` として数えられる。[contract.md](../contract.md) §14 は「多めに拾い、少なく拾わない。振り返りが読んで捨てる」と決めている。

### 今ある「実行の結果から学ぶ」口

16. **振り返り（retro）は名前だけ。** [design.md](../design.md) §1.4 のアウターループ・用語集・問いの `from: retro`（schema の enum）・ワークストリーム「ふりかえり（Retrospective）」（`process/workstreams/retrospective.yaml`。名前と目的だけ）はあるが、記録を読んで PR を出す仕事は無い（[ADR-0007](0007-interim-gap-inventory.md) の R8）。
17. 方針は決まっている。振り返りの出口は PR で、skill を直接は書き換えない。同じ手直しが2度あったときだけ直す（[design.md](../design.md) §1.9 の 5・(b)）。標準は「機械が確かめる形（schema・command の照合・ゲートの条件表・テスト）→ 文（skill・依頼書の雛形・`AGENTS.md`）→ 人のレビュー」の順に置く（[ADR-0006](0006-survey-fix-decide.md) 決めたこと 14）。案件の repo の直しは Chief of Staff の判断、Andon のパッケージの直しは人。
18. **トリアージ**（`andon triage collect`／`apply`）は実装済み。報告の `## Next`・見送り・`## Remember`・`For AGENTS.md:`・memory・課題に切られていない信号を集め、課題に切る・閉じる・人へ回すを決める。`corrections.json`・ゲートの記録・日報は読まない。週1のルーチンは例のファイルがあるだけで、実測したセルには置かれておらず、回っていない。2日で未処理が 103 件（`remember` 51・`next` 40・`memory` 7・ほか 5）溜まっていた。`next` の多くは「マージ後に片付ける」のような、もう済んだ手順の行。
19. **auto memory**（[ADR-0020](0020-auto-memory-as-intake.md)）と **日報**（[ADR-0024](0024-worker-journal.md)）は受け口。memory はトリアージが wiki か repo へ振る。日報は「読む側は、たまった日報を見てから考える」と決めてあり、読む手順は無い。
20. **`andon measure`** は読むだけの command。待ち時間・流量・PR あたりの人の介在回数・自動マージ率・ゲートの差し戻し率・revert の数・レベル別の手直しの数・見積もりと実働の比・課題ごとのトークンを数える。出力するだけで、保存も判定への利用もしない。
21. skill とプロンプトの文面を検査するテストは、古い語が戻っていないか（`tests/words.sh`）と、形と存在（`tests/package.sh`: skill の名前・例が schema に通るか・Chief of Staff の skill が 10KB 以下か）だけ。文面の質は見ていない。2026-11-19 に1度、人の依頼で skill とプロンプトの監査を調べる課題として流した（古いパス・AI 用の文に残る人向けの経緯・effort の指定漏れが見つかった）。
22. 定期の仕事を足す口は2つ。課題を1件足す仕事は台帳のルーチン（`routines/<名>.yaml`）。きっかけは時刻（`schedule`。dispatcher の毎巡の `kanban tick` が撃つ）と、課題があるステータスに入ったとき（`on`）の2つで、`kanban routine run <名>` で手でも撃てる。`open` は同時に開いていてよい課題の数、`paused` は止める印。ほかのルーチンのあとに撃つ、という順序の指定は無い。機械の仕事は dispatcher の巡に段を足す（[ADR-0017](0017-process-definitions.md) 決めたこと 7: ルーチンに「コマンドを打つ」種類は足さない）。
23. 評価（リプレイ・採点）・カナリア・自動ロールバックは無い。[design.md](../design.md) §1.9 の 4 は「judge による run の採点・replay・Pareto は最初の版に入れない。記録の形を先に揃え、必要になったら記録から作る」と決めている。パッケージの置き場はセルに1つ（`/opt/andon`）で、課題ごとに違う版の skill を当てる口は無い。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **2026-11-19 振り返りは、ルーチンが足す「調べる課題」として担当が回す（案 B）。** 読むだけの command が期間の記録を1つにまとめる。担当はそれを読んで繰り返しを拾い、候補（根拠の課題2件以上・直す先・直し方）を返す。command が「根拠が2件以上」を確かめる。Chief of Staff が候補から、上限つきで直す課題に切る。直す PR は今あるライン（独立レビュー・ゲート）を通り、Andon のパッケージに触れる PR は人がマージする。
   理由: 繰り返しを見つけるのは横断の読みで、項目1件ずつの仕分け（トリアージ）とは別の仕事。「根拠が2件以上」を機械で確かめられるので、1回だけの出来事から PR が出ない。出口は今ある「調べる → 切る → 直す PR → ゲート」（[ADR-0006](0006-survey-fix-decide.md)）にそのまま乗り、新しい役も、新しいマージの道も要らない（前提 5）。
   捨てた案: A トリアージを広げる（新しい仕事を作らないが、仕分けと横断のパターン探しが混ざり、量に埋もれてまた溜まる）／C 片付けのたびに dispatcher が過去と突き合わせる（定期の山を作らないが、機械の鍵で合うのは同じファイル・同じ理由の文だけで、言い方の違う同じ手直しを拾えない）／B に C を足す（一番大きい。まず B を回して、機械の鍵で合うものがどれだけあるかを見てから）。
2. **2026-11-19 直す先の範囲は「選んで広げる」。** 仕組みはどのセルでも回る。直す先は、Andon のパッケージ（skill・プロファイル・hook・設定・ゲートの条件表）と、案件の repo のテスト・`AGENTS.md`・`REVIEW.md`。andon の repo を持たないセルで Andon のパッケージの直しが候補に出たら、直す課題ではなく人の課題にする。最初の実測は Andon を開発するセルだけで行う。
   理由: 今の設計が、アウターループの出口を「案件の repo のテスト・観点・指針（Chief of Staff の判断）」と「Andon のパッケージ（人）」の2つに分けている（事実 17）。「テストを文面より先に」という振り分けの順を使うには、直す先にテストと指針が入っている必要がある。
   捨てた案: 保つ（Andon のパッケージだけ。案件のセルの記録が読まれないまま残る）／広げる（セルの設定・依頼書の切り方・プロファイルの選び方・委譲の提案まで。人の持ち物に触れ、範囲が大きい）／減らす（skill と文面だけ。振り分けの順が使えなくなる）。
3. **2026-11-19 版は「commit と食い違いの印」で残す。** 担当を起動するたび（起動し直しも）に、課題のフォルダへ次を1件足す: Andon のパッケージの commit・セルの repo の commit・案件の repo の commit・プロファイルの名前と実際の起動行（モデルと effort を含む）・ハーネス（Claude Code か Codex）の版・外から入る skill と plugin の版。取れない値は null と明示する。セルの中身が commit と食い違うとき（手で上書きした・commit していない変更がある）は「復元できない」の印を付ける。当時の文の復元は git から行う。
   理由: エージェントが読む文のほとんどは git にあるので、commit が分かれば復元できる（git の外にあるものの扱いは決めたこと 14 の 5）。足りないのは commit を課題に結びつける印だけ（事実 9・10）。食い違いの印があれば、復元できない課題を振り返りが根拠から外せる。
   捨てた案: 読まれる文ごとのハッシュも残す（どの文が変わった課題かを機械で分けられるが、記録と実装が重い。commit の差分から同じことが分かる）／文そのものを課題のフォルダに写す（外の skill も含めて確実に復元できるが、課題ごとに数十 KB 以上が台帳に溜まる）。
   受け入れること: 外から入る skill と plugin は版を固定していないので、残るのは入っていた版の名前だけで、当時の文は外の repo の履歴から辿る。`--model opus` のような別名が実際にどのモデルになったかは、起動のときには分からない。片付けのときにセッションログから読んで足す（決めたこと 7）。
4. **2026-11-19 人が端末で打った文を、振り返りの入力にする。** 振り返りの command が、期間のセッションログ（Chief of Staff・Chief Engineer・担当）から、人が打った文だけを印で抜き出す。意味を読むのは振り返りの担当で、command は文を解析しない。抜き出した文はセルの中にだけ置き、PR には写さない（前提 7）。セッションログの保持期間は延ばさない。
   理由: 人がいちばん多く直しているのは Chief of Staff との会話で、`corrections.json` の3種には入らない（事実 12）。前に見送った理由は「文の解析になる」だったが、Claude Code のセッションログは人が打った文に印を付けている（実測: `promptSource` が `typed`、`origin.kind` が `human`。Chief of Staff の1セッションで、人が打った文 14 件・機械が送った文 38 件・道具の結果 190 件を、文を読まずに分けられた）。
   捨てた案: 役の自己申告だけ（人に直された役が memory か日報に書く。今のまま。書かれなかった手直しが消える）／拾わない（一番小さいが、人がいちばん多く直している場所が入らない）／抜いた上で保持を 90 日などに延ばす（後から会話を辿れるが、人とのやり取りの全文がセルに長く残る。週1で回すなら 30 日で足りる）。
   受け入れること: Codex のセッションの記録に同じ印があるかは確かめていない。無ければ Codex の端末の分は抜かない。
   → 同じ日に、抜く規則を決めたこと 14 の 1 で改めた（印だけでは人の文が分かれなかった）。
5. **2026-11-19 振り返りは週1で回し、1回に切る直す課題は3件まで。** ルーチンが毎週、トリアージのあとに振り返りの課題を1件足す。人と Chief of Staff は手でも打てる。止めるのはルーチンの `paused`。読むのは直近 14 日に片付いた課題。候補のうち直す課題に切るのは1回3件までで、残りは理由を書いて捨てる。次回へ持ち越す置き場は作らない（同じことがまた起きれば、次回の 14 日の中でまた拾う）。Andon を開発するセルに、トリアージと振り返りのルーチンを置く（人の go を兼ねる）。
   理由: 14 日は、先週の1回と今週の1回を合わせて「2回」と数えるための重なり。上限は、人がマージする PR（パッケージに触れる直しはレベル C）の数を週3本に抑えるため。持ち越しを作らないのは前提 6。
   捨てた案: 毎日・上限1件（直しまでが早いが、振り返りの課題のコストが毎日かかり、人がマージする PR が毎日来る）／片付いた課題が 20 件溜まるごと（流量に合うが、ルーチンは時刻で撃つ仕組みなので、件数を数えて課題を足す段を dispatcher に足すことになる）／手で打つだけ（一番軽いが、後回しになる）。
   → 同じ日に、頻度・読む期間・上限を決めたこと 13 で改めた（毎日・7 日・2件）。「トリアージのあとに」は、ルーチンに順序の指定が無い（事実 22）ので取り下げる。振り返りは台帳の項目に手を入れない（決めたこと 11）ので、順序は要らない。持ち越しを作らないこと、手で打てること、`paused` で止めること、ルーチンを置く go はそのまま。
6. **2026-11-19 直しが効いたかは、次の振り返りが再発を数えて確かめる。** 振り返りは毎回、前の振り返りが切った直しのうちマージ済みのものについて、マージのあとに同じパターンがまた起きたかを数えて報告する。再発したら、文を足さず、効き目の確かな段（テスト・hook・設計）へ振り分け直すか、効かなかった文を削る候補にする。
   理由: リプレイの評価とカナリアは今回入れないので、確かめる手が無いと、効かない文が skill に足され続ける。前の振り返りが切った直しとマージの日は台帳から辿れるので、新しい仕組みは要らない。
   捨てた案: 今回は確かめない（一番小さいが、効かない文が溜まるのを止められない）／直しの PR 1本ごとに見る日を決めて人が確かめる（確かだが、週3本の直しに観察の課題が3件ずつ増える）。

決めたこと 7〜12 は、Chief Engineer が推奨案として書き、人が最後の確かめで認めたもの（2026-11-19）。反論を受けた直し（決めたこと 14）は、7〜12 の文にも反映してある。

7. **2026-11-19 記録は2つ足す。起動の記録と、結果の記録。** どちらも課題のフォルダ（`library/`）に置き、schema を持つ（[contract.md](../contract.md) に節を足す）。ファイルの名前は実装が決めてよい（下の名前は案）。
   - **起動の記録**（案: `library/launch.json`）。書き手は、エージェントを起動する command（`andon issue start`・起動し直し・dispatcher がレビュアーを起動する段・`andon chief-engineer`）。起動するたびに1件足す。欄: 起動した時刻・役・プロファイルの名前・実際の起動行・ハーネスとその版・パッケージの commit・セルの repo の commit・案件の repo の commit・外の skill と plugin の版・食い違いの印・セッション id・auto memory の目録の写し（決めたこと 14 の 5）。起動のときに決まらない値（Codex のセッション id など）は null。Chief of Staff は課題を持たないので、同じ形の1件をプロジェクトの台帳の置き場に足す。
   - **結果の記録**（案: `library/outcome.json`）。書き手は dispatcher だけ。片付けを拾った段で、`corrections.json` と同じく課題ごとに1回だけ書く。欄: 結果（`merged`＝PR がマージされた／`closed`＝PR が閉じられた／`open`＝PR が開いたまま片付いた／`none`＝PR 無しで片付いた）・PR とマージ commit・head ごとのゲートの最後の判定と理由・レビュアーの子の課題の数・実働の時間・セッションごとのコスト（実際に使われたモデルの id・effort・ターン数・トークン）。コストは片付けのときにセッションログから読む。読むセッションは起動の記録の全部（`issue.yaml` の `session` は上書きされる。事実 10）。セッションログが無ければ null。
   - **マージ後のこと**（revert・main の CI の失敗）は記録に書き足さない。振り返りの command が読むときに、GitHub から読む: 課題のマージ commit の checks の結果と、その PR を revert した PR（決めたこと 14 の 4）。
   - HANDOFF の `ci_failed` と `reverted` は結果の値にしない。Andon では CI の失敗は差し戻しの理由の1つで、課題はそのあとも続く（ゲートの記録の判定と理由で読む）。revert はマージ後のことなので上の段で読む。
   理由: 版は起動したときにしか分からず、コストは片付けのあと 30 日でセッションログごと消える（事実 13）。この2つだけは、その時に書かないと失われる。マージ後のことは GitHub に残るので、読むときに数えれば足りる。1つの記録に書き手は1人（[contract.md](../contract.md) §0）なので、あとから別の書き手が足す欄は作らない。
   捨てた案: 1つのファイルに全部の欄を持つ run の記録（人の文書の表のとおり。書き手が3人になり、既にある記録〈ゲート・手直し・報告〉の写しを持つことになる）／SQLite や1本の JSON Lines に全課題を入れる（新しい保存先。前提 4）／マージ後のことを元の課題に書き足す（「1回だけ書く」が崩れ、いつまで見張るかの決まりが要る）。
8. **2026-11-19 振り返りの流れは、トリアージと同じ3段（集める・判定を書く・当てる）。**
   - **集める**: `andon retro collect`（読むだけ）。読む期間（決めたこと 13）に片付いた担当の課題ごとに、起動の記録・結果の記録・ゲートの記録の判定と理由・レビュアーの指摘と見送り・`corrections.json`・見積もりと実働・報告の `remember[]` と `agents_md[]`・日報・マージ後のことを1件に束ねる。レビュアーの子の課題は親に束ねる。課題の途中でパッケージが当て直されていたら印を付ける（決めたこと 14 の 5）。加えて、期間の人が打った文（決めたこと 4・14 の 1）と、前の振り返りが切った直しのうちマージから 14 日以内のもの（決めたこと 6）を出す。課題にも人が打った文にも、根拠として指せる id を振る。秘密の形に合う文字列は、出力の前に伏せる。
   - **判定を書く**: 担当（新しい skill `retro` を読む）が、束ねた記録からパターンを拾い、パターンの一覧を書く。1つのパターンの欄: 要約・根拠（決めたこと 14 の 2・3）・直す先の段（決めたこと 9）・足すか変えるか削るか・上の段で止められない理由（直す先が skill か文面のとき必須）・期待する効果（何が起きなくなるか）・リスク・判定（`fix`＝直す課題に切る／`drop`＝捨てる。理由つき）。前の直しごとに、再発の数と見立ても書く。書くのは command を通し、command が形を確かめる。
   - **当てる**: Chief of Staff が検収して `andon retro apply` を打つ。`fix` のパターンごとに直す課題を1件足し、依頼書に根拠・直す先・期待する効果・リスクを入れる。andon の repo を持たないプロジェクトで、直す先が Andon のパッケージなら、人の課題にする（決めたこと 2）。
   - **機械で止めること**（command が断る）: 根拠が別々の2件に満たないパターン／根拠が集めた入力に無い id を指している／根拠のどれも前回の振り返りより後でない（決めたこと 14 の 3）／直す先が skill か文面なのに「上の段で止められない理由」が無いパターン／判定の無いパターンが残っている／`fix` が上限（決めたこと 13）を超えている／直す先が振り返り自身（skill `retro` と `andon retro` の command）。
   理由: トリアージが同じ形（`collect`・`decisions.json`・`apply`）で回っており、担当は読むだけ・台帳に手を入れるのは Chief of Staff、という線をそのまま使える。「2回以上」「上限」「全部に判定」を文で頼まず command が断るのは、決めたこと 9 の順を振り返り自身にも当てるため。
   捨てた案: 候補の一覧（`candidates.json`）に欄を足して使い回す（調べる課題の約束に、振り返りだけの必須の欄と検査が混ざる）／振り返りの担当が自分で直しの PR を何本も出す（1つの課題に1つの branch と1つの PR、というラインの形が崩れ、見つける役と直す役が同じコンテキストになる）。
   受け入れること: command が確かめるのは、根拠の数・実在・新しさだけ。そのパターンが根拠の課題で本当に起きたかは確かめられない。見るのは、検収する Chief of Staff と、直す PR を読むレビュアーと人。
9. **2026-11-19 直す先は、効き目の確かな順に5段。削ることも候補にする。**
   1. **設計・型**: schema・command の照合・状態の定義を変え、その問題が起きようのない形にする。
   2. **テスト・lint**: テストか CI の検査にして検出する。ゲートの条件表もここ。
   3. **決まった手順の確かめ**: hook や、command の中の確かめにする。
   4. **skill・指針**: skill・プロファイル・手引き・`AGENTS.md`・`REVIEW.md` の構成や手順を直す。
   5. **文面**: 言い回しを直す。最後の手段。
   上の段で止められるものを下の段で直さない。4 と 5 を選ぶパターンは、1〜3 で止められない理由を書く（決めたこと 8 で必須）。**削る**（効いていない指示・モデルの更新で要らなくなった指示を消す）は、どの段でも候補にできる。直したのに再発した文（決めたこと 6）は、まず削る候補にする。
   理由: 人の文書の ③ と、今の設計の「機械が確かめる形 → 文 → 人のレビュー」（[ADR-0006](0006-survey-fix-decide.md) 決めたこと 14）は同じ向き。文を足すだけの直しは、効いたかどうかが分からないまま skill を太らせる。
10. **2026-11-19 改善の PR は、ふつうの直す課題の PR として出す。ラベルは `retro`。** 本文に必ず書くもの: 何が何回起きたかの要約・根拠の課題が出した PR の番号（公開のもの）・直す先の段と、それを選んだ理由・期待する効果・リスク。根拠の課題番号の一覧・人のコメントや人が打った文の本文・人の名前は書かない（前提 7）。末尾の `Memo:` の1行は今の決まりのまま書く。根拠の記録への道はセルの中に残す: PR → 直す課題 → 振り返りの課題のパターン → 根拠 → その記録。ラベル `retro` が repo に無ければ作る。
    理由: 人の文書は「根拠になった run の id の一覧」を PR の本文に求めるが、Andon の repo は public で、セルの中の資源を指す記述を PR に書かない決まりがある（[ADR-0026](0026-pr-rules-for-outside-readers.md)）。辿る道がセルの中に1本あれば、求めていること（PR から根拠の記録に辿れる）は満たせる。直す課題は別の担当が別のコンテキストで働く。
    受け入れること: PR の本文は機械もレビュアーも検査しない（[ADR-0026](0026-pr-rules-for-outside-readers.md) 決めたこと 7）。要約に人の言葉が混ざっていないかを見るのは、人の目だけ。
11. **2026-11-19 トリアージとは分けたまま回す。** トリアージは項目1件ずつの仕分け（閉じる・課題に切る・人へ回す）で、台帳の項目を片付ける。振り返りは課題の記録を横に読み、台帳の項目には手を入れない。報告の `## Remember` と日報は、振り返りも根拠として読む（日報の「読む側」は、この振り返りにする。[ADR-0024](0024-worker-journal.md) 決めたこと 5 の続き）。auto memory はトリアージだけが読む。
    理由: 同じ項目を2つの仕事が片付けると、どちらが閉じたかが分からなくなる。振り返りは「読むだけ」にしておけば、順番や取り合いの決まりが要らない。
12. **2026-11-19 細部。**
    - 名前は、識別子が `retro`、日本語の文では「振り返り」（[design.md](../design.md) §0.1 のまま）。ワークストリーム「ふりかえり（Retrospective）」（`process/workstreams/retrospective.yaml`）に、きっかけと手順をこの文書のとおり書く。目的の「課題の終わりと週 1 回」も、この文書の頻度に合わせる。
    - 振り返りの担当のプロファイルは、ルーチンの例に既定を書き、Chief of Staff が変えてよい。
    - 伏せる秘密の形（API キー・トークン・秘密鍵の塊など）の一覧は実装が決め、テストにダミーの値を置く。
    - 結果の記録を書く段は、片付けのあとの仕事（`process/states/aftermath.yaml`・[dispatcher.md](../dispatcher.md) §2.6・§7.2）に足す。課題のステータスの移り方は変えないので、形式モデル（`model/`）は変えない見込み。実装が確かめる。
    - 古い課題（この仕組みが入る前に片付いたもの）に起動の記録と結果の記録は無い。振り返りの command は、無い欄を null として読む。さかのぼって作らない。
13. **2026-11-19 振り返りは毎日回し、1回に切る直す課題は2件まで（決めたこと 5 の頻度・期間・上限を改める）。** ルーチンが毎朝1回、振り返りの課題を1件足す。読むのは直近 7 日に片付いた課題。直す課題に切るのは1回2件まで。前の振り返りが扱ったパターン（切ったもの・捨てたもの）は、新しい根拠の課題が増えたときだけ出し直せる。
    理由: 人が価値の仮説の案（週1・見る日は4週間後）を見て「ライフサイクルが長過ぎるかもね、もっと高頻度でやってもいいかも」と言った（2026-11-19）。実測したセルでは1日に約 10 件が片付くので、週1では手直しから直しまでが遠い。毎日なら、読む期間が毎回6日ぶん重なる。同じ根拠だけで同じパターンが毎日出てこないように、出し直しの条件を足した。上限の2件は、振り返りから出る改善の PR を1日2本までに抑えるため。
    捨てた案: 片付くたびに回す（ルーチンの `on: [done]` で組める。一番速いが、振り返りの課題が1日に何件も走り、コストと検収の手間が増える）／毎日・1回1件まで／週1のまま、最初の数回だけ手で撃つ。
    → 同じ日に、出し直しの条件を決めたこと 14 の 3 で改めた。
14. **2026-11-19 反論を受けて5点を改める。** 別のコンテキストにこの設計を壊させ、証明できた指摘を人に見せた。人は5点とも、Chief Engineer の扱いの案を認めた。
    1. **人が打った文を抜く規則（決めたこと 4 を改める）。** 抜くのは、人の印（`origin.kind` が `human`）があり、セッションの最初のメッセージでなく、`hc` の包み（`<hc from=…>`）が無い文。
       理由: 印だけでは分かれなかった。担当と Chief Engineer のセッションログ 24 本では、人の印が付いた 34 件のうち 30 件が機械の文だった（起動の最初のメッセージ 23 件・ほかの端末から `hc send` で届いた文 7 件）。決めたこと 4 の実測は Chief of Staff の1本だけだった。文の意味は読まないが、位置と包みは見ることになる。
    2. **根拠の単位は「課題、または人が打った文」。** 根拠は別々の2件以上。同じ課題の中の2回、同じセッションの中の2回は、1件と数える。
       理由: Chief of Staff は課題を持たないので、Chief of Staff との会話での手直しは「根拠の課題2件」を満たせない。
    3. **出し直しの条件（決めたこと 13 を改める）。** パターンの根拠のうち1件以上は、前回の振り返りより後のもの（後に片付いた課題か、後に打たれた文）でなければならない。command が確かめる。前の振り返りが捨てたパターンの一覧は持たない。
       理由: 「前に扱ったパターンと同じか」は機械で決められず、言い換えれば抜けられる。捨てたパターンの一覧を毎日入力に出すと、それが持ち越しの山になる（前提 6・決めたこと 5 と矛盾する）。「新しい出来事が1件あること」なら、パターンの同一性を決めずに確かめられ、新しい出来事が無い日は何も出せない。
    4. **マージ後のことは GitHub から読む。** 課題のマージ commit の checks の結果と、その PR を revert した PR を、集めるときに読む。信号の記録（`signals.json`）は使わない。
       理由: 信号の記録は workflow ごとに1行で、見えるたびにマージ commit の SHA を上書きする（事実 12）。壊した課題に結べない。
    5. **git の外にあるものの扱い。** 起動の記録に auto memory の目録（`MEMORY.md`）の写しを入れる。課題の途中でパッケージが当て直されたら（[ADR-0027](0027-apply-package-without-rebuild.md) の記録の時刻が、起動と片付けの間にある）、集めるときにその課題に印を付ける。
       理由: 目録は全部の Claude Code のセッションに入るのに git の外にあり、トリアージが消す。写さなければ復元できない。大きさは数 KB。memory の本文は写さない（必要なときに読まれるもので、量も多い）。
    捨てた案: 人が打った文を入力にするのをやめる（1 と 2 が要らなくなるが、Chief of Staff との会話での手直しが入らない）。
15. **2026-11-19 振り返りが切った直す課題のマージは、ラインの決まりに任せる（推奨案は覆された）。** 特別扱いしない。課題の `merge` は、Chief of Staff がほかの課題と同じ決まりで書く。テストだけの直し（レベル A）とコードの直し（レベル B）は、今のゲート（checks・独立レビュー）と委譲の範囲で自動でマージされうる。Andon のパッケージと `AGENTS.md` に触れる直し（レベル C）は、今までどおり人がマージする。
    理由（人の選択）: 今あるラインの決まりで足りる。人の文書が自動マージを止めているのは「プロンプトや skill の変更」で、それはレベル C として今も人がマージする。
    捨てた案: 振り返りが切る直す課題は全部 `merge: person` にする（Chief Engineer の推奨。人の文書の「改善案の PR は自動マージしない」をいちばん広く読む形。オーナーが読む PR が1日2本まで増える）／差分が `tests/**` だけの直しに限って自動マージを許す。
16. **2026-11-19 Andon を開発するセルでは、トリアージも毎日回す。** このセルの台帳に置くトリアージのルーチンの周期を、毎朝1回にする。パッケージの例の既定（週1）は変えない。
    理由: 実測したセルでは未処理が1日に約 50 件増え（事実 18）、1回のトリアージが仕分けるのは 50 件まで。週1では追いつかず、山が残る。周期はセルの台帳のルーチンの1行なので、パッケージの変更は要らない。
    捨てた案: 週1のまま置いて、追いつかなければあとで上げる／パッケージの例の既定も毎日に変える（ほかのセルにも届く。流量の少ないセルには多すぎる）。

## やらないこと（範囲の外。理由）

- **トリアージの例の既定の周期（週1）の見直し。** 変えるのは Andon を開発するセルのルーチンだけ（決めたこと 16）。
- **リプレイの評価・カナリア・自動ロールバック（Phase 2）。** 今回は下のメモだけ。記録（決めたこと 7）と再発の数え（決めたこと 6）が回ってから、別の題で決める。
- **Andon のパッケージに触れる改善の PR の自動マージ（Phase 3）。** レベル C は人がマージする（[design.md](../design.md) §1.10）。変えるなら新しい ADR で覆す。
- **振り返り自身の自動の改善。** skill `retro` と `andon retro` の command を直す先にするパターンは command が断る（決めたこと 8）。直すのは人が頼んだときだけ。
- **今ある自動マージの判定（ゲート）の作り変え。** スコアは足さない。振り返りはゲートの記録を読むだけ。条件表の直しは、ほかの直しと同じく PR の候補として出す。
- **今ある記録の削除・移行・さかのぼっての作成。** 足すだけ（決めたこと 12）。
- **セッションログの全文を振り返りに読ませること・保持期間の延長。** 抜くのは人が打った文だけ（決めたこと 4）。
- **片付けのたびに機械で照らす口（案 C）と、ファイルごとのハッシュ。** 決めたこと 1・3 の捨てた案。
- **セルの設定・依頼書の切り方・プロファイルの選び方・委譲を直す先にすること。** 決めたこと 2 の捨てた案。人の持ち物に触れる。
- **`corrections.json` の拾い方の直し。** 意味の無い手直しが混ざる（事実 15）のは、振り返りが読んで捨てる（[contract.md](../contract.md) §14 のまま）。何度も同じ雑音が出るなら、それ自体が振り返りのパターンになる。
- **信号の記録（`signals.json`）の直し。** マージ commit の SHA が上書きされること（事実 12）は、この題では直さない。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に）

継ぎ目は3つ。(1) command の入出力を、偽のセル（`tests/lib/` の切り離し）と fixture の台帳・セッションログで確かめる `tests/*.sh`。(2) schema の検査（`tests/schema.sh` の並び）。(3) Andon を開発するセルでの実測。3 のうち、人か Chief of Staff が目で見るものは `manual`。

| # | 条件 | command（証拠） | 見る出力 |
|---|---|---|---|

## Phase 2 以降のメモ（今回は実装しない）

Phase 0・1 を調べて分かった前提と制約。決定ではない。

- **リプレイに要るものは、今回の記録でほぼ揃う。** 依頼書（`brief.md`）・案件の repo の commit・パッケージの commit が課題に残るので、「同じ依頼書を、同じ commit の worktree で、違う版のパッケージで流し直す」ことは組める。足りないのは3つ。(a) 版を課題ごとに分けて当てる口（下）。(b) 外の状態（GitHub の PR・CI・外の issue）を再現する手。リプレイでは PR を出さず、worktree の中の差分と検査の結果までで止める形が現実的。(c) 採点の基準。使えるものは、受け入れ条件の証拠（`acceptance[]`）・ゲートの判定・独立レビューの指摘の数・コスト。採点役を別のコンテキストにする線は、独立レビュー（実装と別ブランド）の形を使える。
- **評価セットは、振り返りの記録から作れる。** 失敗例は、パターンの根拠の課題。成功例は、結果が `merged` で手直しが無く、差し戻しも無かった課題。
- **カナリアの壁は、セルにパッケージの置き場が1つしか無いこと**（事実 23）。課題ごとに版を分けるには、起動行の `--plugin-dir` と `--append-system-prompt-file` を版ごとの展開先に向ける形が要る（[ADR-0027](0027-apply-package-without-rebuild.md) が捨てた「commit ごとに完全なパッケージを組む」案に近い）。分けられるのは skill とプロファイルの文だけで、hook・managed settings・`andon` のバイナリはセルに1つ。流量の制約もある: 1日 10 件のセルで 20% に当てると1日2件で、差が見えるまで数週間かかる。
- **自動ロールバックは「revert の PR を自動で出す」までが今の線。** レベル C のマージは人（[design.md](../design.md) §1.10 の安全網 3）。
- **Phase 3（危険の低い改善の自動マージ）のうち、テストとコードの直しは今の決まりで既に自動でマージされうる**（決めたこと 15）。残るのは skill と文面の直しで、「Andon のパッケージは常に人」を覆す決定が要る。判断の材料は、再発の数え（決めたこと 6）の実績と、削るだけの PR・文面だけの PR がどれだけ問題なくマージされたか。
- **指標は `andon measure` に既にある**（PR あたりの人の介在回数・手直しのあった課題・revert・ゲートの差し戻し率）。起動の記録が入れば、版ごと・プロファイルごとに割って比べられる。「マージされた率」だけを追わない線は、今の設計の「自動マージ率は差し戻し率と一緒に見る」（[design.md](../design.md) §1.9 の 4）と同じ。
