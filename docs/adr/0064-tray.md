# ADR-0064: tray（セルが出した報告を集めて読む場所）を andon に足す（仕様・設計。2026-11-27）

- 状態: **決定（2026-11-27）**。オーナーが 2026-11-27 に「決めた」と答えた。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書く。
- 主題: セルが出した報告を読む場所を作る。報告を1か所に集め、セルとプロジェクトで並べ、開いたら既読にする。セルの中で動くローカルの tray が今の `files/` の配る口を置き換え、プロジェクトごとに選べば、同じ物が Cloudflare でも動いてスマホから読める。
- 語は [design.md](../design.md) §0.1。ダイジェストは [ADR-0044](0044-owner-digest.md)、常駐を足さない前提は [ADR-0028](0028-improvement-loop.md)、ハーネスの受け口は [ADR-0060](0060-otel-trace.md) にある。
- この文書で「報告」は、`andon publish`・`andon digest send`・`andon issue report` が tray に送った1件を指す。「一覧の面」は報告の一覧と既読を持つ画面、「報告の面」は報告そのものを返す別オリジンの口、「アップロードの口」はセルが報告を送る口を指す。「ローカルの tray」はセルの中で動く tray、「Cloudflare の tray」はオーナーの Cloudflare のアカウントで動く tray を指す。

## 問題（オーナーの言葉で。言い直しの段落）

オーナーは 2026-11-24 に企画を詰めた依頼（brief）を書き、2026-11-25 に Chief of Staff へ渡した。brief は tray を「報告を読む場所で、既読を持つ」と決め、名前、送る口、3つのホスト名、既読、古い報告の扱いまでを決めている。

言い直し（オーナーが 2026-11-25 に同意した）。困っているのは、セルが上げた報告を読む場所が、端末の Chief of Staff の返事と、セルを動かしている PC でしか開けない `files/` の URL に限られることである。スマホでは読めず、どれを読んだかも残らない。tray は、`andon publish` と `andon digest send` が出した物を1か所に集め、セルとプロジェクトで並べ、開いたら既読にする。既定はセルの中で動くローカルの tray で、プロジェクトごとに選んだときだけ Cloudflare の tray にも送る。tray は読むだけの場所で、オーナー待ちに答える場でも、通知を出す物でもない。

オーナーは同じ日の途中で、こう言い直した。「つまりは `files.<セルの名前>.localhost` を tray で置き換えよう。リモート対応もできるようにしよう。」

調べた事実。

1. 2026-11-25 の時点で、このセルの `files/` にある報告は 2026-11-22 のダイジェスト1枚（46,637 バイト）だけである。外の参照は 0 で、1枚で完結している。毎朝のダイジェストのルーチンはまだ動いていない。
2. Chief of Staff がターンを終えた返事は、2026-11-19 から 11-24 に1日 114〜452 通あった。多い日は 263〜452 通である。空行を除いて3行を超える返事は1日 51〜151 通で、多い日は 107〜151 通だった。10行を超える返事は 11〜22 通、表を含む返事は多い日で 12 通だった。片付く課題は1日に約 35 件ある。
3. セルはホストにもほかのセルにも出られない。ホストからセルへは、ssh の LocalForward で portless の番号だけを引いている。
4. `andon boot` が起動している常駐は、portless、files サーバ、ハーネスの受け口、sshd、dispatcher の5つである。files サーバは `files/` を読み取りで返すだけで、一覧も既読も持たない。
5. `andon publish` は `files/<日付>-<slug><拡張子>` に写して URL を1行出す。上限は 20 MiB で、プロジェクトを引かない。同じ日の同じ slug は上書きになる。
6. `files/` はセルの repo の中にあり、git が無視していない。誰も自動では commit しないので、出した物は追跡されていないファイルとして溜まる。
7. 2026-11-25 に試しに組んだ。Solid 2.0.4、`@solidjs/web` 2.0.4、`@ui-sdk/solid` 0.1.0-beta.17、StyleX 0.19.2、Vite 8、`@solidjs/vite-plugin` 3.0.1、`@cloudflare/vite-plugin` 1.70.1、wrangler 4.168.0 は、依存の衝突なく入った。ビルドは3秒で、workerd の上で D1 と R2 を読む API と画面が動いた。画面の JavaScript は Solid と StyleX だけで 29 kB、UI SDK の部品を1つ足すと 106 kB だった。
8. 同じ試しを `wrangler dev` で常駐させると、メモリは合計 605 MB だった。内訳は wrangler の Node が約 350 MB、workerd が2つで約 250 MB である。止まっている間の CPU 時間は 40 秒で1秒だった。依存の置き場は 603 MB で、うち workerd のバイナリが1つ約 160 MB である。miniflare を直に起動する形は、試しの台本が、入っている miniflare（5 系の beta）の設定の形に合わず、起動できていない。
9. Solid 2.0 の安定したバージョンは 2026-11-17 に出た。UI SDK は beta で、2026-11-12 の初公開からほぼ毎日出ており、API は変わりうると書かれている。TanStack の Solid 向けのルーターは、Solid 2 への対応が rc だけである。`@solidjs/router` 2.0.1 は安定したバージョンで Solid 2 に対応する。Void の Solid 向けの部品は Solid 1 だけを受け、Access を設定する口が無い。
10. Cloudflare の Access は wrangler の設定に書けず、ダッシュボードか Terraform で設定する。静的なファイルを持つ Worker では、画面のファイルの要求は Worker のコードを通らない。Workers の無料の枠は1日 10 万リクエスト、D1 は1日 500 万行の読みと 10 万行の書き、R2 は月 10 GB、Access は 50 人までである。
11. iOS でホーム画面に追加した画面と Access の組み合わせは、公式の文書にも実機の報告にも、動くという裏付けが無い。manifest とアイコンの取得が cookie 無しでログインへ飛ばされる、セッションが切れると取得が落ちる、service worker がログインを塞ぐ、という報告がある。
12. 先行の公開実装（html-share の Cloudflare 向けの実装）を読んだ。報告を別オリジンから `sandbox` 付きの CSP で返す形、Access の JWT を Worker でも確かめる形、参照を `data:` に埋める形は使える。足りない所が3つあった。端末のトークンを失効させる口が無い。本人用の署名付き URL の期限が 30 日である。パスをパーセントで符号化すると、Worker の側の JWT の検査を外れる。
13. `project.json` は、schema も Go の読み手も、知らないキーを断る。古い andon が知らないキーを見ると、`project.json` を丸ごと読めず、委譲が無い扱いに倒れる。
14. 既定の型 `work` と `andon` は、委譲の `publish` が `none` である。`design.md` §1.10 は `internal` を「自分のセルの中（`andon publish`）まで」と書いている。
15. Chief of Staff の skill の前文は、オーナーへの文を「行数では数えない」と書いている。理由は、行数を守ると語を詰めた文になり、その返事だけで通じなくなることである。
16. andon の repo は公開で、CI は Go、モデル、tests の3つである。npm を使ってよいのはモデルの job だけと、検査が固定している。イメージが配るのは `package/` と `schema/` と andon のバイナリで、どのセルにも Node がある。Bun、wrangler、workerd は無い。

モデル: 調べなかった（課題の一生、dispatcher、gate の流れを変えない。状態は、報告ごとのバージョンの番号と、読んだバージョンの番号の比較1つである）

## 前提（同意済み。番号）

オーナーが 2026-11-25 に7つとも同意した。

1. 困りごとは、報告を読む場所が端末と PC の `files/` に限られ、スマホで読めず、既読も残らないことである。
2. 何もしないと、PC の外で読める物は Slack のダイジェストだけになる。
3. ローカルの tray はセルごとに1つで、見えるのはそのセルの報告だけになる。全セルを1か所で見ること、スマホで読むこと、端末をまたぐ既読は、Cloudflare の tray だけが満たす。
4. ローカルの tray は、セルに常駐と保存先を持つ。試した形でメモリは約 600 MB だった。ADR-0028 の「受け口、保存先、常駐を足さない」を tray の範囲で改める。
5. tray は、既定のスタックの候補を試す場を兼ねる。Solid 2.0、UI SDK、StyleX を採り、バージョンを固定する。TanStack と Void は使わない。
6. ADR-0044 の「読むための専用のサイトを外に立てない」と、「長い返事を HTML にする決まりは後で決める」を覆す。
7. tray は andon のイメージに入れて全セルに配る。公開の repo に、ドメインやアカウントの値を書かない。

## 決めたこと

### 範囲と役

1. **範囲は、3行を超える報告を全部 tray に上げる所までにする。**（オーナーが決めた。2026-11-25。Chief Engineer の推奨は「ダイジェスト、Chief Engineer の要点、10行を超えるか表を含む返事に絞る」だった）
   理由: brief の決まりのとおりにする。事実 2 の数から、Chief of Staff の返事だけで1日に 107〜151 枚、担当の報告で約 35 枚が届く見込みである。
   捨てた案: 長い物だけに絞る案は1日 15〜25 枚で済むが、オーナーが選ばなかった。決まりを足さずに役の判断に任せる案は、tray に届く物が1日に数枚になり、読む場所が端末に残る。

2. **名前は tray にする。**（オーナーが決めた。2026-11-24）
   command は `andon tray`、ダイジェストの送り先の kind は `tray` である。tray は andon のサブシステムで、andon の repo の `tray/` に置く。別の repo にしない。
   捨てた案: 別の repo に分けると、セルの側の Go と約束がずれたときに、1つの PR で直せない。

3. **tray は読むだけの場所にする。**（オーナーが決めた。2026-11-24）
   tray はオーナー待ちに答える口を持たない。通知も出さない。判断と呼び出しは、今までどおり `andon waiting list` と行燈が持つ。

### 2つの tray

4. **ローカルの tray が、`files/` の配る口を置き換える。**（オーナーが決めた。2026-11-25）
   `andon boot` は files サーバを起動しなくなり、代わりにローカルの tray を起動する。portless の名前 `files` は無くし、一覧の面に `tray`、報告の面に `tray-view` の名前を付ける。葉 `andon boot serve-files` は消す。フォルダ `files/` の扱いは決めたこと 8 に書く。
   理由: 常駐の数が増えない。オーナーに渡す URL が1種類になる。
   細部: files サーバを消すときに触る所は、`internal/boot/` の起動の段と `files.go`、`internal/cli/leaves.go` の葉と別名、`tests/andon-boot.sh`、`tests/image.sh`、`tests/andon-init.sh`、`package/host/bootstrap` と `init/.gitignore` の `FILES_PORT`、`package/compose.yaml` の注釈、`package/environment.md`、`docs/commands.md`、`docs/operate.md`、`docs/contract.md` の `files` の説明、検証の地図の boot、`docs/dispatcher.md` §7.2 の行 14・15・27 である。
   捨てた案: files サーバを残して tray を並べると、同じ物を配る口が2つになり、どちらの URL を渡すかを役が迷う。

5. **Cloudflare の tray へ送るかは、プロジェクトごとに `project.json` で選ぶ。**（オーナーが決めた。2026-11-24）
   既定はローカルの tray だけである。オーナーが `project.json` に `tray` のキーを書いて commit したプロジェクトだけが、Cloudflare の tray にも送る。
   細部: キーの形は `"tray": {"upload": "https://<アップロードの口のホスト名>"}` である。読むのは、ダイジェストの送り先と同じく `delegate.ReadProject` を通した値だけにする。古い andon はこのキーで `project.json` を読めなくなる（事実 13）ので、キーを書くのはセルの andon を上げたあとにする。運用の手引きにそう書く。

6. **同じ Workers のコードを、セルの中では workerd で動かす。**（Chief Engineer が決めた）
   ローカルの tray と Cloudflare の tray は、同じ TypeScript のコードと同じ画面である。セルの中では、ビルド済みの Worker を miniflare（workerd）で動かし、D1 と R2 はセルのディスクに持つ。
   理由: 一覧、既読、バージョン、署名付き URL、報告の面のヘッダは、守りに効く振る舞いである。実装が1つなら、セルの中の検査が Cloudflare で動くコードそのものを確かめる。セルは Cloudflare に出て検査できないので、これが完了の条件を確かめる唯一の場になる。
   捨てた案: 下の「比べた構造」に書く。

7. **前の前提と決定を、tray の範囲で改める。**（オーナーが決めた。2026-11-25）
   - ADR-0028 の前提 1（受け口）、4（保存先）、5（常駐）を改める。tray は、セルの中に保存先を1つ持ち、files サーバと入れ替わる常駐を1つ持つ。ADR-0060 決めたこと 24 がハーネスの受け口の範囲で改めたのと同じ形である。`docs/dispatcher.md` §7.2 の表は、行 14・15・27 を直し、tray の行を足す。
   - ADR-0044 のやらないこと「読むための専用のサイトを外に立てること」を覆す。
   - ADR-0044 のやらないこと「Chief of Staff・Chief Engineer・担当の長い返事を HTML にする決まり」を覆す（決めたこと 13）。
   - ADR-0044 のやらないこと「Slack のほかの送り先を作ること」を、tray の分だけ覆す（決めたこと 11）。
   - ADR-0044 決めたこと 13 の、Slack の短い文に `files/` の URL を書く所を改める（決めたこと 11）。
   - ADR-0044 決めたこと 15 と 16 の、ダイジェストのページを `files/` に置き、`sent.json` の `files` の行に files サーバの URL を書く所を改める（決めたこと 8 と 11）。
   - ADR-0044 決めたこと 12 が名指す4か所の文（worker skill §5 の表、Chief of Staff の原則 4、`playbooks/blocked.md`、`design.md` §1.10 の `publish` の説明）を改める（決めたこと 14）。
   - Chief of Staff の skill の前文「行数では数えない」を改める（決めたこと 13）。

### 送る側

8. **`andon publish` は tray に送り、いちばん良い URL を1行出す。tray に届いた物は `files/` に写さない。**（`files/` に写さないことはオーナーが決めた。2026-11-25。brief の「`files/` と同時に送る」を改める。URL の出し方は Chief Engineer が決めた）
   順は、ローカルの tray に送る、プロジェクトが選んでいれば Cloudflare の tray に送る、である。stdout の1行は、オーナーに渡す URL を1つだけ出す。Cloudflare の tray に届けばその URL、届かなければローカルの tray の URL にする。ローカルの tray にも届かなかったときだけ、今までどおり `files/` に写し、そのパスを出す。tray へ送れなくても終了コードは 0 で、理由を stderr に出す。
   理由: 報告を出す手は、読む場所の不調で止めない。役は stdout の1行をそのままオーナーに渡せばよい。`files/` は git で追跡する納品物の置き場として決めてある（ADR-0005）。1日に 100 枚を超える報告をそこへ写すと、追跡していないファイルがセルの repo に溜まり続け、配る口はもう無い。
   細部:
   - プロジェクトは、ほかの葉と同じ引き方で引く（`internal/cli/leaves.go` の `project: true`）。引けなければ、プロジェクトを `-` として、ローカルの tray にだけ送る。
   - `--title <タイトル>` を足す。省いたときのタイトルは決めたこと 9 に従う。
   - ローカルの tray のデータは volume の中にあり、セルの repo と一緒には別のマシンへ動かない。動かしたい物は、今までどおり製品の repo か `files/` に手で置く。`docs/operate.md` の `files/` の文と `internal/publish/publish.go` の注釈を直す。
   - 送れなかった分の送り直しは持たない（やらないこと）。
   捨てた案: tray に送れなければ publish を失敗にする案は、tray が落ちている間、どの報告も出せなくなる。`files/` と tray の両方にいつも置く案は brief のとおりだが、上の溜まり方になる。

9. **同じ報告は、セルとプロジェクトと名前の組で見分ける。**（Chief Engineer が決めた。上げ直しを新しいバージョンにすることはオーナーが 2026-11-24 に決めた）
   名前は、`andon publish` では今までの `files/` の名前と同じ `<日付>-<slug>` である。slug を名指して同じ日に出し直すと新しいバージョンになり、日が変われば別の報告になる。slug を省いたときは、名前に時刻を足して、いつも別の報告にする。中身（sha256）が同じ出し直しはバージョンを上げない。
   理由: 日付を外すと、毎日の同じ slug の報告が1行に重なり、前の日の物が読めなくなる。slug を省いたときの既定はファイル名なので、役が同じ一時ファイルの名前で1日に 100 通を出すと、前の返事が読まれないまま上書きされる。中身が同じなら、読み終えた物を未読に戻さない。
   細部:
   - タイトルは、`--title` があればそれ、無ければ HTML の `<title>`、Markdown の最初の見出し、どれも無ければファイル名にする。
   - 残すのは最新のバージョンの中身だけである。前のバージョンの中身は持たない。
   - 名前は UTF-8 のまま持つ。送るときはパーセントで符号化する。断るのは、`/`、制御文字、200 バイトを超える名前だけである。
   捨てた案: 前のバージョンを全部残す案は、差分を見せる画面が無い間は置き場を使うだけである。

10. **HTML は、送る前に手元の参照を埋め込む。外へ送る写しは、秘密の形を伏せる。**（埋め込むことはオーナーが 2026-11-24 に決めた。範囲と伏せることは Chief Engineer が決めた）
    埋め込むのは、ファイルから相対で引いている画像、スタイル、スクリプト、フォントである。`http` と `https` の参照は埋めずに残し、数を stderr に出す。報告の面は外への取得を止めるので（決めたこと 18）、残した参照は表示されない。
    Cloudflare の tray へ送る写しは、`internal/redact` を通す。Markdown とテキストは全体に当てる。HTML は、文の部分（テキストのノード）と属性の値にだけ当て、`<script>` と `<style>` の中身には当てない。ローカルの tray へ送る写しは伏せない。
    理由: 外の参照まで取りに行くと、publish がネットワークに依り、取った中身を確かめられない。伏せる網は、セルの外へ出る所に置く。伏せる式を HTML の全体に当てると、`.secret:hover{…}` のような CSS は閉じタグごと消え、`const token = new …` のようなスクリプトは構文の誤りになる（`internal/redact/redact.go` を写して確かめた）。壊れるのは Cloudflare の写しだけなので、役は気づけない。
    守りの限り: スクリプトとスタイルの中に書かれた秘密は伏せられない。
    細部: 埋め込んだあとの上限は、今の publish と同じ 20 MiB にする。HTML の読み取りに `golang.org/x/net/html` を足してよい。枠の中のリンクが新しいタブで開くように、送る写しの `<head>` に `<base target="_blank">` を足し、`#` で始まるリンクには `target="_self"` を足す。足さないと、ページの中の目次のリンクまで新しいタブで開き、署名の期限のあとは開けない。
    捨てた案: 正規表現で参照を拾う案は、属性の書き方の違いで取りこぼす。秘密の形を見つけたら送らない案は、CSS のクラス名のような当たりで、報告が Cloudflare に届かなくなる。

11. **ダイジェストは tray を送り先の1つに数え、Slack の短い文のリンクを tray の URL に替える。**（kind の名前はオーナーが 2026-11-24 に決めた。数え方は Chief Engineer が決めた。リンクを替えることはオーナーが決めた。2026-11-26）
    `andon digest send` の `sent.json` の行は、次の3種類になる。kind `files` の行は、セルの中に置いたことを表し、`url` はローカルの tray の URL にする。kind `tray` の行は Cloudflare の tray で、プロジェクトが選んでいるときだけ在る。kind `slack` の行は今までどおりである。オーナーは `digest.destinations` に tray を書かない。tray へ送るかは決めたこと 5 のキー1つが決める。
    どの行も、失敗したら次の `send` で送り直し、全部が済むまで、そのダイジェストは済みにならない。Slack の送り先と同じ数え方である。`andon digest send` の前の確かめ（`CheckDestinations`）は、Cloudflare の tray の鍵が在ることも見る。
    Cloudflare の tray に送れたダイジェストは、Slack の短い文に tray の URL を書く。選んでいないプロジェクトでは、ローカルの tray の URL を書く。
    理由: ローカルの tray の URL は、セルを動かしている PC でしか開けない。Slack を読むのはスマホが多い。
    細部: `schema/digest-sent.schema.json` の kind に `tray` を足し、`files` の `url` の説明を直す。行が `files` だけであることを固定している検査（`tests/andon-digest.sh` と、検証の地図のダイジェストの台本）を直す。
    捨てた案: `digest.destinations` に `{"kind": "tray"}` を書かせる案は、publish とダイジェストで設定の場所が2つになる。ローカルの tray と Cloudflare の tray を同じ kind の2行にする案は、今の `send` が kind で済みを数えるので、片方の失敗を見分けられない。

12. **担当の報告は、`andon issue report` が tray に送る。**（Chief Engineer が決めた。担当の報告を範囲に入れることはオーナーが 2026-11-25 に決めた）
    `andon issue report` と `andon issue review-request` は、kanban に報告を書いたあと、人が読む報告（stdin の Markdown）を tray に送る。名前は課題ごとに1つで、日付を付けない。出し直した報告は新しいバージョンになる。タイトルは課題番号とタイトルである。送れなくても報告は成り立ち、理由を stderr に出す。`files/` には写さない。
    理由: 担当に HTML を書かせると、1日に約 35 回、同じ中身を2度書くことになる。報告の Markdown はもう在る。command が送れば、担当の skill に手順を足さずに済み、漏れない。
    捨てた案: 担当の skill に「報告を HTML にして publish する」と書く案は、担当のトークンを使い、書き忘れを検査できない。

13. **役は、3行を超える報告と表を含む報告をファイルにして `andon publish` で出し、返事には URL と要る判断だけを書く。**（オーナーが決めた。2026-11-24。文の細部と形式は Chief Engineer が決めた）
    細部:
    - 入れる所は、Chief of Staff の skill の原則と、Chief Engineer の skill の入口と出口である。担当は決めたこと 12 で足りるので、worker skill には「報告は `andon issue report` が tray に送る」とだけ書く。`package/environment.md` の `andon publish` の文も直す。
    - ファイルの形式は HTML か Markdown のどちらでもよい。表や図が要るときは HTML、文だけなら Markdown にする。brief は「HTML にして」と書いているが、tray は Markdown を整えて見せる（決めたこと 22）。1日 100 枚を超える返事を HTML で書くと、同じ中身に対して出力のトークンが増える。
    - 問いは返事の本文に残す。ask-one-by-one skill §2 の問いの形は3行を超えるが、判断は返事で受ける。
    - 担当が片付けた課題を伝える返事は、担当の報告の tray の URL を指してよい。中身を書き写さない。
    - Chief of Staff の skill の前文は、「行数では数えない」をやめ、「短くするために語を詰めない。3行を超えるなら tray へ出す」に改める。
    - Chief Engineer の skill を変えるので、同じ PR で `design.md` §1.8 も直す。
    - 決まりを守らせる機械の段（Stop のフックで行数を数える）は、今は足さない。問いの形が3行を超えるので、行数だけでは見分けられない。
    捨てた案: どの役にも HTML だけを求める案は、文だけの報告にも HTML の枠を書かせる。

14. **セルの中へ出すことは委譲に依らない。Cloudflare の tray へ送ることは、`project.json` に書いてあることを go にする。**（オーナーが決めた。2026-11-25）
    ローカルの tray と `files/` へ出すことは、委譲の `publish` の値に依らず、どの役も打ってよい。Cloudflare の tray へ送ることは、オーナーが `project.json` に `tray` を書いて commit してあることを、毎回の go とする。ADR-0044 決めたこと 12 と同じ形である。
    理由: 既定の型 `work` と `andon` は `publish` が `none` である（事実 14）。そのままだと、決めたこと 13 の決まりは、この2つの型のプロジェクトで打てない。セルの中の置き場は、セルの外の誰にも届かない。
    止める相手と操作: この決まりは、`andon publish`、`andon digest send`、`andon issue report` が、選んでいないプロジェクトの報告を Cloudflare へ送ることを止める。
    守りの限り: 止めるのは command の道だけである。API キーはセルに1本で、役と同じ利用者のファイルに在る。役は command を通さずに、そのセルの名前で、どのプロジェクトのどの名前にも送れる。残すのは最新の中身だけなので、同じ名前で送れば前の報告を上書きできる。サーバが守るのは、ほかのセルの報告に触れないことと、一覧を読めないことである。ADR-0044 決めたこと 12 の Slack のトークンと同じ限りである。選んだプロジェクトの報告の中身も、1件ごとにオーナーが見ないまま送られる。網は、決めたこと 10 の伏せる段と、Access の内側に置くこと（決めたこと 17）である。
    捨てた案: 鍵を発行するときに、送ってよいプロジェクトを結ぶ案は、サーバで守れるが、プロジェクトを足すたびにオーナーが鍵の画面を開くことになる。

### サーバの側

15. **アップロードの口の約束は `/v1/` でバージョンを持ち、足すだけで変える。**（Chief Engineer が決めた）
    セルの andon と、デプロイ済みの Cloudflare の tray は、別の日に上がる。だから約束はバージョンを持ち、欄は足すだけにする。欄を消すか意味を変えるときは `/v2/` を足す。
    細部:
    - `PUT /v1/reports/<プロジェクト>/<名前>`。本文はファイルの中身そのままである。タイトル、種類（`publish`・`digest`・`report`）、sha256 はヘッダで渡す。プロジェクト、名前、タイトルは UTF-8 をパーセントで符号化する。プロジェクトが無いときは `-` と書く。
    - 答えは JSON で、開く URL、バージョンの番号、バージョンが上がったか、を返す。
    - Cloudflare の tray は `Authorization: Bearer` の API キーでセルを決める。本文にセルの名前を書かせない。
    - ローカルの tray のアップロードの口は、一覧の面と別の番号で `127.0.0.1` にだけ開き、portless の名前を付けない。鍵は求めない。
    - 送る側は、ローカルの tray の宛先を、`andon tray serve` が状態の置き場に書いた控えから引く。控えが無ければ送らない。環境変数で送るのを切れる口を持ち、`tests/lib/isolate.sh` と Go の検査がそれで切る。切らないと、`andon digest send` や `andon issue report` を打つ検査が、動いている本物のローカルの tray に偽の報告を上げる。`tests/isolation` に、本物の宛先に届いたら落ちる見張りを足す。
    - `GET /v1/meta` は tray のバージョンを返す。
    - オーナーからセルへファイルを渡す口は、この ADR では作らない。同じホスト名と同じ鍵の下の `/v1/inbox/` を、その口のために空けておく。
    捨てた案: セルが R2 の S3 の API へ直に書く案は、セルに R2 の資格情報を置くことになり、一覧の行を Worker が作れない。

16. **3つの面は、面ごとに別の Worker にして、要る束縛だけを持たせる。**（3つのホスト名はオーナーが 2026-11-24 に決めた。Worker の分け方は Chief Engineer が決めた。ホスト名の置き方はオーナーが決めた。2026-11-26）
    | 面 | ホスト名の例 | 前に置くもの | 持つ束縛 |
    |---|---|---|---|
    | 一覧の面 | `tray.example.com` | Access | D1、署名の鍵、画面のファイル |
    | 報告の面 | `tray-view.example.com` | 無し（署名付き URL） | R2、署名の鍵 |
    | アップロードの口 | `tray-up.example.com` | 無し（API キー） | R2、D1 |
    理由: 1つの Worker をホスト名で振り分けると、振り分けの誤り1つで、Access の外から一覧が読める。Worker を分ければ、報告の面のコードは D1 に届かず、アップロードの口のコードは署名の鍵に届かない。
    細部: コードは `tray/` の1つの木で、入口のファイルが3つである。ローカルの tray は、3つをまとめてホスト名で振り分ける入口を使ってよい。その入口はデプロイの設定に載せない。MCP の口は作らない（オーナーが 2026-11-24 に決めた）。
    ホスト名は、オーナーの持つ1つのドメインの下に3つの名前を並べる。実際の名前は公開の文書に書かず、オーナーがセルの repo の設定に書く。
    捨てた案: 報告の面を別の登録ドメインに置く案は、cookie の漏れに対していちばん堅いが、ドメインがもう1つ要る。報告の面は `sandbox` で出すので（決めたこと 18）、同じドメインの下でも報告のスクリプトは cookie を読めない。

17. **一覧の面は Access の内側に置き、Worker も Access の JWT を確かめる。**（オーナーが決めた。2026-11-24。細部は Chief Engineer が決めた。Access のポリシーはオーナーが決めた。2026-11-26）
    細部:
    - 一覧の面の `/api/` の下は、どの要求でも `Cf-Access-Jwt-Assertion` を確かめる。見るのは、署名（チームの公開鍵）、アルゴリズム、`aud`、`iss`、期限である。
    - 書き込む要求は `Origin` も確かめる。
    - 画面のファイルは Worker のコードを通らずに返る（事実 10）。画面のファイルにデータを入れない。
    - 検査を通さない組み立ては、ローカルの入口のファイルにだけ置く。デプロイする入口は、Access の設定の値が無ければ要求を断る。
    - パスは `URL` で1度だけ読み、符号化を解いたあとの値で比べない（事実 12）。
    - Access のポリシーは、オーナーのメールアドレス1つだけを通し、セッションを 30 日にする。スマホを失くしたときは、オーナーが Access のダッシュボードでセッションを切る。短くすると、スマホでログインし直す回数が増える。

18. **報告は、一覧の面の枠の中に、短い期限の署名付き URL で別オリジンから出す。**（別オリジンと署名付き URL はオーナーが 2026-11-24 に決めた。枠と細部は Chief Engineer が決めた）
    一覧の面の報告の画面は、上に戻る口だけを持つ細い帯を置き、その下の枠（iframe）に報告を出す。枠の中身は報告の面から来る。報告に見た目を被せない。
    細部:
    - 画面が開くと、一覧の面の API（`POST /api/reports/<id>/open`）が、既読を書き（決めたこと 20）、署名付き URL を返す。既読を書く口は `POST` だけで、`GET` に書き込みを持たせない。
    - 署名は HMAC-SHA256 で、対象は報告の id と期限である。期限は5分にする。期限が切れた URL には、開き直すよう促す短いページを返す。
    - 報告の id は乱数で、R2 のキーにそのまま使う。パスから組み立てない。アップロードは R2 を先に書き、あとで D1 のバージョンを上げる。
    - 枠の要素にも `sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox"` を付ける。`allow-same-origin` と `allow-top-navigation` は付けない。応答のヘッダだけで `sandbox` を付けると、報告のスクリプトが枠を外のページへ移したとき、移った先は `sandbox` の外で動き、1回のクリックで一覧の面ごと別のページへ移せる（Chromium で確かめた）。
    - 一覧の面は `Content-Security-Policy: frame-ancestors 'none'` を返す。
    - 報告の面のヘッダは、`Content-Security-Policy`（`default-src 'none'`、インラインと `data:` のスクリプトとスタイル、`data:` と `blob:` の画像とメディア、`data:` のフォント、`connect-src 'none'`、`form-action 'none'`、`base-uri 'none'`、`frame-ancestors` は一覧の面のオリジンだけ、`sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox`）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`、`X-Robots-Tag: noindex` である。
    - PDF は枠に入れず、署名付き URL を新しいタブで開く。iOS は枠の中の PDF を1ページしか出さないという報告がある。
    - 残る危うさ: 報告の中のスクリプトは、自分の文書の中身を付けて、枠の中を外のページへ移すことができる。CSP はページの移動を止められない。報告を作るのはセルの役で、外から来た文をそのまま HTML のスクリプトにしないことは、役の側の決まりである。
    捨てた案: スマホでは枠を使わずに同じタブで遷移する案は、ホーム画面から開いた画面にブラウザの戻る口が無く、戻れなくなる。署名付き URL を一覧に埋めて長い期限にする案は、URL が漏れたときに 30 日読める。

19. **API キーはセルごとに1本で、一覧の面で発行して失効でき、セルでは volume に置く。**（セルごとに1本はオーナーが 2026-11-24 に決めた。発行と失効は Chief Engineer が決めた。セルの置き場はオーナーが決めた。2026-11-26）
    一覧の面に、セルを足す画面を置く。セルの名前を入れると、鍵を1度だけ見せる。サーバは鍵の SHA-256 だけを持つ。同じ画面で、鍵を失効させ、作り直せる。失効した鍵のアップロードは断る。
    セルでは、オーナーが `andon tray auth` に鍵を stdin で渡す。置き場は `~/.config/andon/tray/` の下のモード 600 のファイルで、compose の新しい volume `tray` に載せる。`andon digest auth` と同じ形である（`signal.PlaceToken`）。
    理由: 鍵が漏れたとき、止める口が無いと、tray ごと作り直すことになる（事実 12）。
    細部: 鍵の正を 1Password に置くときは、ホストで `op read` の出力を ssh 越しに `andon tray auth` へ流す。この1行を運用の手引きに載せる。`op` は必須にしない。volume を足すときは、`package/compose.yaml`、`internal/boot/owners.go` の `HomeVolumes`、`image/Dockerfile` の置き場を作る行を揃える。今あるセルは、bootstrap を打ち直すと volume が付く。
    捨てた案: ペアリングの短いコードで発行する案は、手順が1つ増えるだけで、1人で使う間は利きめが無い。`.env` に `op://` の参照を書いて、ホストの bootstrap が `op run` で解き、環境変数で渡す案は、オーナーが出口で挙げた。セルの中の `op` は 1Password のアプリと連携できないので、解くのはホストになる。その形は、「ホストからトークンを持ち込まない」と「bootstrap のホストの前提は docker と bash だけ」の2つの決まりを変え、鍵がセルの全部のプロセスの環境変数になり、鍵を替えるたびにコンテナを作り直す。

26. **tray は andon のイメージに入れ、boot が起動し、葉 `andon tray` で扱う。**（Chief Engineer が決めた）

## 受け入れ条件

継ぎ目は3つである。Go の検査（`go test ./...`）、tray の検査（`tray/` の中の Workers の検査とブラウザの検査）、端から端の検査（`tray/` の中のスクリプト。job `tray` が回す）である。オーナーの手で見る条件は「オーナーが見る」と書く。

1. セルの中で `andon publish` を打つと、stdout の1行がローカルの tray の URL で、一覧に未読で出る。開くと既読になる。同じ slug で中身を変えて出し直すと未読に戻り、同じ中身なら既読のままである。slug を省いて同じファイル名で2度出すと、2件の報告になる。tray に届いた報告は `files/` に無い。証拠は端から端の検査の出力である。
2. ローカルの tray が止まっているときに `andon publish` を打つと、`files/` に写り、stdout の1行がそのパスで、終了コードは 0 である。証拠は Go の検査の出力である。
3. 最後に上がった日時が 30 日より前の報告は、一覧に出ず、古い報告のページに出る。証拠は Workers の検査の出力である。
4. `andon digest send` が出したダイジェストが、同じ一覧に並ぶ。`sent.json` の `files` の行の `url` がローカルの tray の URL で、選んだプロジェクトでは kind `tray` の行が在る。Cloudflare の tray への送りが落ちた `send` は、打ち直すとその行だけを送り直す。証拠は Go の検査と端から端の検査の出力である。
5. `andon issue report` を打つと、課題の報告が一覧に出る。出し直すと同じ行が未読に戻る。tray が止まっていても、報告は kanban に書かれ、終了コードは 0 である。証拠は Go の検査の出力である。
6. Markdown、画像、PDF、テキストが開け、ほかの形式はダウンロードになる。証拠はブラウザの検査の出力である。
7. `project.json` に `tray` を書いたプロジェクトの報告だけが、偽の Cloudflare の tray に届く。書いていないプロジェクトの報告は届かない。証拠は Go の検査の出力である。
8. Cloudflare の tray へ送る HTML の文の部分に秘密の形の文字列を入れると、届いた中身では伏せてある。同じ HTML に `.secret:hover{}` のスタイルと `const token = …` のスクリプトがあっても、届いた中身のスタイルとスクリプトは元のままである。ローカルの tray の写しは変わらない。証拠は Go の検査の出力である。
9. 相対で引いた画像とスタイルを持つ HTML を出すと、tray の写しは1枚で表示できる。`#` で始まるリンクは同じ枠の中で動き、外へのリンクは新しいタブで開く。証拠は Go の検査とブラウザの検査の出力である。
10. 一覧の面の API は、正しい Access の JWT が無い要求を断る。`aud` の違う JWT、期限の切れた JWT、署名の合わない JWT も断る。`Origin` の違う書き込みも断る。証拠は Workers の検査の出力である。
11. アップロードの口は、API キーの無い要求と、失効させた鍵の要求を断る。あるセルの鍵で、別のセルの報告は上書きできない。証拠は Workers の検査の出力である。
12. 報告の面は、署名の無い URL、期限の切れた URL、別の報告の署名を付けた URL を断る。証拠は Workers の検査の出力である。
