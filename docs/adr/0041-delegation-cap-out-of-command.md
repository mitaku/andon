# ADR-0041: 委譲の上限を andon コマンドから外し、オーナーが前もって任せた PR をオーナーを待たずにマージする（仕様・設計。2026-11-21）

## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-21）: 「語を置き換えるだけの PR は自動マージの範囲に入れていい」「仕様から変えていいんじゃない。というのも、andon コマンドが、プロジェクトについて強く認識しているのは違和感がある」。

役の名前を「オーナー」に改める [ADR-0036](0036-owner-not-hito.md) と、3 語を改める [ADR-0040](0040-kanban-gate-version-words.md) の実装が十数本の PR になり、その多くがオーナーのマージに回った。オーナーのマージを待つ間に、ほかの PR が先に入り、rebase とレビューのやり直しが重なった。オーナーは語の置き換えの PR を自動でマージしてよいと決め、`andon delegate grant merge C` を打ったが、command は「andon プロジェクトの merge は B まで」と断った。この上限は、command が `andon` というプロジェクトの名前を見て決めている。オーナーは、command が特定のプロジェクトを名前で知っていること自体をおかしいと見ている。この文書は、上限を command から外し、オーナーが前もって任せた PR がオーナーを待たずに入る道を決める。

モデル: 調べなかった（項目の状態・状態を動かすコマンドの順・自動で動く部品の順を変えない。変わるのは、gate がレベルを決める規則と、委譲の `merge` の値の読み方である。`model/IssueLife.tla` は、委譲の `merge` が変わることを行動 `MergeSettingChanges` として写していて、名指しの付与と取り消しは、その課題にとって同じ出来事になる。gate を回し直すきっかけは足さない。事実 15 と決めたこと 8）。

## 読んで分かった事実（2026-11-21。main `524b5e5` と、Andon を開発しているセルで実測）

1. **上限の場所。** `internal/delegate/delegate.go` の定数 `AndonProject = "andon"` と関数 `andonCap` が、プロジェクトの slug が `andon` のときだけ、`merge` の値 C と、`line-change` の `none` 以外の値を断る。同じファイルの `Parse` は、slug が `andon` のプロジェクトに型 `andon` 以外を書くことも断る。`internal/delegate/cmd.go` は、slug が `andon` のプロジェクトに初めて委譲を書くとき、型を `andon` にする。検査は `tests/andon-gate.sh` に 1 行、`internal/delegate/delegate_test.go` の `TestParseRejects` に 2 つの場合がある。
2. **上限の出所。** [design.md](../design.md) §6 の問い 26 で、オーナーが 2026-11-05 に「『何を作るか』と Andon 自身のパッケージが常にオーナー、はそのまま」と答えた。§1.10 の範囲の表は「Andon 自身のライン（Andon のセルの `andon` プロジェクト）は常に `B` まで（型 `andon` で固定）」と書き、[contract.md](../contract.md) §11 の読み方 6 が同じことを書き、[ADR-0028](0028-improvement-loop.md) は事実 6 に写して、やらないことに「Andon のパッケージに触れる改善の PR の自動マージ。レベル C はオーナーがマージする」を置いた。同じ日の問い 7 の答えは「案件 repo の `AGENTS.md`・`REVIEW.md` はレベル B に下げる。Andon の repo はレベル C のまま」だった。[ADR-0039](0039-retro-scale-with-flow.md) 決めたこと 9 は、skill を下げたときに「`AGENTS.md`・テンプレート・hook などは C のまま」と書いた。
3. **上限が止めているもの。** 委譲を書けるのはオーナーだけである。読む側は、セルの repo の HEAD の `project.json` を、最後に変えた commit の書き手が `andon.toml` の `owner` のときだけ信じる。上限が止めているのは、オーナー自身が Andon のプロジェクトに広い委譲を書くことだけである。
4. **もう 1 つの道は開いている。** セルの `gate.local.json` はキーごとに既定の条件表を置き換え、`tier_overrides` はパスごとにレベルを決め直せる。gate がこのファイルを重ねるのは、最後に変えた commit の書き手がオーナーのときだけである。オーナーは 2026-11-20 に、Andon を開発するセルで `package/skills/**` を B に下げた（[ADR-0039](0039-retro-scale-with-flow.md) 決めたこと 9・10）。上書きに当たったパスは既定の C の決まりを通らないが、追加行のパターン・行数・担当の申告は今までどおり効く。
5. **委譲の範囲 `line-change` は判定に使われていない。** 値の検査と表示にしか使われていない（[ADR-0039](0039-retro-scale-with-flow.md) 事実 8）。
6. **語の置き換えの PR の行き先。** 語を置き換える PR は 12 本がマージ済みである（#369・#383・#389・#391・#392・#394・#395・#397・#398・#401・#404・#406）。9 本がレベル C になってオーナーのマージに回り、3 本はレベル B で自動でマージされた。C の 9 本のうち 4 本（#383・#392・#394・#404）は、当たった理由が追加行のパターンだけだった。残りの 5 本はパスに当たった（#369 は `package/` のテンプレート・hook・`codex.rules` など、#389 は `package/environment.md`・`package/writing.md`・テンプレート、#391 はモデルの規則と対応表、#398 は `AGENTS.md`、#406 は workflow・`image/**`・`AGENTS.md`・モデルの規則）。オーナーを待つ間に head が動き、gate の記録は #391 の課題で 6 回、#394 の課題で 4 回残った。
7. **追加行のパターンの空振り。** gate は、追加行（`+` の行）がパターンに当たれば C にする。語を置き換えると、書き換えた行は丸ごと追加行になるので、その行にもとからあった `sudo` や `password=` の語に当たる。2026-11-18 からのマージ 145 本のうち、パターンに当たったのは 17 本だった。hunk ごとに、当たった文字列の数を追加行と削除行で比べると、当たる箇所が増えていたのは 7 本で、10 本はもとからあった語への空振りだった。kanban の gate の記録で数えると、パターンが理由に入った課題 15 件のうち 10 件が空振りだった。
8. **語の置き換えだけかは、機械で見分けられない。** マージ済みの PR を、語の表（「人」→「オーナー」、3 語 → kanban・gate・バージョン）どおりの置き換えだけでできているかで測った。語の前後の空白の違いは無視した。測ったのは #404 と #406 が入る前の 10 本である。表どおりの置き換えだけでできた PR は 0 本だった。行で数えると 75〜88% が表どおりで、残りは手での言い直しだった（同じ句に「オーナー」が 2 つ並ぶ所、識別子をバッククォートで囲む所、検査の見本、ADR の索引の行など）。
9. **オーナーがマージする理由の内訳（kanban の gate の記録。課題ごとに最後の判定）。** 記録のある課題は 123 件で、レベル A が 4 件、B が 55 件、C が 64 件。C の 64 件が当たった理由は、多い順に、skill が 27 件、追加行のパターンが 15 件、`AGENTS.md` が 12 件、`image/**` が 8 件、`package/environment.md` と `package/writing.md` が 7 件、モデルの規則と控えと対応表が 6 件、workflow が 5 件、行数が 4 件、テンプレートが 3 件、`package/settings.json` と `package/codex.rules` が 3 件、`package/gate.json`・hook・`package/compose.yaml` が 1 件ずつだった。1 件が複数の理由に当たるので、合計は 64 を超える。C の 64 件のうち 5 件は、報告の受け入れ条件に `manual` があった（#389 の課題を含む）。
10. **線を動かしたときに残る数（同じ 64 件で数えた）。** skill を B にした今の線では 45 件が C に残る。空振りを直すと 39 件、`package/environment.md` と `package/writing.md` を下げると 35 件、`AGENTS.md` も下げると 26 件になる。さらにテンプレートを下げると 24 件、モデルの規則も下げると 19 件、`image/**` も下げると 16 件になる。
11. **オーナーのマージが止めたもの。** 2026-11-18 からの 3 日で、オーナーのマージの前に PR の中身を直させた記録は無い。欠陥を止めたのは独立レビューと checks だった（[ADR-0039](0039-retro-scale-with-flow.md) 事実 7）。
12. **課題の `merge` の予約キー。** Chief of Staff は、C になる見込みの課題に `merge: person` を書く。自動マージは、課題が `merge: auto` で、最後に書いたのが Chief of Staff のときだけ進む（`internal/issue/merge.go` の `Authorized`）。マージの直前に、委譲の `merge` を読み直し、gate のときと違えばマージしない。
13. **担当の申告。** 報告の受け入れ条件に `manual` があるとレベルが 1 つ上がり、`risk.one_way` が `true` だと C になる（`internal/gate/decide.go` の `FromReport`）。条件表のレベルがもう C のとき、`manual` は理由の行を足さない。
14. **`project.json` は知らないキーを断る。** 古いバージョンの `andon` は、知らないキーのある `project.json` を読めないものとして扱い、委譲なし・書いてよい repo なしに倒れる（[contract.md](../contract.md) §11 の `signals` の注）。
15. **gate は、決めたあとは head が動くまで回り直さない。** dispatcher は、gate の記録に判定があり、PR の head が動いていなければ、gate を回さない（`internal/issue/merge.go`）。回り直すのは、head が動いたときと、approve のあとマージの直前の読み直しが通らなかったときだけである（`model/IssueLife.tla` の `Regate`）。`needs_human` で止まった課題は、委譲が変わっても回り直さない。`merge: person` のまま approve が出て Chief of Staff に知らされた課題は、あとで `auto` に直しても回り直さない。同じ head の gate の問いが開いている間は、担当の `andon issue ready` も断られる（`internal/issue/issue.go`）。
16. **レベル A のパス。** 既定の条件表の `tier_a_paths` は `docs/**`・`tests/**`・`README*`・`CHANGELOG.md` である。`tests/**` は行数に数えない。レベル A の PR は、課題が `review: on` でなければ、独立レビューなしで入る。
17. **課題と PR の結びつき。** gate が課題と PR を結ぶのは、報告の `pr` と branch の名前である（`internal/gate/gate.go`）。PR に依頼書の外の変更が混ざっているかを、機械は見ない。見るのは独立レビューである。
18. **`override` の当たり方。** `tier_overrides` に当たったパスは、既定の C の決まりを通らない（`internal/gate/decide.go`）。鍵を `**/AGENTS.md` と書くと、どの階層の `AGENTS.md` にも当たる。

## 前提（同意済み。番号）

オーナーが 2026-11-21 に、入口の確かめで 6 つとも同意した。1 の数は、あとで数え直して事実 6 の数に直した（結論は変わらない）。6 の「何も書かなければ」は、今ある `project.json` の型と値が変わらないことを指す（決めたこと 2 の「変わらないこと」）。

1. 困りごとは、オーナーのマージを待つ間に rebase とレビューのやり直しが重なることである。オーナーに回った語の PR の半分は、もとからあった語への空振りだけが理由だった（事実 6・7）。
2. 何もしなければ、残りの語の課題もオーナーのマージに回る。語を改める ADR はこの 2 週間で 3 本出ていて、次も同じことが起きる。
3. 語の置き換えだけの PR かどうかは、機械では見分けられない（事実 8）。
4. 上限を外しても、委譲を書けるのはオーナーだけという守りは変わらない（事実 3）。
5. このテーマは、オーナーが 2026-11-05 に決めた「Andon 自身のパッケージはいつもオーナーがマージする」を、固定の決まりから、オーナーが委譲で広げられる既定に変える（事実 2）。
6. 変更はパッケージのバージョンアップで全セルに届く。既定の値は変えず、何も書かなければ今までどおり B までが自動である。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案。あとから覆したら上書きせず下に足す）

### 範囲

1. **2026-11-21 このテーマの範囲は 4 つにする（オーナーが決めた。Chief Engineer の推奨は、このセルのパスの線の引き直しを入れない 3 つだった）。** 上限を command から外すこと、追加行のパターンの空振りを直すこと、オーナーが課題を名指しして前もって任せる口を足すこと、Andon を開発するセルでオーナーがマージするパスの線を gate の記録から引き直すこと、の 4 つである。
   理由: [ADR-0039](0039-retro-scale-with-flow.md) は skill だけを下げ、残りの線の引き直しを別のテーマに送っていた。記録が 3 日分たまり、線ごとの数が読める（事実 9・10）。
   推奨が違った理由: 上限を外せば、オーナーは期限つきの `merge C` をいつでも打てる。名指しの口があれば語の PR は通るので、線の引き直しは急がない案だった。
   捨てた案: 新しい口を足さず、オーナーが期限つきの `merge C` を打って通す（効いている間は、gate の条件表・workflow・設定・1,000 行を超える PR・担当が戻せないと申告した PR まで、全部が自動になる）／Andon のプロジェクトの既定を、v0.0.x の間は全部自動にする（gate の条件表と設定と workflow は、自動で変わると gate そのものを緩められる）。

### 上限を command から外す

2. **2026-11-21 `andon delegate` は、プロジェクトを名前で見分けて上限を決めない（オーナーが決めた）。** slug が `andon` のプロジェクトも、ほかのプロジェクトと同じ決まりで委譲を読み書きする。`merge` を C まで、`line-change` を `plant` まで委譲でき、型も選べる。オーナーが 2026-11-05 に決めた「Andon 自身のパッケージが常にオーナー」（[design.md](../design.md) §6 の問い 26）を、固定の決まりから、オーナーが委譲で広げられる既定に変える。[design.md](../design.md) §1.10 の「常に `B` まで（型 `andon` で固定）」と、[contract.md](../contract.md) §11 の読み方 6 と、[ADR-0028](0028-improvement-loop.md) のやらないこと「Andon のパッケージに触れる改善の PR の自動マージ」のうち、オーナーが委譲しても変えられないとしていた所を覆す。
   理由: command が特定のプロジェクトを名前で知っているのは、道具の形としておかしい（オーナー）。上限が止めていたのはオーナー自身だけで、エージェントは委譲を書けない（事実 3）。パスの線は、オーナーがセルの条件表を書けば今でも下げられ、上限は片方の道だけを塞いでいた（事実 4）。
   変わらないこと: 委譲を書けるのはオーナーだけである。今ある `project.json` の型と値は変わらない。Andon を開発するセルは、型 `andon` のまま B までが自動である。委譲の無いプロジェクトは、今までどおり何も任せていないものとして読む。`irreversible` に `delete-remote` を入れられないことは、どのプロジェクトにも効く決まりなので残す。
   変わること: slug が `andon` のプロジェクトに、型を書かずに command で初めての委譲を足すと、型はほかのプロジェクトと同じ既定の `work` になる。`work` と `andon` の違いは `line-change` の値だけで、この値は判定に使われていない（事実 5）。型 `andon` にしたいオーナーは、`project.json` に型を書く。
   細部: 消すのは、定数 `AndonProject`、関数 `andonCap` とその呼び出し 2 か所、`Parse` の「andon プロジェクトの preset は andon だけ」、`cmd.go` の初めての委譲で型を `andon` にする行。検査は、`tests/andon-gate.sh` の 1 行と、`internal/delegate/delegate_test.go` の `TestParseRejects` の 2 つの場合を、通ることを確かめる検査に替える。直す文は、[design.md](../design.md) §1.3 と §1.10（上限の行と、Andon のパッケージは常にオーナーと書いた行）、[contract.md](../contract.md) §11 の読み方 6、`schema/project.schema.json` の `delegation` の説明文、repo の `AGENTS.md` の「gate がオーナーのマージに回す」と書いた 2 行、Chief of Staff の手引き `retro.md` とトリアージの skill の「レベル C で、オーナーがマージ」と言い切っている 2 行。`docs/vision.md` の原則 5 は、読んで食い違うなら注を足す。
3. **2026-11-21 上限の置き場を別に作らず、型 `andon` の名前と値は残す（Chief Engineer が決めた）。** 上限をデータに移す口は作らない。型 `andon` は、どのプロジェクトも選べる型の 1 つとして残す。
   理由: 上限を書くのも外すのもオーナーなので、データに置いた上限は、同じ書き手が同じファイルで外せる 1 行になる。検査を足さずに手順だけが増える。型の名前を変えると、知らない型のある委譲は読めないものとして扱われ、バージョンが食い違う間は委譲なしに倒れる。
   捨てた案: `project.json` の `delegation` に上限のキーを足す（上の理由）／型ごとに上限を持たせる（command がプロジェクトの種類ごとの方針を持ち続ける）／型 `andon` を別の名前に改める（上の理由。動いているセルの `project.json` をオーナーが書き直すことにもなる）。

### 空振りを直す

4. **2026-11-21 追加行のパターンは、当たる箇所がその hunk で増えたときだけ C の理由にし、増えていなければ B の理由にする（オーナーが決めた）。** gate は、差分の hunk ごとに、パターンに当たった文字列を追加行と削除行で数える。同じ文字列の数が追加行のほうで多い hunk が 1 つでもあれば、今までどおり「追加行 <パターン>」をレベル C の理由にする。追加行が当たっていても、どの hunk でも増えていなければ、「追加行 <パターン>（増えていない）」をレベル B の理由にする。
   理由: 語の置き換えで書き換えた行は丸ごと追加行になり、もとからあった語に当たる。パターンに当たった 17 本のうち 10 本がこの空振りだった（事実 7）。パターンが見たいのは、危ない語が新しく入ることである。B の理由に残すのは、当たった行が書き換わった PR を、独立レビューなしのレベル A に落とさないためである（事実 16）。
   受け入れること: 1 つの hunk の中で `sudo` の行を 1 つ消し、別の `sudo` の行を 1 つ足した変更は、C にならない。鍵を足す行を別の鍵に書き換える変更も同じである。こうした変更は、オーナーでなく独立レビューが見る。
   細部: 新しいファイルと、足すだけの hunk は、今までどおり C になる。ファイルを消して別の名前で足した変更は、hunk が別なので C になる。どのパスにも、どのパターンにも同じ決まりを使う。条件表のキーは足さない。数えるときは差分を hunk の形で読み、行の頭が `+++` の追加行も数える（今のコードは、hunk の中でも `+++` で始まる行を見ていない）。
   捨てた案: 増えていなければ理由にしない（`docs/**` や `tests/**` だけの PR がレベル A になり、当たった行の書き換えが独立レビューなしで入る。反論で見つかった）／ファイルごとに数える（離れた所の消した行で打ち消せるので、hunk ごとより緩い）／当たった行を、削除行と字が近いかで見分ける（決まりが説明できなくなる）／`docs/**` をパターンから外す（文書に新しく書いた `curl … | sh` は、読んだ利用者が打つ）／セルの条件表でパターンの一覧を置き換える（今でもできるが、全部の PR で外れる）。

### 前もって任せる口

5. **2026-11-21 語の置き換えだけの PR かどうかを、機械で見分けない（Chief Engineer が決めた）。** gate に、差分が語の表どおりの置き換えだけかを確かめる規則は足さない。
   理由: マージ済みの 10 本を測ると、表どおりの置き換えだけでできた PR は 0 本だった（事実 8）。語を改める作業には、手での言い直しが必ず入る。
   捨てた案: オーナーが語の表を条件表に書き、gate が表どおりの差分だけを通す（上の理由で 1 本も通らない）／Chief of Staff か担当が「語の置き換えだけ」と印を付け、gate が信じる（kanban の予約キーは、広げる向きには使わない。[design.md](../design.md) §1.10）／PR へのオーナーの承認やラベルを gate が読む（セルの `gh` はオーナーのアカウントで動くので、GitHub の上ではオーナーとエージェントを見分けられない）。
6. **2026-11-21 オーナーは、課題を名指しして `merge` を委譲できる（Chief Engineer が形を決めた。口を足すことは、オーナーが範囲で決めた）。** `andon delegate grant merge <A|B|C> --issues <id,id,…>` が、名指しの委譲を `project.json` に足す。名指しされた課題の PR は、プロジェクト全体の `merge` の値と、名指しの値のうち、広いほうで判定される。ほかの課題の判定は変わらない。独立レビュー・checks・受け入れ条件は、今までどおり要る。
   理由: 見分けるのが機械にできないなら、見分けるのは任せると決めたオーナーである。オーナーの決断を、PR ができたあとの 1 本ずつのマージから、作業の前の 1 回に移す。置き場を委譲にすれば、書き手の照合・根拠・期限・取り消しを、今ある仕組みのまま使える。
   受け入れること: 名指しの値が C なら、その課題の PR は、どのパスに触れても、1,000 行を超えても、自動でマージされる。依頼書の外の変更が混ざっていても、機械は止めない（事実 17）。止めるのは、独立レビューと checks である。プロジェクト全体の `merge C` と同じ広さが、名指しした課題の数だけ付くことになる。
   細部:
   - 形: `grants[]` の 1 件に、任意のキー `issues`（課題の id の配列。1 件以上、重なりなし）を足す。`issues` を書けるのは `scope` が `merge` で、値が `A`・`B`・`C` の grant だけである。
   - 読み方: `issues` のある grant は、プロジェクト全体の値（`andon delegate show` の実効の値）に重ねない。重ねる所は `Effective` の 1 つで、直し忘れると名指しの値がプロジェクト全体に漏れる。課題ごとの値は、プロジェクト全体の `merge` と、その課題を名指しした有効な grant の値のうち、いちばん広いものにする。名指しは広げる向きにだけ効く。狭めるのは、今までどおり課題の `merge: person` か `revoke` である。
   - command: `--issues` は `grant` だけが取る。`narrow` は取らない。名指しする課題は、そのプロジェクトの kanban にあり、`done` でないものに限る。無い id と `done` の id は断る。
   - 読む所: gate の判定（`internal/gate/gate.go`）と、マージの直前の読み直し（`internal/issue/merge.go` の `stillAuthorized`）の 2 か所が、課題ごとの値を読む。委譲の `merge` を読むのは、この 2 か所だけである。gate のあとに名指しが取り消されるか期限が切れれば、マージの直前の読み直しが断る。
   - 表示: `andon delegate show` は、名指しの grant を、名指しした課題と一緒に並べる。`--json` の `grants` に `issues` が入る。
   - バージョン: `issues` を書くのは、セルのパッケージを `issues` を知るバージョンに上げてからにする（事実 14）。書くのは新しいバージョンの command なので、手順どおりなら起きない。パッケージを古いバージョンに戻すときは、先に名指しの grant を行ごと消す必要があるので、戻す手順に 1 行足す。`project.json` を読むのは `andon` と `kanban` だけで、どちらも同じパッケージのバージョンである。
   - モデル: 行動は足さない。`model/IssueLife.tla` の `MergeSettingChanges` の注釈に、名指しの付与と取り消しも同じ出来事であることを書く。
   捨てた案: パスごとの上書きに期限を付ける（どの課題かを言えない。語の PR のほかも通る）／kanban の問いに前もって答える形にする（kanban には、書き手がオーナーであることを確かめる仕組みが無い）／課題の親や ADR の番号で名指しする（課題の `parent` は誰でも書ける。[ADR-0039](0039-retro-scale-with-flow.md) 事実 8）／名指しに、通してよいパスの一覧も書かせる（語の PR は workflow や hook にも触れた。一覧を書く手間が、1 本ずつマージする手間に近づく）。
7. **2026-11-21 名指しの委譲は、担当が戻せないと申告した PR には効かない（オーナーが決めた）。** 担当の報告の `risk.one_way` が `true` のとき、gate は名指しの委譲を読まず、プロジェクト全体の `merge` で判定する。受け入れ条件に `manual` があるだけの PR には、名指しが効く。
   理由: 名指しは、作業の前に、依頼書の中身を見て出す許しである。作業の途中で担当が「戻せない」と申告したなら、許しの前提が変わっている。戻せないことはオーナーが決める。`manual` は、機械で確かめられない条件があるという申告で、レベルを 1 つ上げるだけである。この repo の `manual` の多くは、マージのあとにセルで確かめる条件である。C の 64 件のうち 5 件に `manual` があり、語の PR の #389 もその 1 つだった（事実 9）。`manual` で名指しを止めると、ねらった PR が通らない。
   細部: プロジェクト全体の `merge` が C のプロジェクトでは、今までどおり申告のある PR も自動でマージされる。
   捨てた案: `manual` があっても名指しを読まない（上の理由。#389 が通らない）／名指しは申告があっても全部通す（戻せない変更が、作業の前の許しで入る）。
8. **2026-11-21 名指しは gate が回る前に出し、Chief of Staff がその課題の `merge` を `auto` に書く（Chief Engineer が決めた）。** オーナーが名指しを書いたら、Chief of Staff は `andon delegate show` で読み、名指しされた課題の予約キーを `merge: auto` に直す。直すのは、担当が `andon issue ready` を打つ前である。gate を回し直すきっかけは足さない。
   理由: 自動マージは、課題が `merge: auto` のときだけ進む（事実 12）。gate は、決めたあとは head が動くまで回り直さない（事実 15）。名指しは作業の前に出す許しなので、gate のあとに効かせる道は要らない。gate が `needs_human` を決めて止まった PR は、オーナーがその場にいるので、今までどおりオーナーがマージすれば済む。
   細部: gate がもう決めた課題に名指しを書いても、head が動くまで効かない。rebase や直しで head が動けば、gate が回り直し、そのときから効く。Chief of Staff の手引き（`brief.md` と `gate.md`）に、この順を 1 行ずつ足す。
   捨てた案: 委譲が変わったら dispatcher が gate を回し直す（状態を動かす流れを変える。使い道は、オーナーがその場にいる場面だけである）／名指しが `merge: person` を飛び越える（狭める向きの口が効かなくなる）。

## やらないこと（範囲の外。理由）

- **パッケージの既定の条件表（`package/gate.json`）を変えること。** 変えるのは Andon を開発するセルの上書きだけ（決めたこと 11）。
- **hook・gate の条件表・設定・workflow・公開の検査・`image/**` を下げること。** C のまま（決めたこと 10）。語の置き換えのように前もって任せられる課題は、名指しで通す。
- **行数の線（1,000 行）を変えること。** 大きい機械的な PR は、名指しで通す。
- **担当の申告（`manual`・`one_way`）の扱いを、プロジェクト全体の `merge` が C のプロジェクトで変えること。** 型 `hobby` の今の扱いのまま。
- **委譲の範囲 `line-change` を判定に使うこと。** 今は表示だけである（事実 5）。上限を外すだけで、読む所は足さない。
- **振り返りの直す先の種類 `andon`（`internal/retro`）を変えること。** これは、直す先が Andon のパッケージであることを表す種類で、プロジェクトの名前を見ていない。
- **`merge` のほかの範囲（`deploy`・`publish`・`irreversible`）の名指し。** 要ると分かってから足す。
- **gate がもう決めた課題を、名指しのあとに回し直すこと。** 名指しは gate が回る前に出す（決めたこと 8）。
- **課題と PR の結びつきを強めること。** 報告を書ける端末の照合や、依頼書の外の変更を機械で見ることは、名指しより前からある別のテーマである（事実 17）。
