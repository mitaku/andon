# ADR-0051: 外の信号の受け口を実際に流し、main の失敗を壊した変更に結ぶ（仕様・設計。2026-11-22）

- 状態: **決定（2026-11-22）**。オーナーが対話の中で「決めた」と言った。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書き、この行を「覆された → ADR-NNNN」に直す。小さな改めは「決めたこと」に下から足す。

## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-21）: 「Signalをもう少し強化したいと思っています。」前提として、選択的な Dark Factory としての骨子は固まってきたと言い、オーナーの介在は扱っているものの性質上まだ多いが、もっと減らして、なおかつ効率的にできそうだと言った。

Signal は、起きたことが自分からラインに入り、オーナーを通らずに課題になる受け口である。オーナーが望んでいるのは、この受け口が実際に流れている状態と、オーナーが見て言っていることを機械が先に拾う状態である。オーナーは 2026-11-22 にこの言い直しに同意した。

調べると、受け口は Andon を開発するセルで一度も動いていなかった。読む出所を書く場所に、何も書かれていなかったからである。動いていたとしても、main の CI が落ちたという信号から、落とした変更までは辿れない形だった。工場の中の出来事では、着手できる課題があるのに担当が 1 人も動いていない時間が、約 90 時間のうち 35 時間あった。この最後の件は、同じ日に別の ADR が決めたので、この文書では扱わない（決めたこと 2）。

モデル: 調べなかった（決めたことは、信号の記録の 1 項目の書き方と、通知の項目と、設定の下書きで、状態の動き方を変えない。検討の途中で、起動されない課題の知らせを 2 つの形でモデルにして調べたが、その知らせはこの文書の決定に入れていない。数は事実 9 に書いた）

## 読んで分かった事実（2026-11-22。main `7b1f4ab` と、Andon を開発しているセルの kanban と記録で実測。時刻は日本時間）

1. **受け口は、このセルで一度も動いていない。** セルの `project.json` に `signals` が無い。dispatcher は、`signals` が無ければ信号を読む command を打たない（`internal/dispatcher/signals.go` の `hasSignals`）。信号の記録のファイルも無い。セルの repo の履歴にも、`signals` を書いた commit は無い。ADR-0011 が決まったのは 2026-11-09 で、13 日がたっている。
2. **読める出所は 2 つである。** `andon signal collect` が読むのは `github-ci` と `github-issues` だけで、Sentry・Linear・Cloudflare は名前とトークンの置き場だけがある（ADR-0011 決めたこと 3・14）。
3. **main の CI の失敗は、ADR-0011 のあと 4 回あった。** 2026-11-10 に 1 回、2026-11-19 の夜から 2026-11-20 の 0 時 13 分までに 3 回で、どれも `tests.yml` である。そのあとは無い。4 回とも、信号としては拾われていない。それより前の 2026-11-07 には、11 時から 20 時までの約 9 時間、`go.yml` と `tests.yml` が 19 回ずつ続けて落ちた。その間のマージは、どれも落ちた main の上に乗った。
4. **外の issue は少ない。** この repo の issue は全部で 6 件で、open は 1 件である。repo は public なので、外の人が issue を書ける。今は、オーナーが GitHub を見ない限り、だれも気づかない。
5. **外の信号から切られた課題は 0 件である。** 観察の課題は 13 件が見る日を待っていて、見る信号は kanban と gate と measure の記録か、オーナーの目視である。信号の記録を使うものは無い。
6. **信号の記録は、見えるたびに `release` を上書きする。** `internal/signal/signal.go` の `merge` は、見えた信号の `release` をそのまま記録に書く。`readCI` が返すのは、workflow ごとの最新の run の commit である。main が落ちている間に別の PR がマージされると、`release` は新しい commit に移る。[ADR-0028](0028-improvement-loop.md) は、このために失敗を壊した課題に結べないと書き、そのテーマでは直さないとした。
7. **最初に見えた時点でも、`release` は壊した変更とは限らない。** dispatcher が出所を読むのは既定で 10 分に 1 回である。落とした変更のあと、読む前に別の変更がマージされると、最新の run の commit は別の変更を指す。このセルでは、約 13 時間に 33 回のマージがあった。
8. **通知 `signal` は `release` を運ばない。** `detail` は `source`・`key`・`url`・`title`・`weight` である（ADR-0011 決めたこと 16）。Chief of Staff の手引き（`package/skills/chief-of-staff/playbooks/cut.md`）は、直す課題に切って `links` に `url` と `key` を書くところまでで、壊した変更を引く手は無い。
9. **着手できる課題があるのに、担当が動いていない時間が長い。** kanban の履歴（2026-11-19 の 2 時から 2026-11-22 の 20 時までの約 90 時間）から数えた。担当が 1 人も動いていないのに着手できる課題があった時間は、15 分以上続いたものだけで 10 回、合計 35.3 時間である。3 時間以上が 4 回で、28.9 時間を占める。枠が 1 つ以上空いていて着手できる課題がある状態は、75.5 時間あった。数え方は、`after` と並行の上限の履歴を入れ、`review` の課題も枠を使うものとして数えた。オーナーの go を待っていた時間と、ぶつかるので並べていた時間は、履歴から見分けられないので含んでいる。同じ期間に、オーナーが Chief of Staff へ枠の空きを言った文は 4 通あった。
10. **起動されない課題の知らせは、まとめ方で数が大きく変わる。** 事実 9 の履歴に当てると、課題ごとに 15 分で知らせる形は 244 回、ライン全体でいちばん長く待っている課題の時間で 1 件にまとめる形は 41 回になる。モデルで調べると、課題ごとの形は、空いている枠の数より多くの知らせを 1 巡で積んだ。ライン全体で 1 つの時間だけを持つ形は、Chief of Staff が課題を起動した直後に別の課題が着手できるようになると、条件が続いて見えて、働いている Chief of Staff に知らせた。
11. **工場の中の出来事の多くは、もう通知になっている。** dispatcher が届ける通知の種類は 19 で、止まった担当（`stalled`・`error`）、見込みとのズレ（`estimate`）、課題どうしのぶつかり（`impact`）、マージ（`merged`）、memory の量（`memory`）がある。2026-11-19 から 2026-11-22 に届けた通知は 1238 件である。
12. **`project.json` は、オーナーが commit したものだけが読まれる。** `andon signal collect` は `delegate.ReadProject` で読み、これはオーナーが作者の commit の中身を返す（`OwnerFile`）。`andon create` が書く下書きは、オーナーが commit するまで読まれない。

## 前提（同意済み。番号）

オーナーが 2026-11-22 に同意した。

1. このセルでは、外の出所を増やすより、工場の中で起きたことを機械が拾うほうが、オーナーの介在が減る。
2. 何もしないと、オーナーが見ていない時間の止まりや失敗は、オーナーが気づくまでラインに入らない。
3. 受け口・信号の記録・Chief of Staff への通知・毎朝のトリアージを使い、新しい役は足さない。
4. 配り方は今と同じにする。何を見るかは、オーナーが `project.json` に書く。

前提 1 が指していた工場の中の出来事のうち、いちばん効くものは、同じ日に別の ADR が決めた（決めたこと 2）。

## 決めたこと

### 範囲

1. **2026-11-22 範囲は、受け口を流すことと、失敗を壊した変更に結ぶことの 2 つにする（オーナーが決めた）。** 入口でオーナーが選んだ範囲は、受け口を流す・工場の中の信号を同じ道に乗せる・信号が課題になるまでの穴を塞ぐ、の 3 つだった。このうち工場の中の信号を、この文書から外す。
   理由: 工場の中の出来事で、数の裏づけがいちばん大きいのは、着手できる課題が起動されないまま残る件である（事実 9）。これは、同じ日に決まった別の ADR（枠が空いたままのとき、トリアージと振り返りと点検を回す）が、dispatcher が空きを見つけて Chief of Staff に知らせる形で決めた。同じ知らせを 2 つの文書で決めない。
   捨てた案: 起動されない課題の知らせを、この文書でも決める（決定が 2 か所になり、どちらが正か分からなくなる）／Sentry・Linear・Cloudflare を読む command まで広げる（入口でオーナーが範囲の外にした。ADR-0011 決めたこと 3 のまま、使う案件が出たときにする）。
2. **2026-11-22 工場の中の出来事は、信号の記録に乗せず、この文書では新しく足さない（Chief Engineer が決めた）。** 工場の中の出来事を機械が拾うときは、今までどおり dispatcher の通知の種類として足す。
   理由: 信号の記録は、外の出所のためにできている。`url` は `https` の URL が必須である。届いた信号を Chief of Staff は直す課題に切る。トリアージはタイトルを外の人の文として扱う。読むかどうかは、オーナーが `project.json` に書いたかで決まる。工場の中の出来事は、この 4 つのどれにも合わない。工場の中の出来事のうち、止まった担当・見込みとのズレ・ぶつかり・マージ・memory の量は、もう通知になっている（事実 11）。検査の遅さとレビューの回数は、振り返りが拾う。オーナーを待っているものは、行燈が出す。
   捨てた案: 信号の記録に、工場の中の出所を足す（上の 4 つを、出所ごとに分ける書き足しが要る）／夜の間、オーナーのマージ待ちの後ろで課題が止まっていることを知らせる（オーナー待ちは行燈が出している。機械が代わりにできることが無い）。

### 受け口を流す

3. **2026-11-22 Andon を開発するセルは、main の CI の失敗を `now`、issue を `later` で読む（オーナーが決めた）。** オーナーが、セルの `project.json` に次の 2 行を書いて commit する。issue への書き戻し（`write_back`）は付けない。
   理由: 受け口が 13 日のあいだ動いていない（事実 1）。main の CI の失敗は、落ちている間のマージが全部その上に乗るので、すぐに Chief of Staff へ届ける。issue は急がないので、毎朝のトリアージに載せる。書き戻しは、public の repo の issue に Andon がコメントを書くことで、外への約束になる。今は open の issue が 1 件なので、要るときにオーナーが足す。
   細部:
   ```json
   "signals": [
     {"source": "github-ci", "weight": "now"},
     {"source": "github-issues", "weight": "later"}
   ]
   ```
   `project.json` を書くのはオーナーだけである（[contract.md](../contract.md) §11）。書いたあと、`andon signal collect --project <slug>` が終了コード 0 で終わり、信号の記録に open の issue の 1 件が載ることを確かめる。
   捨てた案: main の CI の失敗だけを読む（外の人が書いた issue に、だれも気づかないままになる。事実 4）／issue も `now` で届ける（外の人が書くたびに Chief of Staff のターンを使う）。
4. **2026-11-22 `andon create` の下書きに、main の CI の失敗を `now` で読む 1 行を入れる（Chief Engineer が決めた）。** repo を 1 つ以上渡して作るプロジェクトの `project.json` の下書きに、`{"source": "github-ci", "weight": "now"}` を入れる。`andon create` は、入れたことと、要らなければ消すことを、最後の案内に 1 行で出す。
   理由: 受け口を決めたセル自身が、13 日のあいだ書かずにいた（事実 1）。書き忘れに気づく仕組みが無い。下書きはオーナーが commit するまで読まれないので（事実 12）、「書かなければ何も取りに行かない」という ADR-0011 の前提 7 は変わらない。
   細部: repo を渡さずに作るプロジェクトの下書きには入れない。issue は下書きに入れない。open の issue が多い repo では、最初の朝にトリアージの項目が issue の数だけ増えるからである。
   捨てた案: 何も入れない（今と同じ書き忘れが、次のプロジェクトでも起きる）／`signals` が無いことを毎朝 Chief of Staff に知らせる（要らないと決めたプロジェクトでも鳴り続ける）／issue も入れる（上のとおり）。

### 失敗を壊した変更に結ぶ

5. **2026-11-22 `github-ci` の `release` は、失敗が始まった run の commit にする（Chief Engineer が決めた）。** 最新の結果が失敗の workflow について、読んだ run を古いほうへ辿り、結果の出た run が失敗である間さかのぼる。いちばん古い失敗の run の commit を `release` にする。`url` と `title` は、今までどおり最新の run のものにする。
   理由: 最新の run の commit は、落ちている間にマージされた別の変更を指す（事実 6・7）。失敗が始まった run の commit なら、最初に読んだのが何回かのマージのあとでも、始まりを指す。
   細部:
   - 辿るのは、今も読んでいる新しい 100 件の中だけである。GitHub への問い合わせは増やさない。
   - 結果の出た run とは、今までと同じく、成功・失敗・時間切れ・起動の失敗である。取り消しと飛ばしは、辿るときも数えない。pull request の run は、今までどおり除く。
   - 100 件の中に成功の run が無ければ、読めた中でいちばん古い失敗の run の commit にする。
   - 毎回の変更で走らない workflow では、失敗が始まった run の commit が、壊した変更そのものとは限らない。壊した変更は、最後に成功した run の commit のあとから、失敗が始まった run の commit までの間にある。だから、決めたこと 8 では「候補」と呼ぶ。
   捨てた案: 最新の commit のままにして、Chief of Staff が run の履歴を手で辿る（落ちるたびに同じ手作業をする）／始まりの commit を別のキーで足す（commit が 2 つになり、どちらを辿るかを読む側が決めることになる。最新の commit は `url` の run から読める）。
6. **2026-11-22 出来事が続いている間、信号の記録の `release` を書き換えない（Chief Engineer が決めた）。** 記録が `active` のまま、また見えたときは、`release` を今の値のままにする。記録に `release` が無いときだけ、見えた値を入れる。初めて見えたときと、消えてまた出たとき（`episodes` が増えたとき）は、見えた値を入れる。出所によらず同じにする。
   理由: 落ちている時間が長いと、失敗が始まった run が 100 件の外へ出る。そのとき決めたこと 5 の辿り方は、もっと新しい commit を返す。記録に残した始まりを、それで上書きしない。
   細部: [contract.md](../contract.md) §15 の「見えたものは `release` を今の値にする」を、この決まりに直す。`schema/signal.schema.json` の形は変えず、`release` の説明だけを直す。
   捨てた案: 毎回上書きする（今の形。事実 6）。
7. **2026-11-22 通知 `signal` の `detail` に `release` を足す（Chief Engineer が決めた）。** 記録に `release` があるときだけ、同じ値を載せる。`<news>` の行には、先頭の 12 桁を出す。
   理由: Chief of Staff が受け取るのは通知で、信号の記録は読まない。通知に無ければ、決めたこと 5・6 で残した commit が Chief of Staff に届かない（事実 8）。
   細部: `schema/notification.schema.json` の `signal` の形に、任意の `release`（40 桁の 16 進）を足す。[contract.md](../contract.md) §6 の表も直す。ADR-0011 決めたこと 16 が書いた `detail` の 5 つの項目は、そのまま残る。
   ```json
   {"at": "2026-11-22T01:00:00Z", "project": "sample-site", "kind": "signal",
    "detail": {"source": "github-ci", "key": "github.com/example/sample-site/tests.yml@main",
     "url": "https://github.com/example/sample-site/actions/runs/1", "title": "tests: Add the button",
     "weight": "now", "release": "9c4e1b0d7a3f5e2c8b6d4a1f0e9c7b5a3d2e1f08"}}
   ```
   捨てた案: dispatcher が GitHub に聞いて PR の番号まで載せる（dispatcher が GitHub に聞く回数が増える。切る前に 1 回だけ要る問い合わせなので、切る人がする）。
8. **2026-11-22 Chief of Staff は、`release` から壊した変更の候補を引いて依頼書に書く（Chief Engineer が決めた）。** `release` のある `signal` の通知を受けたら、直す課題を切る前に、その commit の PR を引く。依頼書の「解決すべき問題」に、失敗が始まった変更の候補として、PR の URL と、何の変更だったかを書く。課題の `links` にも PR の URL を足す。
   理由: 直す担当が最初にするのは、何が変わって落ちたかを探すことである。Chief of Staff が 1 回引けば、担当はそこから始められる。
   細部:
   - 引き方は `gh api repos/<owner>/<repo>/commits/<sha>/pulls --jq '.[0].html_url'` である。PR が引けなければ、commit の URL を書く。
   - その PR を出した課題は、PR の本文の末尾のメモの行から分かる。まだ動いている課題なら、Chief of Staff は、新しい課題を切るか、その担当に直させるかを、今までどおり自分で決める。
   - 直すか、戻すかも、今までどおり Chief of Staff が決める。変更のレベルが C ならオーナーへ知らせる線も変えない。
   - 手引き `cut.md` の「`signal` の通知を受けたら」に、この手を足す。command は足さない（ADR-0011 決めたこと 17 のまま）。
   捨てた案: `andon signal trace <sha>` を足す（`gh` の 1 行で足りる）／壊した課題の担当へ、dispatcher が自動で差し戻す（片付いた課題を機械が起動し直すことになり、課題の一生の動きを変える。別のテーマである）。

## やらないこと（範囲の外。理由）

- **起動されない課題の知らせと、空いた枠の使い道。** 決めたこと 1。同じ日に決まった別の ADR が扱う。事実 9・10 の数は、その実装と観察で使える。
- **Sentry・Linear・Cloudflare を読む command。** 入口でオーナーが範囲の外にした。ADR-0011 決めたこと 3 のまま、使う案件が出たときにする。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に）

継ぎ目は今あるものを使う。信号を読む所は、`internal/signal` の `GH`（`gh` を呼ぶ関数を差し替える口）である。通知は `internal/dispatcher` の通知を組む関数と、`tests/schema.sh` の schema の照合である。下書きは `internal/create` の `Draft` である。本物の GitHub を読む確かめは、条件 8 だけである。

1. 新しい順に、失敗（commit C）、失敗（commit B）、成功（commit A）の run を返す偽の `gh` で `andon signal collect` 相当を回すと、記録の `release` が B になる。証拠は `go test ./internal/signal/` の出力である。
2. 条件 1 の run の間に、取り消しの run と pull request の run を挟んでも、`release` は B のままである。証拠は同じ検査の出力である。
3. 返した run が全部失敗のとき、`release` は、返した中でいちばん古い失敗の commit になる。証拠は同じ検査の出力である。
4. 条件 1 のあと、さらに新しい失敗（commit D）を足して 2 回目を回すと、`count` は 2 になり、`url` は D の run になり、`release` は B のままである。証拠は同じ検査の出力である。
5. 条件 4 のあと、成功を挟んでまた失敗（commit F）させると、`episodes` が 2 になり、`release` が F になる。証拠は同じ検査の出力である。
6. `release` のある記録から積んだ通知 `signal` の `detail` に、同じ `release` がある。`release` の無い記録から積んだ通知には、`release` のキーが無い。どちらも `schema/notification.schema.json` に通る。証拠は `go test ./internal/dispatcher/` と `tests/run --changed` の中の `tests/schema.sh` の出力である。
7. `andon create` が repo を 1 つ渡されて作る下書きに、`github-ci` を `now` で読む 1 行があり、`delegate.ParseProject` に通る。repo を渡さない下書きには `signals` が無い。証拠は `go test ./internal/create/` の出力である。
8. オーナーが決めたこと 3 の 2 行を commit したあと、セルで `andon signal collect --project <slug>` が終了コード 0 で終わり、信号の記録に `github-issues` の 1 件がある。オーナーが見る（`manual`）。Chief of Staff が、当てたあとの検証の課題で確かめてもよい。
9. 手引き `cut.md` の「`signal` の通知を受けたら」に、決めたこと 8 の手がある。レビュアーが読んで確かめる。
