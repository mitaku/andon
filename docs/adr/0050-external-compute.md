# ADR-0050: 重い command を外のマシンで回し、定期の仕事を API キーで対話なしに動かす（仕様・設計。2026-11-22）

- 状態: **提案（2026-11-22）**。検討の途中までの結果である。オーナーは出口で、全体の設計をもう少し検討したいと言い、「開いている問い」の 4 つを決めていない。決まるまで、この文書から依頼書を切らない。「決めたこと」のうち、決めたこと 1 だけがオーナーの決めたことで、ほかは Chief Engineer の案である。続きを検討するときは、この文書を土台にして「決定」に直すか、新しい ADR を書く。
- 主題: セルを動かしている PC の CPU に縛られずに、並行して動かす担当の数を増やせるようにする。担当が回す検査とビルドを、セルの外のマシンで走らせる口を足す。あわせて、サブスクリプションに付く API キーのクレジットを使えるように、定期の仕事を API キーで対話なしに起動する道を足す。コードをセルの外のマシンへ送る決定と、セルの外のサービスへお金を払う決定と、セルに新しい資格情報を置く決定を含む。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。この文書が足す約束は「決めたこと」に形を書き、実装の課題が写す（それまでは提案）。

## 問題（オーナーの言葉で。言い直しの段落）

オーナーは 2026-11-21 に、v0.0.13 のあとにやりたいことの 1 つとして、こう言った。「このPCでは４つ（＋アルファ）しか動かすのが大変とわかったので、もう少し外部リソースを活用できる仕組みなどを考えておきたい（たとえばCloudflare Sandbox+Agentsのようなものだったり）」。

オーナーの目的は、ラインで同時に動かせる担当の数を、この PC の力に縛られずに増やせるようにすることである。困りごとは、この PC で担当を 4 つより多く動かすと、負荷が高くて大変なことである。Cloudflare Sandbox と Agents は例で、それに決めたわけではない。

オーナー（2026-11-22。入口の前提の確かめで）: 「基本的に同意だが、今はClaudeやGPT、GeminiのサブスクリプションでAPI-Keyにクレジットがつくためここも活用できたらしたいと考えている。CloudflareのAI-Gateway経由でそのAPI-Keyを活用する手段とかも考慮できるといいかも」。

オーナー（2026-11-22。出口の 1 問目で）: 「もう少し検討をしてみてもいいかもね、全体の設計を。なので途中までの結果を残しつつ閉じてもいいかも」。この文書は、その途中までの結果である。

モデル: 調べなかった（課題の状態の定義も、状態を動かす command の順と断り方も、dispatcher の順も、役の間のやりとりも変えない。決めたこと 24）

## 読んで分かった事実（2026-11-22。main `7b1f4ab` と、Andon を開発しているセルの kanban と記録で実測）

1. **PC の大きさ。** セルを動かしている PC は 8 コア 16 スレッドで、メモリは 31 GB ある。セルのコンテナが使ったメモリは、最大で約 12 GB だった。
2. **並行の上限の経緯。** オーナーは 2026-11-20 に上限を 4 から 6 に上げ、約 3 時間後に CPU の負荷を理由に 4 へ戻した。上限の値は `project.json` の `chief_of_staff.parallel` にあり、守らせているのは Chief of Staff の手引きの文だけである（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 事実 11）。
3. **エージェント本体は軽い。** 動いている Claude Code のプロセス 3 つは、起動してからの時間に対して CPU を 2〜10% 使い、メモリは 0.45〜0.53 GB だった。`doing` の課題が 8 件から 11 件あった約 25 分のあいだ、セルのコンテナが使った CPU 時間と、Claude Code と Codex のプロセス自身の CPU 時間を 15 秒おきに控えた。セル全体は平均で 5.2 コア分を使い、15 秒の区切りの最大は 15.6 コア分だった。エージェント本体の分は約 2 割で、残りの約 8 割は、エージェントが打つ command の分である。
4. **重いのは検査である。** `tests/run` は、検査のスクリプトをスレッドの数と同じ 16 本まで並べて走らせる。`tests/run` は自分で鍵（`/tmp/andon-tests-run.lock`）を取るので、セルの中で同時に走るのは 1 本だけで、2 本目は待つ。担当 2 人が全部の検査を同時に回したときに、load average が 25 だった記録がある（[ADR-0032](0032-shorten-time-to-merge.md) 事実）。負荷の高いときに検査が揺れて落ち、単独で回し直した件を、振り返りが 2 回、合わせて 8 件拾っている。
5. **検査 1 回の時間。** 担当が証拠に撮った記録は 288 件ある。`tests/run --changed` は、鍵を待つ時間を含めて平均 269 秒（9 回）と平均 444 秒（3 回）だった。`bash tests/schema.sh` は平均 597 秒（3 回）だった。`tests/isolation` は 15 分以上かかる。記録の実行時間を足すと、2026-11-20 は 139 回で 2.2 時間、11-21 は 144 回で 1.9 時間だった。担当が記録を撮らずに回した分は、ここに入らない。同じ repo の CI は、4 vCPU の runner で検査の全部を平均 192 秒で回している（14 回）。`tests/run --changed` は、変えたファイルを `origin/main` との分かれ目から引く。
6. **流れ。** 動いている課題は平均 3.96 件で、上限の 4 にほぼ張り付いていた（ADR-0042 事実 5）。`andon measure` で 2026-11-18 から 11-21 の 4 日を 11-22 に数えると、片付いた課題は 260 件で、1 日に 65 件だった。課題が待った時間の平均は、前の課題を待つ状態で 3.36 時間、起動を待つ状態で 3.0 時間だった。作業の時間は平均 0.74 時間、レビューの時間は平均 0.47 時間だった。待ちには、前の課題やオーナーを待つ分も含まれる。
7. **起動の内訳。** 同じ期間の起動の記録は 477 件で、レビュアー（プロファイル `codex-review`）が 253 件、担当が 202 件（`claude` 165、`sonnet` 36、`codex` 1）、Chief Engineer が 22 件だった。
8. **トークンと、API の定価に直した額。** 同じ 4 日間で、Claude Code はキャッシュの読みが 34.8 億、キャッシュの書きが 5,700 万、出力が 1,260 万トークンだった。Opus 5.5 の定価で数えると約 1,230 ドルで、1 日あたり約 310 ドル、1 セッションの平均は約 4 ドルになる。Codex は入力 3,350 万、キャッシュの読み 5.0 億、出力 570 万トークンで、レビュアーが使う GPT-6 Luna の定価なら約 11 ドル、GPT-6.2 Sol の定価なら約 170 ドルである。
9. **作業側を別のマシンに出す形は、設計だけがある。** [design.md](../design.md) §1.5 は、担当とレビュアーを別のマシンで動かしてよいと書く。課題の予約キー `machine` はその起動先だが、`andon issue start` と `andon issue resume` は `machine` のある課題を断る（`internal/issue/start.go`・`internal/issue/resume.go`）。[contract.md](../contract.md) の原則 5 は、作業側が別のマシンのとき、command が置き場に書き、dispatcher が引く形を書いている。[dispatcher.md](../dispatcher.md) §7.3 の G7 は、kanban の鍵が別のマシンをまたいで効かないことを書いている。[ADR-0002](0002-herdr-spaces.md) 決めたこと 19 は、別のマシンでの worktree の作り方を「その先」に回した。[ADR-0007](0007-interim-gap-inventory.md) は、このテーマが立ってから Chief Engineer が決めるとした。
10. **担当をセルに縛っているもの。** 担当を別のマシンで動かすと、次のものが成り立たなくなる。kanban を読み書きする command（`kanban`・`andon issue report`・`ready`・`ask`・`record`）は、セルのファイルと鍵を使う。レビュアーは `findings.json` を、担当は作業の控えを、kanban の置き場に直接書く。Stop フックは kanban と dispatcher の控えを読む。起動し直しは、セルにあるセッションの記録と worktree を使う。コストの集計と振り返りも、セルにあるセッションの記録を読む。Claude Code と Codex と `gh` のログインは、セルの volume にある。オーナーに見せる dev サーバと `andon publish` は、セルの中で動く。
11. **hc は、別のマシンを扱う口を持っている。** hc 0.1.17 は、`hc machine add` で SSH か任意の command 越しにマシンを足す。短命のマシンに付ける印 `--temp` がある。`hc run --on <machine>` は別のマシンに端末を立てる。`hc exec --on <machine>` は端末なしで command を走らせ、出力と終了コードを返す。`hc exec -i` は標準入力を渡し、`--env` は環境変数を足す。`hc exec` は、最長 600 秒で command と、それが起動したものを終わらせる。このセルの `hc machine ls` は空である。hc の手引きは、エージェントを対話で動かし、1 回で出力して終わる形では動かさないように書いている。hc の template は、渡した task を最初のメッセージとして端末に貼る。
12. **手元で確かめたこと。** この repo の worktree で、commit していない変更を含む今の木を、index にも worktree にも触れずに commit の形にできた。それを `git bundle` で標準出力に出し、別の bare の repo が標準入力から受け取れた。全体の bundle は 5.4 MB で、受け取りは 1 秒だった。相手が main を持っているときの差分の bundle は 419 バイトだった。手元の `hc exec -i` は、30 万バイトの乱数をそのまま通した。別のマシン越しでは確かめていない。この repo には submodule も LFS も無く、無視されていて検査に要るファイルも無い。
13. **資格情報の決まり。** 認証はセルの中で取り、ホストからトークンを持ち込まない。git は HTTPS で、SSH 鍵を作らない（パッケージの `environment.md`）。外の信号のトークンは、`andon signal auth <出所>` が標準入力の 1 行を、モード 600 のファイルに置く。置き場は compose の volume である。[ADR-0011](0011-signals-and-value-loop.md) 決めたこと 10 は、置き場は守りではなく、守りはトークンの scope が読み取りだけであることだと書いている。セルの中の役は同じユーザーで動くので、どの役もファイルを読める。
14. **外の計算資源の候補。** 公式の文書で読んだ値は次のとおり。

    | 候補 | 大きさと料金 | 入り方とディスク |
    |---|---|---|
    | Cloudflare Sandbox と Containers | 1 つあたり最大 4 vCPU・12 GiB・ディスク 20 GB。CPU は使った分で 1 vCPU 秒 0.00002 ドル、メモリは確保した分で課金 | Worker 越しに command を走らせる。SSH では入れない。止まるとディスクは全部消える。実行の時間は保証されない |
    | 固定料金の VPS（例: Hetzner） | 共有 8 vCPU・16 GB で月 59〜70 ユーロ。共有 16 vCPU・32 GB で月 111 ユーロ。時間で課金され、いつでもやめられる | SSH で入る。ディスクは残る |
    | Fly Machines | 2 vCPU・4 GB で動いている間だけ月 66 ドル相当。秒で課金 | 専用の command か SSH で入る。volume は残る |
    | Sprites | CPU 1 時間 0.0385 ドル、メモリ 1 GB 時間 0.021875 ドル | 100 GB のディスクが残る。使わないと眠り、課金が止まる |
    | GitHub Actions | public の repo は無料。4 vCPU・16 GB。同時に 20 ジョブ | 対話では入れない。1 ジョブ 6 時間まで |
    | Claude Code の cloud セッション | 追加の料金は無く、プランの使用量から引かれる。4 vCPU・16 GB | 端末は無い。CLI から起動して追伸できる |

    Cloudflare の公式の例は、Claude Code を対話なしの `claude --print` で動かし、モデルの認証に AI Gateway のトークンを使う。サブスクリプションのログインを Sandbox で使う公式の例は見つからなかった。
15. **サブスクリプションに付く API クレジット。** Anthropic は、Max に月 100 ドル、Ultra に月 200 ドルの API クレジットを付けている。繰り越しは無い。対話で動かす Claude Code は対象外で、対象は API の直接の呼び出しと、Agent SDK と、連携した Console の組織の API キーで動かす `claude -p` である。クレジットが切れると、購入したクレジットが無い限り、次の月まで API の要求が止まる。OpenAI は ChatGPT Pro に月 100〜500 ドルを付けているが、API キーで動かす Codex は対象外と書いている。Google は AI Pro に月 10 ドル、AI Ultra に月 40 ドルか 100 ドルの Google Cloud のクレジットを付けていて、Gemini API に使える。
16. **AI Gateway。** Cloudflare の AI Gateway は、Claude Code と Codex と Gemini CLI をつなぐ手順を公式の文書に持つ。Claude Code は、接続先の URL と追加のヘッダを環境変数で渡す。プロバイダの鍵を Cloudflare の側に預ける形と、要求に鍵を付けて通す形がある。Gateway ごとにコストの上限を決められる。記録には、既定でプロンプトと応答の中身が残る。Gateway のトークンは、1 つの Gateway だけに絞れない。鍵を預けた形で Claude Code がどう動くかは、Cloudflare の文書の間で書き方が食い違っている。
17. **Claude Code の認証と、対話なしの旗。** 環境変数 `ANTHROPIC_API_KEY` があると、対話なしの `claude -p` はいつもその鍵を使う。環境変数はプロセスごとなので、同じセルで、あるセッションはサブスクリプション、別のセッションは API キーで動かせる。接続先を替えても、キャッシュの印とヘッダがそのまま通れば、プロンプトのキャッシュは効く。Claude Code 2.1.330 の `claude -p` には、1 回に使う金額の上限（`--max-budget-usd`）と、許可の確認に誰が答えるかの旗（`--permission-prompts`。`none` は、確認が要る操作を自動で拒む）がある。
18. **定期の仕事。** このセルのルーチンは、毎朝の振り返り（プロファイル `claude`）と、毎朝のトリアージ（プロファイル `sonnet`）である。毎朝のダイジェストが [ADR-0044](0044-owner-digest.md) で決まっている。どれも読むだけの仕事で、結果は JSON にして command が形を確かめる。ルーチンが足した課題には、ルーチンの名前（`routine`）が付く。1 回のコストは、ADR-0044 事実 7 のトークンを定価に直すと、トリアージが約 1 ドル、振り返りが 2〜3 ドルで、これにキャッシュの書きの分が加わる。3 つを毎朝回すと、月に 150〜250 ドルの見込みである。
19. **起動と、端末が消えた担当の扱い。** `andon issue start` は、hc の template と最初のメッセージで端末を起動する（`internal/spawn/spawn.go`）。届かなければ、ラベル `first_message.sent=false` を付けて、dispatcher が送り直す。boot は、プロファイルの frontmatter から `resume:` の行を抜いて `<名前>-resume` の template を作り、hc には知らないキーを渡さない（`internal/boot/boot.go`）。dispatcher は、`doing` の課題の端末が消えていたら `andon issue resume` を 1 回打ち、`<名前>-resume` で同じセッションを起動し直す（[dispatcher.md](../dispatcher.md) §2.9）。`andon issue resume --fresh` は、プロファイルそのものの template で、新しいセッションを起動する。`review` の課題は dispatcher の見張りの外で、端末が消えても何も起きない。Stop フックは、担当が報告か問いを kanban に返していれば、ターンの終わりを通す。
20. **外へ送ることの今の決まり。** 担当の決まり（skill `worker` §5 の表）と、Chief of Staff の原則 4 と、手引き `playbooks/blocked.md` の表は、プロジェクトの外のサービスへの送信と資格情報の作成を、その都度オーナーの go が要る操作に数えている。ADR-0044 決めたこと 12 は、ダイジェストの送信に限って、`project.json` に送り先を書いたことを go とする例外を足した。`project.json` と証拠の記録の読み手は、知らないキーを断る。`project.json` に新しいキーを書くと、それを知らないバージョンの andon は、委譲も、書いてよい repo も読めなくなる。
21. **対話なしの起動は、今は無い。** [ADR-0038](0038-statechart-in-chief-engineer-design.md) 事実 15 は、役はどれも対話の `claude` で起動され、対話なしの起動は無いと書いている。担当の許可の確認は、端末が止まって Chief of Staff が課題の範囲の中で答える形である（[operate.md](../operate.md)）。

## 前提（同意済み。番号）

オーナーが 2026-11-22 に同意した。前提 6 には、API キーのクレジットも使いたいという追加があった。

1. 大変だったのは CPU の負荷である。メモリや、Claude と Codex の使用量の上限が理由ではない。
2. CPU を使っているのは、主に担当が回す検査とビルドである（事実 3・4）。
3. 並行を増やせば、ラインは今より速く流れる（事実 6）。
4. 一から作らず、前から設計にあるものを土台にしてよい（事実 9・11）。
5. 有料の外のサービスを使う案を、候補に入れてよい。
6. 並行を増やすと、Claude と Codex の使用量もその分増える。外の計算資源が外すのは CPU の上限だけである。サブスクリプションに付く API キーのクレジットも、使えるなら使う。
7. Andon のパッケージの機能として作り、外のサービスは 1 つに決め打ちしない。
8. このテーマの成果は設計の文書で、実装は別の課題に切る。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案）

### 範囲と構造

1. **2026-11-22 範囲は、外の計算資源を使う仕組みと、対話なしの実行を 1 種類だけ足すことの 2 つにする（オーナーが決めた。Chief Engineer の推奨は、外の計算資源を使う仕組みだけだった）。** 対話なしの実行は、端末で対話せずに、依頼を 1 回渡すと最後まで走って終わる形を指す。Cloudflare Sandbox の公式の例と、Anthropic の API クレジットが使える形は、どちらもこれである（事実 14・15）。
   推奨の理由だったこと: API クレジットは月 100〜200 ドルで、今のラインの 1 日分の約 310 ドルに届かない（事実 8）。対話なしの実行は、Andon に今は無い形である（事実 21）。

2. **2026-11-22 担当はセルに残し、重い command だけを外のマシンで回す（Chief Engineer が決めた。入口でオーナーに伝えた形は、担当の端末ごと別のマシンへ出す形だった）。** 担当とレビュアーの端末、kanban、dispatcher、ログインは、今のままセルにある。担当が打つ検査とビルドだけが、セルの外のマシンで走り、出力と終了コードがセルへ戻る。
   理由: CPU の約 8 割は command の分で、エージェント本体は 1 つあたりコアの 1 割とメモリ 0.5 GB である（事実 3）。command だけを外へ出せば、負荷の大半が PC から消える。担当をセルに縛っているもの（事実 10）には、何も触れない。外のマシンに資格情報を置かずに済む。
   捨てた案は「代案」の節に書く。

### 外のマシンで回す

3. **2026-11-22 口は `andon issue run` の 1 つにし、走る場所は command が決める（Chief Engineer が決めた）。** `andon issue run <id> [--local] -- <command>` は、課題の worktree の今の木で command を走らせ、出力を流し、command の終了コードで終わる。プロジェクトに外のマシンが書いてあり、届けば、外で走らせる。書いてなければ、今と同じに手元でそのまま走らせる。`--local` は手元で走らせる。証拠を撮る `andon issue record` は、同じ道で走らせてから記録を書く。
   理由: 担当が場所を選ぶ形にすると、選び忘れが負荷になる。外のマシンの無いセルでも、同じ打ち方で動く。
   捨てた案: `tests/run` の中で外へ回す（この repo の検査にしか効かない）。担当が `hc exec --on` を直に打つ（木の送り方と、届かないときの扱いが、担当ごとにばらつく）。
   細部: 走らせるのは shell を通さない 1 つの command で、`andon issue record` と同じ渡し方にする。外で作られたファイルは戻さない。戻すのは出力と終了コードだけである。外では、端末なしの `hc exec` でなく、`hc run --bg --on` で立てた hc の端末の中で走らせる。`hc exec` は最長 600 秒で command を終わらせ、この repo の検査には 10 分に届くものと 15 分を超えるものがあるためである（事実 5・11）。出力と終了コードは外のマシンのファイルに受け、`andon issue run` が短い `hc exec --on` で読み継いで、手元に流す。

4. **2026-11-22 外のマシンは hc の machine で、使うマシンはオーナーが `project.json` に書く（Chief Engineer が決めた。コードをセルの外へ送ることと、借りるマシンは、オーナーが決める。出口で聞く）。** `project.json` に `remote` を足す。`machine` は hc の machine の名前で、`jobs` は同時に回す数である。Andon は、マシンがどのサービスのものかを知らない。hc が SSH か command で届くものなら、どれでも使える。`project.json` に書いてあることを、そのプロジェクトのコードをそのマシンへ送る go として扱う。
   理由: 別のマシンへ届く道は、もう hc にある（事実 11）。design.md も、別のマシンへは hc 越しに届くと決めている。`project.json` は、オーナーが書いたことを commit の作者で確かめているファイルである。
   捨てた案: Cloudflare Sandbox を直に呼ぶ口を Andon に持つ（Worker と、それを呼ぶコードを Andon が持つことになり、サービスを 1 つに決め打ちする。前提 7）。セルの `andon.toml` に書く（コードを外へ送る go は、プロジェクトごとに違う）。
   細部: 形は次のとおり。`jobs` は 1 以上で、既定は 1 である。`remote` が無いか、`project.json` を信じられないときは、外へ送らない。`remote` は、それを知るバージョンにセルを上げてから書く（事実 20）。

   ```json
   "remote": {"machine": "<hc の machine の名前>", "jobs": 1}
   ```

   改める決まり: 今の決まりは、プロジェクトの外のサービスへの送信を、その都度のオーナーの go で受ける操作に数えている（事実 20）。この決定は、その決まりに例外を 1 つ足す。足す先は、skill `worker` §5 の表、Chief of Staff の原則 4、手引き `playbooks/blocked.md` の表の 3 つである。足す文は「`andon issue run` と `andon issue record` が、`project.json` の `remote` のマシンへ課題の木を送ることは、オーナーがマシンを書いたことで go が出ている。ほかの外への送信は今までどおり」である。
   受け入れること（守りの限り）: セルの中の役は同じ境界にいる（事実 13）。どの役も、hc 越しに外のマシンで好きな command を走らせられる。守りは、外のマシンに資格情報を置かないこと（決めたこと 7）と、外のマシンをこの用途だけに使うことである。外のマシンから戻る出力は、担当のコンテキストに入る。これは、手元で回した検査の出力と同じ扱いである。

5. **2026-11-22 今の木を commit の形にして、git の bundle を hc 越しに送る（Chief Engineer が決めた）。** command は、課題の worktree の今の木を、commit していない変更と追跡していないファイルを含めて、1 つの commit の形にする。worktree と index には触れない。外のマシンが持っていない分だけを `git bundle` にして、`hc exec -i --on <machine>` の標準入力で渡す。外のマシンは、repo ごとの bare の写しに受け取り、課題ごとの作業フォルダをその commit にしてから command を走らせる。
   理由: GitHub を通さないので、外のマシンに GitHub の資格情報が要らない。作業の途中の木を push しないので、PR の head が動かず、レビューと gate が回り直さない。差分だけなら数百バイトで済む（事実 12）。
   捨てた案: 担当が push して外のマシンが GitHub から取る（private の repo で資格情報が要る。commit の前の木を試せない。PR を出したあとは push のたびに CI とレビューが回り直す）。rsync（SSH でしか届かないマシンに限られる）。
   細部: commit していない変更が無いときは、HEAD をそのまま送る。あるときは、HEAD を親にした commit を作って送る。bundle には、`origin` の既定の branch の参照も入れ、外の作業フォルダでも `origin/main` が手元と同じ commit を指すようにする。`tests/run --changed` のように、main との分かれ目を引く検査があるためである（事実 5）。無視されているファイルは送らない。外のマシンの作業フォルダは課題ごとに残し、無視されているファイルは消さないので、ビルドのキャッシュは次の回に使える。`andon issue finish` は、手元の片付けを全部済ませたあとに、外のマシンのその課題の作業フォルダを消す。届かなければ、消せなかったことを 1 行出して、そのまま終わる。

6. **2026-11-22 外のマシンの道具は、セルと同じイメージで揃える（Chief Engineer が決めた）。** 外のマシンでは、Andon のイメージのコンテナを 1 つ動かし、hc はその中に入る。指揮側（Chief of Staff・dispatcher・kanban）は起動しない。セルの repo は置かない。
   理由: 手元と同じ command が、同じ道具で動く。道具を入れる段を、Andon が別に持たずに済む。
   捨てた案: 素の Linux に道具を入れる手順を持つ（セルのイメージと別に、道具の一覧をもう 1 つ保つことになる）。
   細部: 用意はオーナーの手作業で、手順は [operate.md](../operate.md) に書く。雛形 `package/host/cloud-init.yaml` に、外のマシン用の形を足す。

7. **2026-11-22 外のマシンに、資格情報とセルの環境変数を渡さない（Chief Engineer が決めた）。** 外で走る command には、セルの環境変数を渡さない。渡すのは、Andon が決めた 2 つだけである。`ANDON_RUN_SLOT` は取った枠の番号で、`ANDON_RUN_JOBS` は枠の数である。Claude Code と Codex と `gh` のログインも、API キーも、外のマシンに置かない。資格情報の要る command は、`--local` で手元で走らせる。
   理由: 外のマシンに置かれるのは、コードの写しとビルドの生成物だけになる。マシンを失っても、漏れるのはコードだけである。

8. **2026-11-22 外のマシンに届かないときは手元で回し、手元は同時に 1 本にする（Chief Engineer が決めた）。** 外のマシンが書いてあるのに届かないとき、木を送れないとき、外で command を起動できないときは、理由を 1 行出して、手元で走らせる。このときは、セルに 1 つの鍵を取り、手元で同時に走るのを 1 本にする。
   理由: ラインを止めない。並行の上限を上げたあとに外のマシンが落ちても、手元の負荷が上限を上げる前より重くならない。
   細部: 外で起動できたあとに接続が切れたときは、手元で走らせ直さない。command は外の端末で走り続けているので、読み継ぎをやり直して結果を受け取る。10 分のあいだ届かなければ、0 でない終了コードで終わる。`remote` が無いプロジェクトでは、鍵を取らない（今と同じ）。

9. **2026-11-22 外のマシンで同時に回す数は `jobs` で決め、外のマシンの鍵で数える（Chief Engineer が決めた）。** 外のマシンに `jobs` 個の鍵を置き、command はどれか 1 つを取って走る。空きが無ければ、待っていることを 1 行出して待つ。鍵は、command のプロセスが終われば外れる。待つのは外の端末の中なので、`hc exec` の 600 秒の上限には当たらない。
   理由: 数える所を、走る所と同じにする。セルの側で数えると、接続が切れたときに数がずれる。
   細部: 既定は 1 である。証拠に撮った command の実行時間は 1 日に合わせて約 2 時間で（事実 5）、1 本ずつでも 1 台に収まる見込みである。この repo の `tests/run` は自分の鍵で 1 本ずつにしているので（事実 4）、`jobs` を 2 以上にしても、今のままでは `tests/run` どうしは並ばない。並べるには、この repo の `tests/run` を、枠の番号ごとの鍵と、枠の数で割った並べ方に直す。これはこの repo の検査の直しで、要るようになってから切る。

10. **2026-11-22 証拠の記録に、走ったマシンの名前を書く（Chief Engineer が決めた）。** 走らせた記録（contract.md §24）に `machine` を足す。外で走ったときだけ書く。commit と、commit していない変更の有無は、今と同じに、送る時点の worktree で決める。gate は、走った場所を問わない。
    理由: どれだけ外で走ったかを、あとで記録から数えられる。キーを足すだけなので、約束のバージョンは上げない。記録の読み手は知らないキーを断るので（事実 20）、読み手と書き手は同じ PR で直す。

11. **2026-11-22 外のマシンへ入る鍵はセルの中で作り、hc の machine のためだけに使う（Chief Engineer が決めた。セルに新しい資格情報を置くことは、オーナーが決める。出口で聞く）。** SSH で届くマシンを使うときは、鍵をセルの中で作り、オーナーが公開鍵を外のマシンに置く。ホストからは持ち込まない。git は今までどおり HTTPS である。パッケージの `environment.md` の「SSH 鍵を作らない」を、この 1 つの使い道を除く文に直す。
    理由: 認証はセルの中で取る、という今の決まりと同じ形にする（事実 13）。

12. **2026-11-22 担当の決まりに「検査とビルドは `andon issue run` で打つ」を足す（Chief Engineer が決めた）。** worker skill に 1 行足す。プロジェクトの `AGENTS.md` は、どの command が重いかを名指してよい。守らせる仕組みは足さない。
    理由: 外のマシンの無いセルでも同じ打ち方で動くので、決まりを 1 つにできる。短い command まで外へ回すと、送りと待ちのほうが長くなるので、何を回すかは担当とプロジェクトの指針に任せる。
    受け入れること: 担当が `andon issue run` を通さずに打った command は、今までどおり手元で走る。証拠に撮った分は 1 日に約 2 時間で、CPU の大半は、記録を撮らずに回した分とみられる（事実 3・5）。効きめは、担当がこの決まりに従う割合で決まる。価値の仮説の止める条件で見る。

13. **2026-11-22 並行の上限の値と数え方は変えず、上げるのはオーナーにする（Chief Engineer が決めた）。** 上限は今までどおり `project.json` の `chief_of_staff.parallel` で、数え方は ADR-0042 決めたこと 10 のままである。Andon は上限を自動で上げない。
    理由: 上限は、オーナーが PC の様子を見て決めてきた値である。外のマシンで回した割合を見てから上げられる。

14. **2026-11-22 課題の `machine` と、作業側を別のマシンに出す設計は、今のまま残す（Chief Engineer が決めた）。** `machine` は「まだ使えない」のままで、`andon issue start` は今までどおり断る。この ADR は、design.md §1.5 を覆さない。
    理由: 担当ごと外へ出す形は、メモリか、エージェント本体の CPU が次の上限になったときに要る。この ADR の部品（外のマシンの用意・木の送り方）は、そのときも使える。

15. **2026-11-22 最初の課題で、偽のマシンを使って hc の別のマシンの振る舞いを確かめる（Chief Engineer が決めた）。** 外のマシンを借りる前に、同じセルの中に、別の HOME で動く hc を「別のマシン」として足し、次を確かめる。bundle が `hc exec -i --on` をそのまま通ること。`hc run --bg --on` で立てた端末で、15 分かかる command が最後まで走ること。その出力と終了コードを、短い `hc exec --on` で読み継げること。途中で接続を切っても、command が走り続けて結果を受け取れること。エージェントでない command を `hc run` に直に渡したときの、端末の状態と終わり方。
    理由: 別のマシン越しの振る舞いは、手引きを読んだだけで、動かして確かめていない（事実 11・12）。お金のかかる手作業の前に、設計の前提を確かめる。最後の 1 つは、決めたこと 17 の起動の形の前提でもある。
    細部: 確かめた結果で、決めたこと 3・5・8・17 の細部を直す。前提が崩れたら、実装に進まず、Chief Engineer に戻す。

### 対話なしの実行と API キー

16. **2026-11-22 対話なしの実行は定期の仕事に当て、どのルーチンかはオーナーが `project.json` に書く（Chief Engineer の推奨。どの種類に当てるかはオーナーが決める。出口で聞く）。** `project.json` に `headless` を足す。`auth` は使う API キーの名前で、`routines` は対話なしで起動してよいルーチンの名前の並びである。`andon issue start` は、課題のルーチンの名前がこの並びにあるときだけ、対話なしの起動を選ぶ。ほかの課題は、今と同じに対話で起動する。
    理由: 定期の仕事は、読むだけで、PR もレビューも gate も通らず、結果の形を command が確かめる（事実 18）。途中で誰かが端末に話しかける場面が無い。月のコストの見込みは 150〜250 ドルで、付いてくるクレジットの大きさに近い。毎日決まった量を使うので、繰り越せないクレジットを使い切りやすい。
    捨てた案: レビュアーに当てる。レビュアーは起動の半分を占めるが（事実 7）、今は安いモデルの Codex で動いていて、API キーで動かす Codex はクレジットの対象外である（事実 15）。Claude の API キーで動かすと、担当と同じブランドになり、独立レビューに数えられない。レビューは安全の網なので、最初の 1 種類にしない。
    細部: 形は次のとおり。`headless` が無いか、`project.json` を信じられないときは、今と同じに対話で起動する。`headless` は、それを知るバージョンにセルを上げてから書く（事実 20）。

    ```json
    "headless": {"auth": "anthropic", "routines": ["triage"]}
    ```

17. **2026-11-22 プロファイルに `print:` の行を足し、最初の起動だけを対話なしにする（Chief Engineer が決めた）。** プロファイル `sonnet` と `claude` の frontmatter に、対話なしの command を書く `print:` の行を足す。boot は、`resume:` の行と同じに、この行を抜いて別に持ち、hc には知らないキーを渡さない（事実 19）。課題の `profile` は、今と同じ対話のプロファイルの名前のままである。担当は今と同じ skill を読み、同じ command で報告して、`kanban review` まで自分で進める。走り終わると端末は終わる。起動し直しは、`andon issue resume` も `--fresh` も、今のコードのまま、対話の command で起動する。
    理由: 起動・報告・検収の道を、もう 1 通り作らずに済む。端末の中で走らせるので、オーナーは今と同じ場所で画面を見られる。プロファイルの名前を分けないので、起動し直しの道が対話なしの command を拾うことが無い。
    捨てた案: 対話なしのプロファイルを別の名前で足す（`andon issue resume --fresh` はプロファイルそのものの template で起動するので、対話なしの command が、最初のメッセージを貼る形で起動される。事実 19）。
    細部: 対話なしの起動は、hc の template を通さず、`hc run` に command を直に渡す。最初のメッセージは、端末に貼らず、command の引数にする。hc の template は task を端末に貼るので、1 回で終わる command には渡せないためである（事実 11）。[contract.md](../contract.md) §8 の「起動の仕方」に、この形の行を足す。dispatcher は、対話なしで起動した端末に、最初のメッセージの送り直しと「続けて」を打たない。起動の記録には、対話なしで起動したことを書く。hc の手引きは対話で動かすように勧めているが、その理由は、途中で見て舵を切れるようにするためである。定期の仕事は舵を切る場面が無いので、この種類に限って外れる。ADR-0038 事実 15 の「対話なしの起動は無い」は、定期の仕事に限って変わる。定期の仕事は statechart を使わないので、その事実に依る決定は変わらない。
    受け入れること: 担当が報告か問いだけを返してターンを終えると、Stop フックが通し、`doing` のまま端末が終わる（事実 19）。このときは dispatcher の起動し直しが 1 回打たれ、続きは対話で動く。壊れはしないが、その回は API クレジットで走り切らない。

18. **2026-11-22 API キーは command がセルの中で聞いて置き、起動のときだけ環境変数に入れる（Chief Engineer が決めた。API キーをセルに置くことは、オーナーが決める。出口で聞く）。** `andon api auth <名前>` が、標準入力の 1 行を、モード 600 のファイルに置く。置き場は compose の volume を 1 つ足す。`andon api env <名前> -- <command>` が、そのプロセスにだけ鍵を環境変数で渡して起動する。`print:` の行の command は、これを通して `claude -p` を起動する。鍵を、command の引数・出力・記録に書かない。
    理由: 資格情報は、道具が自分の置き場に置く（事実 13 と同じ置き方）。環境変数はプロセスごとなので、ほかの担当はサブスクリプションのまま動く（事実 17）。
    受け入れること（守りの限り）: 置き場は守りではない（事実 13）。セルの中のどの役も、鍵のファイルを読めて、`andon api env` も打てる。API キーには、読み取りだけに絞る scope が無い。守りは、使える額の上限である。オーナーは、Console で自動の買い足しを切り、購入したクレジットを置かない。こうしておけば、鍵が漏れても、失うのはその月に付いたクレジットまでで、プランには請求されない（事実 15）。この手順は [operate.md](../operate.md) に書く。

19. **2026-11-22 API キーは Anthropic へ直接つなぎ、AI Gateway は接続先を書き足せば通せる形にする（Chief Engineer の推奨。AI Gateway を通すかはオーナーが決める。出口で聞く）。** `andon api auth` は、鍵と一緒に、接続先の URL と追加のヘッダも置ける。置いてあれば、`andon api env` がそれも環境変数で渡す。何も置かなければ、Anthropic へ直接つなぐ。
    理由: 今使う鍵は 1 つで、クレジットは切れたら自分で止まる（事実 15）。AI Gateway を通すと、プロンプトの通る相手が 1 つ増え、落ちる所も 1 つ増える。鍵を預けた形の動き方は、文書の間で食い違っている（事実 16）。AI Gateway の値打ちは、プロバイダが 2 つ以上になったときと、購入したクレジットに上限を掛けたいときに出る。
    細部: AI Gateway を通すときは、記録にプロンプトと応答の中身を残さない指定のヘッダを付ける。

20. **2026-11-22 クレジットが切れたら、サブスクリプションの対話で続ける（Chief Engineer が決めた）。** `andon issue start` は、対話なしで起動する前に、同じ鍵でいちばん安いモデルに 1 回だけ短く問い、通るかを確かめる。鍵が置かれていないとき、プロファイルに `print:` の行が無いとき、この確かめが通らないときは、今と同じに対話で起動し、理由を 1 行出す。走っている途中で切れたときは、端末が終わり、dispatcher の今ある起動し直しが 1 回打たれて、同じセッションの続きが対話で動く。セッションの記録が残る前に落ちたときは、今と同じに `finished` の知らせが出て、Chief of Staff が `andon issue resume --fresh` で対話の担当を起動する。
    理由: 定期の仕事が、クレジットの残りに左右されずに毎朝終わる。起動し直しの道は今あるものをそのまま使い、dispatcher も `andon issue resume` も直さない（事実 19）。
    捨てた案: 切れたら Chief of Staff に知らせて止まる（毎月、クレジットが切れた日からオーナーの手が要る）。
    細部: API キーで始めたセッションを、サブスクリプションのログインで続きから起動できることは、実装の課題がセルの本物で確かめる（受け入れ条件 13）。できなければ、続きは `--fresh` の道に寄せる。

21. **2026-11-22 対話なしの実行に、時間と金額の上限を付ける（Chief Engineer が決めた）。** `print:` の行の command は、時間の上限（60 分）を過ぎたら止まる。1 回に使う金額の上限（10 ドル）も、`claude -p` の旗で付ける。どちらで止まっても端末が終わり、決めたこと 20 と同じ道で、対話が続きを動かす。
    理由: 対話なしの端末は状態を報告しないことがあり、止まったまま動かない担当を dispatcher が見分けられない。金額の上限は、1 回の実行が月のクレジットを使い切らないための歯止めである。定期の仕事の 1 回は 1〜3 ドルの見込みである（事実 18）。
    細部: 値はプロファイルの `print:` の行に書く。セルごとに変えるときは、セルの `templates.local/` のプロファイルで上書きする。

22. **2026-11-22 API の残高は Andon で数えず、プロバイダの側の上限に任せる（Chief Engineer が決めた）。** Andon は API の残高を読まず、月に使った額を数えて止めることもしない。
    理由: 付いてくるクレジットは、切れたら要求が止まり、プランに請求されない（事実 15）。Andon が二重に数えても、守りは増えない。トークンの数は、今までどおり `andon measure` がセッションの記録から数える。

23. **2026-11-22 対話なしの実行のために、許可のモードを緩めない（Chief Engineer が決めた）。** 対話なしの起動は、許可の設定を対話のときと同じにし、確認が要る操作は誰も答えずに拒まれる形（`--permission-prompts none`）にする。許可の確認を飛ばす旗は使わない。拒まれて進めなくなった担当は、終わって、決めたこと 20 の道で対話に替わる。
    理由: 今は、許可の確認に Chief of Staff が課題の範囲の中で答えている（事実 21）。対話なしではその道が無い。確認を飛ばすと、安全の網が 1 つ減る。定期の仕事は読むだけなので、確認が要る操作はほとんど無い見込みである。実際に拒まれる操作があるかは、受け入れ条件 13 で確かめる。

24. **2026-11-22 このテーマでは statechart のモデルを書かない（Chief Engineer が決めた）。** 外のマシンで回す口は、課題の状態を動かさない。対話なしで起動した端末が終わることは、課題の一生のモデル（`model/IssueLife.tla`）の「端末が落ちる」に、そのあとの起動し直しは「dispatcher が起動し直す」に、今の形のまま当たる。`andon issue start` は対話なしの起動を選ぶだけで、断る条件を足さない。`andon issue resume` と dispatcher は直さない。`andon issue finish` に足す外のマシンの片付けは、手元の片付けが全部済んだあとに打ち、失敗しても結果を変えない。課題の状態の定義、状態を動かす command の順と断り方、dispatcher の順、役の間のやりとりは、どれも変えない。

## 代案（構造の違う案と、選んだ理由）

B を選んだ理由は、決めたこと 2 のとおりである。C が B より余分に外せるのは、エージェント本体の分（CPU の約 2 割と、1 つあたりメモリ 0.5 GB）だけで、直す所は事実 10 の全部になる。A は外のお金がかからないが、この repo にしか効かず、Andon の仕組みにならない。D は PC を空けられるが、並行を増やすには今の PC より大きいマシンが要る。

## やらないこと（範囲の外。理由）

- **担当の端末ごと別のマシンで動かすこと。** 代案 C。`machine` は「まだ使えない」のまま残す（決めたこと 14）。
- **セルごとクラウドに置くこと。** 代案 D。PC を閉じても回すテーマは、別に立てる。
- **Cloudflare Sandbox と Agents を直に使う口。** Sandbox は SSH で入れず、止まるとディスクが消える（事実 14）。hc の machine として足せる command が用意できれば、決めたこと 4 の形のまま使える。Andon は、そのための Worker を持たない。
- **使うたびにマシンを起動して、終わったら止める仕組み。** サービスごとに起動の呼び方が違う。最初は、届く状態のマシンを前提にする。
- **担当とレビュアーを対話なしで動かすこと。** 担当は、レビューと gate の指摘を端末で受け取る。その流れを作り直す大きさになる。
- **OpenAI と Google の API クレジットを使うこと。** API キーで動かす Codex は対象外である。Gemini を動かすハーネスは Andon に無い（事実 15）。
- **API の残高を Andon が数えて止めること。** 決めたこと 22。
- **外で作られたファイルをセルへ戻すこと。** 戻すのは出力と終了コードだけである（決めたこと 3）。
- **gate が自分で回す検査を外へ回すこと。** この repo の条件表には、gate が回す検査が無い。要るようになってから決める。
- **この repo の `tests/run` を、外のマシンで 2 本以上並べること。** 決めたこと 9 の細部。要るようになってから切る。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に）

継ぎ目は 3 つである。1 つ目は `tests/andon-issue.sh` で、偽の `hc` を PATH の先頭に置いて、`andon issue run` と `record` と `start` が打つ `hc` の引数と、受け取った出力の扱いを見る。2 つ目は Go の検査で、木を commit の形にする所と、プロファイルの `print:` の行の読み方を見る。3 つ目はセルの本物で、偽のマシン（決めたこと 15）と、借りた外のマシンで動かす。

1. `remote` の無いプロジェクトで `andon issue run <id> -- sh -c 'exit 3'` を打つと、手元で走り、終了コード 3 で終わる。偽の `hc` は 1 回も呼ばれない。証拠: `bash tests/andon-issue.sh` の出力の該当の行。
2. `remote` のあるプロジェクトで `andon issue run` を打つと、偽の `hc` に、木を送る `exec -i --on <machine>` と、端末を立てる `run --bg --on <machine>` が、この順で届く。偽の `hc` が返した出力と終了コードが、そのまま返る。証拠: 同じ検査の出力。
3. commit していない変更と追跡していないファイルのある worktree で送ると、受け取った側の木に両方が入っていて、受け取った側の `git merge-base HEAD origin/main` が手元と同じ commit を返す。送ったあとも、手元の `git status --porcelain` の出力が送る前と同じである。証拠: `go test ./internal/issue/` の該当の検査の出力。
4. 偽の `hc` が「届かない」を返すと、理由が 1 行出て、手元で走る。同時に 2 本打つと、2 本目は 1 本目が終わるまで走らない。証拠: `bash tests/andon-issue.sh` の出力。
5. 外で走らせた `andon issue record` の記録に `machine` があり、手元で走らせた記録には無い。`tests/schema.sh` が両方の形を通す。証拠: `tests/run --changed` の出力。
6. `project.json` の最後の commit の作者がオーナーでないとき、`remote` があっても外へ送らず、手元で走る。証拠: `bash tests/andon-issue.sh` の出力。
7. 偽のマシンで、15 分かかる command の出力と終了コードが戻り、途中で接続を切っても結果を受け取れる。証拠: 調べる課題の報告と、`andon issue record` で撮った記録。
8. 借りた外のマシンで、`andon issue record <id> -- tests/run --changed` が外で走り、記録の `machine` がそのマシンの名前になる。そのあいだ、セルの load average が上がらない。オーナーが見る（`manual`）。
9. `headless` の `routines` に名前のあるルーチンの課題を `andon issue start` すると、偽の `hc` に、template の名前でなく command を直に渡す `run` が届き、最初のメッセージがその引数に入っている。名前の無い課題は、今と同じ template の `run` が届く。証拠: `bash tests/andon-issue.sh` の出力。
10. 鍵が置かれていないとき、プロファイルに `print:` の行が無いとき、前もっての確かめが通らないときは、どれも対話の template で起動し、理由が 1 行出る。証拠: 同じ検査の出力。
11. 対話なしで起動した課題を `andon issue resume` と `andon issue resume --fresh` で起動し直すと、どちらも対話の template の `run` が届く。証拠: 同じ検査の出力。
12. `andon api auth` が置いたファイルのモードが 600 で、`andon api env` の出力と起動の記録に鍵が出ない。boot が作った hc の template に `print:` の行が残らない。証拠: `go test ./...` の該当の検査の出力。
13. セルの本物で、トリアージのルーチンを対話なしで 1 回流すと、`andon triage apply <id> --dry-run` が通る所まで進み、Console の使用量にその回が出る。許可の確認で拒まれた操作があれば、報告に書く。途中で端末を止めると、dispatcher の起動し直しで、続きが対話で動く。オーナーが見る（`manual`）。

## 価値の仮説

1. **誰の何が変わるか。** オーナーの PC の負荷が下がり、並行の上限を 4 より上げてもラインが回る。サブスクリプションに付く API クレジットが、毎月使われる。
2. **見る信号。** 走らせた記録のうち `machine` のあるものの割合を、kanban の置き場の記録から数える。1 日に片付いた課題の数と、起動を待つ時間の平均を、`andon measure` で読む。対話なしで起動した回の数を、起動の記録から数える。PC の重さは、オーナーの目視である。API クレジットの使われ方は、オーナーが Console で見る。
3. **見る日。** 2026-12-13。外のマシンを借りて並行の上限を上げてから、7 日を見込む。
4. **誰が要るか。** オーナー。外のマシンを借りる、公開鍵を置く、`project.json` に書く、上限を上げる、Console の組織を連携して API キーを置く。
5. **効いたとどう分かるか。** 並行の上限を 8 にして 3 日回し、走らせた記録の 8 割以上が外のマシンで走っている。負荷で揺れて回し直した検査を、振り返りが拾わない。オーナーが PC を重いと感じない。`andon measure` で数えた 1 日に片付く課題が、65 件より増える。定期の仕事が、月のうち 20 日以上、対話なしで起動する。
6. **何があれば止めるか。** 外で回した検査 1 回が、手元の 2 倍より長くかかる。外のマシンに届かない日が、週に 2 日以上ある。記録の 8 割が外で走っているのに、オーナーが PC を重いと感じる。このときは、担当が `andon issue run` を通さずに回している分が大きいので、代案 C をテーマに立てる。上限を上げても片付く数が増えないときは、サブスクリプションの使用量が先に上限へ来ていないかを見る。

7. **オーナーの手作業: API キーを置き、`project.json` に `headless` を書く。** Console の組織を連携する、自動の買い足しを切る、`andon api auth anthropic` を打つ。受け入れ条件 13 を見る。6 がセルに当たったあと。
8. **観察。** 価値の仮説の見る日に、信号を読む。
