## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-23）: 「ModのKanbanだけどDoneした古いやつは読み込まないか別のViewにしたほうがいいかも」。

言い直し（オーナーが同意 2026-11-23）。オーナーは、ボードを開いたときに片付いた課題が多すぎて今の仕事が埋もれることと、片付いた課題まで毎回読むせいでボードが重いことに困っている。目的は、ボードを「動いている仕事と、片付いたばかりの仕事」を見る場所に戻すことである。古い片付いた課題は、要るときにだけ見られれば足りる。

モデル: 調べなかった（読むだけの mod の見せ方と読み方の変更で、課題の状態の定義にも、状態を動かす command にも、自動で動く部品にも触れない）

## 読んで分かった事実（2026-11-23。main `3348bdd` と、Andon を開発しているセルの kanban で実測）

数は 2 回に分けて数えた。1 回目は課題が 735 件のとき、2 回目は 751 件のときである。どちらの回の数かは、項目ごとに書く。

1. **片付いた課題が 9 割近い。** 1 回目は、課題 735 件のうち 638 件が片付いていた。開いている課題は 97 件だった。セルは 5 日目で、課題は 1 日に約 150 件増えている。
2. **mod は、見回りのたびに全部の `issue.yaml` を読む。** 読み方は、決まったシェルの文を `exec` で動かす形である。課題 1 件につき、大きさを見る `wc` と `tr`、中身を出す `head` の 3 つのプロセスを起動する。10 秒ごとに読み直す。
3. **1 回の読みに 2.0 秒かかる。** mod の決まったシェルの文を、1 回目の kanban に 3 回当てた。2.03 秒、2.06 秒、2.06 秒だった。出力は 243 KB だった。ボードを開いている間、セルの CPU 1 つの約 2 割を使い続ける計算になる。
4. **同じファイルを Go で読むと 0.1 秒かからない。** `kanban list` は全部の `issue.yaml` を読み、片付いていない課題だけを出す。これが 0.04 秒だった。全部を JSON で出す `kanban list --json --all` は 0.11 秒、`andon waiting --json` は 0.08 秒だった。重さの原因は、ファイルの数ではなく、mod の読み方である。
5. **今の読み方は、課題の数に比例して重くなり、上限がある。** mod は 1 回の読みで出す量を 4 MiB で止め、超えた課題を「読めない」と出す。`issue.yaml` は 1 件あたり平均 331 バイトなので、約 12,600 件で上限に達する。課題は番号の順に読むので、読めなくなるのは番号の新しい課題からである。今の増え方だと約 80 日後に当たる。1 回の読みが見回りの間隔の 10 秒を超えるのは約 3,600 件で、約 20 日後に当たる。
6. **Board の Done の列は、全部を番号の順に並べる。** 1 回目は 638 枚だった。片付いたばかりの課題は一番下にある。List も全部の課題を出す。mod は、見えていない行を描かない仕組みを使っていない。
7. **Flow は、もう片付いた課題を外している。** 片付いていない課題と、親の下に片付いていない課題がある間のその親の片付いた課題だけを出す（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 13。オーナーが決めた）。
8. **片付いた課題の `updated` は、実測では片付いた時刻のままだった。** kanban の履歴にある「片付いた」の記録 647 件を、その課題の `updated` と比べた。60 秒を超えて後ろにずれていたものは 0 件だった。コードの上では、片付いた課題に `kanban set` を打てば `updated` は動く。
9. **片付いた課題は、片付いたあとも、ほかの課題から指される。** 2 回目の数である。片付いていない課題は 104 件、片付いて 24 時間以内の課題は 82 件だった。この 2 組の親をたどった先の課題は 51 件、この 2 組の `after` の相手は 103 件、片付いていない課題の親をたどった先の課題のどれかを親に持つ課題は 108 件だった。重なりを除くと、全部で 247 件になる。JSON にすると 126 KB だった。751 件のうち 504 件は、どれにも当たらない。
10. **`kanban list` は、知らないフラグを黙って読み飛ばす。** 仮の kanban で、値を付けた知らないフラグを渡した。終了コードは 0 で、片付いていない課題だけが出た。知らない sub command は、終了コード 1 で断る。`andon` は、知らない葉を終了コード 2 で断る。
11. **kanban の CLI に葉を足さないと決めてある。** [ADR-0053](0053-command-system.md) の決めたこと 20 と「やらないこと」である（オーナーが決めた 2026-11-22）。kanban は課題を読み書きする汎用の道具のまま残し、Andon の決まりを伴う操作は `andon` が持つ。
12. **mod とセルのバージョンは、別々に上がる。** mod はオーナーの手元の Herdr App に置く。`bin/bootstrap host-install` は今あるファイルを上書きしないので、新しいバージョンはオーナーが置き直す。`package/host/**` の変更は、既定の条件表でオーナーがマージする。
13. **mod は、もうセルの command を 1 つ呼んでいる。** Flow の印のために、読み直すたびに `andon waiting --json` をプロジェクトのフォルダで呼ぶ。印の読みは課題の読みと別に走らせてあり、command が返らなくても課題は読める。command が無いか、違うバージョンを出すときは、印を出さずに今までどおり動く（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 14）。mod `inbox` は、同じ command を `--project` を付けて呼んでいる。
14. **mod が呼ぶ command の一覧は、検査が 2 か所で固定している。** `tests/host/screen.mjs` は、`exec` の呼び先の並びと、`andon` の引数が `waiting --json` だけであることを見る。`tests/commands.sh` は、`package/host/` の mod が `andon` に渡す引数が `waiting --json` と `waiting answer` だけで、どちらも葉の表に在ることを見る。README の「What it runs」にも一覧がある。
15. **手元が Windows のときは、別の読み方をする。** セルを通さず手元の kanban を読むとき、mod は PowerShell で大きさと symlink を確かめてから、1 件ずつ読む。この道では `andon waiting` も呼ばない。
16. **`issue.yaml` を直に読む実装は、今 6 つある。** kanban の CLI（`cmd/kanban`）、`andon waiting`（`internal/waiting`）、ダイジェストの入力を集める command（`internal/digest`）、振り返りの入力を集める command（`internal/retro`）、`andon measure`（`internal/measure`）、mod の js-yaml である。`internal/ledger` を通して読む `andon` の command は、`kanban list --all --json` を呼んで読む。
17. **kanban の CLI の読み方には、mod が持つ守りが無い。** mod は、`issue.yaml` かそのフォルダが symlink のとき、256 KiB を超えるとき、YAML の alias を含むときに、読まずに「読めない」と出す。kanban の CLI は、symlink の `issue.yaml` を読み、symlink のフォルダの課題を黙って飛ばし、大きさを見ず、alias を開く。仮の kanban に、alias を 12 段重ねた 289 バイトの `issue.yaml` を置くと、`kanban list --json --all` は 1.39 MB を出した。1 段ごとに倍になる。`kanban lint` は通った。同じファイルを `andon waiting --json` は「読めない」と出して数えず、出力は膨らまなかった。
18. **名詞は、扱うものの名前にすると決めてある。** [ADR-0053](0053-command-system.md) の決めたこと 6 である。同じ ADR の決めたこと 10 は、名詞を呼び手で名づける案を捨てている。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案。あとから覆したら上書きせず下に足す）

### 見せ方

1. **2026-11-23 範囲は、Board と List から古い片付いた課題を外し、古いものを見る表示を 1 つ足し、毎回の読みを軽くすることにする（オーナーが決めた。Chief Engineer の推奨どおり）。** 全部のプロジェクトを見る表示にも、同じに効かせる。
   理由: 前提の 1 と 2 の困りごとは、この範囲で両方直る。
   捨てた案: 古い片付いた課題の表示を振り返りに使える形にする（片付いた日ごとのまとまりと、親ごとの畳み。困りごとに無い）／ボード以外の読み手も含めて、kanban が増え続けても重くならない仕組みを作る（事実 4 のとおり、ほかの読み手は今は困っていない）／見る表示を足さない（前提 4 を外すことになる）。

2. **2026-11-23 「古い」の線は、片付いてから 24 時間にし、課題の `updated` で測る（オーナーが決めた。Chief Engineer の推奨どおり）。** Board と List は、`updated` が今から 24 時間前より前の片付いた課題を、古いものとして外す。
   理由: オーナーの言葉は「古いやつ」で、古さは時間で言うのが言葉に合う。24 時間なら、朝に開いたときに、前の日の夕方から片付いたものが残っている。`updated` は、実測では片付いた時刻のままである（事実 8）。
   受け入れること: 線の内側の数は、仕事の速さで変わる。事実 9 の回では 82 件だった。48 時間なら 165 件、72 時間なら 361 件になり、列がまた長くなる。
   細部: 24 時間は mod の定数にする。オーナーが画面で変える口は作らない。片付いたあとで手で書き換えられた課題は、`updated` が動いて線の内側に戻る。それは、最近触られた課題として出てよい。
   捨てた案: 新しい順に決まった件数だけ出す（1 日に 150 件片付く今の速さでは、50 件は 8 時間分にしかならず、朝に前の晩の分が見えない）／48 時間や 72 時間（上の数のとおり、列が長いまま残る）。

3. **2026-11-23 Board の Done の列は、線の内側の課題だけを、片付いた新しい順に並べる。List も同じ線で外す（Chief Engineer が決めた）。**
   - Done の列の見出しの数は、列に出ている枚数にする。列の一番下に、古い課題の数と History へ行く口を 1 行で出す（「565 older · History」）。押すと表示が History に替わる。古い課題が無ければ、この行は出さない。
   - List は、片付いていない課題と、線の内側の片付いた課題を出す。古い片付いた課題でも、下に出す課題を持つ親は、木の見出しとして残す。
   - ほかの列の並びは変えない。
   理由: 片付いたばかりの課題が一番下にあるのが、今の見づらさの半分である（事実 6）。行き先を列の中に書いておけば、消えたように見えない。
   細部: 一番下の行の数は、プロジェクトの全部の古い課題の数である。repo のチップか `/` で絞っている間は、数を出さず「Older · History」とだけ出す。絞った中での数は、command の道では数えられないためである。
   捨てた案: Done の列を番号の順のままにする（線の内側でも、新しいものが下に沈む）／Done の列を無くす（片付いたことを確かめる場所が無くなる）。

4. **2026-11-24 4 つ目の表示 History を足す。片付いた課題の全部を、片付いた新しい順に 1 列で並べ、`/` で片付いた課題の全部から探せるようにする（オーナーが決めた。Chief Engineer の推奨どおり）。** 表示のボタンは Board・List・Flow の隣に置く。キー `v` は、Board、List、Flow、History の順に回る。
   - 1 行は、番号、片付いた日時、タイトル、プロファイルである。全部のプロジェクトを見る表示では、プロジェクトの名前も出す。木にはしない。行を押すと、今と同じ詳細の欄が開き、依頼書と報告が読める。
   - 最初に 200 件を出す。一番下の「Load older」で 200 件ずつ増やす。2,000 件まで増やしたら、それより古いものは `/` で探すよう 1 行で伝える。
   - History を出している間の `/` は、打っている間は出ている行を絞り、Enter で片付いた課題の全部から探す。
   - Board・List・Flow の `/` は、今までどおり、その表示が持っている課題の中で絞る。古い片付いた課題は探さない。
   理由: 古い課題を見に行くのは、「あの課題はどうなったか」を確かめるときである。新しい順の 1 列と、全部からの検索があれば足りる。
   細部: 名前は「History」にする。「Done」は列の名前と重なる。「Archive」は、しまった、移した、と読めるが、ファイルは動かさない（前提 3）。行に親のタイトルは出さない。古い課題の親は、mod が持っている課題の中に無いことがある。親は詳細の欄に番号で出し、mod が親を持っていればタイトルも添える。
   捨てた案: Done の列の下で、押すたびに古いものを広げる（列が元の長さに戻る）／List の中に畳んだ節として置く（List は親と子の木で、片付いた順に並べられない）／端末の `kanban list --all` で見る（前提 4）。

5. **2026-11-23 Flow と、カードと、詳細の欄が出すものは変えない。そのために要る片付いた課題は、古くても毎回の読みに含める（Chief Engineer が決めた）。** Flow の出し方は [ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 13 のままで、親の下に片付いていない課題がある間は、その親の片付いた課題を薄く出す。カードの親のタイトルと、まだ片付いていない `after` の相手も、今までどおり出す。
   理由: Flow の出し方はオーナーが決めたもので、このテーマで覆す理由が無い。古い片付いた課題を読まなくしても、出ている課題が指す相手が欠けると、カードと Flow が誤ったことを出す。
   細部: 24 時間の線は、Board の Done の列と List にだけ当てる。Flow が木を作るのに使う課題の組には当てない。当てると、Flow から薄い行と古い親が消える。

### 読み方

6. **2026-11-23 毎回の読みは、読むだけの command `andon issue board` をセルで呼んで受ける（Chief Engineer が決めた）。** mod は、kanban を読み直すたびに、プロジェクトのフォルダを作業フォルダにして `andon issue board --json --since <時刻>` を `exec` で呼ぶ。全部のプロジェクトを見る表示では、プロジェクトごとに 1 回呼ぶ。`<時刻>` は、mod が今から 24 時間前を計算して渡す。
   理由: 重さの原因は mod の読み方で、同じファイルを Go で読めば 0.1 秒かからない（事実 3・4）。どの課題が要るかは、親と `after` をたどって決まるので、`issue.yaml` を YAML として読める所で決めるのがよい。mod は、もう同じ形でセルの command を呼んでいる（事実 13）。葉を `andon` に置くのは、kanban の CLI に葉を足さない決まりに従うためである（事実 11）。
   受け入れること: 読む時間は、課題の数に比例したままである。全部を読んで一部を出す `kanban list` が 735 件で 0.04 秒だったので、1 件あたり約 50 マイクロ秒と見る。今の 2 秒に戻るのは約 36,000 件で、今の増え方だと約 8 か月後に当たる。そのときは、command の中の読み方を軽くすれば足りる。出力の形と mod は変えずに済む。
   細部:
   - 名前は [ADR-0053](0053-command-system.md) の決めたこと 5・6・7 の形に合わせた。名詞は扱うものである課題で、2 語目はその葉が出すものの名前である。別のバージョンの mod から呼ばれる葉なので、名前はあとから変えない（同じ ADR の決めたこと 9）。
   - `--since` は省けない。24 時間の線を持つのは mod だけにする。`--project` と `--json` は、ほかの葉と同じ意味で受ける。`--json` を付けないと、人が読む行を 1 課題 1 行で出す。知らないフラグは断る。
   - プロジェクトがセルの `projects/<slug>/` に在るとき、mod は `--project <slug>` も付ける。セルの環境に `KANBAN_ROOT` があっても、違うプロジェクトを読まないためである。mod `inbox` は、もうこの形で呼んでいる（事実 13）。
   捨てた案:
   - 決まったシェルの文を、課題ごとにプロセスを起動しない形に書き直し、片付いた課題を文の中で外す。mod の中だけで済むが、親と `after` を awk の正規表現で読むことになる。読む前に symlink と大きさを確かめる今の守りも、1 件ずつプロセスを起動せずには保ちにくい。
   - `kanban list` にフラグを足す。古い `kanban` は知らないフラグを黙って読み飛ばし、片付いていない課題だけを返す（事実 10）。mod は、片付いた課題が欠けたことに気づけない。
   - 葉の名前を `andon board issues` にする。名詞が、扱うものではなく呼び手の名前になる（事実 18）。
   - 見せ方だけを変え、読み方は今のままにする。約 80 日で新しい課題から読めなくなる（事実 5。前提 2）。
   - 片付いた課題を kanban の中の別のフォルダへ移す。形式が変わり、kanban を読む全部の command に効く（前提 3）。

7. **2026-11-23 `andon issue board` が出す課題の範囲は、次の 5 つの組にする（Chief Engineer が決めた）。**
   - ア: 片付いていない課題と、読めない課題の全部。
   - イ: `updated` が `--since` の時刻以降の、片付いた課題。
   - ウ: アとイの課題の、親をたどった先の課題の全部。
   - エ: アの課題の親をたどった先の課題のどれかを、親に持つ課題。
   - オ: アとイの課題の `after` の相手。
   片付いたかどうかは、今と同じく、状態が `config.yaml` の `columns` の最後の列かどうかで決める。
   理由: ウはカードと List が出す親のタイトルに、エは Flow の薄い行に、オはカードの「after …」と Flow の段に要る（決めたこと 5）。事実 9 の回では、751 件のうち 247 件になった。
   細部: 見せ方の決まり（24 時間の線、並び、History）は mod が持つ。command が決めるのは、渡す範囲だけである。mod は、範囲より多く受け取っても正しく描く。出力には、`updated` が `--since` より前の片付いた課題の数を `older` として付ける。ウ・エ・オで範囲に入った課題も、この数に数える。Done の列の一番下の行は、この数を出す。
   受け入れること: 範囲の大きさは、開いている課題と、それに関わる課題の数で決まる。片付いた子を何百も持つ親が開いている間は、その子が全部入る。

8. **2026-11-23 History の読みは、もう 1 つの command `andon issue history` にする（Chief Engineer が決めた）。** mod は、History を出している間だけ、`andon issue history --json --limit <件数>` を呼ぶ。Enter で探すときは `--match <文字>` を足す。
   - 出すのは片付いた課題で、`updated` の新しい順に `--limit` の件数までである。`--limit` を省くと 200 件、上限は 2,000 件にする。
   - `--match` は、番号、タイトル、repo、プロファイル、端末の名前のどれかに、その文字を含む課題だけを残す。大文字と小文字は分けない。mod の今の絞り込みの 6 つの欄から、プロジェクトの名前を除いた 5 つである。
   - 出力には、条件に合うのに出さなかった課題の数を `more` として付ける。
   理由: 片付いた課題の全部を 1 回で渡すと、数に比例して増え、`exec` が受け取れる 8 MiB をいつか超える。件数で切り、探すのはセルの側でする。
   細部: 「Load older」は、件数を 200 増やして読み直す。続きの位置を覚える形にしない。同じ秒に片付いた課題が多く、位置がずれるためである。全部のプロジェクトを見る表示では、プロジェクトごとに同じ件数で呼び、mod が新しい順に混ぜる。そのとき、探す文字がプロジェクトの名前に含まれるプロジェクトには、`--match` を付けずに呼ぶ。`--match` の文字は、`exec` の引数の 1 つとしてそのまま渡し、シェルを通さない。
   捨てた案: `andon issue board` にフラグを足して 2 つの読みを兼ねる（出す範囲も並びも違い、1 つの葉が 2 つの仕事を持つ）／片付いた課題を全部渡して mod が探す（上の理由）。

9. **2026-11-23 2 つの command の出力は、バージョンを持つ 1 つの形にする（Chief Engineer が決めた）。** 形の正は `schema/` に新しい schema として置き、[contract.md](../contract.md) に節を足す。
   細部: `andon issue board --json` の出力は次の形である。

   ```json
   {
     "version": 1,
     "at": "2026-11-23T13:00:00Z",
     "project": "sample-site",
     "done": "done",
     "since": "2026-11-22T13:00:00Z",
     "issues": [
       {"id": "S-0012", "title": "返事の下書きボタン", "status": "doing", "parent": "S-0010", "updated": "2026-11-23T12:10:00Z"},
       {"id": "S-0013", "broken": "symbolic link"}
     ],
     "older": 565
   }
   ```

   - `issues` の 1 件は、`kanban list --json` が出す課題と同じ中身である。`issue.yaml` のキーと、フォルダの名前から取った `id` を持つ。読めない課題は、`id` と、理由を 1 行で書いた `broken` だけを持つ。
   - `project` はプロジェクトのフォルダの名前、`done` は片付いた列の名前である。
   - `andon issue history --json` は、同じ形から `since` と `older` を除き、`more` を足す。`issues` は `updated` の新しい順に並ぶ。
   - キーを足してもバージョンは上げない。mod は、知らないキーを読み飛ばす。意味を変えるときだけバージョンを上げる。
   理由: mod とセルのバージョンは別々に上がる（事実 12）。mod が形を確かめられるように、`andon waiting --json` と同じく、出力に `version` を持たせる。

10. **2026-11-23 2 つの command は `issue.yaml` を自分で読み、symlink・大きすぎるファイル・alias のあるファイルの中身を出さない（Chief Engineer が決めた）。** 次のどれかに当たる課題は、読めない課題として出す。`broken` には、今の mod と同じ向きの短い文を書く。
    - `issue.yaml` かその課題のフォルダが symlink である（`symbolic link`）。
    - `issue.yaml` が 256 KiB を超える（`larger than 262144 bytes`）。大きさは、読む前に確かめる。
    - `issue.yaml` が YAML の alias を含む。alias は開かない。
    理由: kanban のファイルはエージェントが書く。mod の今の読み方は、読む前にこの 3 つを断っている（事実 17）。読む口を command に替えても、同じ守りを残す。`kanban list --all --json` を呼んで読む形では、守れない。kanban の CLI は symlink の先を読み、alias を開いてから渡すので、あとから外しても遅い（事実 17）。
    受け入れること: `issue.yaml` を直に読む実装が、Go の側でもう 1 つ増える（事実 16）。読むのには、kanban の CLI と同じ YAML のライブラリを使う。守りに当たらない課題の出力が `kanban list --json --all` と同じになることを、検査で見る（受け入れ条件 5）。
    細部: 出力が 8 MiB を超えて `exec` に切られたときは、JSON として読めないので、決めたこと 11 の道に戻る。戻った先では、今の 1 件ごとの上限と、全体の 4 MiB の上限が効く。
    捨てた案: kanban の CLI の読み方に守りを足し、それを呼ぶ（kanban の CLI を変える話で、ほかの全部の command に効く。このテーマではしない。事実 17 は、別の直しの種として Chief of Staff に渡す）。

11. **2026-11-23 command が使えないとき、mod は今の読み方に戻り、同じ見せ方を当てる（Chief Engineer が決めた）。** mod は、読み直すたびに command を先に呼ぶ。次のどれかのとき、今の決まったシェルの文で全部の `issue.yaml` を読む。

## やらないこと（範囲の外。理由）
