# ADR-0044: オーナーが読むダイジェストを定期に作り、Slack へ送る（仕様・設計。2026-11-22）

- 状態: **決定（2026-11-22）**。オーナーが対話の中で決めた。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書き、この行を「覆された → ADR-NNNN」に直す。小さな改めは「決めたこと」に下から足す。
- 主題: 工場で起きたことを、オーナーが後から短い時間で理解できる 1 枚（ダイジェスト）にまとめ、決まった時刻に作って、セルの外の Slack へ送る。ダイジェストを作る流れ、載せる中身と見た目、送り先の設定と送る口、資格情報の置き方を決める。セルの外のサービスへ定期に送る口を足す決定と、オーナーに届くものを増やす決定を含む。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。この文書が足す約束は「決めたこと」に形を書き、実装の課題が写す（それまでは提案）。オーナー待ちと、それを読む command `andon waiting` は [ADR-0042](0042-owner-waits-do-not-stop-the-line.md) が決めた。

## 問題（オーナーの言葉で。言い直しの段落）

オーナーは 2026-11-21 に、自分の介在を減らすうえで、自分へのレポーティングを強くしたいと言った。方向は、オーナーの言葉で「ルーティーンでオーナーが理解をするための報告HTMLをSlackなどのコミュニケーションツールへ報告する」である。前提として「選択的DarkFactoryとしての骨子は固まってきた」と言い、介在はまだ多いが、もっと減らして効率的にできそうだとも言った。

オーナーが目指しているのは、自分が手を出す回数を減らしても、工場で何が起きたかを分かったままでいられることである。今、起きたことを知る道は、Chief of Staff の端末の返事と GitHub の PR の 2 つしかない。1 日の出来事を 1 枚で読める場所は無い（事実 1・2）。任せる範囲を広げるほど、オーナーが読まないまま入る変更は増える（事実 3）。それを後から短い時間でまとめて理解でき、気になれば覆せる報告を、決まった時刻に作って、端末の外の Slack へ届ける。

オーナー（2026-11-22。検討の途中で）: 「レポートはHTMLのままで構いません。認知負荷を下げるためにグラフィカルであることが好ましいです。また、依存関係のない単一のHTMLであることが好ましいです」。参考として、AI の長い報告を HTML の 1 枚にして読む場所を 1 つに集める発表を挙げた（事実 13）。

モデル: 調べなかった（課題の一生と、状態を動かす command を変えない。足すのは、今あるルーチンが足す課題の 1 種と、読んで集める command と、外へ送る command である。決めたこと 21）

## 読んで分かった事実（2026-11-22。main `8d67335` と、Andon を開発しているセルの kanban と記録で実測）

1. **オーナーが今読んでいる量。** Chief of Staff の会話の記録で、ターンを終えた返事を数えた。2026-11-19 は 219 通で 63,674 字、11-20 は 338 通で 86,910 字、11-21 は 206 通で 55,073 字だった（日付は UTC）。同じ 3 日にオーナーが打った文は、1 日に 29〜45 通だった。1 日の出来事は、200 通を超える短い返事に散らばっている。
2. **流れる量。** `andon measure` で 2026-11-15 から 11-21 の 7 日を数えると、マージされた PR は 192 本、片付いた課題は 244 件で、1 日に 34.9 件だった。
3. **オーナーを通らずに入る変更。** 同じ 7 日で、dispatcher が自動でマージした PR は 81 本だった（42%）。gate がオーナーに回した判定は 100 件だった。自動でマージしたものの記録は、課題ごとの gate の記録と結果の記録（`outcome.json` の `gates[].merged`）と PR にある。まとめて読める場所は無い。[design.md](../design.md) §1.10 は、任せたあとに残す安全網の 1 つ目を「記録。オーナーが後から読める」と書いている。
4. **オーナーの代わりに決められた決定。** Chief Engineer は、線の外の決定を自分で決め、文書の「決めたこと」に「（Chief Engineer が決めた）」の印を付ける（[ADR-0037](0037-chief-engineer-autonomy.md) 決めたこと 3）。オーナーは読みたいときに読んで覆せる。印の付いた行が増えたことを、オーナーに知らせる口は無い。Chief of Staff の決定は、トリアージの記録（`library/triage/`）、振り返りの記録（`library/retro-applied.json`）、範囲の問いの答えにある。
5. **オーナー待ちは読める。** `andon waiting --json` が、マージの依頼・判断・手作業の 3 種と並行の枠を出す（[contract.md](../contract.md) §25）。手作業のオーナー待ちでは行燈が灯らないと決まった（[ADR-0043](0043-lamp-lights-on-owner-waits.md) 決めたこと 4）。2026-11-22 の朝、このセルには手作業が 7 件あり、いちばん古いものは 1 日前からだった。
6. **定期に課題を足す仕組みは kanban にある。** ルーチン（`routines/<名前>.yaml`）は、`schedule` の時刻が来ると課題を 1 件足す。dispatcher が 1 巡ごとに `kanban tick` を打つ（[dispatcher.md](../dispatcher.md) §7.2 の 8）。このセルでは、振り返りが毎朝 8:17、トリアージが毎朝 9:07 に足される（パッケージの例は、振り返りが毎朝、トリアージが週 1 である）。ルーチンは、`open` の数の課題が片付いていない間は、時刻が来ても課題を足さない。飛ばした回は、後から足されない（[ledger.md](../ledger.md) の Routines）。どちらも、読むだけの command が入力を集め、担当が判定を書き、command が当てる 3 段である（[ADR-0028](0028-improvement-loop.md) 決めたこと 8）。
7. **定期の課題 1 回のコスト。** 振り返りの課題 5 件は、出力が 31,408〜44,537 トークン、キャッシュの読みが 717 万〜1,082 万トークンだった（プロファイル `claude`）。トリアージの課題 1 件は、出力が 33,189 トークン、キャッシュの読みが 589 万トークンだった（プロファイル `sonnet`）。
8. **`andon publish` の URL は、セルを動かしているマシンでしか開けない。** `files/` にコピーして `http://files.<セルの名前>.localhost:<番号>/<日付>-<slug>` を返す（`internal/publish/publish.go`）。`files/` はセルの repo が git で追跡する。委譲は読まない。このセルの repo に remote は無い。
9. **セルの外へ書く口は、今は GitHub だけである。** 外の信号（`andon signal`）は読むだけで、トークンは `andon signal auth <出所>` が標準入力の 1 行を `~/.config/andon/signals/<出所>.token` にモード 600 で置く（[ADR-0011](0011-signals-and-value-loop.md) 決めたこと 10）。置き場は compose の volume で、セルを作り直しても残る。セルの中の役は同じユーザーで動くので、どの役もこのファイルを読める。ADR-0011 は、置き場は守りでなく、守りはトークンの scope が読み取り専用であることだと書いている。出所は、オーナーが `project.json` の `signals` に書いたものだけを読む。`project.json` は、セルの repo の HEAD のものを、最後に変えた commit の作者がオーナーのときだけ信じる（`internal/delegate/project.go` の `ReadProject`）。照合が見るのは commit の作者のメールアドレスである。古いバージョンの `andon` は、知らないキーのある `project.json` を読めないものとして扱う（[contract.md](../contract.md) §11）。
10. **委譲の `external-requests` は、外へ送る許しではない。** ほかのプロジェクトから委譲の印つきで来た依頼を、承認とみなすかどうかの値である（[design.md](../design.md) §1.10）。外への公開の範囲は `publish` で、説明に「投稿」の語がある。値は、`internal` が `andon publish` まで、`public` が取り消せない公開である。Chief of Staff の原則 4 は、外向きの送信をオーナーの go が要る操作に数えている。担当の手順（skill `worker` の §5）と、Chief of Staff の手引き（`playbooks/blocked.md`）も、外の API への書き込みを、オーナーの go で受ける操作に数えている。
11. **Slack へファイルを投稿する手順。** Slack の公式の文書によると、bot のトークンと scope `files:write` で、`files.getUploadURLExternal`（ファイルの名前とバイト数を渡す）、返った URL へ中身を送る、`files.completeUploadExternal`（`channel_id` と `initial_comment` を渡す）の 3 回の呼び出しで、文を添えたファイルを 1 つの投稿にできる。bot がそのチャンネルのメンバーでないと `not_in_channel` で断られる。`initial_comment` が装飾の記法を解釈するかは書かれていない。HTML のファイルがどう表示されるかも書かれていない。セルから `https://slack.com/api/api.test` は 200 で返った。
12. **既製の部品。** Slack の Go のライブラリ `github.com/slack-go/slack` は v0.36.0（2026-11-14）があり、直接の依存は 4 つである（`gorilla/websocket` を含む）。この repo の `go.mod` の依存は 4 つである。この repo の Go のコードで HTTP を話すのは、`files/` を配るサーバ（`internal/boot/files.go`）だけである。外へ HTTP を出すコードは無く、外の API は `gh` を呼んで読んでいる。HTML を組み立てるコードは無い。秘密の形を伏せるコードは `internal/retro/redact.go` に 1 つあり、Slack のトークンの形も伏せる。
13. **参考の発表が言っていること。** オーナーが挙げた発表（出典）は、AI が何本並行で動いても最後に判断するのは人で、長い文の報告が 1 日に何十件も届くと読み切れない、と捉える。手は次のとおりである。長い報告は HTML の 1 枚にし、チャットには結論とリンクだけを書く。見た目の決まりを決めて、毎回同じ形で出す。図解にし、判断が要る所だけを目立たせる。読む場所を 1 つに集め、新しい順と既読が分かるようにし、スマホでも読めるようにする。経緯・言い訳・捨てた案を書かず、同じ一覧を 2 度読ませない。HTML を出す前に検査を通し、図が 1 枚も無いページに警告する。Slack へ送る話と、定期に回す話は、この発表には無い。
14. **語の使われ方。** `digest` は、この repo で hash の意味で 2 か所に使われている（`andon version` の出力のキーと、dispatcher の中の関数の名前）。「ダイジェスト」は使われていない。用語集の「報告」は担当が課題ごとに書く結果で、「日報」は担当の `library/journal.md` を指す。

## 前提（同意済み。番号）

オーナーが 2026-11-22 に、入口の確かめで 5 つとも同意した。

1. ダイジェストは理解のためのもので、オーナーに決断を求める場にしない。マージの依頼や判断待ちは「待っているもの」として載せるが、オーナーを呼ぶ仕組みは、行燈とオーナー待ちのペインのまま別に持つ。
2. 何もしなければ、任せる範囲を広げるたびに読まれない変更が増え、安心して任せられないので、介在は減らない。
3. 材料はもうセルにある。足りないのは、材料を 1 枚にまとめる役と型、セルの外へ送る口の 2 つである。
4. Slack へ送る狙いは、端末を開いていないときや PC の前にいないときにも届くことである。要点は Slack の投稿だけで読めて、全文も PC の外で開ける。
5. Andon のパッケージの機能として入れ、送り先はオーナーがセルで設定する。設定の無いセルでは何も送らない。Slack を最初の送り先にし、ほかの道具は後から足せる形にする。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案）

### 範囲と名前

1. **2026-11-22 範囲は、定期のダイジェストと、セルの外へ送る口の 2 つにする（オーナーが決めた）。** ダイジェストの中に「待っているもの」の節は入れる。送る口は、後でほかの知らせにも使える形で作る。
   理由: オーナーを呼ぶ側の仕組みは、行燈の整理（[ADR-0043](0043-lamp-lights-on-owner-waits.md)）とオーナー待ちのペイン（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 12）が今作られている最中である。呼ぶ知らせを Slack にも出す話は、それらが入ったあとに、同じ送る口へ足せる。
   捨てた案: マージの依頼や判断待ちが出たときにも Slack へ知らせる（行燈の線引きと合わせる手間が増える）／Slack の中から判断に答えられるようにする（端末の外から答えを書く口の設計が要り、1 つのテーマに収まらない）／`files/` へ出すまでにして、送る口を次のテーマに回す（PC の前にいないときに届かない。前提 4）。
2. **2026-11-22 仕組みの名前は「ダイジェスト」（`digest`）にし、毎朝の 1 枚は「デイリーダイジェスト」と呼ぶ（オーナーが決めた）。** command は `andon digest`、skill の名前と `project.json` のキーは `digest` にする。ルーチンの名前は `daily-digest`、ルーチンのタイトルは「デイリーダイジェスト」にする。HTML の見出しと Slack の短い文の 1 行目には、課題のタイトル（ルーチンのタイトル）をそのまま出す。用語集に「ダイジェスト」の 1 語を足す。
   理由: 「報告」は担当が課題ごとに書く結果を、「日報」は担当の過程の記録を指している（事実 14）。同じ語を使うと、`andon issue report` や `report.json` と取り違える。「ダイジェスト」は、定期に届くまとめを指すふだんの語である。オーナーは、毎日届くものだと名前で分かるように daily を付けたいと言った。頻度を持っているのはルーチンなので、daily はルーチンの名前とタイトルに付ける。command と設定のキーに付けないのは、頻度を変えたり、週次のルーチンを足したりしたときに、名前と中身が合わなくなるからである。
   細部: `digest` が hash の意味で使われている 2 か所（事実 14）は、出力のキーと関数の名前で、command の名前とは場所が違う。直さない。
   捨てた案: レポート（英語にすると `report` で、担当の報告と識別子が重なる）／日報（担当の日報と重なる）／まとめ（「まとめる」が文のあちこちに出て、語として探せない）／command と設定のキーにも daily を付ける（上の理由。オーナーが選ばなかった）。

### 作る流れ

3. **2026-11-22 集める command、書く担当、組み立てて送る command の 3 段で作る（Chief Engineer が決めた）。** 振り返りとトリアージと同じ形である（事実 6）。
   - 集める: `andon digest collect <id>` が、期間の記録を 1 つの JSON にまとめ、課題の `library/digest/input.json` に書く。kanban と記録を読むだけで、ほかに書かない。
   - 書く: ダイジェストの課題の担当が、入力を読み、要旨とテーマと気になることを JSON で書く（決めたこと 8）。手順は新しい skill `digest` に書く。
   - 組み立てる: `andon digest build <id> -` が、標準入力の JSON を schema と入力に照らし、通れば `library/digest/digest.json`・`digest.html`・Slack に添える短い文 `message.txt` を書く。
   - 送る: `andon digest send <id>` が、HTML を `files/` に出し、設定された送り先へ送り、結果を `library/digest/sent.json` に書く。
   - 担当は報告を書いて課題を `review` にし、Chief of Staff が `andon issue finish` で片付ける。PR は無い。
   理由: PR のタイトルを並べただけの一覧は、1 日に 27 本あると、端末の返事を遡るのと変わらない（事実 1・2）。理解には、変更をテーマに束ねて「何が変わったか」を言う手が要り、それは読んで書く仕事である。一方、数と一覧を担当が書き写すと、食い違いが起きる。数え方を持つのは command だけにする（決めたこと 8）。

4. **2026-11-22 回すきっかけは kanban のルーチンにし、並行の枠を別に持たせない（Chief Engineer が決めた）。** ルーチンの例を skill `digest` の `assets/daily-digest.yaml` に置く。kanban へ写すのは、オーナーの go で Chief of Staff がする（振り返りとトリアージと同じ）。足された課題は、Chief of Staff がオーナーに聞かずに起動する。起動できる課題が複数あるときは、ダイジェストの課題を先に起動する。オーナーが臨時に頼んだら `kanban routine run daily-digest` を打つ。止めるときは、オーナーがルーチンに `paused: true` を書く。
   理由: 常駐と定期の処理を走らせるのは dispatcher の 1 者で、ルーチンはその口をもう持っている（事実 6）。新しい常駐の処理を足さない。並行の枠は、オーナー待ちの課題を数えなくなった（[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 10）ので、朝に枠が埋まったままになることは減る。
   受け入れること: 枠が全部動いている朝は、枠が空くまでダイジェストが遅れる。前のダイジェストの課題が片付いていない朝は、ルーチンが課題を足さず、その朝のダイジェストは抜ける（事実 6）。臨時の `kanban routine run daily-digest` も同じ決まりで断られる。どちらの場合も、期間は前のダイジェストの終わりから数えるので、載らない出来事は出ない（決めたこと 5）。抜けを減らすため、Chief of Staff は、ダイジェストの課題の報告が届いたターンで片付ける（手引きに書く）。ルーチンの `open` は 1 のままにする。2 にすると、同じ期間のダイジェストが 2 枚できる。
   捨てた案: dispatcher が担当を通さずに command を直接打つ（書く段に担当が要る。決めたこと 3）／ダイジェストの課題に並行の枠を別に持たせる（上限を数える式がまた 1 つ増える。上限はオーナーが CPU の負荷で決めた値である）。
5. **2026-11-22 読む期間は、前に送ったダイジェストの終わりから今までにする（Chief Engineer が決めた）。** 前に送ったものが無ければ 24 時間前からにする。7 日より前へは遡らず、切ったときは、ダイジェストの冒頭に「それより前は載せていない」と出す。冒頭には、期間と、前のダイジェストを送った時刻を出す。

12. **2026-11-22 送り先はオーナーが `project.json` に書き、書いてあることを毎回の送信へのオーナーの go として扱う（オーナーが決めた）。** `project.json` に任意のキー `digest` を足す。

    受け入れること（文の誤り）: 担当が書いた文の誤りは、送る前に誰も読まない。数と一覧は command が描くので合う。文の誤りは、指している課題から確かめられ、価値の仮説の止める条件で数える。
    細部: `digest` を書くのは、セルのパッケージを `digest` を知るバージョンに上げてからにする（`signals` と同じ。事実 9）。
    捨てた案: 委譲に新しい範囲を足す（送り先を書くことが go そのもので、置き場が 2 つになる）／委譲の `publish` を読む（`public` は取り消せない公開を任せる値で、オーナー自身への知らせには広すぎる。事実 10）／Chief of Staff が読んでから送る（上の理由）／別ブランドのレビュアーに読ませてから送る（毎朝のコストと時間が倍になる。誤りの数を見てから考える）。
13. **2026-11-22 Slack へは、短い文と HTML のファイルを 1 回の投稿で送る（Chief Engineer が決めた。HTML のまま送ることはオーナーが決めた）。** 手順は事実 11 の 3 回の呼び出しである。HTML のファイルを上げ、短い文を `initial_comment` に入れる。

## 受け入れ条件（テストできる形。どの継ぎ目でテストするかを先に）

継ぎ目は 3 つにする。1 つ目は Go の検査で、一時の kanban と記録を置いて `internal/digest` の集める・組み立てる・送るを通す。Slack は、検査の中に立てた偽の HTTP のサーバに向ける。2 つ目はシェルの検査 `tests/andon-digest.sh` で、切り離したセルで command を端から端まで打つ。3 つ目はオーナーの目視である。証拠は、テストの command と、その出力の見る所で書く。

1. **集める。** 一時の kanban に、dispatcher がマージした課題とオーナーがマージした課題を 1 件ずつ置く。`andon digest collect <id>` の `input.json` で、2 件のマージした者が分かれ、待っているものが同じ時刻の `andon waiting --json` の行と同じである。証拠: `go test ./internal/digest -run TestCollect` の ok の行。
2. **期間。** 前に送ったダイジェストがあるとき、期間の始まりがその終わりと同じである。無いときは 24 時間前である。前が 8 日前のときは 7 日前で切れ、切ったことが入力に書かれる。組み立てただけで送っていない前のダイジェストは数えない。送り先に Slack があって、Slack へ送れなかった前のダイジェストも数えない。証拠: `go test ./internal/digest -run TestPeriod`。
3. **組み立てが断る。** 入力に無い課題を指した JSON、要旨の無い JSON、テーマが 9 つある JSON、知らない図の型のある JSON を、`andon digest build` が終了コード 1 で断り、`library/digest/` に何も書かない。証拠: `go test ./internal/digest -run TestBuildRejects`。
4. **落とさない。** どのテーマにも入れなかったマージ済みの課題が、HTML の「そのほか」にタイトルで出る。証拠: `go test ./internal/digest -run TestBuildRest`。
5. **単一の HTML。** 組み立てた `digest.html` に `<script` が無く、`<link` が無く、`<a>` のほかに外を指す `src`・`href`・`url(` が無く、`<svg` が 1 つ以上あり、`ZgotmplZ` が無く、暗い色の指定（`prefers-color-scheme: dark`）があり、1 MiB より小さい。当たる場合があることを、同じ検査で、壊した HTML を照らして確かめる。証拠: `go test ./internal/digest -run TestSingleFile`。
6. **色。** 待っているものが手作業だけの入力から組み立てた HTML に、琥珀のクラスの付いた要素が無い。マージの依頼が 1 件あれば、その行と冒頭の数に付く。失敗の無い入力では、赤のクラスの付いた要素が無い。証拠: `go test ./internal/digest -run TestColors`。
7. **秘密を伏せる。** 課題のタイトルに GitHub のトークンの形の文字列を置くと、`digest.html` と `message.txt` に、その文字列が無く、伏せた印がある。証拠: `go test ./internal/digest -run TestRedact`。
8. **送り先が無い。** `project.json` に `digest` が無いとき、`andon digest send` は `files/` に HTML を出し、URL を出力し、偽のサーバに 1 度も来ない。作者の照合が通らない `project.json` でも同じである。証拠: `go test ./internal/digest -run TestSendNoDestination`。
9. **Slack へ送る。** 送り先があるとき、偽のサーバに、名前とバイト数、中身、チャンネルと短い文が、この順に 3 回来る。短い文に、要旨と、待っているものの数と、`files/` の URL がある。待っているものが 40 件ある入力でも、短い文は 3,000 字以下で、削った数が出る。もう一度打つと、偽のサーバに来ない。証拠: `go test ./internal/digest -run TestSendSlack`。
10. **送れなかった。** 偽のサーバが `not_in_channel` を返すと、終了コード 1 で、bot を招く手順の 1 行を出し、`sent.json` に理由が残る。偽のサーバを直して打ち直すと送る。証拠: `go test ./internal/digest -run TestSendFails`。
11. **トークンと確かめ。** `andon digest auth slack` が置いたファイルのモードが 600 で、どの command の出力にも `sent.json` にも、トークンの文字列が無い。`andon digest check` は、偽のサーバに、送るときと同じ 3 回の呼び出しで来る。送り先の設定が無いセルでは、何も送らず、設定が無いと 1 行で出す。証拠: `tests/andon-digest.sh` の出力の該当の行と、`go test ./internal/digest -run TestCheck`。
12. **端から端まで。** 切り離したセルの課題で、集める・組み立てる・送るを順に打つと `files/` に HTML ができる。同じ日に別の課題でもう 1 枚作っても、前の 1 枚が残る。ルーチンの例を kanban に写して `kanban lint` が通り、`kanban routine run daily-digest` で課題が足される。証拠: `tests/andon-digest.sh` の ok の行。
13. **約束。** `project.json` の `digest`、入力の JSON、担当の JSON の schema があり、[contract.md](../contract.md) の例が schema に通る。証拠: `tests/run --changed` の中の `tests/schema.sh` の行。
14. **代わりに決めたこと。** 一時の repo に、「決めたこと」の節へ「（Chief Engineer が決めた）」「（Chief Engineer が決めた。推奨は別の案だった）」「（オーナーが決めた）」の 3 行を足す commit と、節の外に同じ印の文を足す commit を置く。入力の決定の行は、前の 2 行だけである。証拠: `go test ./internal/digest -run TestDecisions`。
15. **セルを作り直しても残る。** compose に、トークンの置き場の volume がある。証拠: CI の `tests/image.sh` の該当の行（手元には docker が無い）。
16. **オーナーが見る（`manual`）。** Slack に届いた最初の 1 通で、スマホの Slack から HTML が開ける。待っているものだけが琥珀である。図がある。オーナーが、5 分で前の日のことが分かったと言える。
