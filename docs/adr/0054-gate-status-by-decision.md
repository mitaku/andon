# ADR-0054: gate は、オーナーのマージ待ちの PR に赤い印を付けない（仕様・設計。2026-11-22）

- 状態: **決定（2026-11-22）**。オーナーが対話の中で「決めた」と言った。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書き、この行を「覆された → ADR-NNNN」に直す。小さな改めは「決めたこと」に下から足す。
- 主題: `andon gate` が PR の head の commit に付ける印（commit status `andon/gate`）を、どの判定のときに、どの状態で書くか。検査が落ちたことと、gate がルールで自動のマージを止めたことを、PR を開く前に見分けられるようにすること。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。印とコメントの文を外の読み手に向けて書くと決めたのは [ADR-0026](0026-pr-rules-for-outside-readers.md) 決めたこと 9。
- この文書で「印」は、GitHub が commit に付ける合否の表示を指す。gate の印は commit status で、名前（context）は `andon/gate`。CI の印は GitHub Actions の check run で、名前は `tests`・`go`・`model`。「オーナー待ち」は gate の判定 `needs_human`、「差し戻し」は判定 `fix` を指す。

## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-22）: 「CIのgateのステータスチェック、ルールでgateが通らない場合にFAILになると、オーナーにはFAILでメールの通知が行ってしまい、テストで落ちているのか判断がつかないということを感じている」

gate は、判定が `approve` でなければ、PR の head の commit に赤い印（commit status `andon/gate` の `failure`）を付ける。オーナーがマージする変更のように、ルールで自動のマージを止めただけで、何も壊れていないときも赤になる。検査が落ちたときの印も同じ赤である。そのため、FAIL の知らせや赤い印を見ても、検査が落ちたのか gate のルールなのかが、PR を開いて印の名前を読むまで分からない。オーナーが欲しいのは、開く前に見分けがつくことである。

モデル: 調べなかった（変えるのは、gate が判定のあとに GitHub へ書く印の有無と値と文だけで、課題の状態の動き方も、gate の判定も、dispatcher の順も変えない）。

## 読んで分かった事実（2026-11-22。main `1e9edc5` と、Andon を開発しているセルの記録と GitHub で実測）

**gate が書く印。** `internal/gate/gate.go` の `postGitHub` は、判定が `approve` なら `success`、それ以外なら `failure` を書く。続けて PR にコメントを書く。判定が `wait` のときは、印もコメントも書かない。印の説明文は `internal/gate/comment.go` の `StatusDescription` が作り、`approve` 以外では見出しに変更の区分を括弧で足す（例「andon gate: メンテナーの判断が要る変更です（メンテナーが見る変更）」）。印にリンク（`target_url`）は付けていない。

**判定の順。** gate の決定式（`internal/gate/decide.go` の `Decide`）は、委譲の範囲の外かどうかを、CI の結果より先に見る。そのため、オーナー待ちの判定は、CI が走っている最中にも出る。

**印を読む所。** gate は、CI の結果をまとめるときに自分の印を数えない（`SummarizeChecks`）。dispatcher がマージの直前に読み直すときも同じ読み方をする。dispatcher のマージは `gh pr merge` に `--auto` を付けない。gate が PR から読むマージの可否（`mergeStateStatus`）は、衝突（`DIRTY`）だけを見る。repo のコードで、`andon/gate` の印の状態を読んで動きを変える所は無い。

**担当の checks の待ち方。** 担当は、PR を出したあと `gh pr checks <n> --watch` を裏の端末で走らせて checks を待つ（`package/skills/worker/SKILL.md` §3 の 4）。レビューで直すものが無ければ、checks の終わりを待たずに報告へ進む（同 §4 の 4）。そのため、担当の待ちが走っている間に、gate が同じ commit を判定することがある。セルのセッションの記録では、177 のセッションがこの command を使っていた。`pending` の字を探して待つ、自作の待ちも見つかった。

**記録の数。** セルの gate の記録は 214 件で、日付は 2026-11-19 から 2026-11-22 の 4 日である。記録は commit ごとに 1 件で、同じ commit を判定し直すと上書きされる。

| 判定 | 記録（commit の数） | GitHub に印を書いた回数 | 今の印 |
|---|---|---|---|
| `approve` | 100 | 100 | 緑（`success`） |
| `needs_human` | 107 | 107 | 赤（`failure`） |
| `fix` | 7 | 9 | 赤（`failure`） |

- 赤い印の記録 114 件は、どれも理由が 1 件だった。
- `needs_human` の 107 件のうち 96 件は、理由が「自動でマージしてよい範囲を超える変更」だけだった。オーナーがマージすると決めてある変更で、何も壊れていない。残りの 11 件は、条件表にその repo が無い（8 件）と、課題の設定を確かめられない（3 件）だった。
- `fix` の 7 件の理由は、PR が開いていないか draft（4 件）、branch が違う（1 件）、レビューがまだ無い（1 件）、直す重さの指摘が残っている（1 件）だった。
- 114 件のうち、判定のときに CI が落ちていたものは 0 件である。判定のときに CI が走っていたものは 32 件で、うち 31 件が `needs_human` だった。32 件のうち、あとで `tests` が落ちたものが 1 件、取り消されたものが 3 件あった。
- 同じ commit を判定し直したものは 3 件あった（`fix` から `approve` が 2 件、`needs_human` から `fix` が 1 件）。

**メールの出どころ。** 2026-11-19 から 2026-11-22 に、この repo についてオーナーへ届いた GitHub のメールは 14 通で、全部が GitHub Actions の実行の失敗の知らせだった（件名は「Run failed」か「PR run failed」。workflow は `tests` が 12 通、`model` が 2 通）。14 通は、同じ期間の Actions の失敗した実行に 1 通ずつ対応する。うち 3 通の実行は、再実行で通った。11 通は PR か branch の実行で、3 通は main の実行だった。gate の印についてのメールは 1 通も無い。

**GitHub の仕様。**

- commit status の状態は `error`・`failure`・`pending`・`success` の 4 つだけである。push できる利用者の token で書ける。同じ commit と名前の印は、新しいものが古いものに代わる。消す API は無い。
- check run なら `neutral`・`action_required` などの結論と詳細のページが使えるが、作れるのは GitHub App だけである。GitHub の文書は「OAuth apps and authenticated users can view check runs and check suites, but they are not able to create them」と書く。セルは、オーナーの `gh` の token で GitHub に書いている。
- commit status をまとめた状態は、どれかが `error` か `failure` なら `failure`、そうでなく `pending` があれば `pending`、全部が `success` なら `success` になる。
- `gh pr checks <n> --watch` は、commit status も check run も同じ一覧で数え、`pending` が 1 つでも残る間は終わらない（GitHub CLI のソースで確かめた）。落ちたものがあれば終了コード 1、落ちたものが無く `pending` があれば 8 で終わる。必須の check だけを数える `--required` は、必須の check の無い repo ではエラーになる。
- GitHub の文書が挙げる CI の通知は、GitHub Actions の workflow の実行の知らせだけである。API で書いた commit status の通知については、何も書かれていない。上のメールの実測と合う。

**この repo の決まり。** main の ruleset が必須にしている check は `tests` と `go` で、`andon/gate` は入っていない。Andon の文書は、`andon/gate` を必須の check にするよう勧めていない。条件表の `check` は、gate が自分で回す検査の command で、CI の無い repo でも使える。このセルの条件表には書かれていない。

## 前提（同意済み。番号）

オーナーが 2026-11-22 の入口で全部に同意した。

1. 直すのは、gate が PR に付ける印の見え方である。gate のルールと判定、必須の check は変えない。
2. メールは gate の印からは出ていない。届いた 14 通は全部 Actions の検査の失敗だった。見分けにくさの元は、メールを開いた先の PR で、gate がいつも赤い印を付けていることである。
3. 何もしないと、赤い印が失敗を知らせる役を果たさないままになる。赤い印の 114 件のうち 96 件は「オーナーがマージする変更」だけが理由で、判定のときに検査が落ちていたものは 0 件だった。
4. PR を開けば、印の名前で今も見分けられる。足りないのは、開く前に一覧の 1 つの印で分かることと、ひと目で分かる色の違いである。
5. 直しは gate のコードに入り、次のバージョンから新しい判定に効く。今開いている PR の印は直さない。このセルが扱う repo は 1 つで、`andon/gate` は必須の check でない。

入口では「赤い印を 114 回書いた」と伝えた。114 は commit の数で、書いた回数は 116 回だった（上の表）。前提の中身は変わらない。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案）

1. **2026-11-22 範囲は、gate が PR に付ける印の出し方だけにする。**（オーナーが決めた）
   直すのは、印を書くかどうかと、状態と説明文と、印から理由へのリンクである。GitHub のメールと Actions の設定、gate のルールと判定、必須の check には触れない。
   理由: 赤い印の 114 件のうち 96 件は何も壊れていない。これが赤でなくなれば、赤が失敗の知らせに戻る。直す所は gate の 1 か所と、その文書と検査で済む。
   捨てた案: コードを変えず、見分け方を文書に書くだけにする（赤い印がそのまま残る）／GitHub の失敗のメールを切る手順も運用の文書に書く（メールの設定はオーナーのアカウントにあり、今回の困りごとの元ではない）／gate 用の GitHub App を作って check run へ移す（決めたこと 4）。

2. **2026-11-22 オーナー待ちでは、印を書かない。通したら緑、差し戻しは赤のままにする。**（オーナーが決めた）
   `approve` は緑（`success`）、`fix` は赤（`failure`）で、今と同じである。`needs_human` では印を書かず、PR のコメントだけを書く。`wait` は今までどおり何も書かない。
   理由: オーナー待ちは失敗ではない。印を書かなければ、PR の印は検査の結果と、gate の差し戻しだけになる。検査が通っていれば一覧の印は緑、落ちていれば赤になり、開く前に見分けがつく。4 日の記録に当てると、gate が書く赤い印は 116 回から 9 回に減る。なぜオーナー待ちなのかは、今までどおり gate のコメントが PR に書く。差し戻しは、担当が直すまでマージできない状態で、gate が自分で回した検査が落ちたときも含むので、赤が合う。
   捨てた案:
   - オーナー待ちを黄の印（`pending`）にする。gate はオーナー待ちを CI の途中でも判定する（107 件のうち 31 件）。そのとき担当が裏で走らせている `gh pr checks --watch` は、黄の印が残る間は終わらない。黄の印は、オーナーがマージしたあとも消えない。一覧では、CI が走っている黄と同じ色になり、CI が通っても色が変わらない。直すには、担当の待ち方を替える command が要る。
   - オーナー待ちを緑にして、説明文で伝える。gate が通していないのに緑になる。`andon/gate` を必須にしている repo では、マージが通ってしまう。
   - gate は緑しか書かず、差し戻しでも印を書かない。赤は CI の失敗だけになり、決まりは一番単純になる。ただし、gate が自分で回した検査（条件表の `check`）が落ちたとき、PR のどこも赤くならない。
   - 今のまま赤にして、説明文とリンクだけ直す。一覧の印は赤のままで、開く前に見分けがつかない。

3. **2026-11-22 同じ commit に前の判定の印が残っているときだけ、オーナー待ちを黄（`pending`）で上書きする。**（Chief Engineer が決めた）
   gate は判定の前に、同じ commit の前の記録を読んでいる。前の記録の判定が `approve` か `fix` で、今の判定が `needs_human` のときは、印を `pending` で書く。前の記録が無いか、前も `needs_human` なら、書かない。
   理由: 印は消せない。書かないままだと、「直してから出し直す」の赤や「確かめが通った」の緑が、オーナー待ちの commit に残る。同じ commit の判定し直しは 4 日で 3 件で、この向き（`approve` か `fix` から `needs_human`）は 0 件だった。まれな道なので、黄の印の難点（決めたこと 2 の捨てた案）は小さい。
   捨てた案: 前の印を残す（今の判定と違う文が PR に出る）／赤で上書きする（今と同じ見え方に戻る）／GitHub から印を読んで、在るときだけ上書きする（前の記録で足りる。GitHub への問い合わせが増える）。

4. **2026-11-22 印は commit status のまま、名前も `andon/gate` のまま変えない。**（Chief Engineer が決めた）
   理由: check run を作れるのは GitHub App だけで、App の登録と秘密鍵の置き場が、Andon を使う人ごとに要る。名前は機械が読む約束で、gate と dispatcher が自分の印を CI から除くのに使っている（[ADR-0040](0040-kanban-gate-version-words.md) 決めたこと 3）。
   捨てた案: GitHub App を作って check run へ移す（入口でオーナーが範囲の外にした）／PR にラベルを付けて示す（付け外しの状態が増える）。

5. **2026-11-22 印の説明文は、見出しに最初の理由を括弧で足す。**（Chief Engineer が決めた）
   `approve` 以外の説明文を「andon gate: <見出し>（<最初の理由>）」にする。理由が 2 件以上あれば「ほか N 件」を足す。理由の文は、PR のコメントと同じ外向けの文を使う。`approve` の説明文と、判定ごとの見出しは変えない。
   理由: 今の括弧の中は変更の区分で、赤い印を見ても、なぜ差し戻されたかが分からない。赤い印に理由が出れば、検査が落ちたのか、レビューが無いのかが、印の行だけで読める。
   細部:
   - 例: 「andon gate: 作った側が直してから出し直す変更です（レビューがまだ無い）」「andon gate: 作った側が直してから出し直す変更です（CI が落ちた: tests）」「andon gate: メンテナーの判断が要る変更です（自動でマージしてよい範囲を超える変更）」。
   - GitHub の上限の 140 字を超えるときは、理由を「…」で切る。理由には、branch の名前や検査の command のように、長さの決まらない値が入る。
   - 内輪の語を出さない決まり（ADR-0026 決めたこと 9）は変えない。表に無い理由は「そのほかの理由」と書く。
   捨てた案: 今のまま変更の区分を足す（差し戻しの理由が出ない）／理由を全部並べる（140 字に収まらない）。

6. **2026-11-22 印から、理由を書いた PR のコメントへ飛べるようにする。**（Chief Engineer が決めた）
   gate は PR のコメントを先に書き、`gh pr comment` が出す URL を印のリンク（`target_url`）に入れる。GitHub は、印の行にこのリンクを出す。
   理由: 赤い印を見た読み手が、理由の全部を 1 回で読める。今は、印の行からコメントを探す。
   細部: コメントを書けなかったときは、リンクの無い印を書く。印を書けなかったときも、今までどおり判定は変えない。コメントの頭の `andon gate: ` は変えない。
   捨てた案: リンクを付けない（今のまま）／gate の記録を見せるページを別に作る（記録はセルの中にあり、外の読み手は開けない）。

7. **2026-11-22 今ある PR の赤い印は直さない。**（Chief Engineer が決めた）
   実装が入る前に付いた赤い印は、そのままにする。前のバージョンが赤を書いたオーナー待ちの commit を、新しいバージョンが判定し直してオーナー待ちになったときも、書き換えない（決めたこと 3 は、前の記録が `approve` か `fix` のときだけ上書きする）。
   理由: 過去の PR の印を直すには、全部の commit に書き直すことになる。開いている PR は少なく、新しい commit が push されれば、印はその commit から付け直される。
   捨てた案: 開いている PR の印だけ、当てたときに書き直す（1 度きりの手当てのために、書き直す手順と確かめが要る）。

8. **2026-11-22 印の決まりの正は `docs/contract.md` に置き、オーナー向けの読み方を `docs/operate.md` に書く。**（Chief Engineer が決めた）
   `docs/contract.md` の gate の節に、判定ごとに印を書くかどうかと、状態と説明文の形を書く。`docs/operate.md` に、PR の印の読み方を短く書く。書くのは次の 3 つである。印の名前で検査と gate を見分けること。gate の印は、通したときの緑と、差し戻したときの赤だけで、オーナー待ちには付かないこと。GitHub の失敗のメールは Actions の実行が落ちたときだけ届き、gate の印では届かないこと。
   理由: メールが検査の失敗だけを知らせていることは、オーナーも Chief of Staff も確かめるまで知らなかった。
   捨てた案: README に書く（初めて来た読み手に要る話ではない）。

## やらないこと（範囲の外。理由）

- **gate のルールと判定、判定の順を変えること。** どの変更をオーナーが見るかは、条件表と委譲が決める。前提 1。
- **GitHub のメールと Actions の通知を変えること。** メールは検査の失敗だけを知らせていて、gate の印とは別である。設定はオーナーの GitHub のアカウントにある。決めたこと 1。
- **再実行で通る検査を直すこと。** 14 通のうち 3 通は再実行で通った。検査の不安定さは別のテーマである。
- **`andon/gate` を必須の check にすること、必須の check の顔ぶれを変えること。** 前提 1。
- **check run と GitHub App。** 決めたこと 4。
- **担当の checks の待ち方を変えること。** オーナー待ちで印を書かなければ、担当の待ちは今より悪くならない。差し戻しの赤い印が一覧に出るのは今と同じである。
- **今ある PR の印を書き換えること。** 決めたこと 7。
- **PR のコメントの文を変えること。** コメントは理由を全部書いていて、今回の困りごとの元ではない。
- **gate の記録（`library/gate/<head>.json`）の形を変えること。** 印は記録から作る写しで、記録に項目は足さない。

## 受け入れ条件（テストできる形）

継ぎ目は 2 つ。印を書くかどうかと状態と説明文を決める純粋な関数（`internal/gate/comment.go`）と、`andon gate` が `gh` に渡す引数（`tests/andon-gate.sh` の偽の `gh` が控える）。本物の GitHub には書かない。

- **A1 印を書くかどうかと状態が、今の判定と前の判定で決まる。** `go test ./internal/gate/` に表のテストがある。行は次のとおり。`approve` は `success`。`fix` は `failure`。`needs_human` で前の記録が無いときは書かない。`needs_human` で前の記録が `needs_human` のときは書かない。`needs_human` で前の記録が `approve` か `fix` のときは `pending`。証拠は、テストの command と、表の行が通った出力。
- **A2 説明文が見出しと最初の理由になる。** `go test ./internal/gate/` で、理由が 1 件のとき「andon gate: <見出し>（<理由の外向けの文>）」、2 件以上のとき「ほか N 件」が付くこと、長い branch の名前と長い command を入れた理由でも 140 字を超えないこと、内輪の語が出ないことを見る。`approve` の説明文は今と同じである。証拠は、テストの command と出力。
- **A3 `andon gate` が、オーナー待ちでは印を書かず、コメントは書く。** `tests/andon-gate.sh` のオーナー待ちの場面で、偽の `gh` の控えに印の書き込みが無く、コメントの書き込みがあることを見る。差し戻しの場面に `state=failure`、通した場面に `state=success` があることも見る。印が無いことを見る grep には、同じ控えで印の書き込みを拾える場合があることを確かめる行を添える。証拠は、`tests/run --changed` の表の `andon-gate.sh` の行。
- **A4 同じ commit の判定し直しで、印が上書きされる。** `tests/andon-gate.sh` で、差し戻しのあとに同じ commit がオーナー待ちになる場面を作り、2 度目に `state=pending` が書かれることを見る。証拠は A3 と同じ行。

## 価値の仮説

1. **誰の何が変わるか。** オーナーが PR の一覧と PR の印を見たとき、赤い印は、検査が落ちたか、gate が担当に差し戻したかのどちらかだけを指す。オーナーのマージを待つ PR は、検査が通っていれば緑になる。
2. **見る信号。** 2 つ。1 つは、実装をセルに当てたあとの gate の記録で、判定が `needs_human` の commit の `andon/gate` の印を `gh api repos/<owner>/<repo>/commits/<head>/statuses` で数えた数。もう 1 つは、オーナーの目視（赤い印を見て、検査か gate かを迷った回数と、オーナー待ちの PR を見落とした回数）。
3. **見る日。** 2026-12-01。実装のマージの見込みを 2026-11-24 として、その 7 日後。
4. **誰が要るか。** オーナー。迷った回数と見落とした回数を一言で答える。
5. **効いたとどう分かるか。** 実装を当てたあとの `needs_human` の判定で、`andon/gate` の赤い印が 0 件。オーナーが迷った回数が 0 回。
6. **何があれば止めるか。** オーナーが、印が無いせいでオーナー待ちの PR を見落とした、または gate が見たのかどうか分からないと言ったら、オーナー待ちに印を出す形を検討し直す。そのときは、担当の checks の待ち方を替える command と一緒に決める。
