# ADR-0060: 開発の一連の流れを OpenTelemetry のトレースで辿れるようにし、振り返りと measure がそこから読む（仕様・設計。2026-11-24）

- 状態: **提案（2026-11-24）**。Chief Engineer が作り込んだ案である。オーナーが出口で「決めた」と言うまで、この文書から依頼書を切らない。
- 主題: Claude Code と Codex が自分で出す OpenTelemetry のトレースとイベントを、セルの中の受け口で受けて課題ごとに貯めること。kanban の記録から導いた段と束ねて、課題 1 件の流れを通して引けるようにすること。その内訳を、結果の記録と `andon measure` と振り返りの入力に足すこと。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。この文書が足す約束は「決めたこと」に形を書き、実装の課題が写す（それまでは提案）。OpenTelemetry の語（トレース・span・OTLP・resource 属性）は英語のまま使う。

## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-24）: 「振り返り、wiki にも通じますが、セル内のテレメトリーもう少し本格的に考えても良さそうです」「開発の一連の流れを Otel でトレースできるようになること、そこから改善できることが factory たる所以かも」「セルの中に otel サーバーの受け口を用意するのが良いんじゃないかな」。知識の蓄え方の話は「分けて考えよう」と言い、別のテーマにした。

オーナーの目的は、工場である Andon を、実行の記録から直せるようにすることである。今は記録が目的ごとのファイルに分かれている。そのため、1 件の仕事が信号かテーマから始まり、依頼書、担当、レビュー、gate、マージ、マージ後へ進む流れを、通して辿れない。課題の中でどの段が時間とトークンを使ったかも見えない。skill を直したあとに、同じ段の数字を直す前と比べる土台も無い。これを OpenTelemetry のトレースで辿れるようにし、振り返りと `andon measure` がそこから読めるようにする。受け口はセルの中に置く。オーナーは 2026-11-24 にこの言い直しに同意した。

モデル: 調べなかった（受け口は記録を受けて書くだけで、課題の状態、状態を動かす command の順と断り方、dispatcher と gate とレビューの順、役の間のやりとりのどれも変えない）

## 読んで分かった事実（2026-11-24。main `2b79050` と、Andon を開発しているセルの kanban と記録と、入っている道具で実測）

1. **記録は 8 種類あり、どれも時刻を持つ。** 起動の記録（`launches.jsonl`）、結果の記録（`outcome.json`）、走らせた記録（`runs/<n>.json`）、gate の記録（`gate/<head>.json`）、オーナーの手直し（`corrections.json`）、届けた通知の記録、信号の記録、kanban の行（`log.jsonl`）である。課題の一生の段は、この記録から時刻つきで並べ直せる。足りないのは、段の中で起きたことである。
2. **課題ごとのトークンの合計は、今も出ている。** `andon measure` は、Claude Code と Codex のセッションの記録を読んで数える。2026-11-18 から 2026-11-24 の 7 日では、動いた課題 873 件のうち 750 件で数えられた。合計は、入力 4,903 万、出力 2,983 万、キャッシュ読み 61.9 億、キャッシュ書き 1.02 億トークンである。入力の側の 97.6% がキャッシュ読みである。
3. **課題の中の内訳は出ていない。** 数えは課題ごとの合計で、どのターン、どのツール、どの役が使ったかに分かれない。`andon measure` は課題の `session` の 1 つだけを読むので、起動し直して `session` が替わった課題は前の分を数えない。
4. **Chief of Staff が使ったトークンは、どこにも出ていない。** Chief of Staff は課題でなく、起動の記録の `session` が `null` である。`andon measure` も結果の記録も数えない。
5. **待ちの内訳は出ていない。** `andon measure` の待ち時間は kanban の列ごとの平均である。`doing` の中の、オーナー待ち、レビュー待ち、CI 待ち、モデルの応答待ち、ツールの実行は分かれない。実働の数え（`ledger.Worked`）は、問いとレビューと端末が死んでいた間を引いた 1 つの数である。
6. **段の中で起きたことは、セッションの記録にしか無い。** 7 日以内に更新された Claude Code のセッションの記録は 532 本、1.3 GB である。ツール呼び出しは約 6.4 万回あった。この記録の形は公開の約束でなく、Claude Code は既定で 30 日で消す。Codex の記録は別の形である。
7. **パッケージのバージョンは細かく変わる。** 起動の記録にある担当の起動 309 回のうち、パッケージの commit は 176 種類あり、10 回以上起動された commit は無い。担当のプロファイルは `claude` が 253 回、`sonnet` が 55 回、`codex` が 1 回である。レビュアーの起動は 376 回、Chief Engineer は 34 回である。
8. **Claude Code はトレースとイベントを OTLP で出せる。** 入っているのは v2.1.331 である。文書（Monitoring）では、トレースはベータで、`CLAUDE_CODE_ENABLE_TELEMETRY=1` と `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` と `OTEL_TRACES_EXPORTER=otlp` で出る。プロンプト 1 つが根の span `claude_code.interaction` になり、その下に `claude_code.llm_request` と `claude_code.tool` が入る。ツールの下には、権限待ちの `claude_code.tool.blocked_on_user` と実行の `claude_code.tool.execution` が入る。サブエージェントの span は、親のツールの span の下に入る。
9. **対話のセッションは、親のトレースを引き継がない。** 文書は、環境変数 `TRACEPARENT` を読むのは Agent SDK と `claude -p` だけで、対話のセッションは読まないと明記している。担当、レビュアー、Chief of Staff、Chief Engineer は、どれも対話の `claude` で起動している（`package/templates/`）。逆向きには渡る。Claude Code は、Bash の子に、実行中のツールの span を指す `TRACEPARENT` を渡す。`OTEL_` で始まる環境変数は、Bash とフックと MCP の子に渡さない。
10. **起動のときに載せた属性は、span にもイベントにも載る。** `claude -p` を `OTEL_RESOURCE_ATTRIBUTES=andon.project=…,andon.issue=…,andon.role=…` つきで打って実測した。3 つの属性は、resource の属性と、span とイベントのそれぞれの属性の両方に載った。`session.id` も span に載った。文書はこの 2 点を span について書いていない。対話のセッションでは実測していない。
11. **個人の属性が、全部の記録に載る。** 同じ実測で、`user.email`、`user.account_uuid`、`user.account_id`、`user.id`、`organization.id` が、span とイベントの全部に載った。文書に、メールアドレスを止める設定は無い。
12. **本文は、既定では載らない。** プロンプト、応答、ツールの入力と出力は、それぞれ `OTEL_LOG_USER_PROMPTS`、`OTEL_LOG_ASSISTANT_RESPONSES`、`OTEL_LOG_TOOL_DETAILS`、`OTEL_LOG_TOOL_CONTENT` を立てたときだけ載る。既定で載るのは、プロンプトの長さ、ツールの名前、Bash の最初の語（`bash_argv0`）、所要時間、トークンの数である。`OTEL_LOG_TOOL_DETAILS` を立てると、Bash のコマンドの全文、ファイルのパス、検索の語、skill の名前、サブエージェントの型が載る。
13. **送る形は標準の OTLP の JSON である。** `OTEL_EXPORTER_OTLP_PROTOCOL=http/json` で使い捨ての受け口へ送らせて実測した。`/v1/traces` と `/v1/logs` へ、`Content-Type: application/json` の POST が届いた。圧縮は無く、`Content-Length` が付いていた。span は 1 つあたり約 2.7 KB、イベントは 1 件あたり約 1.9 KB だった。セッションの始めに、フックと plugin の登録のイベントが十数件出る。
14. **受け口が閉じていても、セッションは遅れない。** 送り先を、誰も listen していない `127.0.0.1` のポートにして `claude -p` を打つと、2.7 秒で終わった。送らないときは 2.8 秒だった。届かないアドレスに向けたときは 4.8 秒かかった。
15. **Codex もトレースとログを出せる。** 入っているのは v0.166.0 で、そのタグのソース（`codex-rs/config/src/types.rs`・`codex-rs/otel/`）を読んだ。設定は環境変数でなく `config.toml` の `[otel]` で、ログの `exporter`、`trace_exporter`、`metrics_exporter` を別々に持つ。OTLP/HTTP は `protocol = "json"` を選べる。`span_attributes` で、全部の span に属性を足せる。ログには足せない。`TRACEPARENT` を読むのは `codex exec` と app-server で、対話の画面の側に読む所は見つからなかった。動かしての実測はしていない。
16. **Codex の metrics の既定の送り先は、セルの外である。** `metrics_exporter` の既定は `statsig` で、送り先は `https://ab.chatgpt.com/otlp/v1/metrics` である。送るかは `analytics.enabled` に従う。セルの `config.toml` は、`analytics` も `otel` も指定していない。実際に送っているかは確かめていない。
17. **OpenTelemetry Collector の中身。** 最新は v0.165.0（2026-11-07）である。core の配布に、OTLP の受け口と、ファイルへ書く exporter（alpha）と、属性を書き換える transform（beta）が入っている。属性を落とす redaction は contrib の配布にだけある。ファイルへ書く exporter は、resource 属性 1 つでファイルを分けられるが、その属性の無い記録は捨てる。同じ exporter の文書は、フィールドの名前が変わらない保証は無いと書いている。イメージの道具を入れている aqua の標準の登録簿に、Collector は無い。端末で見る閲覧器 `otel-tui` はある。
18. **Andon の依存と常駐は少ない。** `go.mod` の直接の依存は 4 つで、OpenTelemetry のものは無い。boot が起動する常駐は、portless、files のサーバ、sshd、dispatcher の 4 つである。バイナリの中の HTTP のサーバは、files のサーバの 1 つである。秘密の形を伏せる部品（`internal/redact`）は 1 つあり、振り返りとダイジェストが共有している。
19. **起動の行は、呼び手の環境変数を継がない。** hc の template は、起動した側の環境変数を受け取らない。そのため、セッションの id は端末のラベルに載せ、template の行が `andon issue session` で読んでいる。担当とレビュアーの端末のラベルは `project`、`issue`、`title`、`session` で、`role` は無い。`role` があるのは Chief of Staff と Chief Engineer と dispatcher の端末だけである。App の mod は、`role` が無いことで担当の端末を見分けている（`package/host/andon/main.js`）。レビュアーの端末の `issue` は、親の課題でなく、レビュアーの課題の id である。起動の記録は、役をプロファイルから決めている（`internal/issue/start.go` の `roleOf`）。
20. **置き場とディスク。** kanban は git の外にある。dispatcher の控えは、作り直しても残る volume（`~/.local/state`）にある。このセルのディスクの空きは 892 GB である。事実 6 と 13 から見積もると、トレースとイベントは、このセルの流量で週に 1 GB 弱になる。
21. **関わる過去の決定。** トークンをドルに直さない（[decisions/2026-11-12-measure-tokens.md](../decisions/2026-11-12-measure-tokens.md)）。judge による採点と replay は最初のバージョンに入れない（[design.md](../design.md) §1.9 の 4）。記憶と指標はファイルで持ち、ホストされた置き場を持たない（同 §1.9 の 5）。ダイジェストの節は 8 つである（[ADR-0044](0044-owner-digest.md) 決めたこと 6）。工場の中の出来事は信号の記録に乗せない（[ADR-0051](0051-signals-flow-and-breaking-change.md) 決めたこと 2）。重い command を外のマシンで回す [ADR-0050](0050-external-compute.md) は、提案のままである。
22. **改善のループを決めたときの前提と、向きが逆の所がある。** [ADR-0028](0028-improvement-loop.md) の前提は、オーナーが 2026-11-19 に同意している。前提 1 は「新しい受け口は足さない」、前提 4 は「新しい保存先を作らない。記録は kanban の課題のフォルダに置く」、前提 5 は「新しい役と常駐を足さない」である。
23. **常駐と定期の処理を足すときの決まりがある。** [dispatcher.md](../dispatcher.md) §7.1 は、定期の処理は dispatcher だけが走らせると書いている。§7.4 は、常駐か定期の処理を足すときは、先に §7.2 の表に行を足すと書いている。files のサーバの二重の起動は、listen の確認と bind の失敗で防いでいる。
24. **結果の記録は課題ごとに 1 回だけ書かれる。** レビュアーの課題と Chief Engineer の課題にも、それぞれの `outcome.json` が書かれる。親の課題の `outcome.json` は、レビュアーのセッションを持たない。書く時点で、その課題の端末は片付いている（`internal/issue/finish.go`・`internal/dispatcher/outcome.go`）。親子は `issue.yaml` の `parent` で引ける。

## 前提（同意済み。番号）

オーナーが 2026-11-24 に同意した。

1. 困りごとは、記録が足りないことではなく、散っていて内訳が見えないことである。見えていないのは、課題の中のどの段とどのツールが時間とトークンを使ったか、待ちの内訳、Chief of Staff 自身が使ったトークンの 3 つである。
2. 何もしないと、振り返りは再発の数でしか直しの効きめを見られないままになる。内訳を知るには、セッションの記録を手で読むしかない。
3. ターンとツールとトークンの記録は、Andon が作らない。Claude Code と Codex が自分で出す。Andon が足すのは、その上の段の記録と、セッションを課題に結ぶ処理と、受け口の 3 つである。
4. 流れの単位は課題にする。課題の id で束ねて、起動からマージ後までを通して引ければよい。全部が OpenTelemetry のトレース 1 本に入っていることは求めない。
5. 記録はセルの外へ出さない。外へ送る話は、このテーマでは決めない。
6. 配り方はパッケージに入れる形にする。どのセルでも、手作業なしで既定で動く。止める設定は用意する。

## 決めたこと

### 範囲

1. **2026-11-24 範囲は、受け口と保存、課題 1 件の流れを引く command、measure と振り返りへの内訳、直しの前後の比較までにする（オーナーが決めた）。** 入口で 4 つの向きを並べ、オーナーは「選んで広げる」を選んだ。Chief Engineer の推奨も同じだった。
   理由: オーナーの言葉の「そこから改善できる」に届くのは、直す前と後を比べられるところまで作ったときである。
   捨てた案: 受け口と保存と、流れを引く command だけにする（数字を自分で command を打って読むことになり、振り返りが使わない）／measure と振り返りに内訳を足すところまでにする（直しが効いたかは、今と同じく再発の数だけになる）／今の記録をトレースから作り直す形に替え、judge と replay にも手を付ける（gate と dispatcher が読む記録が受け口の稼働に頼り、受け口が止まるとラインが止まる。[design.md](../design.md) §1.9 の 4 も覆す）。

### 受け口

2. **2026-11-24 受け口は andon のバイナリの中に作り、OpenTelemetry Collector は入れない（Chief Engineer が決めた）。** `andon otel serve` が、OTLP/HTTP の POST を受けてファイルに書く。使うのは Go の標準のライブラリだけで、`go.mod` の依存は増やさない。
   理由は 3 つある。1 つ目に、受け口の仕事の半分は Andon に固有である。課題ごとに振り分けること、個人の属性を落とすこと、振り返りとダイジェストが共有している部品で秘密の形を伏せることである。Collector ではこれを設定の言語で書くことになり、伏せる正規表現が 2 か所に分かれる。2 つ目に、受ける相手は信頼の境界の中の 2 種類の道具だけで、形は実測で確かめた標準の JSON である（事実 13）。3 つ目に、このセルの PC は並行 4 つが限度で、常駐は軽いほうがよい。
   標準から外れないための歯止めを 1 つ置く。書く行の形を、Collector のファイルの exporter と同じ OTLP の JSON にする（決めたこと 9）。あとで Collector や閲覧器を足すとき、貯めたファイルをそのまま読ませられる。
   捨てた案: Collector の core の配布をイメージに入れて常駐させる（イメージに別のバイナリが 1 つ増える。aqua の標準の登録簿に無いので、入れ方も別に持つ。個人の属性を落とす設定と伏せる正規表現を、Go と別の言語で二重に持つ。事実 17）／受け口を持たず、セッションの記録から読むときに組み立てる（今のトークンの数えと同じやり方。記録の形が公開の約束でなく、30 日で消え、Codex は別の形である。オーナーの向きとも違う）／andon の command と dispatcher にも OpenTelemetry の SDK を入れ、全部を 1 本のトレースとして送る（依存が増える。対話のセッションが親のトレースを引き継がないので、1 本にはならない。事実 9）。
3. **2026-11-24 受けるのは OTLP/HTTP の JSON のトレースとログだけで、metrics は受けない（Chief Engineer が決めた）。** 受け口は `127.0.0.1:4318` だけに listen する。受ける道は `/v1/traces` と `/v1/logs` の 2 つである。`/v1/metrics` と、JSON でない本文は断る。認証は付けない。
   理由: metrics の中身は、トークンと所要時間ではイベントと span に重なる。重ならないのはドルに直したコストで、Andon はトークンをドルに直さないと決めている（事実 21）。protobuf を受けるには依存が要る。Claude Code も Codex も JSON で送れる（事実 13・15）。
   捨てた案: metrics も受ける（量が増え、読み手が無い）／gRPC と protobuf も受ける（依存が要る。送り手の側で JSON を選べる）／`0.0.0.0` に listen する（セルの外から届く口を作る理由が無い）。
4. **2026-11-24 受け口は boot と役の起動のたびに確かめて起動し、止まっていても課題を止めない（Chief Engineer が決めた）。** boot は、files のサーバと同じ形で受け口を起動する。決めたこと 5 の `andon otel env` は、打たれるたびにポートが listen しているかを見て、していなければ起動する。listen している相手が andon の受け口であることは、受け口が返す名前で確かめる。別のプロセスがポートを取っているときは、送る設定を出さない。受け口が止まっている間の記録は欠ける。欠けは、読む側が「記録なし」として見せる（決めたこと 14・15）。二重の起動は、files のサーバと同じく、listen の確認と bind の失敗で防ぐ。ポートを取れるプロセスは 1 つだけである。常駐を足すので、[dispatcher.md](../dispatcher.md) §7.2 の表に、受け口の行を先に足す（事実 23）。
   理由: 受け口が閉じていても、送り手は遅れない（事実 14）。記録のために課題を止める理由が無い。起動し直す所を起動の口に置けば、dispatcher の 1 巡に手を入れずに済む。
   捨てた案: dispatcher の 1 巡で確かめる（dispatcher の検査に手が入る。起動のたびに確かめれば足りる）／受け口が止まっていたら起動を断る（記録のためにラインを止めることになる）。

### 送り手

5. **2026-11-24 送る設定は起動の行で渡し、役の起動だけが送る（Chief Engineer が決めた）。** command `andon otel env` を足す。自分の端末のラベルから `project` と `issue` と `role` を読み、送る設定を `KEY=VALUE` の並びで出す。ラベル `role` があれば、その値を役にする。無ければ、ラベル `issue` の課題のプロファイルから、起動の記録と同じ決め方で、担当かレビュアーかを決める（事実 19）。端末にラベルは足さない。App の mod が、`role` の無いことで担当の端末を見分けているからである。template の行は、これを `env` に渡して `claude` を起動する。送らない設定のとき（決めたこと 11）、ラベルが読めないとき、受け口を起動できないときは、何も出さずに終了コード 0 で終わる。起動は止めない。
   managed settings の `env` には置かない。送るのは、template から起動した担当、レビュアー、Chief of Staff、Chief Engineer のセッションだけになる。オーナーが自分で打った `claude` は送らない。
   理由: 属性は起動ごとに違うので、どのみち起動の行で渡す。送り先も同じ所で渡せば、止める設定を 1 か所で効かせられる。managed settings に置くと、オーナーが手で起動したセッションまで送ることになり、オーナーの記録の扱いを広げる。
   捨てた案: managed settings の `env` に送り先を置く（役でないセッションも送る。止めるには settings を書き換える）／課題に結ぶ処理を受け口の側でする（受け口が kanban を読むことになる。属性で渡せば受け口は何も引かない）。
   細部: Claude Code に渡すのは、`CLAUDE_CODE_ENABLE_TELEMETRY=1`、`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`、`OTEL_TRACES_EXPORTER=otlp`、`OTEL_LOGS_EXPORTER=otlp`、`OTEL_METRICS_EXPORTER=none`、`OTEL_EXPORTER_OTLP_PROTOCOL=http/json`、`OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`、`OTEL_RESOURCE_ATTRIBUTES`、それに決めたこと 7 の 1 つである。起動し直す行（`resume:`）にも同じものを渡す。
6. **2026-11-24 セッションを課題に結ぶのは、起動のときに載せる resource 属性にする（Chief Engineer が決めた）。** 属性は `andon.project`、`andon.issue`、`andon.role` の 3 つである。`andon.issue` は端末のラベルの値のままで、レビュアーではレビュアーの課題の id になる。Chief of Staff には `andon.issue` を載せない。パッケージのバージョン、プロファイル、何回目の起動かは載せない。読む側が、`session.id` と時刻を起動の記録（`launches.jsonl`）と照らして引く。
   理由: 属性が載ることは実測した（事実 10）。バージョンとプロファイルは起動の記録が正で、2 か所に持つと食い違う。
   捨てた案: 環境変数 `TRACEPARENT` で親子を結ぶ（対話のセッションは読まない。事実 9）／`session.id` だけで結ぶ（Chief of Staff は起動の記録に `session` が無い。Codex は起動のときに id が決まらない）。

### 載せる中身

7. **2026-11-24 ツールの詳細は載せ、プロンプトと応答の本文は載せない（Chief Engineer の推奨。オーナーが出口で決める）。** 渡すのは `OTEL_LOG_TOOL_DETAILS=1` だけである。`OTEL_LOG_USER_PROMPTS`、`OTEL_LOG_ASSISTANT_RESPONSES`、`OTEL_LOG_TOOL_CONTENT` は立てない。載るのは、Bash のコマンドの全文、ファイルのパス、検索の語、skill の名前、サブエージェントの型である。プロンプトは長さだけが載る。ツールの出力は載らない。
   理由: ツールの詳細が無いと、Bash は最初の語までしか分からない。`go test` と `go build` が分かれず、CI を待っている時間も切り出せない。どの skill が呼ばれたか、wiki のどのページを読んだかも分からない。改善の材料として効くのは、この詳細である。同じ中身は、セッションの記録としてセルの中に既にある（事実 6）。本文は、振り返りがセッションの記録から要る分だけ抜いている（[ADR-0028](0028-improvement-loop.md) 決めたこと 4）ので、トレースに重ねて持たない。
   捨てた案: どちらも載せない（文書の既定。内訳はツールの名前までになり、待ちの内訳から CI 待ちが落ちる）／本文も載せる（オーナーが端末で打った文と、依頼書と報告の全文が、寿命 30 日の置き場にもう 1 つできる。読み手が無い）。
8. **2026-11-24 受け口は、書く前に個人の属性を落とし、秘密の形を伏せる（Chief Engineer が決めた）。** 落とす属性は `user.email`、`user.account_uuid`、`user.account_id`、`user.id`、`organization.id` である。そのあと、行の全体を `internal/redact` に通す。Codex の、ツールの出力を運ぶ属性も落とす（属性の名前は決めたこと 19 の実測で決める）。
   理由: 1 人のセルで、個人の属性は読み手が無い。ファイルがセルの外へ出たとき、誰のセルかが分かる値になる（事実 11）。Bash のコマンドの全文には、トークンが混ざりうる。
   捨てた案: 送り手の設定で止める（メールアドレスを止める設定が無い）／伏せずに書き、読むときに伏せる（置き場に秘密が残る）。

### 保存

9. **2026-11-24 置き場は作り直しても残る volume にし、課題ごとのファイルに OTLP の JSON の行で書く（Chief Engineer が決めた）。** 置き場は `~/.local/state/andon/otel/<project>/` である。課題の属性のある記録は `issues/<id>/traces.jsonl` と `issues/<id>/logs.jsonl` に、課題の属性の無い役の記録は `roles/<role>/<日付>.traces.jsonl` と `roles/<role>/<日付>.logs.jsonl` に足す。日付は UTC である。1 行は、resource 1 つ分の OTLP の JSON（`resourceSpans` か `resourceLogs` を 1 つ持つ書き出しの要求）である。
   `andon.project` が無い記録、`andon.project` と `andon.issue` と `andon.role` が id の形に合わない記録は書かずに捨て、捨てた数を受け口のログに残す。
   理由: 課題ごとに分ければ、`andon trace` は、その課題とレビュアーの課題のフォルダを読むだけで済む。寿命もファイルの単位で切れる。行の形を Collector の exporter と同じにしておけば、標準の道具がそのまま読める（事実 17）。属性は送り手が書く値なので、パスに使う前に形を確かめる。
   捨てた案: 日ごとの 1 ファイルにする（課題 1 件を引くのに、期間の全部を読む）／データベースに入れる（記憶と指標はファイルで持つ。事実 21）。生の記録を kanban の課題のフォルダに置く案は、決めたこと 24 で比べる。
10. **2026-11-24 生の記録の寿命は 30 日、合計の上限は 10 GB にし、片付けは dispatcher が 1 日に 1 回走らせる（Chief Engineer が決めた）。** 片付けは、そのプロジェクトの dispatcher が 1 日に 1 回走らせる。最後に書いてから 30 日を過ぎたファイルを消す。プロジェクトの置き場の合計が上限を超えたら、古いファイルから消す。圧縮はしない。片付けが失敗しても、dispatcher の 1 巡は止めない。[dispatcher.md](../dispatcher.md) §7.2 の表に、片付けの行を先に足す。消すだけの処理で、2 度走っても結果は同じである。
   片付けを受け口にさせない理由は 2 つある。定期の処理は dispatcher だけが走らせる決まりである（事実 23）。寿命と上限はプロジェクトの設定で、`project.json` を決まった読み方で読むのは dispatcher である（決めたこと 11）。受け口は kanban も設定も読まず、受けて書くだけにする。
   理由: 30 日は、Claude Code がセッションの記録を消すまでの日数と同じである。直しの前後の比較は、マージから 14 日以内の直しが対象で、30 日あれば足りる（決めたこと 17）。このセルの流量で 30 日は 4 GB ほどになる（事実 20）。長く残したい数は、結果の記録に内訳として残る（決めたこと 15）。
   捨てた案: 消さない（セルの PC の容量を食い続ける）／受け口が自分で 1 日に 1 回片付ける（定期の処理を走らせる者が 2 つになる。送らない設定のプロジェクトで、古い記録が残り続ける）／圧縮する（量が 1 割ほどになるが、標準の道具がそのまま読めなくなる。上限に当たるセルが出てから足す）。
11. **2026-11-24 止める設定と寿命の設定は `project.json` の任意のキー `otel` に置き、既定は送る。読めないときは送らない（Chief Engineer が決めた。既定で動かすことは前提 6 でオーナーが同意した）。** 形は `{"enabled": false, "days": 30, "max_gb": 10}` で、どのキーも任意である。`project.json` が読めて `otel` が無ければ、送り、30 日と 10 GB で回す。`andon otel env` は、`enabled` が `false` のプロジェクトで何も出さない。`project.json` が無いとき、読めないとき（オーナーの commit でない、schema を通らない）も、何も出さない。そのとき、片付けは既定の 30 日と 10 GB で回す。
   理由: `project.json` は、オーナーが commit したものだけが読まれる（[contract.md](../contract.md) §11）。記録の扱いを変える設定の置き場として合う。読めない値を黙って既定に落とさない決まり（[contract.md](../contract.md) の原則 2）に合わせ、読めないときは送らない側に倒す。止めると書いた設定が読めなくなったとき、黙って送り始めない。
   捨てた案: セルの `andon.toml` に置く（置き場はプロジェクトごとに分かれていて、止めたい単位もプロジェクトである）／環境変数で止める（template は呼び手の環境変数を継がない。事実 19）。

### 段と流れ

12. **2026-11-24 段は kanban の記録から導き、andon の command と dispatcher とフックは span を出さない（Chief Engineer が決めた）。** 課題の一生の段は、読むときに、今ある記録から時刻つきで組み立てる。新しく書く記録は無い。
   理由: 段の時刻は、今の記録に全部ある（事実 1）。同じ出来事を、記録と span の 2 か所に書かない。過去の課題にも、さかのぼって段を引ける。受け口が止まっていても、段は欠けない。dispatcher と gate の検査にも手が入らない。
   捨てた案: command ごとに span を出す（同じ出来事を 2 か所に書く。OpenTelemetry の SDK の依存か、span を組む自前のコードが要る）／dispatcher の 1 巡を span にする（誰が何を決めるために読むかが無い）。
   細部: 導く段と、元の記録は次のとおり。

   | 段 | 元の記録 |
   |---|---|
   | 列ごとの待ちと動き | `log.jsonl` |
   | 起動、起動し直し | `launches.jsonl` |
   | 走らせた command | `runs/<n>.json` |

13. **2026-11-24 流れの単位は課題にし、レビュアーの課題は親の課題の木に入れる（Chief Engineer が決めた。課題を単位にすることは前提 4 でオーナーが同意した）。** レビュアーの記録は、レビュアーの課題のフォルダに貯まる（決めたこと 6）。読む側は、`issue.yaml` の `parent` がこの課題で、プロファイルがレビュアーの課題を引き、その記録を同じ木に入れる。Chief Engineer のテーマと、そこから切った課題は、`parent` の id を出すだけにし、1 本の木にしない。信号と課題も、`links` を出すだけにする。Chief of Staff のターンは、課題に割り当てない。

### 読み手

14. **2026-11-24 `andon trace <id>` を足し、1 本のトレースに縫い直した OTLP の JSON も出せるようにする（Chief Engineer が決めた）。** 出すのは、課題 1 件の木である。上から、段、起動、プロンプト 1 つ分の `interaction`、その下のモデルの呼び出しとツールの順に並べる。既定は人が読む表で、プロンプト 1 つ分までを 1 行ずつ出す。`--json` は木の全部を出す。`--otlp` は、同じ木を OTLP の JSON の 1 本のトレースとして出す。

   捨てた案: 受け口が、受けたときにトレースの id を書き換える（受け口が起動の記録を読むことになる。送り手が出した形が残らない）／表だけを出す（オーナーの「Otel でトレースできる」に届かない）。
15. **2026-11-24 結果の記録に課題ごとの内訳 `breakdown` を足し、生の記録が消えたあとも残す（Chief Engineer が決めた）。** dispatcher は、課題が片付いて `outcome.json` を書くとき、その課題の生の記録を読んで内訳にまとめ、任意のキー `breakdown` として一緒に書く。生の記録が 1 行も無い課題は `breakdown: null` と書く。内訳は、今の `sessions[]` と同じく、課題ごとに持つ。レビュアーの課題と Chief Engineer の課題にも、それぞれの内訳を書く。親の課題の内訳に、レビュアーの分は入れない（事実 24）。`andon measure` と振り返りは、課題の分については、生の記録でなく、この内訳を読む。

   ```json

     "tokens": {"input": 1200, "output": 35000, "cache_read": 2400000, "cache_write": 180000},
     "errors": {"llm": 2, "tool": 5},
     "tools": [{"name": "Bash", "argv0": "go", "count": 14, "ms": 412000, "errors": 1}],
     "waits": {"owner_ms": 0, "review_ms": 540000, "ci_ms": 300000, "gone_ms": 0}}}
   ```

   `role` は、起動の記録の役である。`coverage` は、起動の記録にあるセッションのうち、生の記録に span が 1 つでもあったものの数である。サブエージェントの分は、親のセッションに入れる。`tools` は、時間の長い順の上から 10 個である。`waits` の `owner_ms` と `review_ms` と `gone_ms` は kanban の記録から、`ci_ms` は PR の checks を待つ command のツールの span から数える。
16. **2026-11-24 `andon measure` に内訳の節とプロファイルごとの節を足す（Chief Engineer が決めた。足すことは決めたこと 1 でオーナーが決めた）。** 内訳の節は、期間に片付いた課題の `breakdown` を役ごとに合わせて、次を出す。担当の課題の待ちの内訳。役ごとのトークンと、キャッシュ読みの割合。時間を使ったツールの上から 10 個。モデルの呼び出しとツールの失敗の数。内訳の無い課題の数。あわせて、期間の Chief of Staff のトークンと、全体に占める割合を出す。
   Chief of Staff には課題が無く、内訳を置く `outcome.json` が無い。この分だけは、役ごとの生の記録から数える。生の記録は 30 日で消えるので、数えられるのは残っている日の分だけである。期間がそれより前に掛かるときは、数えられた日数を添えて出す。長く残す数は、振り返りの入力に載せる（決めたこと 17）。
   プロファイルごとの節は、プロファイルごとに、課題の数と、実働とトークンの中央値と、gate の差し戻しの率と、レビューの周回の中央値を出す。
   `--json` にも同じ節を足す。
   理由: 前提 1 の、見えていない 3 つに当たる。
   捨てた案: 課題ごとの行に内訳を足す（今も課題ごとの行が千行を超える）／ドルに直したコストを出す（事実 21 の決定を覆す。サブスクリプションでは意味の薄い数である）。
17. **2026-11-24 振り返りの入力に、課題ごとの内訳と、直しの前後の数字を足す（Chief Engineer が決めた。足すことは決めたこと 1 でオーナーが決めた）。** `andon retro collect` は、全文の束に `breakdown` を足す。前の直しの一覧 `fixes[]` には、直しのマージの前と後の数字を足す。前と後は、それぞれ、マージの時刻より前と後に片付いた担当の課題の、近いほうから 30 件までである。出すのは、実働とトークンの中央値と、gate の差し戻しの率と、レビューの周回の中央値である。前か後が 10 件に満たないときは、数字を出さず、件数が足りないと書く。束には、振り返りの期間の Chief of Staff のトークンの合計と、数えられた日数も足す。束は振り返りの課題のフォルダに残るので、生の記録が消えたあとも、この数は残る。
   振り返りの担当は、直しの見立てを書くとき、再発の数に加えてこの数字を読む。数字だけで直しを戻す判定はしない。
   理由: 直しが効いたかを、今は再発の数だけで見ている（前提 2）。前後の数字は、直しと関係の無い変化も拾うので、判定でなく材料にする。
   捨てた案: 直しが当たったセッションだけを起動の記録の commit で選ぶ（確かだが、起動のたびに git の履歴を引く。まず時刻で分け、粗さが問題になってから改める）／数字が悪くなった直しを自動で戻す（skill の自己書き換えと同じで、ラインの変更になる。[design.md](../design.md) §1.9 の 5）。
18. **2026-11-24 比べる形はバージョンごとの表にせず、プロファイルごとと直しの前後にする（Chief Engineer が決めた）。** 入口では「skill とプロファイルのバージョンごとの比較」と言った。調べると、パッケージの commit は 176 種類あり、10 回以上起動されたものが無い（事実 7）。バージョンごとに並べても、1 行が数件にしかならない。
   理由: 比べたいのは、ある直しの前と後である。直しのマージの時刻で分ければ、前後に数十件ずつ集まる。
   捨てた案: バージョンごとの表を出す（1 行が 2 件足らずになる）／タグを打ったバージョンごとに並べる（直しとバージョンが 1 対 1 にならない）。

## 価値の仮説

1. 誰の何が変わるか。オーナーと振り返りの担当が、課題の中でどの段とどのツールが時間とトークンを使ったかを、セッションの記録を手で読まずに引ける。振り返りが、直しの効きめを、再発の数に加えて前後の数字で見る。
2. 見る信号。外の信号は使わない。見るのは、課題の `library/outcome.json` の `breakdown` と、振り返りの課題の `library/retro.json` の、パターンの根拠と直しの見立ての文である。あわせて、オーナーが `andon trace` と `andon measure` の内訳を読んで何かを決めたかを、オーナーに聞く。
3. 見る日。2026-12-12。
4. 誰が要るか。オーナー。`andon measure` の内訳を 1 回読む。
5. 効いたとどう分かるか。見る日までの 7 日に片付いた担当の課題のうち、`breakdown` が `null` でないものが 9 割以上ある。見る日までに回った振り返りのうち、パターンの根拠か直しの見立てに、内訳か前後の数字を引いたものが 3 件以上ある。
6. 何があれば止めるか。振り返りが内訳も前後の数字も 1 度も引かず、オーナーも内訳を読んで決めたことが無いなら、既定を「送らない」に替える案をオーナーに出す。置き場が合計の上限に 2 回当たったら、寿命を縮める。`breakdown` のトークンが `sessions[].cost` と 2 割以上ずれる課題が続くなら、内訳を比較に使うのを止め、数え方を調べる。
