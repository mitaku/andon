# ADR-0067: オーナーのマージを待つ PR の branch の上で、後ろの課題を起動する（仕様・設計。2026-11-26）

- 状態: **決定（2026-11-27）**。オーナーが 2026-11-27 に「決めた」と答えた。実装は「依頼書に切る案」のとおり別の課題（切るのは Chief of Staff）。覆すときは新しい ADR を書く。
- 主題: `after` で前の課題を待つ担当の課題を、前の課題がオーナーのマージを待っている間に、前の課題の PR の branch の上で起動する（Stacked PR）。[ADR-0065](0065-owner-waits-never-stop-launch.md) 決めたこと 2 が次のテーマに回した仕組みである。[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 11 の前半（`after` で待つ課題を、前の課題がマージされる前に起動する道は作らない）と、[decisions.md](../decisions.md) の 2026-11-03 の仮の決定（積み重ねた PR は採らない）を覆す。同じ文書の 2026-11-05 の決定（base が既定の branch でない PR は、いつもオーナーへ回す）を、積んだ PR についてだけ改める。
- 語は [design.md](../design.md) §0.1。機械が読む形の正は [contract.md](../contract.md) と `schema/`。この文書が変える約束は「決めたこと」に形を書き、実装の課題が写す（それまでは提案）。
- この文書の語: 「前の課題」は、`after` で待たれている課題を指す。「後ろの課題」は、それを `after` で待つ課題を指す。「積んだ課題」は、前の課題の PR の branch の上で起動した後ろの課題を指し、その PR を「積んだ PR」と呼ぶ。「分かれ目」は、積んだ課題の branch を切った時の、前の課題の PR の head の commit を指す。「載せ替え」は、積んだ課題の自分の commit だけを、既定の branch の先へ移すこと（`git rebase --onto`）を指す。

## 問題（オーナーの言葉で。言い直しの段落）

オーナーは 2026-11-25 に「オーナー確認待ちが溜まったから工場が止まるというのは変です。」と言った。ADR-0065 は、オーナー待ちの数で起動を止める歯止めを外した。そのときオーナーは、たまった PR には新しい上限も新しい知らせも足さず、rebase が要らない形に仕事を組んで扱うと決め、その仕組みを次のテーマに回した。

オーナーが望んでいるのは、自分のマージを待つ PR がいくつたまっても工場が止まらないことと、たまった PR が main の動くたびに取り直しにならないことである。この文書は、そのうち「止まらない」の残りを扱う。歯止めを外しても、順番に並べた課題の列は止まる。後ろの課題は、前の課題が main に入るまで起動されない。前の課題がオーナーのマージを待っている間、後ろの課題は何もせずに待つ。

「取り直しにならない」は、この文書では扱わない。事実 2 のとおり、取り直しの 7 割は関係の無い PR が main に入ったことが原因で、積んで起動する仕組みでは減らない。オーナーは 2026-11-26 に、この文書の範囲を Stacked PR の仕組みだけにし、取り直しをまとめる仕組みは続けて次のテーマにすると決めた。

14. **GitHub の側。** Andon の repo は、マージした PR の head の branch を自動で消す設定である。GitHub は、消した branch を base にしていた open の PR の向き先を、マージした PR の base に付け替える。CI のワークフロー（`.github/workflows/`）は、PR の base の branch でも draft かどうかでも絞っていないので、積んだ draft の PR でも走る。ただし、`pull_request` のワークフローは、PR が base と衝突している間は走らない。向き先の付け替えと、draft を外すことでは、ワークフローは走らない（既定の種類は、開く、push、開き直すの 3 つである）。main の ruleset が必須にしている checks は `tests` と `go` で、対象は main へ向く PR だけである。
15. **GitHub の Stacked PR の機能。** GitHub は 2026-10-06 に、Stacked PR の機能を全部のプランで一般提供にした。積んだ PR の組を「stack」として登録する形で、登録は REST の API（`POST /repos/{owner}/{repo}/stacks`）か、画面か、gh の拡張 `gh stack`（v0.3.0、2026-10-26。gh 2.0 以上と Git 2.36 以上が要る）で行う。文書によると、stack の一番下の PR がマージされると、残りの branch は GitHub の側で自動で rebase され、次の PR の向き先が既定の branch になる。stack の PR はどれも、stack の base（ふつうは main）の決まりで見られる。途中の PR をマージすると、その下の PR も一緒に main へ入る。下の branch に push されるか main が進むと、stack は線の形でなくなることがあり、そのときはマージの前に stack の rebase が要る。この repo で `GET /repos/{owner}/{repo}/stacks` を打つと、空の並びが返った。API は応えるが、stack はまだ 1 つも無い。文書に書かれていないことが 6 つある。向き先を前の branch にしただけの PR が、登録なしで stack になるか。自動の rebase が squash のマージのあとにも起きるか。自動の rebase が衝突した時にどうなるか。自動の rebase が head を書き直した時に CI が回り直るか。draft の PR を stack に入れられるか。下の PR がマージされずに閉じた時に上の PR がどうなるか。`gh stack link` の説明は「PR がまだ stack に入っていなければ、新しい stack を作る」と書いているので、向き先をつないだだけの PR は、登録するまで stack ではないと読める。
16. **印と draft についての前の決定。** [ADR-0056](0056-gate-required-before-merge.md) 決めたこと 2 で、オーナーは `andon/gate` を main の必須の check にすると決め、判定の前の PR を draft で守る案を捨てた（だれでも 1 押しで外せる。守る状態が 2 つになる）。同じ ADR の決めたこと 3 は、通したときとオーナー待ちを緑、差し戻しを赤、止めている間を黄と決めている。決めたこと 9 は、止めのために新しい判定を足す案を、待ちと同じ動きで足りるとして捨てた。
17. **squash と載せ替え。** この repo の PR は squash でマージされることが多い。squash でマージすると、前の課題の commit は main に入らず、同じ中身の新しい commit が 1 つ入る。積んだ課題の branch は前の課題の古い commit を含んだままなので、main へ向けるには、自分の commit だけを main の先へ移す載せ替えが 1 回要る。手元の一時の repo で試すと、`git rebase --onto origin/<既定> <分かれ目>` は、前の課題が squash で入ったあとも、マージ commit で入ったあとも、終了コード 0 で済んだ。ただし、済んだあとに同じ行を打ち直すと、head が変わらないのは、分かれ目より後の main に、同じ行を 2 回変えた commit の並びが無いときだけだった。在ると、打ち直しは main の commit を積み直そうとして、衝突で止まる。反論の役が、この repo の履歴の写しで分かれ目を 5 commit 前に置いて試すと、打ち直しは衝突で止まった。
18. **今の手引き。** `package/skills/chief-of-staff/playbooks/start.md` は、「`after` で前の課題を待つ課題は、前の課題がオーナーのマージを待っていても先に起動しない（`after` を外さない・前の課題の branch の上で起動しない）」と書いている。担当の skill は、PR を base の指定なしで出し、頼まれていない rebase をしないと書いている。
19. **モデル。** `model/IssueLife.tla` は課題 1 つと PR 1 つの一生を写す。`after`、branch の base、PR の向き先、`queued` は持たない。

5. GitHub の既にある仕組みで済む部分は小さい。向き先の付け替えと、main へ向かない PR の CI は使える（事実 14）。マージの直前に GitHub が検査を回し直す merge queue は、個人のアカウントの repo では使えない見込みである。これは 2023 年の発表と外部の解説で確かめたもので、今の公式の文書では確かめ切れていない。

前提 5 は、入口のあとで事実が足りないと分かった。GitHub には Stacked PR の機能がある（事実 15）。入口では比べていなかった。2026-11-27 の出口で、足りなかったことをオーナーに伝え、使うかどうかを聞いた。オーナーは、今は使わずに実測すると決めた（決めたこと 3）。

入口で前提 3 に添えた「前の PR が直されたときも載せ替えが要る」は、設計で要らなくした（決めたこと 11）。載せ替えは、積んだ課題 1 件につき、前の課題が main に入った時の 1 回だけである。

3. **2026-11-27 GitHub の Stacked PR の機能には、今は登録しない。Andon が、向き先を前の課題の branch にした PR で積む。捨てる前提の repo で実測してから、登録するかを決め直す（オーナーが決めた）。**

### 積んで起動する

4. **2026-11-26 積めるのは、待つ相手が 1 つだけ残り、その PR を gate が今の head で通している課題だけにする（Chief Engineer が決めた）。**
   後ろの課題が次の全部を満たすとき、その課題を「積める」と言う。`queued` の担当の課題である。`after` のうち `done` でない課題がちょうど 1 つである。その前の課題は同じ repo の担当の課題で、`review` にいて、止められておらず（`hold` が無い）、PR が open である。前の課題の PR の今の head に、今の `review` の回の gate の記録があり、判定が approve か needs_human か、決めたこと 8 の `behind` である。`not_before` の日が来ている。

5. **2026-11-26 `andon issue start` が、積める課題の branch を前の課題の PR の head から切り、予約キー 2 つに控える。kanban は、積んだ相手を待つ相手に数えない（Chief Engineer が決めた）。**

   理由: Chief of Staff が打つ口を増やさない。積めるかどうかは command が確かめるので、手引きの読み違いで、通っていない PR の上に積むことが起きない。`after` を書き換えずに残すと、kanban が `doing` へ動かすことを断る（事実 6）。最初の起動でも、gate の直しを受けて戻る時でも断られるので、kanban の側の数え方を変える。
   細部:
   - branch は、前の課題の PR の head（gate が通した commit）から切る。origin を取り直してから切り、origin の branch の先がその commit と違えば、起動せずに理由を 1 行出す。

   - 担当の最初のメッセージに、前の課題の上で起動したことと、PR の出し方（決めたこと 7）を 1 行足す。
   - 途中で失敗したら、今の起動と同じに、作った worktree と branch と書いたキーを戻す。
   捨てた案: `--onto <id>` の旗を足して Chief of Staff が前の課題を名指す（待つ相手は `after` に書いてあり、名指しは二重になる）。`after` から前の課題を外して `todo` にする（前の課題が何件を後ろに持つかの数えと、片付けの順が崩れる）。担当に `kanban start --force` を打たせる（守りを外す旗を、手順の文に書くことになる）。

6. **2026-11-26 積める課題を `andon waiting list --json` の `stackable` に出し、積む深さに上限を置かない（Chief Engineer が決めた）。**
   理由: 積めるかどうかは gate の記録を読んで決まり、gate の記録を読んで数える式は `andon waiting list` だけが持つ（[contract.md](../contract.md) §25）。オーナーは、たまった PR に新しい上限を足さないと決めている（ADR-0065 決めたこと 2）。動いている担当の数は、並行の上限が今までどおり抑える。
   細部:
   - 出力の一番上に `stackable` を足す。中身は `{"id": "<後ろの課題>", "on": "<前の課題>"}` の並びで、無ければ空の並びである。

   捨てた案: 積む深さを 1 段までにする（3 つ以上並んだ列が、2 つ目のマージ待ちでまた止まる。実測した列には 6 つ並んだものがある）。積める課題を `kanban ready` に出す（kanban が gate の記録と PR の状態を読むことになる）。

### PR と gate

7. **2026-11-27 積んだ PR は draft で出し、向き先を前の課題の branch にする。積んでいる間は、base が既定の branch でないことをオーナーへ回す理由にしない（オーナーが決めた）。**
   担当は、積んだ課題の PR を `gh pr create --draft --base <前の課題の branch>` で出す。前の課題が main に入ると、決めたこと 13 の載せ替えが向き先を既定の branch にし、draft を外す。オーナーがマージする時の PR は、今と同じ、main へ向くふつうの PR である。
   理由: 向き先が前の課題の branch なら、GitHub の画面の差分は積んだ課題の分だけになり、CI も走る（事実 14）。向き先が main でない PR には main の ruleset が効かないので、`andon/gate` を必須にしても、積んだ PR を前の課題の branch へ誤ってマージすることは止まらない。draft の PR は GitHub がマージさせない。PR の一覧でも、まだオーナーの番でないことが見て分かる。
   前の決定との関係: ADR-0056 決めたこと 2 は、判定の前の PR を draft で守る案を捨てた（事実 16）。守る相手が違う。そこで守ったのは main へ向く PR で、必須の check が守れる。ここで守るのは main へ向かない PR で、必須の check が届かない。draft を外して押すことは止めない（やらないこと 6 と、決めたこと 15）。[decisions.md](../decisions.md) の 2026-11-05 の行は、base が既定の branch でない PR を、いつもオーナーへ回すと決めている。その狙いは、そういう PR を機械がマージしないことである。積んだ PR は、積んでいる間、approve にもオーナーのマージ待ちにもならない（決めたこと 8）。狙いは保ったまま、オーナーへ回すことだけを外す。
   オーナーに見える変わり方: GitHub の PR の一覧に、draft で、向き先が main でない PR が並ぶ。前の課題の PR が rebase で書き直されると、その上の積んだ PR は、載せ替えるまで、画面の差分に前の課題の古い変更が混ざって見えるか、衝突していると表示されることがある。gate とレビュアーは分かれ目から数えるので、判定は混ざらない（決めたこと 9）。
   捨てた案: GitHub の stack に登録して、main の決まりを積んだ PR にも効かせる（決めたこと 3）。PR を出さず、前の課題が main に入るまで担当が手元で待つ（レビューと CI を先に済ませられない。待つ間も `doing` で、並行の枠を 1 つ塞ぐ）。draft にせず、向き先だけを前の課題の branch にする（オーナーが、前の課題の branch へ誤ってマージできる）。向き先を main にした draft で出す（画面の差分に前の課題の変更が全部混ざる）。

8. **2026-11-26 gate に判定 `behind`（前の PR 待ち）を足す。積んでいる間、gate は approve もオーナー待ちも決めない（Chief Engineer が決めた）。**
   理由: 積んだ PR は、前の課題が main に入るまでマージできない。approve にすると dispatcher がマージを試みる。オーナーへ回すと、今の作りでは「マージするか」の問いと、オーナー待ちの一覧のマージの行になり、オーナーに押せない依頼が届く（事実 8）。一方で、検査とレビューは前のマージを待たずに済ませたい。担当へ返す理由が無いことを確かめたうえで、置いておく判定が要る。オーナーへ回す理由は、載せ替えたあとの gate が、マージできる PR について出す。
   細部:
   - 決まりは 1 つである。積んだ課題（信じられる `stacked_on` が在る）の PR で、判定が今なら approve か needs_human になるときは、どちらも `behind` に置き換える。gate が判定できずに終わったときも同じである。担当へ返す判定（fix）と、待ち（wait）は、今のままである。今ならオーナーへ回す理由は、積んでいる間は理由にせず、記録の理由の行に写しておく。当たるのは、作者がセルの gh のアカウントでない、条件表の設定が信じられない、repo が条件表に無い、Must fix が同じ head で 2 度目、見送った Must fix、通すか決められない checks、checks が 1 つも無いまま時間が過ぎた、マージがオーナーのものである、の 8 つである。記録の 1 行目は「前の課題 <id> の PR がまだ main に入っていない」とする。
   - 積んだ PR で見ないものは 5 つである。base が既定の branch でないこと。draft であること。base と衝突していること。変更したファイルの件数が GitHub の数と合うか（決めたこと 9 で、ファイルを分かれ目から取るので合わない）。古い base の検査の確かめの 2 つの向き（検査の置き場が base で動いたか。PR が検査の置き場を変えていて base が進んだか）。5 つ目は rebase を求める直しで、積んでいる間は担当が解けない（決めたこと 11）。載せ替えたあとの gate が見る。
   - 代わりに見るものは 2 つである。PR の base が前の課題の branch でも既定の branch でもないとき、または draft でないときは、担当へ返す（fix）。
   - 担当へ返す理由（検査、GitHub の checks の失敗、レビューが無い・古い・Must fix がある、受け入れ条件、走らせた記録、画面の証拠）は、今と同じ順で見る。GitHub の checks が走っている間は、今と同じに待つ。
   - `behind` は gate の記録（`library/gate/<head>.json`）に書く。判定の値を絞っている 4 つの約束に `behind` を足す。`schema/gate.schema.json`、通知の `schema/notification.schema.json`、片付けの控えの `schema/outcome.schema.json`、振り返りの収集の `schema/retro.schema.json` である（事実 13）。足さないと、通知を積んだ dispatcher の控えが保存できず、片付けの控えと振り返りの収集も書けない。
   - 印 `andon/gate` は黄（`pending`）で、文は「andon gate: 前の PR のマージを待っている」とする。積んだままの head には、緑の印を付けない。PR に付ける判定のコメントの見出しは「前の変更のマージを待っている変更です」とする。
   - 計測と振り返りは、差し戻しとオーナー待ちの率の分母に `behind` の記録を数えない。決めたこと 12 の載せ替えの直しは、記録に印（`restack: true`）を付け、差し戻しに数えない。差し戻しの率が、積んだ課題の数だけ上がって見えないようにする。
   - `behind` を決めたら、dispatcher は通知 `gate` を Chief of Staff に届ける。枠が 1 つ空くので、Chief of Staff は起動の手順を読み直す。オーナーへの問いは出さない。
   - `behind` のあと、gate が回り直すきっかけは 3 つである。PR の head が動いた。前の課題が `done` になった（決めたこと 12・14）。Chief of Staff が止めた（`hold`。今と同じに判定を捨てる）。[contract.md](../contract.md) §7 の「gate は、決めたあとは head が動くまで回り直さない」に、2 つ目を足す。approve とオーナー待ちのあとの回り直しは変えない。
   受け入れるもの: 前の課題の branch が書き直されて、積んだ PR が衝突していると、そのあとの push では CI が走らない（事実 14）。そのときは CI の結果が無いまま `behind` になる。載せ替えたあとの gate が、新しい head の CI を見る。Must fix を担当が直さないと判断したときのオーナーの判断は、前の課題が main に入るまで遅れる。
   捨てた案: 止め（`hold`）を使い回し、積んだ課題を機械が止める（止めている課題に gate は回らないので、CI の失敗とレビューの指摘が前のマージのあとまで担当に返らない。Chief of Staff の止めと書き手が混ざる）。判定を足さず、待ち（wait）を返し続ける（待ちは記録を書かないので、毎分 gate が検査を回し直す。枠にも数えられない。ADR-0056 決めたこと 9 は、止めには待ちで足りるとして新しい判定を捨てた。止めている間は gate を回さないので足りた。ここでは、回して確かめた結果を覚える記録が要る）。積んだ PR でも、オーナーへ回す理由があれば回す（押せないマージの依頼が届く。問いの形を理由ごとに分ける作りが要る）。

9. **2026-11-26 積んでいる間の差分は、gate も照合もレビュアーも、分かれ目から数える。レビューが見た差分の起点は、レビュアーの課題に控える（Chief Engineer が決めた）。**
   理由: GitHub の PR の差分は、PR の base の今の先との merge-base から数える。前の課題の PR が rebase で書き直されると、積んだ PR の差分に前の課題の古い commit が混ざる（事実 9）。分かれ目から head までなら、前の課題がどう動いても、積んだ課題の自分の変更だけになる。
   細部:
   - 積んでいる間（信じられる `stacked_on` が在る間）、PR の差分を読む所は全部、`stacked_base` から head までで取る。当たるのは 5 か所である。gate の、変更したファイルと差分（レベルの判定と行数）。レビューが要るかを差分のレベルで決める所。照合の、今の head の差分。レビュアーの依頼書。詰まりの兆し（大きい差分）を見る dispatcher。
   - dispatcher は、積んだ課題のレビュアーを起動するとき、差分の起点（`stacked_base`）をレビュアーの課題に控え（予約キー `review_base`）、依頼書に `git diff <起点>..<commit>` で読むよう書く。`gh pr diff` は使わせない。レビュアーの課題を作るのは dispatcher だけなので、照合は、dispatcher の端末が書いた `review_base` だけを信じる。
   - 照合は、レビューした commit の差分を、レビュアーの課題に信じられる `review_base` が在ればそこから数え、無ければ今までどおり既定の branch との merge-base から数える。載せ替えたあとの head の差分は、今までどおり既定の branch との merge-base から数える。
   - 再レビューの依頼書は、前の回の差分の起点を、前の回のレビュアーの課題に `review_base` が在ればそこに取る。今のままだと、前の課題が squash で入ったあとの再レビューで、前の回の範囲に前の課題の commit が混ざる（事実 9）。
   - 引き継ぎの決まり（事実 9）は変えない。前の課題のあとからの直しが、積んだ課題の変更を囲む行を変えていなければ、衝突の無い載せ替えのあと、積んでいた間のレビューが新しい head に引き継がれる。囲む行が変わっていれば、衝突が無くても引き継がれず、担当がレビューを頼み直す。反論の役が一時の repo で試すと、直しの無い載せ替えでは、squash でもマージ commit でも引き継がれた。前の課題に関数の宣言の行を変える直しを足すと、引き継がれなかった。
   捨てた案: `stacked_base` を載せ替えのあとも残し、「commit が `stacked_base` の子孫なら、そこから数える」と決める（前の課題がマージ commit で main に入ると、載せ替えたあとの head も分かれ目の子孫になる。反論の役が一時の repo で試すと、自分の 2 ファイルの差分に、前の課題の変更と main のほかの変更が混ざって 4 ファイルになった）。

10. **2026-11-26 前の PR 待ちの課題は並行の枠に数えず、オーナー待ちにも数えない。数は `slots.behind` に出す（Chief Engineer が決めた）。**
    `review` にいて、今の head に今の `review` の回の gate の記録があり、判定が `behind` の課題は、`slots.working` にも `slots.waiting` にも数えない。`slots.behind` に数える。`items` には行を足さない。前の課題の行の `holds` には、今と同じに `after` をたどって数えられる。
    理由: 前の PR 待ちの課題の担当は何もしていない。枠に数えると、積むほど起動できる数が減り、積む意味が無くなる。オーナーがすることは前の課題のマージだけで、それはもう前の課題の行として出ている。`slots.waiting` に入れると、ペインが「waiting on you」と数える（事実 11）。オーナーを待っているのは前の課題で、積んだ課題ではない。
    細部: `slots` にキー `behind` を足す。`slots.waiting` の意味は変えない。`slots.working` は、オーナー待ちと前の PR 待ちを引いた残りの数で、動いている課題の数のままである。[contract.md](../contract.md) §25 と schema の説明の文は、その形に書き直す。キーを足すだけなので、出力のバージョンは 1 のままにする（[contract.md](../contract.md) §10）。古い読み手は `behind` を読まず、今までどおりに描く。
    捨てた案: `slots.waiting` に数える（上の理由。意味が変わるので、バージョンも上がる）。オーナー待ちの一覧に「前の PR 待ち」の行を出す（オーナーに届く行が、押せないもので増える）。

11. **2026-11-26 積んだ課題は、前の PR が動いても追わず、ほかの PR のマージでも rebase を頼まれない（Chief Engineer が決めた）。**
    理由: 積んだ課題は、前の課題が main に入った時に必ず 1 回載せ替える。その 1 回が、前の課題のあとからの直しも、その間に main に入ったほかの変更も、まとめて取り込む。途中で追うと、載せ替えが前の課題の直しの回数だけ増える（ADR-0042 決めたこと 11 が積む案を捨てた理由）。
    細部:
    - 担当は、積んでいる間、前の課題の branch へも main へも rebase しない。gate の直しは、積んだ branch の上に commit を足して push する。
    - `andon issue impact` は、積んだ課題（信じられる `stacked_on` が在る）の行に `stacked_on` を出す。Chief of Staff は、その行ではぶつかり、重なり、検査の置き場の動きで rebase を頼まない。
    - マージした課題が、その行の `stacked_on` の課題そのものなら、Chief of Staff は何もしない。gate が載せ替えを頼む（決めたこと 12）。積んだ課題の依頼書は前の課題のファイルを名指すことが多いが、前の課題の変更は積んだ時にもう読んでいるので、手を止めさせない。
    - ほかの課題のマージで、依頼書が名指すファイルが変わったとき（`brief_refs`）の「一度止めて向きを確かめる」は、今と同じに当てる。
    - 載せ替えたあとの課題は、ふつうの課題である。影響の表は今と同じに当たる。
    受け入れるもの: 前の課題があとから大きく直されると、載せ替えの時の衝突が大きくなる。3 つ以上積んだ列では、2 つ目が載せ替えた時に、3 つ目の載せ替えで衝突することがある。反論の役が一時の repo で試すと、前の課題に直しの commit が 1 つ足されてから入った場合に、3 つ目の PR が 2 つ目の新しい branch と衝突した。どちらの衝突も、載せ替えの 1 回の中で担当が解く。前の課題のあとからの直しが、積んだ課題の変更を囲む行を変えたときは、衝突が無くてもレビューが引き継がれず、レビューの回を 1 つ使う（決めたこと 9）。

### 載せ替え

12. **2026-11-26 前の課題が main に入ったら、gate が積んだ課題の担当に載せ替えを頼む（Chief Engineer が決めた）。**
    dispatcher は、`behind` を決めた積んだ課題について、巡のたびに前の課題の状態を kanban で読む。前の課題が `done` で、その PR が既定の branch へマージされていれば、gate を回し直す。gate は、積んだままの open の PR で前の課題が main に入っていれば、ほかの理由より先に担当へ返す（fix）。理由の行は「前の課題 <id> が main に入った。`andon issue restack` で載せ替える」である。記録には、載せ替えの直しの印を付ける（決めたこと 8）。前の課題の PR が既定の branch でない base にマージされていたときは、main に入ったと読まない（決めたこと 15）。
    理由: 直しを担当へ直に送る道（`sendFix`）は今もあり、届かなかったときに Chief of Staff へ知らせる守りも付いている（規則 R2）。直しを決めたあとは head が動くまで回らないので、頼みは 1 回だけ届く（事実 10）。Chief of Staff が中継する文を足さずに済む。前の課題が main に入ってから載せ替えが頼まれるまでが、dispatcher の 1 巡で済む。
    細部:
    - 積んだ課題がまだ `doing` のうちに前の課題が main に入ったときは、gate は回っていない。担当は、PR を出す前と `andon issue ready` の前に `andon issue restack` を打つ（決めたこと 13。前の課題がまだなら何もしない）。`andon issue ready` は、積んだままの課題の前の課題が `done` なら、載せ替えが先だと 1 行出して断る。
    - 載せ替えを頼まれた担当が動き出すと、動いている課題が一時だけ上限を超えることがある。今の取り直しと同じに受け入れ、下回るまで新しい課題を起動しない（ADR-0065 決めたこと 9）。
    捨てた案: Chief of Staff が通知を読んで担当に頼む（オーナーがいないターンで Chief of Staff が動かないと、載せ替えが止まる。頼む文が 1 つ増える）。dispatcher が自分で載せ替える（「やらないこと」の 2）。

13. **2026-11-26 載せ替えは、担当の口 `andon issue restack` の 1 つで済ませる（Chief Engineer が決めた）。**
    理由: 載せ替えは、rebase、PR の向き先、push、draft、課題のキーの 5 つを同じ順で動かす。順を誤ると、CI が古い base で回る（事実 14）。どれかが抜けると、gate が古い形の PR を読む。手順を文で渡すより、command が順に済ませ、できなかった所を 1 行で言うほうが、抜けない。
    細部:
    - `andon issue restack <id>` は担当の端末で、`doing` の課題に打つ。積んでいない課題と、前の課題がまだ `done` でない課題では、何も変えずに、その旨を 1 行出して終了コード 0 で終わる。
    - 前の課題が `done` なら、origin を取り直し、移す先の commit（既定の branch の先）を課題に控えてから（予約キー `restack_onto`）、`git rebase --onto <移す先> <stacked_base>` で自分の commit だけを移す。衝突したら rebase の途中で止まり、終了コード 1 で、解いてから打ち直すよう 1 行出す。
    - 打ち直しでは、同じ rebase を打ち直さない。済んだ rebase を打ち直すと、main の commit を積み直そうとして、偽の衝突で止まることがある（事実 17）。`restack_onto` が在るときは、次のように進む。rebase の途中なら、解いて続けるよう 1 行出して止まる。HEAD が控えた commit の子孫なら、rebase は済んだと読み、下の続きから進む。どちらでもなければ（担当が rebase をやめた）、控えを消して初めからやり直す。
    - rebase が済んだら、次の順で動かす。PR が在り、向き先が既定の branch でなければ、先に付け替える。次に `git push --force-with-lease` で push する。まだ push していない branch では、ふつうの push をする。push が CI を既定の branch を base にして回す。そのあと draft を外し、最後に `stacked_on` と `stacked_base` と `restack_onto` を消す。PR がまだ無ければ、push とキーを消すことだけをする。
    - origin の branch が、取り直した時に手元と違っていても（GitHub の側で書き直された場合）、手元の自分の commit から載せ替えたもので上書きする。
    - GitHub が向き先を付け替えずに PR を閉じていたら、開き直しを試み、できなければ、PR を出し直して報告の `pr` を書き換えるよう 1 行出す。
    - そのあとは今の取り直しと同じである。担当は検査を通し、報告を書き直し、レビューが引き継がれなければ頼み直し、`andon issue ready` を打つ。gate は、ふつうの PR として判定する。
    - 前の課題がマージされずに終わったときも、同じ口で載せ替える。前の課題の変更は移らないので、積んだ課題の変更だけが main の先に載る。
    捨てた案: 載せ替えの手順を、gate の直しの文と担当の skill に書く（5 つの段のどれかを飛ばしても、気づくのは次の gate になる）。push してから向き先を付け替える（前の課題の branch が残っている場合、CI が前の課題の branch を base にして回り、付け替えでは回り直らない）。

14. **2026-11-26 前の課題がマージされずに終わったら、積んだ課題をどうするかを、Chief of Staff がオーナーに 1 問聞く（Chief Engineer が決めた）。**
    前の課題が `done` で、その PR がマージされていないとき、dispatcher は積んだ課題の gate を回し直す。gate は `behind` のまま、理由の 1 行目を「前の課題 <id> がマージされずに終わった」に替えて記録し、通知 `gate` が Chief of Staff に届く。同じ head では 1 回だけ届ける。Chief of Staff は、オーナーに 1 問聞く。選択肢は、「この課題もやめる」と「前の課題の変更なしで続ける」の 2 つである。「続ける」なら、Chief of Staff が担当へ返し、担当は `andon issue restack` で載せ替えてから直す。
    理由: 前の課題をやめたとき、その上の課題をやめるか続けるかは、何を作るかの決断で、オーナーのものである。機械がやめることも、黙って続けることもしない。gate の問いは「マージするか」の 1 つの形なので（事実 8）、この問いは Chief of Staff が、今ある問いの出し方で出す。前の課題をやめるのは、オーナーの go が要るまれな出来事である。
    細部: Chief of Staff は、前の課題をやめる go をオーナーに取る時に、その上に積んだ課題があれば、同じ返事でそのことを言う（`package/skills/chief-of-staff/playbooks/finish.md`）。
    捨てた案: gate がオーナーへの問いを出す（問いの形と選択肢を、理由ごとに分ける作りが要る）。前の課題をやめたら、積んだ課題も機械がやめる（オーナーが残したい仕事を消す）。積んだ課題が在る間は、前の課題をやめる口を断る（やめる順をオーナーに強いる）。

15. **2026-11-27 既定の branch でない base にマージされた PR は、片付けずに Chief of Staff へ知らせる（オーナーが決めた）。**
    片付け（`andon issue settle`）は、マージされた PR の base を読む。base が既定の branch でなければ、課題を片付けず、通知で Chief of Staff に知らせる。知らせるのは、今の「片付けていない」の通知と同じに、理由ごとに 1 回だけである。
    理由: オーナーが draft を外して、積んだ PR を前の課題の branch へマージすることは止めない。今の片付けは base を読まないので（事実 13）、そのとき、main に入っていない課題が「マージ済み」として片付き、その後ろの課題が起動できるようになる。知らせれば、Chief of Staff とオーナーが、前の課題の PR にまとめて進めるかを決められる。
    前の決定との関係: オーナーは 2026-11-19 に、`doing` のうちにマージした PR も片付けると決めた（事実 13）。その決定は、main へマージした PR についてのものだった。ここで足すのは、main でない所へマージした PR だけの例外である。
    細部: 積んだ PR が前の課題の branch へマージされたあと、前の課題の PR が main に入れば、積んだ課題の変更も一緒に main に入る。そのとき、Chief of Staff は積んだ課題を手で片付ける（`andon issue finish`）。gate は、open でない PR の担当に載せ替えを頼まない（決めたこと 12）。settle の約束の写し（コードの注釈、[dispatcher.md](../dispatcher.md)、[contract.md](../contract.md)、`process/states/human-merge.yaml`）を揃える。
    捨てた案: 今のまま片付ける（上の理由）。前の課題の branch へのマージを、main へのマージと同じに読んで、前の課題が main に入るまで積んだ課題を `review` に置く（片付けの記録に、待つ状態が 1 つ増える。まれな出来事で、Chief of Staff が手で片付ければ足りる）。

### モデルと手引き

16. **2026-11-26 課題の一生のモデルに、積んだ課題の動き 6 つと規則 7 本を足す（Chief Engineer が決めた）。**
    モデルは課題 1 つの一生なので、前の課題は、その PR の状態だけを変数で持つ。`queued` はモデルに無いので、積める課題の起動は、`todo` からの起動の枝として写す。
    細部（実装の PR が `model/` に写す。下書きは課題の資料に在る）:
    - 足す変数は 3 つである。積んだ課題の branch が載っている所（既定の branch か、前の課題の branch か）。前の課題の PR の状態（前の課題が無い、main に入っていない、main に入った、マージされずに終わった）。前の課題がマージされずに終わったことを、Chief of Staff に知らせたか。
    - 足す動きは 6 つである。gate が前の PR 待ちと判定する。担当が載せ替える。前の課題が main に入る。前の課題がマージされずに終わる。前の課題が終わったことを、dispatcher が Chief of Staff に知らせる。知らせたあと、オーナーの答えで Chief of Staff が担当へ返す。
    - 今ある動きに足す守りは次のとおり。起動は、前の課題が main に入っていなければ、その branch の上に載せる。approve と、オーナーへ回す判定と、dispatcher のマージと、オーナーのマージは、既定の branch に載った PR だけに起きる。gate の回し直しは、前の PR 待ちの判定のあとに前の課題が main に入ったときにも起きる。前の PR 待ちの判定は、CI の結果が無い head にも起きる（決めたこと 8 の「受け入れるもの」）。
    - 足す規則は 7 本である。1 本目。前の課題の branch に載ったままの PR はマージされない。2 本目。前の PR 待ちと判定した PR には、緑の印が付かず、マージを渡したことにもならず、オーナーにマージを頼まない。3 本目。gate が approve と判定するのは、既定の branch に載った PR だけである。4 本目。前の課題の branch に載ったままの head には、緑の印が付かない。5 本目。前の課題がマージされずに終わる場合を除き、届くどの状態からも、オーナーの判断も、だれかの push も、Chief of Staff の止めも借りずに、既定の branch に載った形まで行ける。6 本目。前の課題がマージされずに終わっても、やめる口も、だれかの push も、Chief of Staff の止めも借りずに、既定の branch に載った形まで行ける。7 本目。Chief of Staff に知らせるのは、前の課題がマージされずに終わったあとだけである。
    - 下書きは、今ある規則 15 本と足す 7 本を、検査器（`model/check --draft`）と TLC の両方で通った。状態の数は 28,004 から 168,644 に増える見込みである。控え（`model/expected.txt`）と対応表（`model/issue-map.txt`）は、実装の PR が直す。

2. 積んだ PR をオーナーへ回すと、押せない「マージするか」の問いが届いた（事実 8）。決めたこと 8 で、積んでいる間は gate がオーナーへ回さない形にした。衝突も理由から外した。
3. 分かれ目のキーを載せ替えのあとも残す案は、前の課題がマージ commit で入ると、レビューの引き継ぎが壊れた。決めたこと 9 で、起点をレビュアーの課題に控える形にした。
4. push してから向き先を付け替えると、CI が古い base で回った。決めたこと 13 で順を入れ替えた。
5. オーナーが積んだ PR を前の課題の branch へマージすると、main に入っていない課題が片付いた（事実 13）。決めたこと 15 を足した。
6. GitHub の Stacked PR の機能を比べていなかった（事実 15）。決めたこと 3 と、比べた案の「既製」を足した。

残りは、`slots.waiting` の意味を変えていたこと（決めたこと 10 で `slots.behind` に分けた）、前の課題のマージで「手を止めろ」と「載せ替えろ」が同時に届くこと（決めたこと 11）、予約キーをだれでも書けること（決めたこと 5 の信じ方）、名指さずに改めていた前の決定（事実 7・10・16 と、決めたこと 6・7・8 に名指した）、大きい差分の兆しの数え方（決めたこと 9）である。

直した案を、もう一度壊させた。裏づけのある指摘は 10 件で、全部を案に入れた。大きいものは次の 4 つである。

## やらないこと（範囲の外。理由）

1. **取り直しを減らす仕組み。** マージ待ちの PR を main が動くたびに取り直すのをやめ、マージの時の 1 回にまとめる仕組みは、次のテーマにする（決めたこと 1）。事実 2 の 25 回と、事実 3 の 33 回は、この文書では減らない。
2. **dispatcher が自分で載せ替える。** 衝突の無い載せ替えを機械が済ませれば、担当の 1 回分（約 8 分。事実 3）が要らなくなる。ただし、担当の branch に機械が push し、報告の commit を機械が書き直すことになり、役の持ち場が変わる。取り直しをまとめる仕組みと同じ問いなので、次のテーマで一緒に決める。
3. **待つ相手が 2 つ以上残る課題を積む。** 1 つの branch の上にしか載せられない。前の課題を束ねる branch を作る案は、消す時の決まりが要り、まれな場合のために仕組みが増える。
4. **違う repo の課題の上に積む。** branch を共有できない。
5. **Chief Engineer の課題とレビュアーの課題を積む。** 文書の PR は gate を回さず、レビュアーは PR を出さない。
6. **オーナーが draft を外して自分でマージすることを止める。** GitHub の上のオーナーの操作は止めない。積んだ PR を前の課題の branch へマージしたときは、決めたこと 15 が受ける。
7. **積む深さの上限と、積んだ PR の数の知らせ。** オーナーが、新しい上限も新しい知らせも足さないと決めている（ADR-0065 決めたこと 2）。
8. **`after` の無い課題を、ぶつかりを避けるために積む。** 積むのは、順番を `after` で書いた課題だけにする。同じファイルを触る課題を並べるか束ねるかは、今までどおり Chief of Staff が切る時に決める。
9. **積んだ PR の画面の差分をいつもきれいに保つ。** 前の課題の branch が書き直されると、載せ替えるまで、画面の差分が混ざるか、衝突と表示される（決めたこと 7）。分かれ目に止めた branch を origin に置いて向き先にすれば防げるが、課題ごとに branch が 1 本増え、消す決まりが要る。

## 価値の仮説

1. **誰の何が変わるか。** オーナーが離れている間も、順番に並べた課題の列が進む。オーナーが前の PR をマージしたあと、次の PR が渡るまでが短くなる。
2. **見る信号。** `source` は、kanban の `log.jsonl` と、課題ごとの gate の記録である。`after` で並んだ担当の課題の組ごとに、前の課題が `done` になった時刻から、後ろの課題の PR を gate が初めて approve か needs_human と判定した時刻までの分を数える（事実 4 と同じ数え方）。積んだ課題は、`log.jsonl` に `stacked_on` を書いた行が在る課題として見分ける。あわせて、積んだ課題 1 件あたりの載せ替えの回数と、載せ替えで衝突を解いた件数を、gate の記録と担当の報告から数える。
3. **見る日。** 2026-12-12。
4. **誰が要るか。** オーナー。積んだ列の PR を、前から順にマージする。
5. **効いたとどう分かるか。** 実装がセルに当たった日から見る日までに、積んで起動した課題が 5 件以上あり、前の課題が `done` になってから後ろの PR が渡るまでの中央値が、今の 91 分から 30 分以下になる。積んだ課題 1 件あたりの載せ替えは 1 回である。
