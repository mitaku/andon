# ADR-0065: オーナー待ちがたまっても、新しい課題の起動を止めない（仕様・設計。2026-11-25）

## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-25）: 「オーナー確認待ちが溜まったから工場が止まるというのは変です。」

オーナーの判断を待つ課題が並行の上限と同じ数たまると、`andon waiting` の `slots.waiting_full` が真になり、Chief of Staff は新しい課題を起動しなくなる。動いている担当が上限より少なく、起動できる課題が残っていても止まる。オーナーはこの決まりがもう無いと思っていた。オーナーが望んでいるのは、自分の答えを待つものがいくつあっても、空いている枠には仕事が入り続けることである。起動を止める理由は、動いている担当の数が上限に達したことの 1 つだけにする。

歯止めは、オーナーが長く離れたときに、マージされていない PR が際限なくたまることを抑えるために置かれた。たまった PR は、main が動くたびに rebase が要る。オーナーは、これを別の上限や知らせで抑えるのでなく、rebase が要らない形に仕事を組むことで扱うと決めた。その仕組みは次のテーマで設計する。

モデル: 調べなかった（空きの数の式から条件を 1 つ外すだけで、課題の状態の定義も、状態を動かす command の順と断り方も、dispatcher の部品の順も変えない。課題の一生のモデルは並行の枠を写していない）

## 読んで分かった事実（2026-11-25。main `ef3df20` と、Andon を開発しているセルの kanban で実測）

1. **歯止めの形。** 数える式は `internal/waiting/waiting.go` の 1 か所にある。`slots.waiting` が `slots.limit` 以上のとき `slots.waiting_full` を真にし、そのとき `slots.free` を 0 にする。そうでなければ `free` は、`limit` から `working` を引いた数である。Chief of Staff の手引き `start.md` の 1 は、`waiting_full` が真なら起動せず、オーナーに「オーナー待ちが N 件たまったので、マージか答えが入るまで新しい課題を起動しない」と言うと書いている。
2. **歯止めが掛かっていた時間。** kanban の履歴から、2026-11-22 00:00 から 2026-11-25 13:30（UTC）までの 5,130 分を、分ごとに数え直した。オーナー待ちの担当の課題が上限以上だった分は 213 分あった。その 213 分は全部、動いている担当の課題が上限より少なく、`todo` の担当の課題があった。上限が 4 だった間は 44 分（2 回）、上限を 2 に書いてからの 1,239 分では 169 分（8 回。長いものは 43 分）で、14% に当たる。数え直しは、歯止めが掛かる条件が成り立っていた分を数えたもので、Chief of Staff が実際に起動を見送ったかは見ていない。オーナー待ちの担当の課題の数は、0 件が 2,739 分、1 件が 1,668 分、2 件が 392 分、3 件が 287 分、4 件が 44 分で、最大は 4 件だった。
3. **上限が小さいほど、早く止まる。** 歯止めの線は上限と同じ数である。ADR-0042 が決めたとき上限は 4 だった。オーナーは 2026-11-23 に上限を 2 に戻した。上限が 2 だと、オーナーのマージを待つ PR が 2 本で止まる。
4. **たまった PR に rebase が要る道。** PR が main に入るたびに、dispatcher が `review` の課題への影響を調べて Chief of Staff に知らせる。Chief of Staff は、ぶつかるとき、検査の置き場が動いたとき、ぶつからないが同じファイルが重なるときの 3 つで、担当に rebase を頼む（手引き `finish.md` の影響の表）。待っている PR が N 本あれば、1 回のマージで最大 N 回の rebase になる。rebase を頼まれた担当は課題を `doing` に戻すので、その間は動いている課題に数えられる。
5. **rebase の実測。** 2026-11-22 以降の gate の記録は 203 件で、approve が 119 件、オーナーへ回したものが 62 件、差し戻しが 22 件だった。差し戻しのうち 19 件は、理由が「base が古い」だった。待った課題は 32 件で、gate の記録は合計 67 件、1 件あたり平均 2.1 回だった。オーナーへ 2 回以上回った課題は 13 件で、最大は 1 件で 9 回だった。待たなかった課題は 120 件で、合計 136 件、平均 1.1 回だった。ADR-0042 の価値の仮説 6 は、撤退の目安を「オーナー待ちの課題 1 件あたりの gate の記録が、平均で 3 回を超える」と置いている。今はそこに届いていない。
6. **振り返りが見たこと。** 2026-11-25 の振り返りは、main に検査の置き場の動きか重なりが入るたびに `review` の PR が rebase と checks の回し直しをしていることを、繰り返しとして拾った。gate の差し戻しが 4 件、オーナーのマージ待ちの PR への rebase の頼みが 2 件あり、そのうち 1 件は 5 回頼まれていた。振り返りは、rebase をマージの直前の 1 回にまとめる直しを見送った。衝突の無い rebase ではレビューが引き継がれ、どれも数分で approve に戻っていたことと、まとめるにはオーナーがマージする時機を機械が知る設計が要ることが理由だった。
7. **`waiting_full` を読む所。** 読むのは 4 か所である。式（`internal/waiting/waiting.go`）、人が読む出力の文（`internal/waiting/cmd.go`）、手引き `start.md` の 1、オーナー待ちのペイン（`package/host/waiting/main.js` の枠の行。真なら「· full」を足し、色を変える）。dispatcher の空きを見る部分（`internal/dispatcher/idle.go`）は `slots.free` だけを読む。ペインは `free` を読まない。ダイジェストは、`andon waiting --json` の出力をそのまま入力に写す。組むとき（`andon digest build`）と送るとき（`andon digest send`）に入力を読み直し、知らないキーがあると断る（`internal/contract/contract.go` の読み方）。キーは読まないが、歯止めを前提にした文が 2 か所ある。手引き `finish.md` の「オーナー待ちが上限の数で止めていた起動も、ここで戻る」と、起動の流れの定義 `process/workstreams/launch.yaml` の待つ段の、待つわけの並びである。待つ段は、問いを出す順として `ask-one-by-one` skill の §3 を指していて、`tests/process.sh` がその指しを固定している。`start.md` の 1 でこの §3 を指すのは、`waiting_full` の箇条だけである。
8. **出力の形。** `schema/waiting.schema.json` は `slots` の 5 つのキーを全部必須にし、知らないキーを断る。ペインは、出力の `version` が 1 でないと、理由を 1 行出して一覧を描かない。mod とセルのパッケージのバージョンは別々に上がる（mod はオーナーが手元で置き直す）。[contract.md](../contract.md) の原則 4 と §10 は、キーを消すときと意味を変えるときはバージョンを上げ、古いバージョンを読む側を 1 バージョンだけ残すと決めている。例外は 1 つあり、[ADR-0008](0008-issue-naming.md) のバージョンアップは古いバージョンを読む側を残さなかった。
9. **空きを見る dispatcher。** [ADR-0047](0047-idle-slots-run-upkeep.md) 決めたこと 17 の後半は、オーナー待ちが上限に達している間は空きを見ないと決めた。決めたのは Chief Engineer で、理由は「オーナー待ちが上限まで積もったときに新しい課題を足さないのは、オーナーが決めた線である」だった。コードに専用の分かれ道は無く、`slots.free` が 0 になることで空きにならない。
10. **今の暫定の扱い。** Andon を開発するセルでは、2026-11-25 から、プロジェクトの指針の 1 行で、Chief of Staff が `waiting_full` では起動を止めず、`slots.working` が `slots.limit` より少なければ起動している。ほかのセルと、command の出力と、ペインの表示は、止める形のままである。
11. **Stacked PR が今は通らない所。** 起動の口は、どの課題の branch も、必ず既定の branch の先頭から切る（`internal/spawn/spawn.go`）。gate は、PR の base が既定の branch でないと、オーナーが見る PR の事情に数え、オーナーへ回す（`internal/gate/gate.go`）。ADR-0042 決めたこと 11 は、後ろの課題を前の課題の branch の上で起動する案を捨てている。理由は、前の PR が直されるたびに後ろも直すことになり、worktree の作り方と PR の base の決まりも変わることだった。決めたのは Chief Engineer である。Andon の repo のマージの方式は squash で、前の PR が squash で入ると、その上に積んだ branch は載せ替えが要る。オーナーは 2026-11-10 にも、大きい課題を分けるときに Stacked PR を使えると言っている（[ADR-0014](0014-issue-estimate.md) 決めたこと 2）。

## 前提（同意済み。番号）

オーナーが 2026-11-25 に、入口の確かめで 4 つとも同意した。

1. 歯止めは、起動できる課題があるのに起動を止めていた。3 日半で 213 分、上限を 2 にしてからは時間の 14% である（事実 2）。
2. 歯止めが守っていたのは、たまった PR の rebase のやり直しである。待った課題の gate の回数は平均 2.1 回、待たなかった課題は 1.1 回である（事実 4・5）。
3. 何もしなければ、止める決まりが command と手引きとペインに残る。今の扱いは、1 つのセルの指針の 1 行だけである（事実 10）。
4. command と手引きの直しは、パッケージのバージョンアップで全部のセルに届く。ペインの「full」を消す直しだけは、オーナーがマージして mod を置き直す。置き直す前でも、古い mod は「full」が出なくなるだけで壊れない（事実 7・8）。

## 決めたこと（番号・日付・誰が決めたか・理由・捨てた案。あとから覆したら上書きせず下に足す）

### 範囲

1. **2026-11-25 オーナー待ちの数を理由に、新しい課題の起動を止めない（オーナーが決めた）。** 起動を止める理由は、動いている担当の課題の数が並行の上限に達したことの 1 つだけにする。[ADR-0042](0042-owner-waits-do-not-stop-the-line.md) 決めたこと 10 の後半を覆す。前半の、並行の枠にオーナー待ちの課題を数えないことは変えない。上限の値と、その置き場も変えない。
   理由: オーナー（2026-11-25）「オーナー確認待ちが溜まったから工場が止まるというのは変です。」動いている担当が上限より少なく、起動できる課題があるのに、3 日半で 213 分止まっていた（事実 2）。上限を小さくすると、歯止めも一緒に早く掛かる（事実 3）。
   受け入れること: オーナーが長く離れると、マージされていない PR が、歯止めのあったときより多くたまる。たまる数に天井は無い。たまった PR は、main が動くたびに rebase が要ることがある（事実 4）。この扱いは決めたこと 2 である。
2. **2026-11-25 たまった PR には、新しい上限も新しい知らせも足さず、rebase が要らない形に仕事を組んで扱う（オーナーが決めた。Chief Engineer の推奨は、何も足さずに gate の回数を見て、平均 3 回を超えたら仕組みを検討することだった）。** オーナー（2026-11-25）: 「まず Rebase がいらないように CoS が工夫をする、Stacked PR とか、特定のブランチからタスクを続けるとか、そういう形でなるべく止まらないほうが好ましいと思う」。
   理由: 上限を別に置けば、数が違うだけで同じ止まり方が戻る。たまった件数は、オーナー待ちのペインの 1 行目と行燈で、今も見えている。オーナーが望むのは、止めることでも知らされることでもなく、たまっても困らない形である。
   細部: 仕組みの中身は、この ADR で決めない（決めたこと 3）。仕組みが入るまでの間、たまった PR の rebase は今の手引きのまま頼む（事実 4）。
   捨てた案: 高い所に別の上限を置く（上限の 3 倍など。オーナーが長く離れると、今と同じ止まり方が遅れて起きる）／オーナー待ちの担当の課題が上限の 2 倍に達したとき、Chief of Staff が 1 回だけ知らせる（オーナーに届く文が増える。件数はペインと行燈がもう出している）。
3. **2026-11-25 この ADR は歯止めを外すところまでにし、rebase が要らない形の仕組みは次のテーマにする（オーナーが決めた）。** 次のテーマは、オーナーのマージを待つ PR の branch の上で次の課題を起動する形（Stacked PR）を中心に、Chief Engineer が設計する。
   理由: 歯止めを外す直しは小さく、ほかのセルは今も止まる。Stacked PR は、手引きの工夫だけでは通らない。起動、gate、マージ、片付けを変える設計で、課題の状態の動きが変わるので、モデルで調べる（事実 11）。1 本にまとめると、歯止めを外す直しが、仕組みの設計とモデルの調べが済むまで出ない。
   次のテーマに渡すこと: 事実 11 の 4 つ（branch を切る所、gate の base の扱い、ADR-0042 決めたこと 11 の捨てた案、squash のあとの載せ替え）。この仕組みが効くのは、待っている PR の後ろに `after` で並んだ課題と、同じ場所を触る次の課題である。関係の無い PR が main に入って検査の置き場が動いたときの rebase（事実 5 の「base が古い」の 19 件）には、別の手が要る見込みである。rebase の頼みを、ぶつかり、検査の置き場の動き、重なりの 3 つに分けて数える所から始める。
   捨てた案: 1 本の ADR で仕組みまで決める（上の理由）／歯止めを外すだけにし、仕組みは rebase が増えたと数で分かってから検討する（オーナーが、仕組みで扱うと決めた）。

### 数え方と約束

4. **2026-11-25 空きの数は、上限から動いている課題の数を引いた数だけで決める（Chief Engineer が決めた）。** `slots.free` は、`slots.limit` から `slots.working` を引いた数で、0 より小さくしない。`slots.waiting` がいくつでも変わらない。
   理由: 決めたこと 1 を、数える式の 1 か所で実現する。式を読む Chief of Staff の手引きと dispatcher は、`free` を読むだけでよい。
   細部: 直すのは `internal/waiting/waiting.go` の式である。人が読む出力（`--json` を付けない出力）から、「オーナー待ちが上限に達したので新しい課題を起動しない」の文を消す（`internal/waiting/cmd.go`）。`slots.waiting` と `slots.working` の数え方は変えない。動いている課題が上限を超えているときは、今までどおり `free` は 0 である。
   捨てた案: 式は残し、Chief of Staff の手引きだけで `waiting_full` を読み飛ばさせる（dispatcher の空きを見る部分は `free` を読むので、そちらは止まったままになる。ペインも「full」と出し続ける）。
5. **2026-11-25 `andon waiting` の出力から `slots.waiting_full` をキーごと消し、出力のバージョンは 1 のままにする（キーを消すことは Chief Engineer が決めた。互換の決まりの例外にしてバージョンを 1 のままにすることは、オーナーが決めた）。** [contract.md](../contract.md) の原則 4 と §10 の決まり（キーを消すときと意味を変えるときはバージョンを上げる）に、この 1 回だけの例外を置く。ADR-0042 決めたこと 9 の細部のうち、出力の `slots` の形と `free` の式を改める。
   理由: 起動を止めない以上、このキーは何も決めない。残すと、名前と説明が「起動しない」を言い続け、読んだ役が起動を止める。バージョンを上げる決まりは、古い読み手を守るためにある。今回は、上げるほうが読み手を壊す。バージョンを 2 にすると、オーナーが mod を置き直すまで、ペインが一覧を描かなくなる（事実 8）。1 のままキーを消しても、読み手は困らない。古い mod は、無いキーを偽として読み、「full」を出さないだけである。新しい mod は、古い command の出力にキーが在っても読まない（決めたこと 6）。`free` の値が変わるのは、オーナー待ちが上限以上のときだけで、`free` を読むのは同じパッケージの手引きと dispatcher だけである（事実 7）。
   受け入れること: 約束の互換の決まりに、2 つ目の例外ができる。パッケージを上げる前に集めたダイジェストの入力は、上げたあとに組むことも、送り直すこともできない（事実 7）。当たるのは、上げる前に集めて、まだ送り終えていない 1 枚だけである。そのときは集め直して送り直す（[contract.md](../contract.md) §28 の、集め直したときの決まりのとおり）。
   細部: `schema/waiting.schema.json` の `slots` の必須のキーと `properties` から `waiting_full` を消し、`free` の説明を直す。`$id` は変えない。[contract.md](../contract.md) §25 の表から `slots.waiting_full` の行を消し、`slots.free` の行と §25 の例を直す。§26 のダイジェストの入力の例の `waiting.slots` も直す。§10 に、この例外を 1 行で足す（ADR-0008 の例外の行と同じ書き方）。ADR-0042 の索引の 9 と、決めたこと 9 の細部に、改めたことを注で足す。
   捨てた案: バージョンを 2 に上げ、mod を 1 と 2 の両方が読める形に先に直して置き直してもらう（歯止めを外す直しが、オーナーの手元の置き直しを待つ。守る相手のいない段取りが増える）／バージョンを 2 に上げ、置き直すまでペインが描かないことを受け入れる（オーナー待ちの一覧が、置き直すまで見えない）／キーを残して、いつも偽を出す（意味の無いキーが約束に残る。値の意味を変えることに変わりはなく、決まりの例外であることも同じである）／キーを残し、「待ちが上限以上」という知らせの値として使う（知らせは足さないと決めた。決めたこと 2。古い mod は「full」と止まった色を出し続ける）。
6. **2026-11-25 オーナー待ちのペインの「full」の表示を消す（Chief Engineer が決めた）。** mod `waiting` の枠の行は、いつも「Slots 2/4 working · 3 waiting on you」の形で、色を変えない。

### 手引きと流れ

7. **2026-11-25 Chief of Staff は、空きが 1 以上なら起動し、オーナー待ちの数ではオーナーに何も言い足さない（Chief Engineer が決めた）。** 手引き `start.md` の 1 から、`slots.waiting_full` の箇条を消す。残るのは、`slots.free` が 1 以上ならその数まで起動することと、`free` が 0 のとき「上限なので S-x（タイトル）が終わってから」と言うことである。
   理由: 決めたこと 1・2。オーナーへの問いの出し方は変えない。Chief of Staff は今までどおり、呼んでいるオーナー待ちを、後ろで待つ課題の多い順に、1 回の返事で 1 問ずつ出す。
   細部: 直すのは 4 つである。1 つ目は `package/skills/chief-of-staff/playbooks/start.md` の 1 と、その文を見る検査 `tests/package/27-cos-slots.sh`。2 つ目は手引き `finish.md` の「オーナー待ちが上限の数で止めていた起動も、ここで戻る」の括弧で、括弧だけを消す（同じ行の「`start.md` の 1 で枠を数え直し」は残す）。3 つ目は起動の流れの定義 `process/workstreams/launch.yaml` で、待つ段の待つわけを「動いている課題が上限の数」の 1 つにし、冒頭と、きっかけ `merged` の注釈を今の数え方に合わせる。`docs/process/` は作り直す。4 つ目は、問いを出す順の指しである。`start.md` の 1 で `ask-one-by-one` skill の §3 を指す文は、消す箇条にしか無い（事実 7）。この指しは、枠の数と切り離した 1 つの箇条に移す。文は「オーナー待ちの呼んでいる行があれば、起動するかどうかにかかわらず、並びの先頭から 1 問ずつ出す」である。待つ段が §3 を指すことと、オーナーへの 1 問を出すことは、今のままでよい。変えないものは 3 つある。マージ待ちの後ろに `after` で並べた課題を先に起動しないこと（ADR-0042 決めたこと 11。次のテーマが見直す）。着手できる課題がオーナー待ちの後ろにしか無いとき、その時点でオーナーに知らせること（手引き `watch.md`）。オーナーが待ちの PR を差し戻すか、rebase で担当が動き出して、動いている課題が上限を超えたとき、下回るまで起動しないこと。
8. **2026-11-25 枠の空きを見る dispatcher も、オーナー待ちの数では止めない（Chief Engineer が決めた）。** [ADR-0047](0047-idle-slots-run-upkeep.md) 決めたこと 17 の後半（オーナー待ちが上限に達している間は、空きを見ない）を覆す。空きは、今までどおり `slots.free` で読む。決めたこと 4 で式が変わるので、オーナー待ちが上限以上でも、動いている課題が上限より少なければ空きになり、トリアージと振り返りと点検のルーチンが撃たれ、起動されないまま残った課題と、`kanban lint` の problem が Chief of Staff に知らされる。Chief of Staff の留守の間は見ないこと（同じ決めたこと 17 の前半）は変えない。
   理由: ADR-0047 決めたこと 17 の後半の理由は、歯止めがオーナーの決めた線であることだった。その線が無くなった。オーナーが離れている間こそ、空いた枠でたまった仕事を崩せる。
   細部: `internal/dispatcher/idle.go` は直さない。空きを見る部分が読むのは `slots.free` の 1 つだけなので（事実 7）、動きは受け入れ条件 1 の式の検査で確かめ、dispatcher の側に検査を足さない。直すのは [dispatcher.md](../dispatcher.md) §2.13 の「見ない回」の最後の 1 文である。空きの仕事を全部止める口は、今までどおり `project.json` の `chief_of_staff.idle_minutes` に 0 を書くことである。
   捨てた案: 空きを見る部分にだけ歯止めを残す（起動は止めないのに、たまった仕事を崩すルーチンだけが止まる。理由が無い）。
9. **2026-11-25 rebase で動き出した課題が上限を超えることは受け入れ、いっぺんに頼む数を絞る決まりは足さない（Chief Engineer が決めた）。**
   理由: 待っている PR が N 本あるとき、main に 1 本入ると、最大 N 件の課題の担当が rebase で動き出す。その間、動いている課題は上限を超えることがあり、超えている間は新しい課題が起動されない（決めたこと 7）。歯止めのあったときは、たまる数に天井があったので、超える数にも天井があった。天井が無くなる分、超える数は大きくなり得る。一方で、実測では待ちの最大は 4 件で、衝突の無い rebase は数分で済んでいる（事実 2・6）。頼む数を絞るには、頼み残した相手を覚える置き場が要る。rebase そのものを減らす仕組みを次のテーマで作るので、間をつなぐ決まりは足さない。
   受け入れること: オーナーが長く離れた直後に main が動くと、上限を超える数の担当が同時に動くことがある。上限の理由は CPU の負荷である。超えた回は、価値の仮説 6 で見る。
   捨てた案: rebase を頼む数を、空きの数までに絞る（上の理由）。
10. **2026-11-25 セルの指針の暫定の 1 行は実装が当たったあとに消し、ADR-0042 の観察は歯止めの無い形で読む（Chief Engineer が決めた）。**
    理由: 暫定の 1 行（事実 10）は、決めたこと 4・7 がセルに当たれば、手引きと同じことを言うだけになる。ADR-0042 の価値の仮説は、歯止めを前提にした文を 2 つ持っている。

## 価値の仮説

1. **誰の何が変わるか。** オーナーが離れていても、空いた枠に課題が起動され続ける。オーナーの判断を待つ課題がいくつあっても、工場は止まらない。
2. **見る信号。** `source` は 2 つである。kanban の `log.jsonl` から分ごとに数え直した、オーナー待ちの担当の課題の数と、動いている担当の課題の数と、`todo` の担当の課題の数（事実 2 と同じ数え方）。課題ごとの gate の記録（`library/gate/<head>.json`）の数（事実 5 と同じ数え方）。あわせてオーナーの目視。
3. **見る日。** 2026-12-05。
4. **誰が要るか。** オーナー。ペインの「full」を消す PR をマージし、mod を手元で置き直す。
5. **効いたとどう分かるか。** 実装がセルに当たった日から見る日までに、オーナー待ちの担当の課題が上限以上だった間にも、担当の課題が起動されている。動いている担当の課題が上限より少なく、`todo` の担当の課題があるのに、30 分を超えて起動が無かった回が、オーナー待ちの数にかかわらず無い。オーナーが「待ちがたまって工場が止まった」と言わない。
6. **何があれば止めるか。** 待った課題 1 件あたりの gate の記録が、平均で 3 回を超える（今は 2.1 回）。または、rebase で動き出した担当のために、動いている担当の課題が上限の 2 倍を超えた回が出る。どちらのときも、歯止めは戻さない。rebase が要らない形の仕組み（決めたこと 3 の次のテーマ）を前に進めるか、間をつなぐ決まり（決めたこと 9 の捨てた案）を入れるかを、オーナーと決める。
