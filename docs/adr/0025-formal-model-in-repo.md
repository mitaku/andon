## 問題（オーナーの言葉で。言い直しの段落）

オーナー（2026-11-19、Chief of Staff への発言）: 「Lean言語によるテストも用意してもいいんじゃないかと思った」。

言い直し（オーナーが 2026-11-19 に「合っている」と答えた）: A-0001 では TLA+ のモデルを一度きり作り、課題の一生の規則 R1〜R5 の破れを 3 つ見つけた。今は規則もモデルも repo の外にあり、次に仕組みを変えても誰も回さない。規則とモデルを repo に置き、仕組みを変えるたびに機械が確かめるようにしたい。Lean はその道具の候補で、道具は比べて決める。

## 前提（同意済み。番号）

1. **分担**: モデルは設計（規則とモデル）を確かめるもの。コードの退行は、今までどおり本物の `andon` を動かす `tests/` の筋書きのテストが確かめる。モデルとコードを機械で照らす仕組みは、この題では作らない（オーナーが同意 2026-11-19）。
2. **何もしないと**: モデルは台帳の資料置き場（git の外。セルを作り直すと消える）に残るだけで、A-0002・A-0003・A-0006・A-0007 がコードを直すと古くなる。次に仕組みを調べるときは、コードを読んで一から写し直すことになる。直したあとの姿にモデルを合わせ、repo に残す価値がある（オーナーが同意 2026-11-19）。
3. **状態の定義の正はモデル**: 状態の定義の正は TLA+ のモデルにする。`process/states/` の YAML はオーナーが書かず、モデルと、行動ごとの言葉・コマンドを書いたファイルから道具が作る。作った YAML は commit し、CI が作り直して差が無いことを見る。[ADR-0017](0017-process-definitions.md) 決めたこと 1（YAML をオーナーが書く正本にする）は、状態の定義について覆す（オーナー 2026-11-19。はじめの案「YAML は正のまま、モデルは足すだけ」にオーナーが同意せず、「TLA+・TLC から YAML を生成するならよい」と言った）。
   - **改め（2026-11-19。同じ対話の中）**: 前提 3 は取り下げた。反論（決めたこと 6 の理由）を見て、オーナーが「`issue.yaml` は人が書くまま、モデルと照らす」を選んだ。状態の定義の正は今までどおり `process/states/` の YAML で、ADR-0017 決めたこと 1 は覆さない。モデルと規則は YAML に足すもので、食い違いは検査が見る。
4. **配り方**: モデルを回すのと YAML を作るのは、andon の repo を開発するとき（手元と CI）だけ。検査器は repo の開発用の依存として版を固定し、セルに配るパッケージと image には入れない。利用者のセルに届くのは、今までどおり作った YAML だけで、`andon` の実行時の動きは変わらない（オーナーが同意 2026-11-19）。
   - **改め（2026-11-19）**: 前提 3 の改めに合わせ、「作った YAML」は「人が書いた YAML」と読む。

確かめた事実（前提の裏づけ。2026-11-19）:

- A-0001 のモデルは課題 1 つ・PR 1 つ・変数 11 個。TLC は 362 状態・860 歩を 1 秒未満で調べ終わる。規則は 5 本（R1〜R5）と「どの状態からも先がある」。モデルと規則は台帳の課題の資料置き場にあり、git の外。
- 見つかった 3 つの破れは、直す課題（A-0002・A-0003）の完了条件に「再現に当たるテストを `tests/` に入れる」とある。見つけた穴が戻らないことは、本物のコードを動かす筋書きのテストが受け持つ。
- モデルは、Go のコードを読んで手で写したもの。コードが変わってもモデルは変わらない。モデルを機械が回しても、見つかるのはモデルと規則を変えたときの破れで、コードの退行ではない。
- repo には状態の定義 `process/states/*.yaml` が 10 本ある（ADR-0017）。`andon issue` は `issue.yaml` に無い移り方を断り、テストが定義と実装の食い違いを見る。規則（破ってはいけないこと）は定義に無く、移る条件（`on`）は人が読む文。
- 道具の大きさ: TLC は Java（303 MB）と `tla2tools.jar`（2.2 MB）。andon を作るセルには pstack statechart が mise で入れたものがある。CI には無い。Lean 4（v4.36.0）は linux 向けの配布物が 579 MB（圧縮）。セルにも CI にも無い。
- Lean は「届く全部の状態で規則が成り立つ」を証明で確かめる。規則が破れたとき、破れまでの道は素のままでは出ない。Lean の上で遷移系を書き、モデル検査と証明の両方をする道具 Veil 2.0（`github.com/verse-lab/veil`）は、破れの道も出すが、z3・cvc5 が要り、最新の tag は 2026-11-07。
- CI は `tests`（`tests/*.sh`）と `go`（`go test` ほか）の 2 本。文書だけの PR は、文書を読む検査だけを走らせる。

## 決めたこと（番号・日付・理由・捨てた案。あとから覆したら上書きせず下に足す）

1. **2026-11-19 道具は TLA+ と TLC（pstack statechart の形: モデル・規則〈INVARIANT〉・図の言葉を決める view）。Lean は今は入れない。**（検査器は決めたこと 2 で TLC から tla-ts に改めた。モデルを書く言葉は TLA+ のまま）（オーナーが比べた表を見て選んだ）
   理由: A-0001 で役に立ったのは「破れまでの最短の道」と「人が読める状態の図」で、TLC と statechart はどちらも出す。Lean は証明が通らなくなるだけで、道も図も素のままでは出ない。今のモデルは有限（362 状態）で TLC が全部調べ切るので、Lean の証明が足す強さが無い。CI の runner には Java が入っていて、足すのは `tla2tools.jar`（2.2 MB）だけ。Lean は 579 MB（圧縮）。A-0001 のモデル・規則・view・再現の手順がそのまま元になる。
   捨てた案: Lean にする（道と図が出ない・一から書く・CI が重い）／TLA+ を土台に Lean も足す（同じ規則を 2 か所に書き、ずれないように保つ手間が増える）／決める前に Lean で試作して測る（オーナーは測らずに選んだ。同じモデルを Lean で書いたときの行数と CI の時間は測っていない）。
2. **2026-11-19 モデルを回す検査器は tla-ts（`github.com/aidenybai/tla-ts`。TypeScript 製で Node の上で動く。Java は要らない）。版を固定し、検査器の誤りに備えた確かめを 2 つ添える: (a) わざと規則を破ったモデルの見本が必ず落ちる、(b) 本物のモデルの状態の数が控えた数と一致する。**（オーナーが tla-ts を挙げ、Chief Engineer が実測して推し、オーナーが選んだ）
   理由: A-0001 のモデルを書き換えずに回せた（tla-ts 0.0.10・Node 26.13.0。状態の数 362、規則 R3 の破れの道、終了コード 12 が TLC と一致。状態と移り方の書き出し `-dump dot,actionlabels` も動き、860 本の移り方が行動の名前つきで出た。`npx` の起動込みで約 2 秒）。Java（303 MB）が要らず、npm のパッケージは 10.7 MB。モデルと設定のファイルは TLC と共通なので、tla-ts に誤りが見つかったり止まったりしたら、TLC に戻すのはコマンドの差し替えで済む。
   知っていて受け入れたこと: tla-ts は 2026-10-26 にできた若い道具で、版は 0.0.10、作者は 1 人。検査器に誤りがあると「破れているのに通る」が起きうる。(a)(b) はそのための確かめ。andon を作るセルでは pstack statechart（TLC）で図を作るので、手元では TLC の結果とも見比べられる。
   捨てた案: TLC（Java）のまま（長く使われているが、手元に Java が要る）／tla-ts と TLC の両方を CI で回して結果を照らす（若さの心配は消えるが、CI の段取りが倍になる）。
3. **2026-11-19 最初にモデルから作るのは、課題の `process/states/issue.yaml` の 1 本だけ。残り 9 本はオーナーが書く YAML のまま。規則を置きたくなったものから 1 本ずつ、別の題で移す。**（オーナーが 4 つの向きから選んだ）
   理由: コードが読むのは `issue.yaml` の 1 本だけ（`andon issue` が定義に無い移り方を断る）で、A-0001 のモデルが持っているのも課題の一生。残り 9 本（担当の端末・ゲート・通知の配達など）はモデルが無く、タイマーや回数を含むので一から書くことになる。
   知っていて受け入れたこと: その間、状態の定義の正が「モデル（`issue.yaml`）」と「人が書く YAML（残り 9 本）」の 2 種類になる。
   捨てた案: 課題に関わる 5 本（課題・担当の端末・ゲート・オーナーのマージ・レビュアー）／10 本全部（正が 1 種類に揃うが、モデルを 9 本分一から書く）／生成は後にして、まずモデルと規則を置いて回すだけ。
4. **（決めたこと 6 で改めた）2026-11-19 作り方は `andon process` に「作る」を足す形（Go）。検査器がモデルを調べて書き出した状態と移り方を読み、課題の `status` で畳み、行動ごとの言葉・誰が打つか・コマンド・2 回起きてはいけないかを書いた別のファイル（YAML）と合わせて `issue.yaml` を書く。作った YAML は commit し、`--check` が作り直して差が無いことを見る（今の `andon process render --check` と同じ型）。人が読む図と表（`docs/process/issue.md`）は、今までどおり作った YAML から作る。**（オーナーが 3 案から選んだ）
   理由: 今ある「YAML → 図」の流れの手前に「モデル → YAML」を 1 段足すだけで、道具（Go）も検査の型（作り直して差を見る）も今のものに揃う。
   捨てた案: 作る道具を Node のスクリプトにし、言葉を pstack statechart の view の形で書く（同じファイルで statechart の図も出せるが、Go の repo に JS の道具が増え、view に `by`・`command` を足す独自の拡張が要る）／それに加えて CI で statechart も回し、破れの印つきの図を `docs/process/` に commit する（CI が repo の外の pstack に依る。pstack は「このセルで試す」段〈ADR-0021〉）。
5. **2026-11-19 最初に置く規則は 6 本。A-0001 の R1〜R5 と、R6「担当の問いが開いたまま review にならない」（A-0006 の完了条件に当たる）。**（オーナーが選んだ）
   - R1 やめると決めた課題で、担当がまた動き出すことはない。
   - R2 ゲートが直しを返したら、担当か Chief of Staff のどちらかが必ずそれを知る。
   - R3 worktree を片付けたら、課題は done になっている（片付けは全部か無し）。
   - R4 done の課題は、マージしたか、やめると決めたものだけ。
   - R5 done の課題に担当は残らない。
   - R6 担当の問いが開いたまま review にならない。
   理由: R6 は R1〜R5 と同じ形（どの状態でも成り立つこと）で書ける。
   捨てた案: R1〜R5 だけで始める／A-0007 に当たる「マージされた課題はいつか必ず片付く」まで最初から置く（「いつか必ず」の形で、モデルに公平さの仮定を足す仕事が増える。開いている問いに残す）。
6. **2026-11-19 決めたこと 4（モデルから `issue.yaml` を作る）を改める。`issue.yaml` はオーナーが書くまま。CI がモデルと `issue.yaml` を 2 方向で照らし、食い違えば落とす。**（反論役の指摘を見て、オーナーが 3 案から選んだ）
   照らす中身: (a) モデルで起きる移り方（コマンドに当たる行動が、どの `status` からどの `status` へ動くか）は、`issue.yaml` の行が許している。(b) `issue.yaml` の行は、モデルで起きるか、「モデルの外」と名指しされている。行動とコマンドの対応と「モデルの外」の行は、モデルの隣の小さな対応表に書く。`issue.yaml` に行を足すと、モデルに入れるか「モデルの外」と書くかを必ず決めることになる。
   理由（反論役が A-0001 のモデルを全探索し直して `issue.yaml` の 16 行と突き合わせた結果）: 今のモデルから出るのは 16 行のうち 5 行だけで、2 行は半分、9 行は出ない（課題を足す・`queued`・報告を書く・PR の無い課題の片付け・Chief Engineer やトリアージの返しなど）。モデルが出すのは「どこからどこへ」だけで、言葉・誰が打つか・コマンド・行の束ね方・行の順・行にしない印は全部別のファイルに書くことになり、そのファイルは今の `issue.yaml` とほぼ同じ大きさになる。出ない行のうち 5 つは何も変えない動き（報告を書く、など）で、規則が何も縛らないのに、行を出すためだけにモデルへ写すことになる。「モデルと、コードが従う定義が黙ってずれない」は、照らすだけでも同じ強さで守れる。
   これで変わること: 決めたこと 3 は「最初に照らすのは `issue.yaml` の 1 本だけ」と読む。モデルに書くのは規則に関わる動きだけでよい。PR の無い課題（調べる課題・トリアージ・Chief Engineer の課題）の一生は、最初は「モデルの外」にできる（規則 R4「done はマージか、やめたものだけ」は PR のある課題の規則として置く）。
   捨てた案: 作る（モデルを 16 行全部が出るまで広げ、課題の型ごとの規則も今決める。正はモデルに揃うが仕事が大きい）／混ぜる（モデルから出る行だけ作り、出ない行は別ファイルに手で書いて合わせる。作るものになるが中身の半分は手書きのまま）。

7. **2026-11-19 CI では、モデルの検査だけの job を足して回す。秘密を渡さず、権限は読むだけ。検査器の依存は lock ファイルで全部固定し、入れるときのスクリプトは走らせない。`tests/*.sh` と release の job では回さない。**（オーナーが選んだ）
   理由: 検査器は外から取る npm のコード。今の tests の job は、`tests/*.sh` を回す段が秘密（公開検査の禁止リスト）を環境変数に持ち、release の job は image を配る書き込みの権限を持ったまま同じ検査を回す。そこに混ぜると、外のコードが秘密と権限のある場所で走る。検査器の依存の 1 つは版が範囲指定（`fflate ^0.8.3`）なので、検査器の版を名指しするだけでは固定にならない。
   捨てた案: 今の tests の job に `tests/*.sh` の 1 本として混ぜる／CI では回さず手元だけ（回し忘れを機械が止めない）。
8. **2026-11-19 置いたあとの決まりを 2 つ足す。(ア) 課題の一生の動き（finish・resume・ゲートの返し方など、モデルの行動が写しているコード）を変える PR は、同じ PR でモデルを直す。`AGENTS.md` に書き、`REVIEW.md` でレビュアーも見る。(イ) 規則を弱める・消す変更と、「モデルの外」を増やす変更は、オーナーが見る（自動でマージしない）。**（オーナーが選んだ）
   理由: 機械が見つけられるのは「モデルと `issue.yaml` の食い違い」と「規則の破れ」だけで、(ア)(イ) は機械では止まらない。
   形: 「人が見る」はゲートの条件表（`package/gate.json` の `tier_c_paths`）がパスで決める。パスでしか分けられないので、規則・検査の設定・対応表を、行動を書くファイルと別のファイルに分け、規則の側のファイルだけを `tier_c_paths` に足す。行動の側（コードに合わせて直す所）は今までどおり流れる。規則を別のモジュールに分けても検査器が読めることは確かめた（tla-ts 0.0.10。`EXTENDS` で行動のモジュールを読む規則のモジュール）。
   捨てた案: 担当の決まり (ア) だけ（規則を弱める変更もレビュアーとゲートに任せる）／決まりは足さず、ずれが起きてから考える。
9. **2026-11-19 価値の仮説は置かない。**（オーナーが選んだ。Chief Engineer は「2026-12-25 に、モデルの job が落ちた回と理由を見る」を推したが、オーナーは「無し」を選んだ）
10. **2026-11-20 開いている問い 4（`issue.yaml` に無い移り方がコードにある）は、M2 の対応表で「モデルの外」と名指しして決めた。`issue.yaml` に行は足さず、直す課題も切らない。**（M2 の PR で決めた。結果は `model/issue-map.txt` の `outside` の行）

## 受け入れ条件

確かめる継ぎ目は 3 つ。(1) モデルの検査の入口（手元と CI が同じ 1 つのコマンドを打つ）。(2) 今ある workflow の検査（`workflow_test.go`）。(3) 今あるゲートの条件表の検査（`internal/gate` のテスト）。どれも本物の検査器・本物の `issue.yaml`・本物の条件表で走らせる。前もって用意した出力は証拠にしない。入口の名前と置き場は実装の課題が決め、下では `<入口>` と書く。

1. **規則が通る**: main の上で `<入口>` が終了コード 0。出力に、調べた規則 6 本（R1〜R6）の名前と、状態の数が出る。証拠: コマンドとその出力。
2. **壊した見本が落ちる**: 直す前の動きに戻した見本を 3 つ持つ（finish が片付けのあとで問いを確かめる → R3、担当の端末が無いときのゲートの直しが誰にも届かない → R2、開いた問いを確かめずに ready → R6）。`<入口>` は見本ごとに検査器を回し、どれも規則の破れで落ちること、落ちた規則の名前が見本ごとの期待と合うことを見る。見本が通ってしまったら `<入口>` が落ちる。証拠: 見本を「規則を破らない形」に書き換えて `<入口>` を打ち、落ちたときの出力。
3. **状態の数が合う**: 本物のモデルの状態の数を控え、`<入口>` が毎回比べる。証拠: 控えの数を 1 つずらして `<入口>` を打ち、落ちたときの出力。
4. **照らす（モデル → YAML）**: モデルの行動に、`issue.yaml` が許していない移り方を 1 つ足す（例: doing の課題に `andon issue start`）と `<入口>` が落ち、出力にその行動・コマンド・`status` が出る。証拠: コマンドと出力。
5. **照らす（YAML → モデル）**: `issue.yaml` に、モデルで起きず「モデルの外」とも書いていない行を 1 つ足すと `<入口>` が落ちる。対応表から「モデルの外」の名指しを 1 つ消しても落ちる。証拠: それぞれのコマンドと出力。
6. **CI の job**: モデルの検査の job が PR と main の push で走り、`<入口>` を打つ。その job は秘密を参照せず、権限は `contents: read` だけ。依存は lock ファイルから入れ、入れるときのスクリプトを走らせない。tests と release の job は検査器を入れない・打たない。証拠: `go test -run <workflow の検査>` の出力（`workflow_test.go` に足す）と、PR の checks でその job が成功した run。検査器が CI の runner の Node で動くことは、この run で確かめる（手元で確かめたのは Node 26.13.0 だけ）。
7. **オーナーが見る変更**: 規則・検査の設定・対応表のファイルを触る PR を、ゲートがレベル C に分ける。行動のファイルだけを触る PR は、そのパスではレベル C にならない。証拠: `go test ./internal/gate/...` の、本物の `package/gate.json` を読むテストの出力。
8. **決まりの文**: `AGENTS.md` に決めたこと 8 の (ア) が 1 行、`REVIEW.md` にレビュアーが見る点が 1 行ある。証拠: オーナーが見る（manual。どちらもレベル C のファイルで、PR を人が読む）。
9. **今の検査を壊さない**: `go test ./...` と `tests/run` が通る。モデルのファイルだけを変えた PR で、image の検査が走らない（`tests/lib/image-scope.sh`）。証拠: コマンドと出力。
