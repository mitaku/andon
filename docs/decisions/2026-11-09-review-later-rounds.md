# 2回目以降のレビューは直しの確認だけ。新しい指摘は critical だけをゲートが数える

- 日付: 2026-11-09
- 出典: 人の依頼（2026-11-09。andon の次の手のレクチャー §3.D）・課題 A-0005。先輩プロジェクト shepherdr の 4 世代の整理（shepherdr 1.0 は再レビューで指摘が増え続け、292 件のうち 67 件が機械の足した行になって、この形をやめた）

2回目以降のレビュー（`review_request.previous` が null でない回）は、`previous..commit` の直しの確認だけにする。

- レビュアー（worker skill の §6・dispatcher が書く依頼書）: 見るのは `git diff <previous>..<commit>` だけ。前の回の指摘が直ったか、直しが壊していないかを書く。**新しい指摘は critical で、起きる条件と証拠（具体的な入力 → 結果）があるものだけ**。ほかは書かない。
- ゲート: 2回目以降の回の critical でない指摘のうち、**前の回の `findings.json` に同じ `file` の指摘が無いもの**を新しい指摘として、`must_fix` の数に入れない。critical と、前の回と同じ `file` の指摘（直していない・直しが足りない）は今までどおり数える。
- 「2回目以降」と「前の回」は台帳から決める: ゲートが数えるレビュアーの子課題を古い順に並べ、最新の1つの前で、`findings.json` が読めて `commit` が最新の回と違う最初のもの（`andon issue review-request` の回の数え方と同じ。古い commit を見た頼み直しは同じ回）。`report.json` の `review_request` は `andon issue report` で書き直されて消えるので読まない。

人が決めていないことで推奨で進めたもの:

- 前の回の指摘と今の回の指摘を `file` だけで突き合わせる。`line` は直しでずれるので使わない。`severity` も、直しで重さを見直すことがあるので使わない（同じ file なら数える＝厳しい側）。
- 前の回の `findings.json` が読めなければ1回目として扱う（全部数える＝厳しい側）。

捨てた案:

- **レビュアーが指摘に `new` のキーを付ける**: 書き忘れるとゲートが緩む向きの申告になる。機械が記録から決められるので要らない。
- **`previous..commit` の差分の外の指摘を全部捨てる**: 直していない前の回の指摘（差分の外に残る）まで捨てる。
- **2回目以降の新しい指摘を全部捨てる**: 直しが入れた critical を見落とす。
