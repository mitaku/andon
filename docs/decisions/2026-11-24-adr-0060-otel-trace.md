# ADR-0060: 開発の一連の流れを OpenTelemetry のトレースで辿れるようにし、振り返りと measure がそこから読む

- 日付: 2026-11-24
- 出典: ADR-0060（[adr/0060-otel-trace.md](../adr/0060-otel-trace.md)。Chief Engineer の課題。元はオーナーの発言 2026-11-24「開発の一連の流れを Otel でトレースできるようになること、そこから改善できることが factory たる所以かも」「セルの中に otel サーバーの受け口を用意するのが良いんじゃないかな」）

実行の記録は目的ごとのファイルに分かれていて、課題の中のどの段とどのツールが時間とトークンを使ったか、待ちの内訳、Chief of Staff が使ったトークンが見えなかった。Claude Code と Codex が自分で出す OpenTelemetry のトレースとログを、セルの中の受け口で受ける。受け口は andon のバイナリの中に作り、`127.0.0.1` で OTLP/HTTP の JSON だけを受ける。OpenTelemetry Collector は入れず、依存も増やさない。送る設定は役の起動の行で渡し、課題とプロジェクトと役を resource 属性に載せる。オーナーが自分で打ったセッションは送らない。ツールの詳細までを載せ、プロンプトと応答の本文は載せない。受け口は、書く前に個人の属性を落とし、秘密の形を伏せ、課題ごとのファイルに OTLP の JSON の行で貯める。生の記録は kanban の外の置き場に置き、寿命は 30 日である。片付けは dispatcher が 1 日に 1 回走らせる。改善のループの前提（ADR-0028 の前提 1・4・5）は、受け口と常駐を 1 つずつ足すことと、生の記録を kanban の外に置くことに限って改める。長く残す内訳は、今までどおり kanban の課題のフォルダに置く。課題の一生の段は、新しく記録せず、kanban の記録から読むときに導く。`andon trace <id>` が、段とハーネスの記録を 1 件の木にして出し、標準の閲覧器が読める 1 本のトレースにも縫い直す。dispatcher は、結果の記録に内訳 `breakdown` を足す。`andon measure` と振り返りの入力は、その内訳を読む。直しの効きめは、バージョンごとの表でなく、直しのマージの前後の数字で見る。今の記録は記録の正のままで、gate と dispatcher は受け口に頼らない。受け口が止まっていても課題は止まらない。metrics、ドルへの換算、セルの外への送信、judge による採点と replay は扱わない。

捨てた案:

- **OpenTelemetry Collector を常駐させる**: イメージに別のバイナリが増え、個人の属性を落とす設定と秘密を伏せる規則を Go と別の言語で二重に持つ。
- **受け口を持たず、セッションの記録から組み立てる**: 記録の形が公開の約束でなく、30 日で消え、ハーネスごとに形が違う。
- **andon の command と dispatcher に OpenTelemetry の SDK を入れ、1 本のトレースとして送る**: 依存が増える。対話のセッションは親のトレースを引き継がないので、1 本にならない。
- **今の記録を、トレースから作り直す形に替える**: gate と dispatcher が読む記録が受け口の稼働に頼り、受け口が止まるとラインが止まる。
- **バージョンごとに数字を並べる**: 担当の起動 309 回にパッケージの commit が 176 種類あり、1 行が 2 件足らずになる。
