# `andon issue start <id> --dry-run [--json]` で、担当を起こす前に渡すものと確かめの結果を出す

- 日付: 2026-11-09
- 出典: 人の依頼（課題 A-0006）・`andon gate --dry-run`・`andon triage apply --dry-run` の流儀

`andon issue start` に乾いた実行を足す。依頼書の欄や、起こしたら担当に何が渡るかを、エージェントを起こさずに確かめるため（あとで AGENTS.md・skill の評価の土台にもなる。評価の仕組みはここでは作らない）。

- **確かめは本番と同じ道を通す**: 本番の `start` を「確かめて渡すものを決める」と「作って起こす」の2つに分け、`--dry-run` は前の半分だけを走らせる。止まる課題（`todo` でない・`after` が済んでいない・書けない repo〈台帳の `config.yaml` の `repos`・`project.json` の `repos`〉・依頼書が無い など）では、本番と同じ終了コード 1 と同じ理由1行を返す。
- **hc を1回も呼ばず、何も作らない**: 端末・worktree・branch・ラベル・信頼の設定を作らず、台帳も書かない。だから hc を呼ぶ確かめ（template があるか・同じ名前の端末が動いていないか）と、作る直前の確かめ（origin に同じ branch が無いか・worktree の置き場が空いているか）はしない。出力の `checks` に `skipped` と書いて、確かめていないことを見せる。
- **出すもの**: 最初のメッセージ（`hc run` に渡す文そのもの）・依頼書の全文とそのパス・付けるラベル・端末の名前・cwd・repo・worktree のパス・branch・プロファイル・確かめの結果（`ok` か `skipped`）。人向けが既定で、`--json` で JSON（`--json` は `--dry-run` と組でだけ使える）。最初のメッセージ・ラベル・名前・cwd・プロファイルは本番と同じ関数で組むので、本番で `hc run` に渡すものと1文字も違わない（`internal/issue/start_test.go` が本番の `hc run` の引数と突き合わせる）。

捨てた案:

- **`--json` の形を `schema/` に足す**: 今この JSON を判定に使う機械の読み手はいない（人と、あとで設計する評価が読む）。読み手が決まったとき（評価を Chief Engineer の題にしたとき）に schema にする。それまでは人が確かめるための出力で、機械は読まない。
- **`--dry-run` でも hc の確かめ（`hc templates`・`hc ls`）を打つ**: 読むだけだが、「hc を1回も呼ばない」を保てなくなり、hc の無い所（評価の土台・CI）で使えなくなる。
