# 測るものに待ち時間・流量・WIP・対抗の指標を足し、価値 → 流れ → 効率の順に並べる（`andon measure`）

- 日付: 2026-11-09
- 出典: 人（2026-11-09「変える前に測る」「自動マージ率は重要だが、顧客の価値の最大化を踏まえたループが重要」）・課題 A-0002・Little の法則（WIP ＝ 流量 × 待ち時間）・Grove の対抗の指標（paired indicators。効率の指標は、それを上げると悪くなるものと組で見る）

[design.md](../design.md) §5.1 の「数える指標」と [vision.md](../vision.md) §4 の「測る」（PR あたりの人の介在回数・自動マージ率・ゲートの差し戻し率・依頼書からマージまでの時間）に、次の4つを足す。

- **1件あたりの待ち時間**（状態ごと。`todo`・`queued`・`doing`・`review` と、問いが `open` の間）
- **1日に閉じた数**（throughput）
- **期間の終わりの WIP**（`doing` と `review` の数）
- **対抗の指標**: マージのあとに revert された PR の数・同じ箇所を直す課題が切られた数（課題の `links` か、マージされた PR の本文が、別の課題のマージされた PR の URL を指すもの）・人が開け直した数（`corrections.json` に1件以上ある課題と、自動マージした PR を revert したもの。ゲートのレベルごと）

WIP だけでは、遅れているのか、たくさん流れているのか分からない。待ち時間と流量を並べると見分けられる（Little の法則）。自動マージ率は PR を細かく刻めば上がるので、率は対抗の指標と組で出す（Grove）。

並べる順は **価値 → 流れ → 効率**。介在回数と自動マージ率は、人の時間を「何を作るか」へ回すための手段の指標で、目的ではない。価値の指標は価値のループ（本番の結果を次の信号にする線。vision.md §4 の「and observe」）ができてから入るので、それまで人向けの表の先頭は「価値: 未計測」の1行にする。

数えるのは読むだけの command `andon measure`（台帳の CLI の外の記録〈ゲートの記録・`report.json`〉も読むので andon 側）。新しい記録は足さず、今ある記録（`log.jsonl`・`issues/<id>/library/gate/<sha>.json`・`report.json`・`questions.yaml`・`corrections.json`）と GitHub のマージされた PR の一覧から導く。何も書かない・保存しない。出力は JSON（[contract.md](../contract.md) §13。`schema/measure.schema.json`）と人向けの表。

数え方のうち設計書と依頼書で割れたもの:

- **ゲートの差し戻し率**は design.md §5.1 のとおり（`fix` ＋ `needs_human`）÷ ゲートの記録。依頼書（A-0002）は `fix` ÷ 記録と書いたが、設計書を正とし、JSON には `fix` と `needs_human` を別に出す。
- **自動マージ**は、ゲートの記録の `merged: true`（dispatcher がマージした）。

捨てた案:

- **集計を台帳か `library/` に保存する**: 「要対応は保存せず導出する」と同じ考えで、導けるものは保存しない。保存すると書き手が増える（1つの約束に書き手は1人）。
- **kanban（台帳の CLI）に置く**: ゲートの記録と `report.json` は Andon の約束で、台帳の形式の外にある。
