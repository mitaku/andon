# Chief of Staff の skill から人への文の行数の上限を外し、許可の確認の線と起動の go の例外を決まりの中に書く

- 日付: 2026-11-12
- 出典: 人 2026-11-09（このプロジェクトでは担当の起動に人の go は要らない）。人 2026-11-10（担当が自分の PR の branch に `git push --force-with-lease` するのは毎回の go なしで許す）。A-0117 の調べた候補 c6・c9・c10・c13。[ADR-0013](../adr/0013-short-role-names-and-plain-japanese.md) 決めたこと 14。課題 A-0123

- 人への文の「1行で」「2行まで」を外し、「短く、人がすることを先に書く。書き方は `writing.md` に従う」の1か所にまとめる。理由: 行数を字義どおり守ると、語を「・」で詰めた文になり、その返事だけで通じなくなる。`writing.md` の「1文に1つのこと」と「その返事だけで通じるように」にもぶつかる。
- 担当の許可の確認に Yes と答える線を、「外へ出さないものだけ」から、Yes と答える操作と人へ回す操作を並べた表に替える。線は worker skill §5 の表と同じにする。理由: 「外へ出す」は push と PR にも読めるので、担当が聞かずにしてよい操作まで人へ回り、課題が止まる。
- 担当を起動するときの人の go は既定のまま残す。例外は3つで、どれも決まりの中に書く: ルーチンが足した課題、委譲の範囲の中の課題、`projects/<slug>/AGENTS.md` の Chief of Staff の節が「起動に人の go は要らない」と書いているプロジェクト。理由: 例外がセルの別のファイルにしか無いと、書かれたとおりに当てるモデルには効きにくい。既定を逆にするかは人が決める。
- idle の担当へ送る続きの文は、worker skill §7 の終わり方（`andon issue report` → `andon issue ready`）を指す。理由: 前の文の `kanban report`・`kanban review` に従うと、`report.json` が書かれず、`andon issue ready` がする確かめも飛ばされる。
