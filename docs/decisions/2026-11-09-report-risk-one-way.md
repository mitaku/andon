# report.json に risk を足す。one_way はレベルを C に上げ、下げる向きには使わない

- 日付: 2026-11-09
- 出典: 人の依頼（2026-11-09。andon の次の手のレクチャー §3.C「返りの欄を足す」）・課題 A-0004

担当の `report.json`（[contract.md](../contract.md) §4）に任意のキー `risk` を足す。形は `{"one_way": true | false, "impact": ["…"]}` で、`one_way` は必須、`impact` は任意。版は上げない（contract.md §0 の原則4）。

- `one_way: true` は、変更そのものが revert で戻らないという担当の申告（データの移行・消す操作・外への約束）。ゲートはレベルを **C** に上げ、`tier_reasons` に「担当の申告: one_way」と書く。委譲の `merge` が C でなければ人へ回る。
- `one_way: false`・`risk` が無い: レベルを変えない。**申告でレベルを下げる分岐は作らない。** 担当の申告は誤りうるので、緩める向きに使うと穴になる（原則2「知らない値は安全側に倒す」と同じ向き）。
- ゲートが読むのは `one_way` だけ。`impact` は人が読む欄で、ゲートは読まない（原則1。判定に使う値は名前を決めたキーにだけ持つ）。
- 同じ考えで、`acceptance[]` の今の扱い（`fail` で `fix`、`manual` でレベルを1つ上げる。design.md §1.9 の (a)）は変えない。worker の skill に書き方を足し、担当が使い始める。

人が決めていないことで推奨で進めたもの:

- `one_way` はレベルを1つでなく **C まで**上げる。戻せない変更は、どのレベルから来ても人が見る範囲に入れる（1つ上げるだけだと A の変更が B で自動マージされうる）。
- 「受け入れ条件のテストは先に落ちるのを確かめる」は約束（記録のキー）にせず、worker の skill の1行だけにする。

捨てた案:

- **`one_way: false` でレベルを下げる・`impact` の文でレベルを決める**: 担当の自己申告でゲートを緩めることになる。
- **レベルを1つだけ上げる（`manual` と同じ）**: 戻せない変更が B に留まり、委譲が B なら人が見ないままマージされる。
- **テストを先に書いた記録を `report.json` に足す**: 書き手の申告で確かめようがなく、キーを増やすだけになる。
