消す条件: ぶつかりの照合（1）は「`andon issue start --dry-run` が動いている課題と出ている PR の files との重なりを確かめるようになったら」。終了コードの読み方（3）は「`andon issue start` が終了コードごとに打つべき1手を出すようになったら」

# 起動する

1. **枠を確かめる**: `andon waiting --json`（`projects/<slug>/` で打つ）の `slots` を読み、`slots.free` が 1 以上のときだけ、その数まで起動する。`kanban list` を目で数えない（数える式は `andon waiting` だけが持つ。`docs/contract.md` §25）。
   - 枠に数えるのは、`doing` と `review` の担当の課題のうち、オーナー待ち（オーナーのマージか答えを待つ課題）でないもの（`slots.working`）だけ。オーナー待ちの課題（`slots.waiting`）は CPU を使わないので数えない。上限（`slots.limit`）は `project.json` の `chief_of_staff.parallel` で、無ければ 2。
   - `slots.waiting_full` が `true`（オーナー待ちが上限の数に達した）なら `free` は 0 で、起動しない。オーナーに「オーナー待ちが N 件たまったので、マージか答えが入るまで新しい課題を起動しない」と言い、`items` の並びの先頭から問いを出す（ask-one-by-one skill §3 の出す順）。
   - `waiting_full` でなく `free` が 0（動いている課題が上限の数）なら起動せず、オーナーに「上限なので S-x（題）が終わってから」と言う。オーナーが待ちの PR を差し戻して、動いている課題が一時だけ上限を超えたときも、下回るまで起動しない。
   - `andon waiting` が終了コード 1 で終わったら、理由の1行を読んで直し、数えられるまで起動しない（履歴が読めないと、オーナー待ちを動いている仕事と区別できない）。
   - `after` で前の課題を待つ課題は、前の課題がオーナーのマージを待っていても先に起動しない（`after` を外さない・前の課題の branch の上で起動しない）。前の課題が何件を止めているかは `items[].holds` に出るので、その多い順にオーナーへ出す。起動できる担当の課題が無く、残りが全部マージ待ちの後ろにいるときは、その時点でオーナーに「S-x（題）がマージされないと、次に動く課題が無い」と1文で言う。
   - 起動できる課題が複数あり、ダイジェストの課題（`routine: daily-digest`）があれば、それを先に起動する（`digest.md`）。
   **ぶつからないかも確かめる**: その課題が触りそうな場所（依頼書の「解決すべき問題」「守ること」のファイル・節。同じ repo なら skill・command・docs）と、
   `doing`／`review` の課題の依頼書と、出ている PR の files（`gh pr view <n> --json files`）を突き合わせる。
   - 重なるなら同時に起動しない。`--after` で並べるか（`kanban set <id> after=<id>`）、1つの課題に束ねる。重ならないものだけ `slots.free` の数まで起動する。
   - 毎回ぶつかる場所（全 PR が触るバージョンの番号や CHANGELOG）は、依頼書に「PR を出す直前に main を取り直し、バージョンを付け直す」と書く。
   - 重なる課題が同時に動くときは、依頼書の「守ること」にその番号（題）を書く。
2. **オーナーの go を取ってから**起動する。次のどれかに当たれば聞かずに起動する: ルーチンが足した課題・委譲の範囲の中の課題・`projects/<slug>/AGENTS.md` の Chief of Staff の節が「起動にオーナーの go は要らない」と書いているプロジェクト。どの場合も枠とぶつかりの確かめ（1）は守る。
3. `andon issue start <id>`（`projects/<slug>/` で打つ）。worktree・branch・端末・`issue.yaml` の欄はコマンドが作る。
   - 終了コード 1: 理由の1行を読んで直す（依頼書が無い・プロファイルが無い・起動済み など）。直せないものはオーナーへ。
   - 予約キーが揃っていない（無い・知らない値・最後に書いたのが今の自分の端末でない）と断られたら、出た `kanban set` の行を自分の端末で打ってから打ち直す。`<…>` の所は `brief.md` の表から値を選んで埋め、依頼書の Settings の写しも揃える。
   - 終了コード 3（最初のメッセージが届いていない）: kanban はもう `doing`・`agent` はその端末。最初のメッセージは**dispatcher が送り直す**（端末が入力を受けられるようになった次の見回りで。手で送らない）。
     画面が止まっていれば（`hc read <address>`）`blocked.md` の決まりで答えるだけでよい。急ぐときだけ、`hc read` で届いていないことを確かめてから、コマンドが出した `hc send <address> …` を打つ。
     コマンドが「ラベルを付けられず、dispatcher は送り直さない」と出したときは、答えてから手で送る。
4. 起動したら、オーナーに知らせる。場所はコマンドの `出た場所` の行を写す（`S-0003（返事の下書きボタン）を claude で起動した。S-0003 返事の下書きボタン / S-0003（t7）`）。そのあと `hc wait` で自分を止めない（オーナーと話す役なので、届いたものをそのターンで処理する）。

担当は `kanban start` → 実装 → PR → `andon issue report` → `andon issue ready`（オーナーへの問いは `andon issue ask`）までを自分でする（worker skill §7）。
担当は `--no-notify` で起動し、この Chief of Staff へ `hc send` しない。通知は dispatcher が `<news>` で届ける（`watch.md` の「`<news>` の読み方」）。
