# 止まったエージェントに答える

届くもの: dispatcher の `<news>`（`<id> blocked`・error・終了・報告・問い。`watch.md` の「`<news>` の読み方」）。

blocked には次の順で答える（規約3: blocked は正常。範囲内だけ答える）:

1. `hc read <agent> --lines 0` で画面を読む。
   入力欄に文が見えても、人が打ったものとは限らない。Claude Code や Codex のサジェスト（入力の候補・薄い字のヒント）が出ていることがある。
   `hc read` には色が入らないので見分けられない。入力欄の文を「人が何かしようとしている」しるしとして読まず、人に確かめに行かない。状態は hc の状態が正（`wake.md`）。
2. 判断:
   - **許可の確認**（コマンド・ファイルの書き込み）: 課題の範囲内で、下の表の左の列に当たるものは「Yes」（**1回だけ**の選択肢）。「常に許可」「このセッションでは聞かない」は選ばない。
     右の列（戻せないか、課題の外に届く操作）と、課題の範囲の外の操作は、委譲の範囲の中でなければ答えず、人へ（ask-one-by-one skill の1問ずつ）。表は worker skill §5 と同じ線で、担当が聞かずにする操作の確認は Yes で通す（止めると課題が止まる）:

     | Yes と答える | 人へ回す |
     |---|---|
     | 自分の課題の PR の branch（`andon/<id>…`）への push。`git push --force-with-lease` も含む（人 2026-11-10） | main・既定の branch・他人の branch への push（force でもそうでなくても） |
     | `gh pr create`・自分の PR の本文と添付の編集・checks の待ち | remote の branch・tag・リリース・データの削除や書き換え |
     | worktree の中のファイルの書き込みと削除・自分の commit の作り直し（push 前） | 本番系（デプロイ・本番のデータ・公開） |
     | 一時の置き場のファイルの作成と削除・検査とテストの実行 | 資格情報の作成・変更・持ち出し |
     | 失敗した command のやり直し | プロジェクトの外の人やサービスへの送信（メール・外のトラッカーへの書き込み・外の API への書き込み） |

   - **「このフォルダを信頼するか」**: セルでは出ない（boot と `andon issue start` が repo の根を信頼済みにする）。出たら想定外なので、`hc keys` で答えず人へ回す（1問ずつ）。Codex のフックの確認画面も人へ。
3. `hc keys <agent> <キー…>`（例: 1番目の選択肢なら `enter`、番号で選ぶ画面なら `1`）。`hc send` は blocked のとき拒まれる（終了コード 9）。`--force` は使わない。
4. `hc read <agent> --lines 0` で、答えが通って先へ進んだことを確かめる。
5. 人に知らせる（`S-0003（返事の下書きボタン）の「npm test を打つ」を許可した`）。

## 人に聞くこと

担当が `## 人に聞くこと` を返したら、ask-one-by-one skill に従って人へ（1回の返事で1問・聞く前に間引く・待ちの問いは台帳の人の課題）。決まったら `hc send <agent> "<決定>"` で返す。
人の答えが推奨案と違った・人の志向が見えたときは、人の言葉を wiki の `raw/` に写して ingest する（`wiki.md`）。

## 範囲の問い

担当が `## 範囲の問い`（見つけたもののどれを直すか）を返したら、**範囲の判断は自分のもの**で、人に灯りはつかない。担当は `library/candidates.json`（候補の一覧。`id`・`text`・`in_scope`）を書き、`kind: scope` の問い（台帳では `（scope）` つきで `<id>#<n>`）を出している。まず `candidates.json` を読む。候補ごとに次の4つを見る:

| 候補が | 自分で決める | 人へ（1問ずつ） | Chief Engineer へ |
|---|---|---|---|
| 場所 | `project.json` の `repos` の中 | 外の repo | — |
| レベル | A・B（ゲートの条件表 `tier_*_paths` で見る） | C（委譲の `line-change` の中なら自分で） | — |
| 種類 | 灯りがつく決断（呼び出し・定位置停止）のどれでもない（誤字・壊れたリンク・落ちるテスト・既に決まった形への揃え） | 事業・利用者・約束・不可逆 | — |
| 直し方 | 1つに決まり、合計が元の PR に収まる（テストを除いて 500 行未満）か、小さい直す課題に切れる | — | 構造の違う案が2つ以上・外との約束・何を作るかに戻る（自分で Chief Engineer を起動する） |

- 4つとも「自分で」の候補は、推奨案どおりか違う組み合わせで決め、候補ごとの行き先を `id` で書いて `kanban answer <id>#<n> "<文>"` で台帳に残し、`hc send <agent> "<文>"` で返す（例「c1・c2 はこの PR で。c3 は別の課題 S-0012（README の英語の段）。c4 は捨てる: その repo に条件が無い」）。別の課題にしたものは `kanban add` し、依頼書の「なぜ」に元の課題の番号と候補を書く。捨てるものは理由を1行。
- 「人へ」の候補はその候補だけ人の問いにし（ask-one-by-one skill §3）、残りは先に答えてよい。「Chief Engineer へ」の候補は、自分で `andon chief-engineer --brief -` を打って経緯（候補・担当の報告のパス・人の言葉）を渡す（`cut.md` の「人の入口」）。担当の課題は止めたまま残し、やめるなら人の go で `andon issue finish`。
- 自分で答えた範囲の判断は人に知らせない（委譲の範囲の中の判断と同じ。記録は担当の報告に残る）。
- 依頼書は書き換えない。答えが依頼書の追記になる。
