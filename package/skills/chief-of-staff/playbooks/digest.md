# ダイジェスト

ダイジェスト（Digest）のワークストリームの AI の手。流れの正は andon の repo の `process/workstreams/digest.yaml` で、このファイルはやり方だけを書く。
書き方は digest skill、入力と送った結果の形は `contract.md` §26〜§28 にあり、ここには書かない。

1. **足す**: ルーチン `daily-digest`（`routines/daily-digest.yaml`。例は digest skill の `assets/daily-digest.yaml`。kanban へ写すのはオーナーの go で。名前は `daily-digest` のまま）が毎朝1件足す。
   オーナーが臨時に頼んだら `kanban routine run daily-digest`（`kanban add` で足さない。`routine` が付かないと期間が前の1枚から続かない）。
   `skipped (open)` なら前の課題が片付いていない。その課題が `todo` なら 2 で起動し（新しく足さない）、`doing`・`review` なら 3 で片付けてから打ち直す。`open` は 1 のまま変えない。
2. **起動する**: オーナーに聞かずに起動する。起動できる課題が複数あれば、ダイジェストの課題を先に起動する（並行の枠を別に持たない。枠〈`andon waiting list` の `slots.free`〉が無ければ空くまで待つ）。
   ルーチンは予約キーを書かないので、先に `kanban set <id> review=off estimate=small`、それから `andon issue start <id>`（`start.md`）。
3. **報告が届いたら、そのターンで片付ける**: 通知は `<id> report`（PR の無い課題なので `review` の通知は来ない。報告を書いたときと `review` に入ったときの2度届きうる）。課題の状態で分ける:

   | 状態 | すること |
   |---|---|
   | `done` なら何もしない | 2つ目の通知 |
   | `doing` | 待つ。報告があるのに担当が止まっている（`stalled`）なら、`kanban review <id>` を打つよう1回頼む（`andon issue ready` は PR が無いので通らない）。端末が終わっていれば `watch.md` |
   | `review` | `issues/<id>/library/digest/sent.json` と報告の「送った結果」を読んで `andon issue finish <id>`。送れていない送り先があっても（`sent.json` が無くても）片付け、理由をオーナーに知らせる |

   文は検収しない（もう届いている）。送り直しは担当が報告の前に1回しているので、頼まない。片付けにオーナーの go は要らない。
   片付けを次のターンへ回さない（前の課題が残っている朝は、ルーチンが足さず、その朝の1枚が抜ける）。片付けたら `start.md` の 1 で枠を数え直し、空いていれば起動できる課題を起動する。
   送れなかった期間は、前に送れた1枚の終わりから次の1枚が拾う（7 日まで）。前に送れた1枚が無ければ次は 24 時間前からなので、載らない出来事が出うることも理由と一緒に知らせる。
4. **オーナーへ**: 届いた1枚のことは知らせない（ダイジェスト自身が知らせ）。例外は2つ。送れなかったときは理由。送り先が `files` だけでオーナーがいるターンなら、その返事に URL を1つ。1枚の中身を返事に写さない。
5. **変える・止める**: 頻度（`schedule`）と `paused: true` はオーナーが書く。
